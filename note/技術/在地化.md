# 在地化

UI 文字全部進 Godot 的翻譯系統，目前有 **zh_TW（原文）與 en** 兩個語系。

## 翻譯表在哪

| 檔案 | 裝什麼 | 條數 |
| --- | --- | --- |
| `locale/game.csv` | 玩家看得到的：對話台詞、數值名稱、輸入框提示、AI 狀態訊息 | 74 |
| `locale/console.csv` | debug 主控台的輸出與 `help` 說明 | 74 |

CSV 是原始檔，Godot 匯入後產生 `locale/*.{zh_TW,en}.translation`（4 個），
由 `project.godot` 的 `internationalization/locale/translations` 掛上。
`.translation` 被 `.gitignore` 的 `*.translation` 擋掉 —— 它們是產物，
**clone 之後第一次開編輯器會自己生出來**，headless 環境要先跑一次 `--import`。

fallback 設成 `zh_TW`，理由見下面「譯文留空」那節。

## key 命名

| 前綴 | 用途 |
| --- | --- |
| `DLG_` | 角色講出來的台詞 |
| `STAT_` | 數值名稱（飢餓／精力／…） |
| `UI_` | 場景上的 UI 文字 |
| `AI_` | AI 設定的狀態訊息 |
| `CON_` | 主控台輸出與錯誤 |
| `HELP_` | `help` 指令的說明欄 |
| `FAIL_` | 行為失敗原因碼翻成的可讀訊息（issue #180，見下方） |

用語意化 key 而不是拿中文原文當 key：中文原文只是「其中一種翻譯」，
改措辭時不必動到程式碼。代價是 CSV 的 key 欄要自己編。

## 兩條路徑：節點自動翻譯 vs `L10n`

**Control 節點上的文字不必碰程式碼。** `Label.text`、`LineEdit.placeholder_text`
這些屬性直接填 key 就會被翻譯（`auto_translate_mode` 預設 INHERIT）。
`chat_input.tscn` 與 `debug_console.tscn` 的 placeholder 就是這樣做的。

**程式碼裡組出來的字串走 `scripts/core/l10n.gd`：**

```gdscript
L10n.t("DLG_OPENING_DISLIKE")
L10n.tf("DLG_OPENING_FRIEND", {"name": listener_name})
```

> [!warning] 為什麼不是 `tr()`
> `tr()` 是 `Object` 的**實例方法**，而需要翻譯的三個地方都拿不到 `self` ——
> `DialogueLines` 全是 `static func`、`Stats.SPEC` 是 `const`、
> `AIConfig.load_from_user()` 也是 static。`L10n` 包的是
> `TranslationServer.translate()`，沒有這個限制。

### 帶參數一律用具名參數

`L10n.tf()` 走 `String.format()` 的 `{name}` 形式，不是 `%s`。
語序在不同語言會變 ——「`{name}`，又見面了！」的英文是
「Good to see you again, `{name}`!」，位置參數翻不動這種調換。

數字要指定精度的話**呼叫端先自己格式化成字串再傳進來**
（`"%.1f" % timeout`）。`format()` 沒有格式規格，
而把 `%.1f` 留在翻譯字串裡等於要譯者處理格式碼。

## 踩過的坑

### 譯文留空會退回 fallback，不會變成空字串

實測過三種情況，結果都是安全的：

| CSV 寫法 | 在 en 底下拿到 |
| --- | --- |
| `KEY,"只有中文",""` | `只有中文`（退回 zh_TW） |
| `KEY,"只有中文",`（整欄省略） | `只有中文`（退回 zh_TW） |
| key 根本不存在 | `KEY` 本身 |

所以**譯者可以安全地把還沒翻的格留空**。
而漏掉的 key 會在畫面上顯示成大寫底線字，一眼就看得出來。

### 譯文撞到 BBCode 標籤會被吃掉

主控台的 `Output` 是 `bbcode_enabled = true` 的 `RichTextLabel`，
所以任何長得像標籤的文字都會被當 markup 解析。
`help` 表的 `locale [code]` 就中招了 —— `[code]` 是 Godot 認得的標籤，
整行渲染成 `locale [/color]`。

`_help_line()` 現在一律把 `[` 轉義成 `[lb]`，之後加指令不必去記哪些字撞名。
**寫譯文時也要避開** `[b]` `[i]` `[u]` `[s]` `[code]` `[url]` `[img]`
`[color]` `[center]` `[table]` `[lang]` 這些；用角括號 `<...>` 最安全。

### 空格對齊在比例字型下本來就不成立

主控台沒有指定字型也沒有 theme，用的是 Godot 預設的比例字型。
舊版 `help` 表靠字面空格把說明排成一欄，那個對齊**本來就只是近似**，
中文剛好每個字等寬才看起來像對齊的。

改成兩行式（指令一行、說明縮排一行），徹底不依賴字元寬度。
`status` 的欄位也不補空白對齊，只用顏色區分欄名。

### 氣泡不必為英文調寬

`bubble.gd` 的 `MAX_LINE_WIDTH = 72` 是照中文密度調的，本來擔心英文會爆版。
實測最壞情況（`DLG_OPENING_FRIEND`）：

| 語系 | 氣泡尺寸 |
| --- | --- |
| zh_TW | 88 × 34 |
| en | 90 × 49 |

寬度只差 2px —— 自動折行本來就把寬度封頂了，英文只是多折一行。
高度多 15px，氣泡往左上長，仍在畫面內。**所以沒有調整任何常數。**

`chat_input.gd` 的 `MAX_LENGTH = 40` 同理沒動：40 個英文字母比 40 個中文字窄，
不是爆版風險。真要讓英文玩家打長一點，得做成隨語系變的上限，那是另一件事。

## 怎麼切語系

主控台的 `locale` 指令：

```
locale          顯示目前語系與可用清單
locale en       切換
```

沒有這個指令就得改 project settings 重開遊戲，等於驗不了翻譯。
指令會先比對 `TranslationServer.get_loaded_locales()` 再切 ——
`set_locale()` 對不存在的語系不會抱怨，只會靜靜地全部 fallback，
看起來就像指令沒生效。

> [!note] 切換後畫面上既有的字不會重繪
> 主控台已經印出去的行、正在播的氣泡都留在舊語系。這是預期行為，
> 打新指令就是新語系了。

## 加語系的話，字型撐得住哪些

實測 `assets/fonts/Cubic_11.ttf` 的涵蓋範圍（`Font.has_char()` 逐字掃）：

| 字集 | 涵蓋 | 能不能加 |
| --- | --- | --- |
| 平假名 | 82 / 82 | ✅ |
| 片假名 | 82 / 82 | ✅ |
| 日文新字體漢字（測 24 個常見的：図学桜気国体児内円当発変声実対広歳込沢直読写辺点） | 全中 | ✅ |
| 日文標點 `、。` | 2 / 2 | ✅ |
| 西里爾字母 | 64 / 64 | ✅ 俄文也可以 |
| 韓文諺文 | **0 / 11172** | ❌ 要另外找字型或掛 fallback |

**日文可以直接加**，不必換字型也不必掛 fallback。加一個語系就是 CSV 多一欄。
韓文要加的話得先解決字型缺字。

## 刻意沒有翻譯的東西

| 類別 | 為什麼 |
| --- | --- |
| `push_error` / `push_warning` / `print` | 引擎 log，不是 UI。這些也是中文，所以「抽出所有中文」的做法會誤抓 |
| 送給 LLM 的 prompt（`AI_PROBE_SYSTEM`、`ai_schema.gd` 的動作詞彙） | 給模型的不是給玩家的。專案規定「外來文字一律視為資料」，翻譯字串更不該插進 prompt |
| group 名、input action、`facing`／動畫值、`PlaceAnchors` 底下的地點節點名、疊圖項目名 | 翻了就壞——這些是 key，不是給玩家看的文字 |
| 角色顯示名 | 角色命名系統還沒做，那是缺功能不是 i18n 缺口 |

## 地點顯示名稱

`PlaceAnchors` 底下的節點名（`home`／`herb_shop`／`tavern`／`pavilion`／`god_stone`）是
key，不能直接顯示給玩家。[[Ailley/scripts/world/places.gd|places.gd]] 的 `display_name(place_name)`
把 key 轉成翻譯過的顯示字串（`UI_LOC_*`，`god_stone` 沿用既有的
`UI_GOD_STONE_TITLE`），查不到的 key 原樣退回。目前還沒有 UI 呼叫這個函式——
LLM prompt／主控台繼續直接用 key（見上表），這個函式是給之後要顯示地點名稱的
UI 用的。

## 失敗原因碼 → 可讀訊息（issue #180）

`character.gd` 的失敗原因碼（`TOO_FAR`、`TARGET_NOT_FOUND`…）本來是純識別字，
`push_warning` 直接把代碼印給開發者看。現在多一張 `Character.FAILURE_MESSAGE_KEYS`
（code → `FAIL_*` key）跟一個 `report_action_failure(action_label, reason)`：
`push_warning` 照舊留給開發者，同時用 `FAIL_*` 的翻譯句透過角色自己的 Bubble
講給玩家聽。這些碼橫跨 talk／work／buy／eat／drink／give／haul／attack 全部
共用同一組扁平詞彙，一張表就夠，不用按行為分開維護——新行為只要呼叫
`report_action_failure()` 就有翻譯，不用回來加表。
