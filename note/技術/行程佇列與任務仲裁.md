# 行程佇列與任務仲裁

把 `agent.gd` 的行程處理從「cron 式時間表」改成「任務池 + 仲裁器」，
讓 LLM 產生的臨時任務與預排行程走同一套選擇邏輯。

這是接 LLM 前的最後一塊結構調整。
動作介面的形狀見 [[talk 動作設計]]，移動與基底分工見 [[Character 基底與 Agent]]。

> [!note] 狀態
> **任務池與仲裁器已實作**（issue #71），刻意不接 LLM——這一版只有 schedule
> 來源的任務，仲裁邏輯本身是通用的，`need_bonus`／`age_bonus` 這兩項先固定
> 回 0，要等 LLM 任務接進來才有意義。下面的設計內容仍然是實作依據，
> 只有「不是直接執行，要先過承諾檢查」那段依實測結果補了一條前提（見下方
> `[!danger]`）。

## 為什麼要改

現在的行程是 cron：`agent.gd:56 _on_time_changed()` 比對 `"%02d:%02d"` 整分字串，
命中就切目標。資料是 `{time, place, state}`。

LLM 接上來之後，會出現一整類**沒有固定時間**的事情：

- 被搭話之後想回訪某人
- hunger 跌破閾值，想去吃東西
- 玩家托付的委託
- 動作失敗後的重試

這些塞不進 `{time, place, state}` —— 它們沒有 `time`。

## 結論：可行，但不要做成佇列

三個要點，順序就是重要性。

> [!important] 一、優先佇列解不了時間
> 佇列只回答「先做誰」。但 `sleep 18:00` 的優先度不是固定值 ——
> 它在 17:59 應該近乎為零，18:00 之後才變高。這是**時間的函數**，不是一個欄位。
>
> 所以要的是**任務池 + 仲裁器**：每次重算所有候選的分數，取最高的做。
> 「佇列」這個詞會誘導你去寫 `push` / `pop`，而 pop 掉的任務就再也回不來了。

> [!important] 二、不要保留兩套資料再合併
> 「schedule 一套、queue 一套、最後合併」會長成兩份各自演化的邏輯。
> 這種「兩份各自演化的邏輯」正是移動實作曾經欠過的債 ——
> 剛靠 `Character` 基底還完，不要再欠一筆。
>
> 行程表應該只是「**預先塞好、且帶時間窗**的一批 Task」，
> 跟 LLM 丟進來的是同一個 struct，走同一個仲裁器。

> [!important] 三、每次重算，不要維護「目前是第幾筆」
> `agent.gd:65 _apply_current_entry()` 已經是這個精神了：對話結束後重算「現在該做什麼」，
> 而不是接續原本那條路。沿用它，開場就不再是特例 —— 開場只是「第一次重算」。

## Task 結構

```gdscript
{
    "id":            "",        # 去重與取消用
    "action":        "",        # §5.3 動作清單裡的一項
    "params":        {},        # place / target / item…，依 action 而定
    "priority":      0.0,       # 基礎值 0..100
    "window":        null,      # {start: "09:00", end: "12:00"}；null = 任何時間
    "duration":      0.0,       # 預期耗時，遊戲分鐘；0 = 做到完成或被搶佔
    "interruptible": true,
    "preconditions": [],
    "source":        "",        # schedule / llm / reflex
    "created_at":    0,         # 遊戲分鐘，aging 用
    "expires_at":    0,         # 0 = 不過期
    "retries":       0,
}
```

對照暫定過的 `{start, duration, place, action, priority, interruptible, preconditions}`：
`start` 擴成 `window`（要有結束才知道何時該放棄），`place` 收進 `params`
（不是每個動作都有地點，`talk` 是對人不是對地方），其餘一致。

## 仲裁

```
score(task, now) =
      task.priority                    # 基礎值
    + time_bonus(task.window, now)     # 時間窗
    + need_bonus(task, stats)          # 需求急迫度
    + age_bonus(task, now)             # 等待加分，防餓死
```

`time_bonus`：窗內給一個明顯大於任何 base priority 的加成（例如 +100），
確保「到點的行程」預設壓過「隨時可做的雜事」；窗外直接濾掉這筆，不進比較。
沒有 window 的任務這項為 0。

選出 `best` 之後，**不是直接執行**，要先過承諾檢查：

```
若 _current 還在自己的 window 內：
  若 _current 不可中斷                         -> 維持
  若 best.score < _current.score + HYSTERESIS  -> 維持
  若 已執行時間 < MIN_COMMIT                    -> 維持（source == "reflex" 除外）
否則（_current 的 window 已經過期）             -> 直接切換，跳過上面三條
```

> [!danger] `interruptible` 只管「搶佔」，不管「自然到期」——這是實作時真的踩到的 bug
> 第一版實作漏了「還在自己 window 內」這個前提，變成不管 `_current` 的
> window 過沒過期，只要 `interruptible == false` 就一律 `return`。
> 結果 `sleep`（`interruptible = false`）過了 `08:00` 也不會醒——因為每次
> 重算都在第一關直接 `return`，永遠沒機會走到「window 已經過期，該讓位」
> 這一步。`interruptible` 回答的是「有沒有更高分的候選能搶著換掉我」，
> 不是「我自己是不是還該待在這裡」——這是兩個不同的問題，只有前者該被
> `interruptible` 擋，後者只看 window 過期沒過期。

> [!danger] 「選任務」跟「往任務移動」要分開，不能只在真的換任務那一刻才嘗試移動——這也是實作時踩到的 bug
> 第一版把「決定要不要換 `_current_task`」跟「呼叫 `move_to()`」寫在同一個
> 函式裡，只有真的換了任務才會嘗試移動。問題：`GameClock.time_changed`
> 不管角色在不在對話中都會觸發重算，所以任務的切換完全可能發生在**對話
> 期間**——那一刻 `_current_task` 已經換成新任務，但移動被 `is_in_conversation()`
> 擋下、記了地點沒真的走。等對話真的結束、`exit_conversation()` 再重算一次
> 時，`best` 通常還是同一筆（跟換任務那一刻比，沒有更高分的新候選），
> 於是「是不是同一筆」直接判定「沒事做」`return`——移動永遠沒有第二次
> 機會被觸發，角色卡在對話結束的地方不動，即使任務其實早就換了。
>
> 修法：把「決定要不要換 `_current_task`」（`_consider_switch`）跟「往
> `_current_task` 的方向前進」（`_pursue_current_task`）拆成兩個函式，
> 每次 `_reevaluate()` 都無條件把兩者都跑一次——不管這次有沒有真的換任務。
> 這樣「換了任務但對話擋住移動」的情況，下一次重算（對話結束後那次）
> 才有機會補跑移動。
>
> 順帶一個效能/正確性細節：`_pursue_current_task()` 現在每次重算都會跑，
> 若不加判斷、每次都呼叫 `move_to()`，會跟 `Character.STUCK_TIME`（卡住
> 判定，預設也是 1 秒，跟預設的仲裁頻率一樣）打架——`move_to()` 每次都
> 重設 `_stuck_timer`，卡住偵測永遠沒機會真的累積到閾值。所以只有
> `not is_moving()` 時才重新呼叫 `move_to()`，已經在路上就不重算路徑。

> [!warning] `is_interruptible()` 現在同時被兩種呼叫端用，接上 work 執行層後行為待確認
> PR #75（工作站）幫 `Character` 加了 `is_interruptible() -> bool: return not _working`，
> 給 `talk_to()` 擋「工作中不能被搭話」。這條分支跟它 rebase 合併時，把
> `Agent.is_interruptible()` 改成三個條件都疊：
> `super() and current_state != "sleep" and _current_task.get("interruptible", true)`。
>
> **目前這個疊加對 Agent 沒有實際作用**——`ai_schema.gd` 的
> `IMPLEMENTED_ACTIONS` 還沒有 `work`，沒有任何執行層會讓 Agent 自己呼叫
> `work_at()`，`_working` 對 Agent 永遠是 `false`，`super()` 永遠回 `true`。
>
> 但 `is_interruptible()` 同時被外部（`talk_to()` 擋搭話）跟內部
> （`_reevaluate()` 拿自己的 `is_interruptible()` 判斷目前任務能不能被搶）
> 兩種呼叫端共用。等 `work` 真的被接上 Agent 執行層那天，「Agent 正在
> 工作」會讓這個函式回 `false`——**不只擋住被搭話，也會連帶讓仲裁器
> 認為目前任務不可打斷，工作中途新排程進來一樣搶不走**。這聽起來合理
> （工作不該被行程重排半途打斷），但這是「共用同一個函式名字」帶出來的
> 自然結果，不是設計文件裡明確拍板過的規則——`work` 接上執行層那個 issue
> 動工時，要回頭確認這個副作用是不是真的要的。

> [!warning] 抖動是這個設計最真實的 bug，不是理論風險
> 兩個任務分數接近時，Agent 會走到一半掉頭、再掉頭。
> Agent 走完一段路要好幾秒，而仲裁掛在 `GameClock.time_changed` 上是一遊戲分鐘一次
> （= 1 現實秒，見 `GameClock.gd` 的 `seconds_per_game_minute = 1.0`）——
> 這個頻率完全足以讓它在兩個地點之間來回。
>
> `HYSTERESIS` 與 `MIN_COMMIT` 是必要的，不是優化。

## 中斷之後怎麼辦

被搶佔的任務要不要回池子，依 `source` 分開處理：

| source | 被搶佔時 | 理由 |
| --- | --- | --- |
| `schedule` | 丟掉，不回池子 | 它是時間的函數，下次重算會自己再被算出來，回收等於重複 |
| `llm` | 放回池子，`retries += 1` | 這是「有人交代的事」，掉了就是沒做 |
| `reflex` | 丟掉 | 觸發它的狀況若還在，下次重算會再觸發 |

`retries` 超過上限就丟掉並記一筆失敗，避免一個永遠做不到的任務卡住池子。

動作失敗（拿到 [[talk 動作設計]] 那組失敗原因碼）走同一條路：
`TOO_FAR` 之類可重試的放回池子，`TARGET_NOT_FOUND` 之類不可能自己好轉的直接丟掉，
「動作失敗」本身也是一個重排時機，可以考慮請 LLM 重排。

> [!note] 什麼時候會請 LLM 重排
> 遊戲日開始、某項需求跌破閾值、被搭話、動作失敗、突發事件（被攻擊或血太低）、
> 進出交誼區。**就這六個** —— 別讓仲裁器每跑一次分就順手叫一次 LLM，
> 它是一遊戲分鐘跑一次的。

## 池子的守則

> [!warning] LLM 可以無限 push，池子必須有上限
> 上限（建議 20，與「每遊戲日最多 20 次 AI 請求」同量級）、
> 同 `action + params.target` 去重（新的覆蓋舊的，不是兩筆並存）、
> `expires_at` 到了就清除。
>
> 沒有這三條，被搭話幾次之後池子就會塞滿重複的「回訪某某」。

> [!warning] LLM 回傳的 action 一定要過白名單
> 只接受 §5.3 動作清單裡的字串，`params` 逐欄位型別檢查。
> 少了這道，計畫安全章節的「外來文字一律視為資料」就形同虛設 ——
> 交誼區來的文字會直接變成動作。

## 不更新就是空陣列

LLM 沒有東西要加就回傳空陣列，**不要為「拒絕更新」另外設計一個特殊值**。
push 語意讓這種欄位變得沒有必要，少一個特殊值就少一種 LLM 回錯格式的方式。
冷卻機制照舊。

## 遷移對照

改動全部在 `agent.gd` 內，`character.gd` 與 `player.gd` 一行都不動。

| 現在 | 改後 |
| --- | --- |
| `schedule: Array` of `{time, place, state}` | `_tasks: Array[Dictionary]`；載入時每筆轉成 Task，`action = state`、`params.place = place`、`window = {start: time, end: 下一筆的 time}`、`source = "schedule"` |
| `_on_time_changed()` 比對整分字串 | 只呼叫 `_reevaluate()`；到沒到點交給 `time_bonus` 判斷 |
| `_apply_current_entry()` | 併進 `_reevaluate()`，開場不再是特例 |
| `_start_entry(entry)` | `_run(task)`，內容幾乎照搬（含 `agent.gd:88` 那個「已在目的地就 return」的修正） |
| `current_place` / `current_state` | 從 `_current_task` 讀，維持 `status` 指令的輸出 |
| `is_interruptible()` 比 `current_state != "sleep"` | 讀 `_current_task.interruptible`；sleep 那筆資料填 `false` |
| `schedule_template` | 不變。仍是「用哪份初始資料」，等行程完全交給 AI 維護之後才會消失 |

`npc_schedule.json` 的欄位可以不動 —— 轉換在載入時做，`window.end` 由下一筆的 `time` 推出，
最後一筆補到隔日 `08:00`。之後要在 JSON 直接寫 `priority` / `interruptible` 也相容。

## debug 指令

> [!important] 沒有 `tasks` 指令就沒辦法 debug 這套東西
> cron 版可以用眼睛看 JSON 推出 Agent 該在哪。改成分數仲裁之後，
> 「它為什麼跑去那裡」只能靠印出每筆候選的分數才回答得出來。

```
tasks [name]
```

輸出池子裡每筆的 `source / action / params / window / score` 拆項（base + time + need + age），
並標出目前執行中的那筆與它已執行多久。做法比照 [[Character 基底與 Agent]] 的 `status`，
共用同一套 `_get_character()`。

## 待決

- [ ] `HYSTERESIS` 與 `MIN_COMMIT` 的值 —— 要實跑觀察抖動才有辦法定
- [ ] `schedule` 的 base priority 相對 LLM 任務的範圍怎麼切
      （建議 schedule 統一給中間值，靠 `time_bonus` 拉開，而不是給高 base）
- [ ] `reflex` 級任務（HP 過低、被攻擊）要不要完全跳過承諾檢查
- [ ] 時間窗過期的 schedule 任務：補做還是跳過（傾向跳過，`sleep` 補做很怪）
- [ ] 仲裁頻率：跟著 `time_changed`（一遊戲分鐘），還是另設較長的節拍
- [ ] `duration` 到期算「完成」還是「重算」——影響 `work` 這類沒有明確終點的動作

## 不在這一版

- LLM 實際接線（計畫 §5.4 模型接取）
- `preconditions` 的求值 —— 結構先留欄位，v1 一律通過
- 記憶系統（計畫 §5.2）對 priority 的影響

> [!note] 已有一條繞過本篇任務池與仲裁器的 AI 移動路徑，但不是這裡規劃的東西
> `village_ai_enabled` 開啟時，`VillageSimDecision.apply()` 決定移動會直接
> 呼叫 `character.move_to()`，完全不經過任務池，也不回寫 `current_place`——
> 跟 `agent.gd` 現有的 cron 式行程表是兩個獨立機制，會互相覆蓋。
> 這是 R&D 驗證線（見 [[LLM 串接與 AI 服務層]]），不是本篇規劃要接的
> 正式排程路徑，兩者現在並存。
