# 行程佇列與任務仲裁

`agent.gd` 的行程處理是「任務池 + 仲裁器」：`_tasks` 是候選池，每次重算
（`_reevaluate()`，掛在 `GameClock.time_changed`，一遊戲分鐘一次）對每筆候選
算分、取最高分的當 `_current_task`，不維護「目前是第幾筆」。

動作介面的形狀見 [[talk 動作設計]]，移動與基底分工見 [[Character 基底與 Agent]]。

> [!note] 狀態
> **任務池與仲裁器已實作**（issue #71），LLM 決策迴圈也已接上（issue #88）：
> `agent.gd::llm_decision_enabled` 開啟後，`source == "llm"` 的目前任務做滿
> 引擎套用過下限的 `duration` 就觸發下一次決策請求，回應驗證通過就推進
> `_tasks`，跟 schedule 任務走同一套仲裁公平競爭。`need_bonus`／`age_bonus`
> 這兩項還是固定回 0——要等 LLM 任務真的帶 Stats 需求與 `created_at`
> 時間戳才有意義，目前有的只有任務本身、還沒有比較急迫程度的依據。
> 下面的設計內容是實作依據，三則 `[!danger]` 是實測驗出來、非遵守不可的前提。

## 為什麼要有仲裁器

`npc_schedule.json` 那種 `{time, place, state}` 只表達得了「幾點幾分做什麼」。
LLM 接上來之後，會出現一整類**沒有固定時間**的事情：

- 被搭話之後想回訪某人
- satiety 跌破閾值，想去吃東西
- 玩家托付的委託
- 動作失敗後的重試

這些塞不進 `{time, place, state}` —— 它們沒有 `time`。

## 結論：可行，但不要做成佇列

三個要點，順序就是重要性。

> [!important] 一、優先佇列解不了時間
> 佇列只回答「先做誰」。但 `sleep 18:00` 的優先度不是固定值 ——
> 它在 17:59 應該近乎為零，18:00 之後才變高。這是**時間的函數**，不是一個欄位。
>
> 所以要的是**任務池 + 仲裁器**：每次重算所有候選的分數，取最高的做。
> 「佇列」這個詞會誘導你去寫 `push` / `pop`，而 pop 掉的任務就再也回不來了。

> [!important] 二、不要保留兩套資料再合併
> 「schedule 一套、queue 一套、最後合併」會長成兩份各自演化的邏輯。
> 這種「兩份各自演化的邏輯」正是移動實作曾經欠過的債 ——
> 剛靠 `Character` 基底還完，不要再欠一筆。
>
> 行程表應該只是「**預先塞好、且帶時間窗**的一批 Task」，
> 跟 LLM 丟進來的是同一個 struct，走同一個仲裁器。

> [!important] 三、每次重算，不要維護「目前是第幾筆」
> `_reevaluate()` 每個遊戲分鐘從候選裡重挑一次，對話結束、工作結束、愣完之後
> 也各補一次。開場因此不是特例 —— 開場只是「第一次重算」。

## Task 結構

```gdscript
{
    "id":               "",     # 去重與取消用
    "action":           "",     # AISchema.ALLOWED_ACTIONS 裡的一項，見《規格書 07 地點與行動》§5
    "params":           {},     # place / target / item…，依 action 而定
    "priority":         0.0,    # 基礎值 0..100
    "window":           null,   # {start: "09:00", end: "12:00"}；null = 任何時間
    "duration":         0.0,    # 預期耗時，遊戲分鐘；llm 來源會被套上 MIN_ACTION_DURATION 下限
    "interruptible":    true,
    "preconditions":    [],
    "source":           "",     # schedule / llm / reflex
    "created_at":        0,     # 遊戲分鐘，aging 用
    "expires_at":         0,    # 0 = 不過期
    "retries":            0,
    "reasoning":         "",    # llm 來源才有：這筆任務為什麼被排進來，見 agent.gd::_push_llm_tasks()
    "inner_monologue":   "",    # llm 來源才有：決策當下的內心獨白，同一次回應複製給這批裡每一筆
}
```

`reasoning`／`inner_monologue` 跟 poc_village_sim 實測輸出裡本來就有的同名
欄位對應（見 [[LLM 串接與 AI 服務層]] 的《06》對照表）——決策準不準沒有系統性
驗證，只能肉眼看這兩個欄位判斷合不合理，正式決策迴圈接上時原樣保留。
schedule 來源的任務不填這兩個欄位，讀取一律用 `.get(..., "")`。

## 仲裁

```
score(task, now) =
      task.priority                    # 基礎值
    + time_bonus(task.window, now)     # 時間窗
    + need_bonus(task, stats)          # 需求急迫度
    + age_bonus(task, now)             # 等待加分，防餓死
```

`time_bonus`：窗內給一個明顯大於任何 base priority 的加成（例如 +100），
確保「到點的行程」預設壓過「隨時可做的雜事」；窗外直接濾掉這筆，不進比較。
沒有 window 的任務這項為 0。

選出 `best` 之後，**不是直接執行**，要先過承諾檢查：

```
若 _current 還在自己的 window 內：
  若 _current 不可中斷                         -> 維持
  若 best.score < _current.score + HYSTERESIS  -> 維持
  若 已執行時間 < MIN_COMMIT                    -> 維持（source == "reflex" 除外）
否則（_current 的 window 已經過期）             -> 直接切換，跳過上面三條
```

> [!danger] `interruptible` 只管「搶佔」，不管「自然到期」
> 承諾檢查（`interruptible`／`HYSTERESIS`／`MIN_COMMIT`）**只保護還在自己
> window 內的 `_current`**。窗口已經過期的任務一律讓位，不受保護。
>
> `interruptible` 回答的是「有沒有更高分的候選能搶著換掉我」，不是「我自己
> 是不是還該待在這裡」——兩個不同的問題，只有前者該被 `interruptible` 擋。
> 混在一起的話 `sleep`（`interruptible = false`）過了 `08:00` 也不會醒：
> 每次重算都在第一關直接 `return`，永遠走不到「窗口過期，該讓位」那一步。
>
> 同一條規則還有第二個出口：**候選一個都沒有的時候，過期的 `_current` 要清掉**。
> `_reevaluate()` 只在 `best` 非空時才走 `_consider_switch()`，所以窗口全空
> 的那一刻走不到上面那條保護解除的邏輯，過期的 `sleep` 會留在 `_current_task`，
> `is_talk_interruptible()` 與 `_is_preemptible()` 從此永遠回 `false`。schedule 任務的窗口由建構方式保證
> 連續，碰不到；有間隔的任務（LLM）才會。

> [!danger] 「選任務」跟「往任務移動」是兩個獨立步驟
> `_reevaluate()` 每次都跑完 `_consider_switch()`（決定要不要換 `_current_task`）
> **和** `_pursue_current_task()`（往 `_current_task` 前進），不管這次有沒有
> 真的換任務。
>
> 兩者不能合併：`GameClock.time_changed` 不管角色在不在對話中都會觸發重算，
> 任務的切換完全可能發生在**對話期間**——那一刻 `_current_task` 已經換好，
> 但移動被 `is_in_conversation()` 擋下。等對話結束再重算時 `best` 通常還是
> 同一筆（沒有更高分的新候選），「是不是同一筆」若直接 `return` 就沒有第二次
> 機會補跑 `move_to()`，角色會卡在對話結束的地方不動。

> [!danger] `_pursue_current_task()` 每分鐘跑一次，所以它必須自己認得「已經在處理了」
> 這個函式裡的 `move_to()`、`push_error("沒有這個地點")` 都是**只該在狀態真的
> 改變時做一次**的事，但它每個遊戲分鐘都會被呼叫。靠兩個欄位分辨：
>
> | 欄位 | 意義 |
> | --- | --- |
> | `_pursued_place` | 上次真的下過指令（或判定到了／走不到）的地點 |
> | `_pursuit_done` | 這一趟已經有結論，由 `move_finished` 訊號設起來 |
>
> 判斷是「地點沒換 **而且**（還在走 或 已經有結論）就什麼都不做」。三種錯法各自
> 對應一個真的會發生的症狀：
>
> - **完全不判斷**：`_check_stuck()` 放棄路徑後，下一次重算又對同一個走不到的
>   目標 `move_to()`，變成卡住／放棄每秒一輪的無限迴圈，warning 無限洗版。
>   實測同一份場景同樣 frame 數，3 則 vs 130 則。
> - **只判斷 `is_moving()`**：任務換了、角色還在走去上一筆的地點時不會改道，
>   要先走完舊路徑才轉向。
> - **判斷了但不看 `_pursued_place`**：對話結束、`stop_moving()` 之後要重新起步
>   的那條路會被一起擋掉（`stop_moving()` 不發 `move_finished`，所以
>   `_pursuit_done` 仍是 `false`，這條路才走得通）。
>
> 另外兩個「刻意站著不動」的狀態也要在這裡擋：`is_working()`（走開會讓
> `_run_work()` 中止而且不撥款）與 `_reacting`（對陌生人「！」的那 2 秒，
> 不擋的話 1 秒後就被重算送回路上，`NOTICE_PAUSE` 等於只有一半）。

> [!note] 搭話中斷跟仲裁器搶占是兩個獨立函式，這是拍板過的行為
> `talk_to()` 擋搭話問的是 `is_talk_interruptible()`；`_consider_switch()`
> 判斷目前任務能不能被搶問的是 `_is_preemptible()`（agent.gd 私有）。兩者不
> 互相呼叫，各自獨立計算，可以各自獨立改。
>
> 在目前的任務類型上，兩個函式算出同一個公式：`not _working and
> _current_task.get("interruptible", true)`。這裡不另外比對
> `current_state == "sleep"`——`_select()` 把 `action` 寫進 `current_state`，
> 而 `interruptible` 是從同一個 `action` 算出來的，兩者恆等。
>
> `ai_schema.gd` 的 `IMPLEMENTED_ACTIONS` 目前沒有 `work`，沒有執行層會讓
> Agent 自己呼叫 `work_at()`，所以 `not _working` 這半對 Agent 恆為 `true`。
> 等 `work` 真的接上 Agent 執行層那天，「Agent 正在工作」會讓兩個函式一起回
> `false`——**不只擋住被搭話，也會連帶讓仲裁器認為目前任務不可打斷，工作
> 中途新排程進來一樣搶不走**，這是設計上要的行為：仲裁器（新排程進來）不能
> 強制打斷工作，只有《02》§3 的強制中斷事件（被攻擊等）能覆蓋；AI 想自己放棄
> 工作改做別的事，走的是同一節新增的「AI 自主中止長動作」檢查點機制，不是靠
> 仲裁器搶任務。三條路徑（強制中斷／自主中止／仲裁器不可搶）已經分工清楚，
> `work` 接上執行層時照這個分工做即可。
>
> 移動那半邊已經對齊：`_pursue_current_task()` 自己看 `is_working()` 直接返回，
> 不然仲裁器會每分鐘把工作中的 Agent 走離工作站，`_run_work()` 的距離重驗就
> 中止而且不撥款。

> [!warning] 抖動是這個設計最真實的 bug，不是理論風險
> 兩個任務分數接近時，Agent 會走到一半掉頭、再掉頭。
> Agent 走完一段路要好幾秒，而仲裁掛在 `GameClock.time_changed` 上是一遊戲分鐘一次
> （= 1 現實秒，見 `GameClock.gd` 的 `seconds_per_game_minute = 1.0`）——
> 這個頻率完全足以讓它在兩個地點之間來回。
>
> `HYSTERESIS` 與 `MIN_COMMIT` 是必要的，不是優化。

> [!danger] 等待 LLM 決策回覆期間，`MIN_COMMIT` 太短擋不住新一輪抖動
> `llm_decision_enabled` 開啟後，任務完成的瞬間會觸發下一次決策請求，等待期間
> 仲裁器照樣運作、退回池子挑一個候選頂著（fallback）。問題是本地 LLM 有延遲，
> 比一般 `MIN_COMMIT`（2.0 秒）長——如果 fallback 只受一般 `MIN_COMMIT` 保護，
> 幾乎每個決策週期都會在 fallback 才做不到一半、LLM 決策準時抵達的那一刻被
> 切掉，變成規律性的抖動，不是偶發的分數接近才會抖。最初設計時參考的是
> 「同機測試 2.5-4 秒」這個舊拓樸下的數字（見 [[LLM 串接與 AI 服務層]]），
> 跟下面 #118 實測的現行拓樸數字不是同一個環境量到的，不要混用。
>
> 解法是 `LLM_WAIT_MIN_COMMIT`（5.0，蓋過已知延遲）：`_awaiting_decision`
> 為 `true` 期間，`_consider_switch()` 的承諾檢查用這個值取代 `MIN_COMMIT`，
> 決策回來（或失敗放棄）之後才恢復一般值。#118（2026-08-17）已對現行
> llama-server 拓樸（本機 SSH port-forward 或直連到 desktop-h9aniv5）實跑
> 校準：6 次真實 plan 決策延遲 596~1866ms，`5.0` 對照最大值仍有約 2.7 倍
> 緩衝，維持不變；`MIN_COMMIT`／`HYSTERESIS` 也一併校準過，真實任務池分數
> 的差距（schedule 間打平、LLM 任務間差距 <0.2）都遠在 `HYSTERESIS`（5.0）
> 的保護範圍內，同樣維持不變。

`_reevaluate()` 算分前會先濾掉 `_is_expired(task, now_minutes)` 為真的候選——
`expires_at` 是「這件事的機會已經徹底過了」，跟 `window`（「現在不是時候，之後還會再輪到」）
是不同語意，過期的候選不該進比較，也不該被選中。`_current_task` 自己過期時走
跟 window 過期同一條清空路徑（否則 `interruptible = false` 的任務會卡死，永遠
沒有機會被判定「早就該結束了」），`_consider_switch()` 的承諾檢查也一樣不保護
已過期的 `_current_task`。schedule 來源的任務一律填 `expires_at = 0`（不過期），
碰不到這條路徑；真的會帶非零值的是 LLM 推進池子的任務。

## 中斷之後怎麼辦

被搶佔的任務要不要回池子，依 `source` 分開處理：

| source | 被搶佔時 | 理由 |
| --- | --- | --- |
| `schedule` | 丟掉，不回池子 | 它是時間的函數，下次重算會自己再被算出來，回收等於重複 |
| `llm` | 放回池子，`retries += 1` | 這是「有人交代的事」，掉了就是沒做 |
| `reflex` | 丟掉 | 觸發它的狀況若還在，下次重算會再觸發 |

`retries` 超過上限就丟掉並記一筆失敗，避免一個永遠做不到的任務卡住池子。

動作失敗（拿到 [[talk 動作設計]] 那組失敗原因碼）走同一條路：
`TOO_FAR` 之類可重試的放回池子，`TARGET_NOT_FOUND` 之類不可能自己好轉的直接丟掉，
「動作失敗」本身也是一個重排時機，可以考慮請 LLM 重排。

> [!note] 什麼時候會請 LLM 重排
> 設計上訂了六個時機：遊戲日開始、某項需求跌破閾值、被搭話、動作失敗、
> 突發事件（被攻擊或血太低）、進出交誼區——別讓仲裁器每跑一次分就順手叫一次
> LLM，它是一遊戲分鐘跑一次的。
>
> issue #88 這一版只接了其中一個：**目前任務做滿引擎套用過下限的 `duration`**
> （`agent.gd::_reevaluate()` 開頭那段事件驅動觸發，對應規格書《10》§5.1「動作
> 完成後才發起下一次決策請求」），加上世界開場的第一次。其餘五個（需求閾值、
> 被搭話、動作失敗重排、突發事件、進出交誼區）都還沒接——沒有 Stats 閾值判斷、
> `talk` 動作還沒觸發重排、失敗任務目前不會自動重試（見下面「中斷之後怎麼辦」
> 的 `retries` 欄位，這一版還沒有任何呼叫端會遞增它）。

## 長動作固定間隔檢查點（issue #336，《02》§3）

跟上面「什麼時候會請 LLM 重排」的六個時機是分開的一條線：任務進行到一半，
不等它做完或被強制中斷，引擎主動每 `LONG_ACTION_CHECKPOINT_INTERVAL`
（10 遊戲分鐘，跟 `MIN_ACTION_DURATION` 取同一個值，理由見常數上方註解）
額外問一次「繼續」還是「放棄、改做別的事」。只套用 `source == "llm"` 的目前
任務——跟 `duration` 到期觸發下一次決策同一個限定範圍，`talk` 任務同理排除
（完成訊號是對話結束，不是 duration）。

問法是獨立的輕量是非題信封（`PromptBuilder.build_checkpoint_envelope()` ／
`AISchema.validate_checkpoint()`），只回 `{"continue": bool}`，不是整套
`tasks` schema——不需要 `visible`／`pool`／`today_plan`／`memory` 這些完整
重新規劃才要看的資料，只需要 `_self_block()` 那份「我現在人在哪、身體狀態
如何」就夠判斷。問到「放棄」由 `_abandon_task_from_checkpoint()` 收尾，
共用既有的 `_finish_task_and_request_next()`（退出任務池、清空目前任務、
補下一次完整決策請求）。

檢查點不限於任務發起者：`Character.get_checkpoint_dependents()` 回傳「這個
長動作觸發檢查點時，還要一併通知的其他角色」，目前唯一情形是被自己 `haul`
的目標（讀既有的 `_hauling_target`）；`Character.on_dependent_checkpoint()`
是收到通知那一端的掛勾，基底 no-op。這兩個介面是給 haul／struggle（issue `#355`／#337）
接的——問「繼續搬 or 放棄放下」跟問「struggle／shout／idle」
是不同的決策內容，本節機制只保證「通知得到」，不代問。

## 排程任務失敗退避（issue #505）

schedule 來源的任務不會因為失敗被移出池子——上面「中斷之後怎麼辦」那格說的
「它是時間的函數，下次重算會自己再被算出來」，對「被搶佔」是對的，但對
「執行失敗」會變成問題：`eat`／`drink` 這類「呼叫一次就完成」的動作
（`_pursue_eat_task()`／`_pursue_drink_task()`）不管成敗都會
`_clear_current_task()`，任務本身還留在 `_tasks` 裡、還在自己的 window
內、分數不變，下一個遊戲分鐘仲裁器一樣會把它選回來、一樣會失敗——`NO_FOOD`
這種硬失敗不會在窗期內自己變好，變成每分鐘重試一次同樣的失敗，log 被洗版、
運算被浪費。

修法是失敗當下記一個退避標記（`agent.gd::_mark_schedule_retry_backoff()`）：
把 `task["_retry_blocked_until"]` 設成這個 window 下一次結束的絕對分鐘數
（`_window_end_minutes()`，跟 `_now_minutes()` 同一個 `day * 1440 + hour *
60 + minute` 基準）。標記掛在 task 這個 Dictionary 物件本身，跟 `_tasks`
池子裡是同一個參照，不是複本，所以 `_clear_current_task()` 把 `_current_task`
換成新的空字典不會把它清掉。`_reevaluate_once()` 選候選那段看到還在退避期
內的任務就跳過，仲裁器改選次高分的候選，或者根本沒有候選（角色安靜站著，
直到窗期結束、標記自然失效）。下一個時間窗（例如明天同一個 window）
`now_minutes` 自然超過這個值，不用另外清除標記。

只對 `schedule` 來源、且有 `window` 的任務生效：`llm` 來源失敗直接
`_remove_task()` 離開池子，本來就不會重試，不需要退避；沒有 `window` 的
排程任務（目前 `npc_schedule.json` 沒有這種案例，見「`npc_schedule.json`
怎麼變成任務」一節）沒有窗期終點可以退避到，先不處理。`talk` 排程刻意不套
這套——它的「重試」是等人到齊、等對方不忙，會隨時間自己好轉，不是
`NO_FOOD` 那種確定性硬失敗，套上退避反而會讓角色錯過真的可以講到話的時機。

## 池子的守則

> [!warning] LLM 可以無限 push，池子必須有上限（已實作）
> 上限 `LLM_TASK_POOL_CAP`（20，與「每遊戲日最多 20 次 AI 請求」同量級，
> 只算 `source == "llm"` 的筆數，不含固定不變的 schedule 任務）、同
> `action + params.target`（沒有 `target` 才退回 `params.place`）去重，
> 新的覆蓋舊的、不是兩筆並存；`agent.gd::_push_llm_tasks()` 做的。單次回應
> 本身另外還有 `AISchema.MAX_TASKS_PER_RESPONSE`（5）擋著，兩層一起防池子
> 被灌爆。`expires_at` 到期清除沿用既有的 `_is_expired()` 機制（#92），
> 不是這次新加的。
>
> 沒有這幾條，被搭話幾次之後池子就會塞滿重複的「回訪某某」。

> [!note] 池滿時大多任務被丟棄，`persuade` 已承諾的任務是唯一例外（#227，已實作）
> `_push_llm_tasks()` 池滿只 `push_warning` 靜默丟棄新任務——一般 LLM 任務這樣
> 沒關係，模型下一輪還會再問一次。但 `persuade` 的 `proposed_task` 被目標接受
> （`persuaded: true`）之後才推進池子，這時 `_pending_persuade` 已經清空、
> 沒有「下次再問」這條退路：對方已經被告知「你被說動了」，池滿卻讓這個承諾
> 憑空消失是靜默的行為矛盾。`_evict_lowest_priority_llm_task()` 用跟仲裁器
> 選 best 候選同一套 `_score()`，池滿時先擠掉分數最低的既有 llm 任務再推進，
> 保證已承諾的說服塞得進去——這是目前唯一會主動騰位置而不是被動丟棄的任務
> 來源，其餘 LLM 任務池滿一律照舊丟棄

> [!warning] LLM 回傳的 action 一定要過白名單（已實作）
> `AISchema.ALLOWED_ACTIONS` 現在是《07》《11》拍板後的 22 個（不含 spec
> 沒有的 `work`），只接受這張表上的字串；`params` 目前只驗證存在且是
> Dictionary，逐欄位型別檢查留給各動作真的接執行層那天一起做。
> 少了白名單這道，計畫安全章節的「外來文字一律視為資料」就形同虛設 ——
> 交誼區來的文字會直接變成動作。

## 不更新就是空陣列

LLM 沒有東西要加就回傳空陣列，**不要為「拒絕更新」另外設計一個特殊值**。
push 語意讓這種欄位變得沒有必要，少一個特殊值就少一種 LLM 回錯格式的方式。
冷卻機制照舊。

## `npc_schedule.json` 怎麼變成任務

JSON 的欄位維持 `{time, place, state}` 不動，轉換在 `_load_schedule()` 載入時做：
`action = state`、`params.place = place`、`source = "schedule"`、
`window.start = time`、`window.end` 是下一筆的 `time`，最後一筆繞回第一筆的
`time`（不寫死 `08:00`，跟著資料檔自己的開場時間走）。`interruptible` 由
`state != "sleep"` 算出來。之後要在 JSON 直接寫 `priority` / `interruptible` 也相容。

> [!important] 只有一筆的行程表不給 `window`
> 一筆的話「下一筆」就是自己，`window` 會變成 `{start: T, end: T}`，
> 而 `_in_window()` 對 `start == end` 一律回 `false`（`now >= T and now < T`
> 不可能同時成立）——唯一的候選永遠不在窗內，`_current_task` 從沒被設定，
> 角色靜靜地站著不動而且什麼都不 log。一筆的意思是「整天都做這件事」，
> 所以直接不給 `window`：仲裁器本來就把沒有 `window` 的任務當成隨時可選。
>
> 同理，`tasks` 指令與 `_select()` 一律用 `.get()` 讀 Task 的欄位，不硬取 key ——
> 沒有 `window` 是這套設計允許的形狀，不是壞資料。

## 回復類動作沒有自己的執行函式

`sleep` / `nap` / `rest` / `wash` / `idle` 五個動作走的是仲裁器**既有**的那條路：
選中之後 `_pursue_current_task()` 走去 `params.place`（沒給就原地不動），
然後佔用 `duration`。沒有一個 `func do_nap()`，也不需要——它們動的只有
`Stats` 的數值跟 `current_state`，沒有新場景物件、沒有新資源。

回復量在 `_on_time_changed()` 每遊戲分鐘結算一次（`_apply_action_recovery()`），
數字見 `ACTION_RECOVERY`。表的形狀是「動作 -> {stat, amount}」（#214），不是單純
「動作 -> 數字」——不同動作要回復的欄位不見得相同，這個形狀讓之後加一個目標
欄位不同的動作（例如 wash 回復 `hygiene`）只需要多加一行，不必重寫整段。
三件事是刻意的：

- **先結算回復再 `_reevaluate()`。** 反過來的話，剛被換掉的那筆任務會用
  *新* 任務的 `current_state` 結算它自己的最後一分鐘。
- **`is_moving()` 為真時不回復。** 還在走去床邊的路上不算在睡覺。
- **`idle` 不在表上。** 發呆本來就不該回復任何東西，它的用途是給 AI 一個
  「合法地什麼都不做」的選項，而不是假裝在忙。`wash` 已接上 `hygiene`（#241）。

`ACTION_RECOVERY` 的四個數字是暫定值。`sleep`／`nap`／`rest` 三個，《07》§2-3
只給相對關係（`sleep` 最多、`nap` 較低、`rest` 小幅），沒有給數字；`wash` 的
`3.0`（回復 `hygiene`）也是暫定值，沒有既有規格可對照。四個都跟 `HYSTERESIS`／
`MIN_COMMIT` 一樣要實跑再校準。`sleep`／`nap`／`rest` 的對照基準是 `stamina`
的自然衰減每遊戲分鐘 1.0（`stats.gd::SPEC`）；`wash` 的對照基準是 `hygiene`
自己的 `drift` 0.5，`3.0` 目前抓約 6 分鐘的自然衰減量，同樣待實跑校準。

## murmur 沒有目標、不用移動，做一次就結束（issue #162）

跟回復類動作（佔滿整段 `duration`）、`talk`（追著會動的目標走）都不同：
`murmur` 一進 `_pursue_current_task()` 就在 `_pursue_murmur_task()` 裡直接
執行完畢——`resolve()` 過一次（`murmur` 沒有硬規則、不擲骰，恆成功，見《99》
P-23「純機率觸發，跟 `idle` 平行」）就講一句話、立刻退出任務池，不等
`duration` 到期。

講什麼由 `DialogueLines.murmur(stats)` 依角色數值挑句子，跟 `talk` 的
`reply()` 同一套「模板先頂著、LLM 版之後再換」的分工（見 [[talk 動作設計]]），
但語氣是講給自己聽，不是講給對話對象聽，句子跟 `reply()` 分開維護。

收尾跟 `talk` 判定失敗同一種：退出任務池、清 `_current_task`／`current_place`、
`current_state` 回 `idle`，`llm_decision_enabled` 開著時主動補一次決策請求
（理由見上面「等待 LLM 決策回覆期間」那條——這筆是在這裡被移除的，不是被
`duration` 完成分支判定的，那個分支不會再被觸發）。

## give／shout 做一次就結束，不佔滿 duration（issue #158）

跟回復類動作（佔滿整段 `duration`）相反的另一個極端：`give`／`shout` 一旦真正
執行過一次（不管成功失敗）就立刻退出任務池，不等 `duration` 到期。兩者都在
`_pursue_current_task()` 裡跟 `talk` 一樣另外分流（`current_state` 判斷），
不落進地點式的 `_pursued_place`／`_pursuit_done` 節流：

- `_pursue_give_task()`：目標是會動的角色，跟 `_pursue_talk_task()` 同一套
  「每次重算重新問一次他在哪」，追到 `GIVE_RANGE`（32px）內就送、結束
- `_pursue_shout_task()`：沒有目標、不用移動，`resolve()` 過一次就廣播
  （複用既有的 `make_noise()`，見 [[聽覺感測]]）、立刻結束

兩者跟 `talk` 判定失敗共用同一個收尾 `_finish_task_and_request_next()`：
退出任務池、清 `_current_task`、主動補一次決策請求（原因見上面「等待 LLM
決策回覆期間」那條——這筆是在這裡被移除的，不是被 `duration` 完成分支判定的，
不主動補的話 Agent 會乾等到不相干的事件才重新決策）。

## debug 指令

> [!important] 沒有 `tasks` 指令就沒辦法 debug 這套東西
> 分數仲裁選出來的結果肉眼看不出理由，「它為什麼跑去那裡」只能靠印出每筆
> 候選的分數才回答得出來。

```
tasks <name>
act <name> <action> [place|target]
```

`act` 直接推一筆任務進池子，看那隻角色真的去做那個動作。它走
`agent.gd::debug_push_task()` → `_push_llm_tasks()`，跟 LLM 決策回應**同一條**
路徑——另開一條執行捷徑的話，驗到的就不是真正會跑的那條。

只收 `AISchema.IMPLEMENTED_ACTIONS` 上的動作：白名單上但還沒接執行層的動作
推進去只會讓角色靜靜地站著，看起來像指令壞了。任務帶 `expires_at`，30 遊戲
分鐘後自己退場——`llm_decision_enabled` 關著的角色沒有「任務做完就重新決策」
那條路徑，不帶的話這筆最高分任務會永遠留在池子裡把角色卡住。

`name` 是必填的，不像 `status` / `inv` 那樣可以省略看玩家自己 —— 玩家不可能有
任務池（只有 Agent 進 `agents` 群組），預設值會是條永遠失敗的死路。

輸出池子裡每筆的 `source / action / params / window / score` 拆項（base + time + need + age），
並標出目前執行中的那筆與它已執行多久。做法比照 [[Character 基底與 Agent]] 的 `status`，
共用同一套 `_get_character()`。

## 前提求值（`preconditions`，issue #477）

跟 `window`／`expires_at` 並排的第三道濾網（見上面「仲裁」一節），兩處都會
查：候選迴圈裡 `_reevaluate_once()` 選出 `best` 之前，`_preconditions_met()`
先把 preconditions 沒過的候選整批濾掉、不進分數比較；`_consider_switch()`
的 `current_still_valid` 也把它跟過期／出窗並列成同一組條件——目前這筆任務
執行中途 preconditions 轉為不成立時，一樣視為「不是自然做完」，跟出窗／過期
被換掉走同一條路徑（`_select()` 記 `ok=false`，或沒有候選可換時
`_clear_current_task(true)` 收尾）。preconditions 是 AND 陣列，一筆不成立
整筆任務就出局：

```gdscript
"preconditions": [
    {"field": "stats.satiety", "op": ">=", "value": 20.0},
    {"field": "relations.trust", "target": "npc_003", "op": ">=", "value": 10.0},
]
```

`field` 只認兩種命名空間：`stats.<key>`（key 要在 `Stats.SPEC` 裡）、
`relations.<key>`（`trust`／`met_count`；`target` 沒填時退回
`task.params.target`，卡「對現在這個任務對象」不用每筆都重複寫 id）。
`op` 認 `>= <= > < == !=`，`value` 一律要求數字（`int`／`float`）。比較前
`_preconditions_met()` 先檢查型別，`value` 不是數字直接 fail-closed 回傳
`false`，不會進入 `_compare_precondition()` 比較——`actual` 永遠是數字，
沒擋住的話 `>=`／`<=`／`>`／`<` 對不相容型別（例如數字對 `null`）會直接丟出
runtime error，不是安全地回傳 `false`，這也是為什麼這裡不能省略型別檢查。
`preconditions` 本身不是 Array、單筆不是 Dictionary、欄位解析不出來（命名
空間打錯、stats key 不存在、沒有 target 可用）、`value` 不是數字，一律
fail-closed——視為不成立，不會被靜默當成湊巧過關的數值 0。`tasks` debug
指令會在每筆任務後面標「（前提不成立）」，
跟「（窗外）」同一種呈現。

目前沒有任何呼叫端會產出非空的 `preconditions`（schedule／llm 建構仍固定填
`[]`），這一版只蓋求值關卡本身。候選從沒被選中就被濾掉的情形不留失敗紀錄、
不觸發 LLM 重排——角色從沒試過，跟「動作失敗」（見下面「中斷之後怎麼辦」）是
不同語意；已經在執行、之後才變成不成立的情形則沿用「被搶占」的既有語意記
`ok=false`，等真的有非空 preconditions 的任務出現、且產品面需要更細的訊號
時再另開範圍評估。

## 不在這一版

- 記憶系統（見《規格書 03 事件評估與記憶》）對 priority 的影響——
  `reasoning`／`inner_monologue` 已經隨 Task 一起存，是為它先鋪的路，
  但還沒有任何東西讀
- 六個 LLM 重排時機裡除了「動作完成」之外的五個（見上面「什麼時候會請 LLM
  重排」）
- 把 LLM 決策的 `action` 接成真正的動作執行——`talk`／`murmur`／`give`／`shout`／
  `persuade` 已接上（分別見 [[talk 動作設計]]、issue #162、issue #158、
  issue #227），`work` 還沒，仍是另一則 issue 的範圍

> [!note] `move_finished` 不是仲裁器獨佔的訊號
> `move_to()` 不管誰呼叫，完成時都發同一個 `move_finished`——仲裁器自己會，
> debug 主控台的 `goto` 指令繞過仲裁器直接呼叫 `character.move_to()` 也會。
> `agent.gd::_on_move_finished()` 靠 `character.gd` 的 `last_move_target` 比對
> 完成的目標是不是仲裁器自己 `current_place` 對應的錨點，不是的話直接忽略——
> 這樣才不會把別人發起的 `move_to()` 完成，誤判成仲裁器自己這趟追逐有結論了。
