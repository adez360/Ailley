# 角色庫與投放

`GameManager.spawn_character()`（#73）是動態生成角色、套進場景的共用機制。官方模板庫
（左邊入口）與玩家自建角色（右邊入口，issue `#122`，見 [[建角面板]]）投放時都呼叫這同一個
`spawn_character()`，不重複實作。

`main.tscn` 已不再固定擺放 `Agent`~`Agent5`，村莊人口一律走這套投放機制決定（《10》）。
原本這 5 個佔位節點的人設**不轉正進模板庫**——2026-08-28 拍板直接丟棄（issue #600），
`npc_schedule.json` 裡 `Agent`~`Agent5` 的 `identities`／`assignments` 死資料已一併移除。

## 定位：這是《00》/《05》生命週期圖的哪一段

`00_設計原則與架構.md` §5 的角色生命週期圖有兩條平行入口，匯流到同一條後續流程：

```text
官方模板庫(50個)  或  玩家自建角(面板)
        └──────────┬────────────┘
                    ▼
              建立中(尚未存檔) → 存檔驗證 → 角色生成(system_prompt + words_to_creator)
                    ▼
              角色庫（靈魂；跟著世界存檔一起持久化，見 #342，投放後紀錄仍保留）
                    │ 投放（上限5人，deployed 旗標標記，不離開角色庫）
                    ▼
              生成該世界的肉體副本 → 存活
```

**#73 只做左邊那條入口（官方模板庫），而且只接「已經是成品」之後的段落**——
「建立中→存檔驗證→角色生成」這三步的本質是把**尚在編輯的原始輸入**轉成
**驗證過、生成完整**的角色紀錄，模板資料本身應該已經是烘焙好的成品（不管
是誰、什麼時候做的），不需要玩家投放的當下重跑一次。#73 接手的是
「已經是成品的模板」→「進角色庫」→「投放」這一段。

右邊那條入口（玩家自建角色）完整涵蓋「建立中→存檔驗證→角色生成」，
issue `#122` 已完成，見 [[建角面板]]。`character_library` 跟著世界存檔一起
存讀（issue #342，見 `GameManager.get_world_save_data()`／
`apply_world_save_data()`）——這份清單不屬於任何一個場上節點，沒有
`Character.get_save_data()` 可以掛，收在世界層這一包裡；「deployed」旗標與
`deploy_from_library()` 現場重算的投放人數也一起還原，不用另外存計數。

還原清單只是「記得住哪些是已投放」，`entry["deployed"] == true` 的紀錄如果
場景裡沒有對應節點（重開遊戲後場上節點不會自己冒出來），要靠讀檔流程另外
重新生成——這段接在 `GameManager._respawn_character()`（issue #344），
跟 `deploy_from_library()` 走同一套 identity_assignments／decision_source／
rebuild_provider 設定，差別只在觸發時機是讀檔而不是使用者按下投放按鈕，
見 [[存檔]]「讀檔會重新生成場景裡缺席的角色」。

官方模板庫（`character_templates`）不在這條路徑上：它是開場讀一次的靜態
`data/character_templates.json`，本來就不會消失，不需要存檔。

## #73 這次的範圍（MVP）

**做**：
1. 官方模板資料：`data/character_templates.json` 的**架構**——`template_id`、
   `character_name`、`system_prompt`/`words_to_creator` 欄位定義。#73 只
   建立這個架構，不填實際內容（當時只有 3 筆佔位資料，`system_prompt`/
   `words_to_creator` 留空字串）；50 筆內容製作是 issue #173 的範圍，
   目前現況見下方「官方模板庫內容」一節
2. 角色庫：記憶體清單 `GameManager.character_library`，跟著世界存檔一起
   持久化（issue #342，見上面「定位」一節）。`character_templates` 是另一份
   官方模板清單，開場讀一次 json，`get_character_template()` 查，本來就
   不需要存檔
3. 投放：`GameManager.spawn_character(scene: PackedScene, identity: Dictionary) -> Character`——
   instantiate → 把 `character_id`/`character_name` 設到節點上（`identity`
   有給就用，沒給就留空讓 `character.gd::_ready()` 既有的 fallback 生效）
   → 節點命名分兩階段：`add_child()` **之前**先把節點名設成 `character_id`
   （有給就用，沒給就先生一個臨時值），避免 `add_child()` 觸發的 `_ready()`
   期間節點名還是場景預設的 `"Agent"`、撞進 `npc_schedule.json` 的
   assignments 表；`add_child()` **之後**再把節點名同步成 `_ready()` 已經
   算出來的最終 `character_id`。`identity` 沒給 `character_name` 時，
   同一時間點也要重算一次 fallback——`_ready()` 當下讀到的是那個臨時節點
   名，不是最終值。
   `add_child()` 之前另外會把 `schedule_template`（如果這個 instance 有這
   個欄位）清成空字串，避免退回 `agent.tscn` 場景檔殘留的 `npc001` 預設值
   （見下面「殘留問題」一節）
4. `identity` 這次只開兩個 key：`character_id`、`character_name`。
   `ai_provider` 之類的欄位等對應功能真的要做時再加，不預留空欄位
5. 呼叫端：debug 指令 `spawn <template_id>`（`debug_console.gd`）驗證管線
   走得通，不等 UI。`help` 欄位留空，跟 `tasks` 指令同一個理由——不進
   `locale/console.csv`，避免動到這台機器上卡過的翻譯資源匯入。這個指令
   組 `identity` 時只給 `character_name`，不帶模板已經算好的
   `words_to_creator`——代價是每次用這個指令生角色都會觸發一次多餘的
   `_generate_words_to_creator()` AI 呼叫，佔掉跟第一次 plan 決策共用的
   冷卻，實測讓角色投放到真的開始依任務行動多等了一次完整冷卻（目前
   30 秒），見 [[LLM 串接與 AI 服務層]]「動態投放到真正依任務移動」一節。
   這是 debug 指令刻意從簡的取捨，不是 bug；正式的 `deploy_from_library()`
   路徑會帶上這個欄位，不受影響
6. spawn 沿用 `agent.tscn`（跟 `Agent`/`Agent2` 同一份場景），不另開一份
   閹割場景——見下面「已考慮但不採用」

**不做**：
- `Agent`/`Agent2` 維持現狀，不強迫遷移——它們是場景裡手擺的固定角色，
  `npc_schedule.json` 的 assignments 查表模式本來就是為它們設計的
- 存檔／永久保存（依賴 #21/#22）
- `system_prompt`/`words_to_creator` 的真正生成邏輯（依賴 #117 的人格資料
  注入，且 `words_to_creator` 本身是全新的第三種 AI 呼叫類型，跟既有的
  `plan`/`dialogue` 都不同，只在建角完成那一刻打一次——這次先留空）
- 建角面板、角色庫首頁 UI（見 #122）

## 已考慮但不採用：把身分套進固定節點（槽位制）

投放上限訂在 5 人，跟 `Agent`/`Agent2` 兩隻現有角色同一個等級，曾考慮
「投放＝把角色庫的身分套進預先擺好的固定節點（未來的 `Agent3`/`4`/`5`）」，
而不是動態生成新節點。

不採用：`Agent`/`Agent2` 的行程表是用**節點名**查 `npc_schedule.json` 的
assignments 表綁定的，槽位制只是換掉節點裡的身分、節點名不變，套進去的
角色會沿用那個節點名原本綁定的行程，跟角色本身的身分脫鉤。這正是
issue #73 本文要解決的問題（「一旦角色不是場景裡預先擺好的，就沒有節點名
可以查表」）走回頭路。完整的槽位制設計要另外跟後端拍板，不在這次範圍內。

## `agent.tscn` 的 `schedule_template` 殘留預設值：程式碼已迴避，場景檔本身未清（issue #132）

`scenes/agent.tscn` 根節點的 `schedule_template` 匯出值被存成 `"npc001"`，
不是 `agent.gd` 原始碼寫的空字串預設值（`@export var schedule_template := ""`）。
`main.tscn` 裡的 `Agent`/`Agent2` 不受影響——`_load_schedule()` 查表命中時一律
用 assignments 的值覆蓋這個欄位，不吃場景檔存的預設值。

`spawn_character()` 在 `add_child()` 之前主動把這個 instance 的
`schedule_template` 清成空字串，避免動態生成的角色退回這個殘留值、
帶著 npc001 的行程走動；判斷用 `get()`/`set()` 而不是型別轉型，因為這個
欄位是 `agent.gd` 才有的，`spawn_character()` 收的是泛型 `Character`。

場景檔本身那個殘留的 `"npc001"` 預設值沒有被清掉——只要生成路徑不是走
`spawn_character()`（例如以後有別的地方直接 instantiate `agent.tscn`），
一樣會撿到這個值。要不要清掉場景檔本身這個殘留值，留給 issue #132，
牽涉共用場景檔的變更確認，不在這次範圍內。

## 官方模板庫內容（issue #173）

`data/character_templates.json` 50/50 筆全部有內容，分兩種品質：

- **`tpl_001`~`tpl_006`（艾莉/小海/阿東/婉婷/老周/小雪）**：手動起草人設，
  `words_to_creator` 是手寫候選文字，不是走真管線生成的
- **`tpl_007`~`tpl_050`（村民007~村民050）**：`character_name` 是流水號、
  `character` 自由文本留空、`words_to_creator` 是固定占位字串，見下方
  「假資料先跑，MVP 後重做」

全部 50 筆都走《01-1》§3 的真實 6→10 轉換式（`Personality.
hexaco_to_personality()`）與 `build_system_prompt()` 組裝，不是隨便塞
數字——極端項數量符合 §2-3 驗證式（`character` 留空的 44 筆要求 3~4 項，
6 筆手寫的要求 2~4 項），滑桿值皆為 5 的倍數整數。每筆除了
`character_name`／`system_prompt`／`words_to_creator`，多存
`hexaco_input`（六維滑桿原始值）與 `personality`（轉換後十項），原因：
`system_prompt` 是純公式組裝，存原始輸入才能之後改文案或調校時重算，
不用整筆重寫。

模板裡的 `personality`／`system_prompt` 是離線用同一套公式算好的快取值，供模板瀏覽
UI 預覽用——這兩欄不是投放時真正吃到的資料：官方模板唯一的投放路徑是 debug 指令
`spawn <template_id>`（`debug_console.gd` 的 `_cmd_spawn()`），它只取
`hexaco_input`／`character`／`words_to_creator` 帶進投放流程（前兩項註冊進
`identity_assignments`，`words_to_creator` 經 `spawn_character()` 設到節點上），
`personality`／`system_prompt` 則由 `character.gd::_ready()` 用當下真正的
`character_id`（投放時才生成的新 id，不是 `template_id`）重新算一次，兩份不
保證逐字元相同，這是所有模板共通的性質。

但這套「跟投放／還原共用同一套機制」只在同一次 session 內成立。
`_cmd_spawn()` 註冊的 `hexaco_input`／`character` 只進了記憶體裡的
`identity_assignments`——這張表開場從 `npc_schedule.json` 重建、不跟著
世界存檔走——spawn 出來的角色也不會寫進會持久化的 `character_library`。
存檔→重載後，這隻角色走 `_respawn_character()`（issue #344）查
`character_library`，查表 miss 就以最小身分重新生成（只帶 `character_id`
的 `spawn_character()`，觸發 `push_warning("…不在角色庫，用最小身分重新
生成")`）：`hexaco_input`/`character`/`words_to_creator` 全部跨存檔丟失，
system_prompt 退回沒有人格資料的最小版。debug 指令生成只適合當下驗證
管線，不是可存續的建角入口；正式入口仍是建角面板→`character_library`
（issue #122）。

### 假資料先跑，MVP 後重做（2026-08-19 拍板）

44 筆走公式產生占位內容（`村民007`~`村民050`），不花心力寫人設文字或走
`PromptBuilder.build_creation_envelope()` 真的生成 `words_to_creator`——
先讓 50 筆全部「有資料能跑」解除 MVP 對這則的依賴，人格/文案設計留到
MVP 完成後重新做。`words_to_creator` 統一填占位字串
`「（佔位假資料，人格待 MVP 完成後重新設計，見 issue #173）」`，之後
真的要生成時只要清空這個欄位重新走一次建角管線即可，不用改資料結構。

驗證方式：`GameManager.spawn_character()` 帶全部 50 個 template_id 各生
一次，`character_id`／`character_name`／`schedule_template` 皆正確，
無非預期錯誤（在 npc-templates-173 worktree 專屬 Godot session 用
`game_eval` 實跑，`{"errors": [], "ok": 50, "total": 50}`；`logs_read`
額外出現 50 筆「沒有指定 schedule_template」`push_error`，跟 6 筆時
同一種預期內訊息，不是新錯誤）。

**發現的落差**：《99》P-10 拍板 `words_to_creator` 的 GBNF 約束是 ≤60 字，
但 `AISchema.MAX_LINE_CHARS`（`creation_response_schema()` 沿用的常數）
實際是 200，跟 dialogue/plan 的行長度共用同一個常數，沒有另外收緊到 60。
現有草稿都在 60 字以內不受影響，但常數本身跟拍板結果不一致，留給之後
真的走管線生成 `words_to_creator` 時一併處理。

## 收回（issue #974）

投放的反向操作：`GameManager.recall_from_library(id)` 把場上肉體 `queue_free()`、
角色庫紀錄的 `deployed` 改回 `false`，釋放一個 `DEPLOY_CAP` 名額。跟
`remove_from_library()`（真的刪紀錄，只對未投放的下手）是兩件不同的事——
收回後靈魂還在角色庫，可以再投放。

兩個例外會被拒絕：

- **目前化身角色**（`id == embodied_character_id`）：玩家自己操控的身體，
  收回後沒有入口能接手「變回天神」，待規劃（見《規格書 05》§7-3）
- **死亡角色**（`character.is_dead`）：MVP 只有單一世界，沒有「投去其他
  世界」這條路，收回等於讓死掉的靈魂在同一世界重新投放，形同繞過死亡的
  後果（《規格書 05》§7-3、《09》死亡禁入例外規則）

節點清除走 `queue_free()`，不另外呼叫 `stop_haul()`——`character.gd::_exit_tree()`
已經處理搬運關係雙向釋放（見該檔案 `_exit_tree()` 上方註解），跟 GameManager
其他直接對角色呼叫 `queue_free()` 的路徑同一套。

UI 入口：`character_create.gd` 的模板長條（未投放紀錄）已有「投放」（一般
NPC，`deploy_from_library(id, false)`）與「操控」（化身，`(id, true)`）兩顆鈕，
`UI_CL_BTN_DEPLOY` 這個 locale key 原本就存在但沒接呼叫端，這次補上。收回鈕
放在 `character_sidebar.gd`（列出場上角色的側欄）——`character_row.tscn`
整列本身是一顆 `Button`（點擊＝選取跟隨鏡頭），沒有直接把「收回」塞進它
裡面當子節點（會撞上 `character_create.gd` 模板列已經踩過的坑：Button 包
Button 會吃掉子按鈕的點擊，見該檔案 `_template_row()` 上方註解），而是在
`character_sidebar.gd::_row()` 用程式碼包一個 `HBoxContainer`，把
`character_row.tscn` 的 Button 跟新的收回 Button 當**兄弟節點**放進去——
兩顆按鈕互不重疊，天然不會有誰吃掉誰的點擊，也不用動 `character_row.tscn`
本身的場景結構。
