# 復活機制

`Character.revive()`（issue #386）。AI 角色與真人角色共用同一套規則，見
《規格書09》§8——這裡只記實作，規則本身以規格書為準。

## 觸發方式

玩家對著死亡（`is_dead = true`）的角色按互動鍵（`player.gd::_unhandled_input()`）。
死人不能搭話，原本會呼叫 `talk_to()` 的分支改成呼叫 `revive()`——同一個
`interact` 按鍵，依對方死活自動分流，不需要另外的按鍵或選單。付款方是操作
復活的那個 `Player`（`self.inventory`），不是屍體本人。

沒有做成獨立 UI 面板：跟 `hunt`／`bury` 一樣，先把核心機制（`Character.revive()`）
做成可測試的引擎函式，UI 細節（付費確認彈窗等）留給有需要時再加，不在這則
issue 範圍內——目前是按下互動鍵直接執行，成功或失敗都用既有的
`report_action_failure()` 顯示在角色頭上。

## `revive()` 檢查順序

跟 `bury()`／`hunt()` 同一種寫法：一路檢查，任何一關不過就回失敗碼，全過
才真的寫入狀態。

| # | 檢查 | 失敗碼 |
| --- | --- | --- |
| 1 | `corpse` 是否存在 | `REVIVE_TARGET_NOT_FOUND` |
| 2 | `corpse` 是不是自己 | `REVIVE_TARGET_IS_SELF` |
| 3 | `corpse.is_dead` 是否為 true | `REVIVE_TARGET_NOT_DEAD` |
| 4 | 距離是否在 `REVIVE_RANGE`（32px，跟 `BURY_RANGE`／`HUNT_RANGE` 同一種「2 格內」） | `REVIVE_TOO_FAR` |
| 5 | 超過 24 小時免費窗口時，`self.inventory` 餘額是否足夠 | `REVIVE_NOT_ENOUGH_MONEY` |

全部通過後：呼叫 `corpse._clear_death_state()` 清空死亡欄位、把 `stats`
恢復到安全值（跟 `_complete_treatment()` 同一套數字：health/satiety/
hydration/wakefulness/hygiene 50、injury/alcohol 0、stamina 恢復到力竭
恢復門檻以上）、對 Agent 目標注入事實句「你被天神復活了」
（`_push_daily_event()`，跟 `haul()`／`stop_haul()` 同一種
`is_in_group("agents")` 判斷，Player 沒有 AI 決策迴圈不需要這步）。

## 免費窗口判斷

`_is_within_free_revival_window()` 比較的是 `death_at`（真實 UTC 時間戳，
`_die()` 寫入）跟 `Time.get_unix_time_from_system()`，不是遊戲內 tick／day
——世界關閉、暫停、或調整時間流速都不影響這個判斷，跟《規格書09》§8 拍板一致。
`death_at` 是空字串時視為已逾期（防呆：沒有時間戳沒辦法判斷免費，寧可保守
收費）。

## 付費金額

`REVIVE_FEE_NORMAL`（未下葬，50）／`REVIVE_FEE_BURIED`（已下葬，100），
兩者互斥二選一，不疊加——2026-08-27 拍板的低風險佔位數字，待經濟數值實測
後可調整，調整不影響機制本身，見《規格書09》§8 與《99》P-24。

## 死亡欄位清理：`_clear_death_state()`

未下葬與已下葬走同一個清理函式，不分兩條路徑——`is_buried` 只是眾多要清空
的欄位之一：

- `is_dead`／`is_buried`／`is_anonymous` 全部歸 `false`
- `death_tick`／`death_day`／`buried_tick` 歸 `-1`，`death_at`／`death_cause`／
  `death_location_id` 歸空字串，`last_words`／`grave_id`／`buried_by` 歸 `null`，
  `corpse_decay` 歸 `0.0`
- `conditions` 過濾掉 `CONDITION_PETRIFIED`，外觀恢復（`_apply_death_tint(false)`）

墓園格數不需要額外釋放邏輯——`_cemetery_grave_count()` 本來就是即時掃描場上
`is_buried` 的角色數，`is_buried` 一清空，格子自然空出來給下一個人安葬。

這個函式同時取代了 `load_save_data()` 讀到 `is_dead = false` 存檔時原本自己
內嵌的一段清理邏輯（兩處要清的欄位完全一樣，抽出來共用，不維護兩份一致的清單）。

## 尚未涵蓋

- **SQLite `grave`／`grave_epitaphs` 表**（`GraveSchema.gd`／`GraveEpitaphSchema.gd`，
  issue #382）：目前沒有任何遊戲邏輯會寫入這兩張表（schema 已建好但沒有
  CRUD 呼叫端），`revive()` 因此也不用清理——之後若悼詞真的接上寫入路徑，
  復活時對應的 `grave`／`grave_epitaphs` 資料列要一併清除，屆時要回來補
- 付費復活的確認 UI（目前是按下互動鍵直接扣款執行，沒有二次確認彈窗）
