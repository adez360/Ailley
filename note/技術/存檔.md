# 存檔

現況是**零** —— 關掉遊戲什麼都不留，全專案沒有任何持久化。
這篇是它的設計。四階段裡排第一，因為記憶系統與共用存檔都卡在它，
見 [[計畫]]。

## 兩層：角色與世界

| | 裝什麼 | 誰讀它 |
| --- | --- | --- |
| **角色存檔** | 所有 player 與 agent 的身分、數值、關係 | 可以被**多個**世界存檔讀取 |
| **世界存檔** | 地圖、地點、時間、誰站在哪 | 一個世界一份 |

> [!important] 這個切法不只是檔案怎麼放
> 角色與世界解綁之後，「帶自己的 agent 進別人的村莊」**是它的直接結果，
> 不是額外要做的功能** —— remote player 帶 agent 連進來，
> 就是拿自己的角色存檔去讀別人的世界存檔。
> 多人那一階段能省多少事，取決於這兩層在這裡有沒有分乾淨。

### 位置屬於世界，不屬於角色

這是切分的第一條界線，也最容易畫錯。

角色在**某個世界裡**的座標，帶到另一個世界毫無意義 ——
你的 agent 走進別人的村莊時，它在你村莊的 `(-62, 99)` 不該跟著過去。
所以 `character_id → 座標` 的對應存在**世界存檔**，角色存檔只回答「這隻角色是誰」。

同理，`current_action`、行程進度、路徑這些也都是世界層的東西。

## 存哪

`user://`，與 `ai_config.json` 同一個地方 —— 在 repo 之外，
Linux 下是 `~/.local/share/godot/app_userdata/ailley4.3/`。

## 兩個前置，都不是存檔本身

### 一、`GameClock` 沒有「日」的概念

`scripts/core/GameClock.gd` 只有 `hour` 與 `minute`，`hour` 到 24 就歸 0，
**沒有任何地方記得今天是第幾天**。

`ai_service.gd:79` 已經因此自己養了一個 `_game_day`，靠偵測 `hour` 回捲來遞增。
那份計數是 AIService 私有的，而且**重開遊戲就歸零** ——
決策裡「每遊戲日最多 20 次 AI 請求」的配額因此可以靠重開來繞過。

日曆該由 `GameClock` 提供並寫進世界存檔，不是各系統各自推算。

### 二、`character_id` 目前不保證唯一

現在是 `@export` 手寫，`character.gd:71` 的 `_warn_if_id_taken()` 只做**偵測**，
撞了就 `push_error`。存檔要的是「建立角色時生成一次並持久化」，
見 [[Character 基底與 Agent]]。

聯機還需要跨玩家唯一 —— 兩個玩家各自有一隻 `agent` 是必然會發生的事。
命名空間或 UUID，這一階段就要決定，因為它會寫進存檔格式。

## 序列化的規則

> [!important] 走訪 `Stats.SPEC`，不要手寫欄位
> `stats.gd` 已經是資料驅動的：SPEC 加一列，數值就自動多一項。
> 存檔照抄這個做法，SPEC 改了存檔不用改。
> 這跟 [[LLM 串接與 AI 服務層]] 的 payload 是同一條規則。

舊存檔缺欄位時用 `SPEC[key]["start"]` 補，不要當成錯誤 ——
SPEC 加一項是預期會發生的事，不該讓舊存檔讀不起來。

`Relationships.records` 直接存，它本來就是純資料，
而且 key 用 `character_id` 不用名字（名字可以改，拿它當 key 等於改名就失憶）。

## 併發與時間線

| 問題 | 這一階段做什麼 |
| --- | --- |
| 兩個 process 開同一份存檔 | **要做** —— 單一 session 鎖 |
| AI 模式跑掉 3 個遊戲日再切回主模式 | **不做** —— 留給 AI 模式階段，但日曆要先有 |

時間線銜接在只有一個模式時不會發生，現在設計等於猜。
但它會需要一個持久化的日曆，所以前置的那一半要在這裡做完。
