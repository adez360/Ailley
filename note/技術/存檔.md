# 存檔

角色／世界存檔骨架、序列化、單一 session 鎖（#19–#23）都已完成，
見下面「拆成哪些 issue」。這篇是它的設計。

## 兩層：角色與世界

| | 裝什麼 | 誰讀它 |
| --- | --- | --- |
| **角色存檔** | 所有 player 與 agent 的身分、數值、關係 | 可以被**多個**世界存檔讀取 |
| **世界存檔** | 地圖、地點、時間、誰站在哪、允不允許 player 加入 | 一個世界一份 |

> [!important] 這個切法不只是檔案怎麼放
> 角色與世界解綁之後，「帶自己的 agent 進別人的村莊」**是它的直接結果，
> 不是額外要做的功能** —— remote player 帶 agent 連進來，
> 就是拿自己的角色存檔去讀別人的世界存檔。
> 多人那一階段能省多少事，取決於這兩層在這裡有沒有分乾淨。

### 位置屬於世界，不屬於角色

這是切分的第一條界線，也最容易畫錯。

角色在**某個世界裡**的座標，帶到另一個世界毫無意義 ——
你的 agent 走進別人的村莊時，它在你村莊的 `(-62, 99)` 不該跟著過去。
所以 `character_id → 座標` 的對應存在**世界存檔**，角色存檔只回答「這隻角色是誰」。

同理，`current_action`、行程進度、路徑這些也都是世界層的東西。

### 允不允許 player 加入，也屬於世界

遊戲**沒有模式之分**，世界之間唯一的差別是裡面有沒有 player。
沒有 player 在場的世界照樣跑，agent 照樣過日子。

所以世界存檔裡有一個建立時決定的旗標：**這個世界允不允許 player 加入**。

- 不允許 → 這個世界只跑 agent，沒有任何 player 能連進來
- 允許 → player **可以**加入，但不強制在場。世界在沒有 player 的情況下一樣成立

> [!important] 旗標是「允不允許」，不是「有沒有」
> 場上有沒有 player 是每一刻都可能變的事實 —— 他可以離開，也可以中途連進來。
> 載入時算一次「這個世界有沒有人」然後拿它到處分支，會在玩到一半有人離線時壞掉。
> 該問的是「這個角色現在有沒有人在操作」，那是角色層的問題，不是世界層的。

這條跟核心約束是同一件事：Player 能做到的 Agent 也必須能做到，
所以少了 player 的世界不缺任何能力，只是少一個角色。

## 存哪

`user://`，與 `ai_config.json` 同一個地方 —— 在 repo 之外，
Linux 下是 `~/.local/share/godot/app_userdata/ailley4.3/`。

## 兩個前置，都不是存檔本身

### 一、`GameClock.day` 還沒持久化

日計數本身已經做好了（#19）：`GameClock` 有 `day`（從 1 起算）與 `day_changed`，
`hour` 回捲時遞增，AIService 訂閱它來清每日配額。

缺的是**存下來** —— `day` 現在只活在記憶體裡，重開遊戲又是第 1 天，
「每遊戲日最多 20 次 AI 請求」的配額還是可以靠重開繞過。
`day` 屬於世界層（它是那個世界的日曆，不是角色的），要寫進世界存檔。

### 二、`character_id` 還沒持久化

格式已經定了（#20）：**UUID v4**，由 `Character.generate_id()` 生成，
不帶任何語意。唯一性是保證不是偵測，細節見 [[Character 基底與 Agent]]。

缺的跟 `day` 一樣是**存下來** —— 現在每次開遊戲都重新生成一組，
所以關係紀錄一重開就全部指向不存在的人。`character_id` 屬於角色層。

> [!important] 擁有者是欄位，不是 id 的一部分
> 選 UUID 就是選擇讓 id 不回答「這是誰的」。角色存檔要帶一個 `owner` 欄位，
> 但那要等真的有帳號概念才寫得出值 —— 現在沒有，所以先不放空欄位佔位。
> 這條界線的好處是帳號模型日後怎麼變都不必替 id 寫遷移。

## 序列化的規則

> [!important] 走訪 `Stats.SPEC`，不要手寫欄位
> `stats.gd` 已經是資料驅動的：SPEC 加一列，數值就自動多一項。
> 存檔照抄這個做法，SPEC 改了存檔不用改。
> 這跟 [[LLM 串接與 AI 服務層]] 的 payload 是同一條規則。

舊存檔缺欄位時用 `SPEC[key]["start"]` 補，不要當成錯誤 ——
SPEC 加一項是預期會發生的事，不該讓舊存檔讀不起來。

`Relationships.records` 直接存，它本來就是純資料，
而且 key 用 `character_id` 不用名字（名字可以改，拿它當 key 等於改名就失憶）。

## 記憶怎麼存

跟《03 事件評估與記憶》的四層架構對齊，但不是四層都要存：

| 層 | 要不要存 | 理由 |
| --- | --- | --- |
| L1 短期工作記憶 | **不用** | 每 tick 滾動、開場即可重建，本來就是暫時性資料 |
| L2 近期記憶 | **要** | 這次跟角色存檔一起做——記憶是「養一個有記憶的夥伴」的核心賣點 |
| L3 長期記憶庫（向量） | **不用** | MVP 不採用向量檢索——要跑在玩家自己的機器上，Godot 端沒有現成方案；跟這裡的存檔範圍決定一致 |
| L4 核心記憶 | **要** | 同 L2，一起做 |

**序列化技術：JSON，不是 SQLite。** 走 `Stats.SPEC`／`Relationships.records` 同一套「走訪資料結構、不手寫欄位」規則，直接存進角色存檔檔案。單機、5 人村莊的規模，SQLite 的索引/查詢優勢用不到，量大到需要時再換不遲，跟《00》§3 一致。

> [!note] SQLite 不是排除，是還沒到需要的時候
> 真的長出「動態、需要查詢」的資料（例如事件記錄、跨世界社交關係、經濟交易歷史）才是 SQLite 該接手的部分，屆時是在存檔介面背後加一塊，不是重寫這裡的序列化規則。實作時存讀角色／世界都包成介面（不要讓呼叫端直接戳 `FileAccess`），就是為了讓這個之後可以換。

`03` 裡「推測待確認」的數值（衰減率、L4 上限 5 條、重要度分級門檻、酒精遺忘判定式）**先用文件裡的暫定值上線，不現在拍板**——這些是可調數值，不影響存檔的資料結構，之後實跑再校準（跟 `agent.gd` 那批仲裁常數同樣的處理方式）。

### 決策情境欄位：只留跨天的承諾

`current_goal`／`today_plan`／`appointment`／`last_action_result` 這四個是 06 定義的「決策情境」欄位，不是全部都要存：

| 欄位 | 要不要存 | 理由 |
| --- | --- | --- |
| `today_plan` | **要** | 角色當天的計畫，玩家重開遊戲後如果整個消失，「今天原本要幹嘛」的連續感就斷了 |
| `appointment` | **要** | 跨天的承諾——重開遊戲後憑空消失，會出現「對方在等你、你卻不記得」的違和 |
| `current_goal` | 不用 | 瞬時念頭，重開等於角色睡醒重新想 |
| `last_action_result` | 不用 | 上一個動作的結果，跟目前情境無關，不需要跨重開留著 |

**「離開」只有一種情境要處理**：世界存檔是一條時間線，只在主機開著世界時推進（見上面「併發與時間線」），所以真正觸發存檔/讀檔的只有「主機關閉世界」這一刻。連線玩家中途斷線不會讓世界停下來、不會觸發存檔——但這個分支這次也不會發生，因為 MVP 這次不做連線/多人。

## 併發與時間線

**一份世界存檔就是一條時間線**，而且只在有人開著它的時候推進 ——
不做離線託管，關掉世界它就停。所以時間不會有兩處各自前進、事後要對齊的問題。

要防的是**同一份角色存檔同時被兩份存檔寫入**：

| 問題 | 這一階段做什麼 |
| --- | --- |
| 兩個 process 開同一份存檔 | **已完成**（#23）—— 單一 session 鎖 |
| 同一份角色存檔被兩個世界同時寫 | **已完成**（#23）—— 鎖鎖在角色這一層 |

角色存檔跨世界共用，你的 agent 被帶進別人的村莊時，兩邊都會想改它的數值與關係。
鎖不能只鎖世界存檔。

### 鎖怎麼做（#23）

每份存檔配一個同名 `.lock`**目錄**當互斥閘門，但閘門不是「先建空目錄、
再補內容」——那個做法有洞：建立閘門跟寫入 `info.json`（`{ pid, acquired_at }`）
是兩個分開的步驟，剛贏得閘門的 process 若在寫完 `info.json` 前被排程延遲，
另一個 process 會看到「閘門存在但內容還沒出現」的中間態，不管用什麼超時
判斷都只能降低誤判機率、無法真正消除。

改成先把完整內容寫進一個只有自己看得到的私有暫存目錄，再用
`DirAccess.rename_absolute()` 一步發布成公開的固定名字：目的地已存在時
`rename_absolute()` 會直接失敗、不覆寫、不部分成功（實測驗證過），所以公開
名字底下要嘛不存在、要嘛一出現就是內容完整的——不會再有可能被誤判成孤兒
鎖的中間態，搶輸的人只是清掉自己的暫存目錄，不影響任何人。

因為鎖要防的是**兩個各自獨立的 Godot process**（而不是同一 process 內的事），
存活判定問系統的 process 清單（Windows 用 `tasklist`、POSIX 用 `kill -0`）——
`OS.is_process_running()` 只認得 `OS.create_process()` 自己開出來的子行程，
拿另一個獨立啟動的 Godot process 的 pid 去問一律回傳 `false`，用不上。

鎖只管**寫入**，不擋讀取：第一次成功 `save_character()`／`save_world()` 某個 id
時取得鎖，之後同一 process 重複寫同一個 id 一定成功（重入），直到 process 正常
結束（`_exit_tree()`）才釋放。別的活著的 process 想寫同一個 id 會被拒絕，
`push_error` 帶出持有者的 pid 與取得時間。

當機留下的鎖不會變死鎖——下一個來搶鎖的 process 發現閘門裡的 pid 已經不在跑，
會先把「這是死鎖」的判斷跟「移除它」合成同一個不可被插隊的步驟：用
`rename_absolute()` 把整個閘門搬到只有這次呼叫看得到的隔離目錄（來源不存在
時 rename 一樣會失敗，兩個 process 同時想搬走同一個閘門只有一個搬得走），
搬走之後才檢查內容——證實真的死了才清掉、重新發布接手；搬走後發現其實還
活著（代表在判斷死鎖到真正搬走這段極短的時間內，原本的死鎖已經被別的
process 清掉並發布了合法新鎖），原封不動搬回去，不動任何人的東西，這次
接手失敗。不能只是「先讀 pid 判斷、再直接刪除」——那樣兩個 process 都判斷
死鎖時，後刪除的那個會把先接手成功的人剛發布的新鎖也一起清掉，兩邊都以為
自己拿到手。

**已知殘留限制**：這整套只靠 `rename`／`mkdir` 的原子性做互斥，沒有真正的
作業系統鎖（`flock`／`LockFileEx`，GDScript 沒有介面能叫）。兩個 process
互搶（含死鎖接手）已經涵蓋，但三個以上 process 同時對同一個 id 搶死鎖接手
時，「搬回去」那一步理論上仍可能因為第三者插隊而失敗——單機、最多兩個
process 會碰同一份存檔，用不到為了這個機率去接原生擴充套件換真正的系統鎖。

實作在 `Ailley/scripts/save/json_save_service.gd`，鎖是 `JsonSaveService` 這個
後端自己的機制，不在 `SaveService` 抽象介面上——`SqliteSaveService` 之後真的
接上 CRUD 時，並行寫入保護會走 SQLite 自己的 transaction，不會重用這套鎖檔。

## SQLite 後端現況

《14》§4 的非阻塞平行開發，跟 JSON 路徑（#19–#23）分開推進。schema 在
`Ailley/scripts/database/schemas/`，`SqliteSaveService`（`scripts/save/sqlite_save_service.gd`）
的四個函式已接上真正的 `DatabaseManager` CRUD（issue #147）。

`get_character`／`save_character` 對齊的是 `Character.get_save_data()` 現在
實際吐出來的形狀的其中一部分——`character_id`／`character_name`／
`stats`（11 項扁平數值）／`relationships`（`{ target_id: {trust, appearance_cache} }`）
——不是《06》完整版那份 identity/hexaco/personality/economy/state.emotion，
後者現在沒有任何 Character 欄位在產生，接了也沒有呼叫端餵得進資料。

`Character.get_save_data()` 現在還會多產生一個 `memory` 欄位（L2/L4，見上面
「記憶已接進角色存檔」），但 `get_character`／`save_character` 目前**不讀寫
它**——schema 已有 `MemorySchema.gd`，只是這兩個函式還沒接上，SQLite
round-trip 之後整段記憶會遺失，不是靜默漏單一欄位。已知缺口：
`npc_state` 沒有 `mood`／`social`／`fun`（Stats.SPEC 有這三項），
`npc_relations` 沒有 `met_count`（Relationships.DEFAULT_RECORD 有）——
這兩項有 `Stats.load_save_data()`／`Relationships.load_save_data()` 本來就有的
「缺欄位用預設值補」機制吞掉，不是靜默漏資料。

`get_world`／`save_world` 對齊的是 `GameManager.get_world_save_data()`：
`day`／`allow_player_join`／`characters{ <npc_id>: {position, current_place?, current_state?} }`。
這一層原本在 schema 裡完全空白（P-37），issue #147 補上 `world`
（`world_id`／`day`／`allow_player_join`）與 `world_character_state`
（`world_id`＋`npc_id` 複合主鍵，`pos_x`／`pos_y`／`current_place`／`current_state`，
兩者都 FK 回各自的父表）兩張表。`location`／`item` 是靜態參考資料，
不屬於世界存檔，`get_world`／`save_world` 不碰它們。

`npc_relations.target_id`／`world_character_state.npc_id` 都有 FK 指向
`npc(npc_id)`：整包覆蓋時如果目標角色還沒存過（例如 debug console `save`
迴圈裡還沒輪到），那一筆跳過並記警告，不讓整包寫入失敗——下次雙方都
存過之後這筆會自己補回來。

### schema 版本化 migration（issue #239）

`DatabaseSchema` 用 `PRAGMA user_version` 追蹤 schema 版本（`CURRENT_VERSION`
常數），`initialize()` 開機時讀出目前版本、依序套用 `MIGRATIONS` 裡版本
比目前新的項目、成功後把版本寫回去，整段跟原本的 `CREATE TABLE IF NOT
EXISTS` 一樣包在同一個 transaction 裡——任何一步失敗就整批回滾，不會
留下版本號跟實際 table 結構對不上的中間態。

`MIGRATIONS` 裡每個 entry 是 `{version, name, apply(db)->bool}`，只處理
「既有 table 的結構變更」（`ALTER TABLE`／重建搬資料）；新增 table 交給
`CREATE TABLE IF NOT EXISTS` 自己處理，不需要另外寫 migration。目前這份
清單是空的——上一輪掛在這裡的欄位清單（`ItemSchema` 的 `decay_rate` 等）
已隨 PR #237 revert 拿掉，等持久層重新落地、確定最終 schema 長相後才會
真的有 pending migration，屆時在 `MIGRATIONS` 加一項、`CURRENT_VERSION`
加一即可。

`initialize()` 開機時會先判斷這是不是「全新資料庫」——查 `sqlite_master`
有沒有任何應用程式 table，`user_version` 也還是 0——是的話直接跳過
`MIGRATIONS`：`CREATE TABLE` 陣列建的本來就是最新欄位，全新資料庫建完
就已經是 `CURRENT_VERSION` 的形狀。只有「有 table 但沒記錄過版本」的
既有資料庫（同樣 `user_version == 0`）才會真的跑 `MIGRATIONS` 裡的
`ALTER TABLE`——這條分界是必要的，否則之後隨便一個 migration 加了
`ALTER TABLE ... ADD COLUMN`，全新資料庫會因為 `CREATE TABLE` 已經
建過那個欄位、`ALTER TABLE` 想再加一次而直接撞欄位重複失敗。

`stored_version` 比 `CURRENT_VERSION` 還新時 `initialize()` 直接拒絕
開啟、不動 transaction也不改 `user_version`——這通常代表切回了舊分支，
但 `user://`（依專案名稱，不分 worktree）被新分支開過；繼續執行只會
把版本號誤降回舊分支認得的 `CURRENT_VERSION`，讓新分支的 migration
之後被重複套用。

> [!warning] `DatabaseManager.update()`／`delete()` 曾經會把外層交易提早關掉
> godot-sqlite 的 `update_rows()`／`delete_rows()` 呼叫完會把 `BEGIN TRANSACTION`
> 開的交易自動 COMMIT 掉（`insert_row()` 沒有這個毛病），用
> `db.get_autocommit()` 實測驗證過。後果是 `SqliteSaveService` 的
> `begin_transaction()` ... `commit_transaction()` 包不住 UPDATE／DELETE：
> 最後的 `commit_transaction()` 會拿到 `"cannot commit - no transaction is active"`
> 而回傳 `false`（即使資料其實正確寫入了），而且中途真正失敗時也救不回
> 已經被提早 COMMIT 掉的前面幾步。2026-08-18（issue #147）已修：
> `update()`／`delete()` 改用 `db.query_with_bindings()` 自己拼帶 `?` 佔位符的
> SQL，不再呼叫 `update_rows()`／`delete_rows()`，值一樣是綁定參數，
> 對外簽章沒變。

## 記憶已接進角色存檔

`Character.get_save_data()`／`load_save_data()` 現在會一併帶 `memory` 欄位
（`Ailley/scripts/character/character.gd`）。`Memory.get_save_data()`／
`load_save_data()`（`Ailley/scripts/character/memory.gd`）只走訪 `entries`
挑出 `level == 2` 或 `level == 4` 的項目，跟 `Relationships.get_save_data()`
同一套「直接吐內部資料，不另外包裝」規則。

`Character.load_save_data()` 讀 `memory` 這件事跟 `stats`／`relationships`
故意不同：後兩者存檔沒帶欄位就直接不呼叫，讀進來的角色保留原本的值；
`memory` 一律呼叫 `Memory.load_save_data()`，沒有 `memory` 欄位或格式不對
就傳空 Dictionary 進去——讀存檔要把角色重設成跟檔案內容一致，不能讓套用
到已經在場上跑過的角色（debug console `load` 就是這樣用）時，殘留讀檔前的
舊記憶。`l1` 沒有存檔，讀檔時一併清空，理由相同。`entries`／`_next_id` 驗證
完整份 `entries` 陣列（不是 Array、項目不是 Dictionary、`level` 不是 2/4 都
跳過該筆）後才一次替換，不會套用到一半。`_next_id` 接續讀進來的最大 id，
避免新記憶跟舊記憶撞號。

目前只有 `JsonSaveService` 走這條路徑——`SqliteSaveService`（見上面「SQLite
後端現況」）還沒接 `memory`，屬於已知缺口，不是這次的範圍。

### `database/` 目錄位置

`DatabaseManager.gd`／`DatabaseSchema.gd`／`DatabaseSeeder.gd`／`schemas/` 放在
`Ailley/scripts/database/`，對齊 `Ailley/CLAUDE.md`「腳本一律進 `scripts/<領域>/`」
規則。`DatabaseManager` 只透過 autoload 名稱、`DatabaseSchema`／各 schema 只透過
`class_name` 被引用；`DatabaseManager.gd` 內另有一處透過 `load()` 呼叫的硬編碼
字串路徑，指向 `res://scripts/database/CharacterStatePersistence.gd`——這種寫法
不會被 `.tscn` 引用掃描抓到，之後這批檔案再搬動要記得一併檢查。
