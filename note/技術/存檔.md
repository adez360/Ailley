# 存檔

角色／世界存檔骨架、序列化、單一 session 鎖（#19–#23）都已完成，
見下面「拆成哪些 issue」。這篇是它的設計。

## 兩層：角色與世界

| | 裝什麼 | 誰讀它 |
| --- | --- | --- |
| **角色存檔** | 所有 player 與 agent 的身分、數值、關係 | 可以被**多個**世界存檔讀取 |
| **世界存檔** | 地圖、地點、時間、誰站在哪、允不允許 player 加入 | 一個世界一份 |

> [!important] 這個切法不只是檔案怎麼放
> 角色與世界解綁之後，「帶自己的 agent 進別人的村莊」**是它的直接結果，
> 不是額外要做的功能** —— remote player 帶 agent 連進來，
> 就是拿自己的角色存檔去讀別人的世界存檔。
> 多人那一階段能省多少事，取決於這兩層在這裡有沒有分乾淨。

### 位置屬於世界，不屬於角色

這是切分的第一條界線，也最容易畫錯。

角色在**某個世界裡**的座標，帶到另一個世界毫無意義 ——
你的 agent 走進別人的村莊時，它在你村莊的 `(-62, 99)` 不該跟著過去。
所以 `character_id → 座標` 的對應存在**世界存檔**，角色存檔只回答「這隻角色是誰」。

同理，`current_action`、行程進度、路徑這些也都是世界層的東西。

### 允不允許 player 加入，也屬於世界

遊戲**沒有模式之分**，世界之間唯一的差別是裡面有沒有 player。
沒有 player 在場的世界照樣跑，agent 照樣過日子。

所以世界存檔裡有一個建立時決定的旗標：**這個世界允不允許 player 加入**。

- 不允許 → 這個世界只跑 agent，沒有任何 player 能連進來
- 允許 → player **可以**加入，但不強制在場。世界在沒有 player 的情況下一樣成立

> [!important] 旗標是「允不允許」，不是「有沒有」
> 場上有沒有 player 是每一刻都可能變的事實 —— 他可以離開，也可以中途連進來。
> 載入時算一次「這個世界有沒有人」然後拿它到處分支，會在玩到一半有人離線時壞掉。
> 該問的是「這個角色現在有沒有人在操作」，那是角色層的問題，不是世界層的。

這條跟核心約束是同一件事：Player 能做到的 Agent 也必須能做到，
所以少了 player 的世界不缺任何能力，只是少一個角色。

### 目前被誰操控，也屬於世界（#373）

`GameManager.embodied_character_id`：世界存檔記錄目前是哪個 `character_id`
被玩家操控，跟 `allow_player_join` 同一層資料。存檔時從場景 `"player"` 分組
即時算出來（沒有玩家在場就是空字串），讀檔時寫回這個變數。

這裡只接存讀路徑，不含真正的「換身」邏輯——場景裡目前的 player 節點如果
跟存檔記錄的不同，`apply_world_save_data()` 只會 `push_warning`，不會自動
把身分套到別的節點上。要接上真正的換身，需要 #371（化身者投放路由）先把
「投放時選由玩家操控」這個機制做出來，之後才有「該把身分換到誰身上」的
決策依據。

## 存哪

`user://`，與 `ai_config.json` 同一個地方 —— 在 repo 之外，
Linux 下是 `~/.local/share/godot/app_userdata/ailley4.3/`。

> [!warning] `user://` 只認 project name，不分 worktree
> `user://` 的實體路徑只依 `project.godot` 的 project name 解析，同一台機器上
> 所有 worktree／checkout 的 project name 都相同。JSON 存檔（`SaveService`）
> 目前檔名寫死，多個平行 worktree 各自跑 Godot 時會共用同一份實體檔案、
> 互相覆寫——跟 SQLite 曾經踩過的問題（下面「SQLite 後端現況」）是同一個病根，
> 但這裡還沒修（issue #334 只處理了 SQLite 那條路徑）。

## 一個前置，不是存檔本身

### `GameClock.day`／`hour`／`minute` 的持久化與自動存檔

`GameClock` 有 `day`（從 1 起算，#19）與 `hour`／`minute`（#517），三者都屬於
世界層（是那個世界的日曆／時鐘，不是角色的），跟著 `get_world_save_data()`／
`apply_world_save_data()`一起存讀。`day` 不用重開就繞過「每遊戲日最多 20 次
AI 請求」的配額（AIService 訂閱 `day_changed`）；`hour`／`minute` 補上之前，
重開遊戲時鐘固定回到腳本預設值 8:00，跟玩家實際離開的時間點對不上——任務池
（`Agent._tasks`）本身不進存檔、每次讀檔都從 `npc_schedule.json` 重建（見上面
「決策情境欄位」一節），不吃任何存檔當下算出的絕對 `expires_at`，所以補上
`hour`／`minute` 不影響排程任務判定。

只有 `JsonSaveService` 走這條路徑——`SqliteSaveService`（`world` 表 schema）
還沒有 `hour`／`minute` 欄位，SQLite round-trip 會遺失，跟同一張表已知缺少
`embodied_character_id`（見上面「SQLite 後端現況」）是同一種已知缺口，不是
這次的範圍。

`day_changed` 現在還接了自動存檔（issue #359）：`GameManager` 訂閱這個訊號，
跨遊戲日時存下場上每個角色＋世界本身（`GameManager.save_all()`，跟 debug
console 的 `save` 指令共用同一套邏輯）。用 `call_deferred()` 排到這次訊號廣播
內所有同步 handler（含 `memory.gd::decay_all()` 的記憶衰減）都跑完之後才真正
存檔，不管 `GameClock.day_changed` 的連線順序是誰先誰後都能保證存到衰減後的
結算狀態，不是半結算狀態。

> [!important] 跨日自動存檔會等在飛的睡眠反思（issue #468）
> 睡眠反思（`agent.gd::request_sleep_reflection()`）不掛在 `day_changed` 上，
> 是角色各自進入 `sleep` 狀態時觸發、不等待的 fire-and-forget AI 呼叫，
> `call_deferred()` 只能確保「同一顆呼叫堆疊內的同步工作」都做完，換不到
> 「還在飛的網路請求」。`Agent.is_sleep_reflection_settled()` 對外暴露
> `_sleep_reflection_in_flight`／`_sleep_reflection_pending` 兩個旗標的綜合
> 狀態（後者是撞期補跑，見 `_finish_sleep_reflection_request()`），
> `GameManager._autosave_on_day_change()` 存檔前先呼叫
> `_wait_for_sleep_reflections_to_settle()`，逐幀輪詢直到場上每個 Agent 都
> settled，才會真正呼叫 `save_all()`。未逾時時，不管連線順序是誰先誰後，
> 保存的是反思「之後」的狀態；逾時時依下方規則繼續存檔，反思可能尚未套用。
>
> 等待有上限：`SLEEP_REFLECTION_WAIT_TIMEOUT_SEC`（30 秒），是抓寬的
> best-effort 窗口，不是精確算出的完整最壞情況上限——`AIService.RETRY_LIMIT`
> （1 次重試）只套用在逾時以外的可重試錯誤，逾時本身不重試
> （見 `ai_service.gd::_interpret()`）；`provider.timeout` 可能被設定檔覆寫，
> 不保證等於 `AIConfig.DEFAULT_TIMEOUT`（10 秒）；`_decide_with_retry()`
> 的驗證重試（`provider.max_validation_retries()`）與撞期補跑
> （`_sleep_reflection_pending`）都可能讓實際等待時間超過這個窗口。
> 逾時就放棄等待、照樣存檔並 `push_warning`——存到的是反思套用前的狀態，
> 跟完全不等的舊行為一樣，不會比之前更差，只是把「等得到」的大多數情況
> 從殘留限制裡拿掉。這個等待只接在跨日自動存檔，離開遊戲時的自動存檔
> （`_notification()`）不在這條路徑上，範圍界線見 #468。

另外一併存檔的時機是**離開遊戲時**（`NOTIFICATION_WM_CLOSE_REQUEST`）：
`project.godot` 的 `application/config/auto_accept_quit` 設為 `false`，
`GameManager._notification()` 攔到關窗請求後呼叫 `save_all()`，不論成功與否
最後都要自己呼叫 `get_tree().quit()`（設完 `auto_accept_quit=false` 引擎不會
再自動關閉視窗）。兩條自動存檔路徑都先檢查場上有沒有角色
（`_has_active_game_session()`）——`GameClock` 是 autoload，退回主選單後
一樣繼續跑，沒有這層擋，會拿一份空的世界狀態去蓋掉玩家還沒讀進來、原本
有效的存檔。

同一個「`GameClock` 在主選單也繼續跑」的根因還有第二個影響面：主選單按
「開始遊戲」進新遊戲時，時鐘原本沒有被拉回設計預期的開場值，玩家在選單
多待一段時間才按開始，一進場時間就已經被選單掛機的時間推走（#606）。修法
是加 `GameClock.reset_to_new_game_start()`，在 `main_menu.gd::_on_start_pressed()`
呼叫（見 [[主選單]]）——跟這裡的自動存檔守門用的是同一個根因，但修法不同：
自動存檔是「事後擋」（發現沒有角色就不存），這裡是「事前重置」（開新遊戲
那一刻就把時鐘打回原點），因為「繼續遊戲」讀檔本來就會覆蓋這三個欄位，
不需要額外的守門判斷。

存檔失敗（`SaveService.save_character()`／`save_world()` 回傳 `false`）目前
只用 `push_error` 標出哪個角色／哪個世界失敗，沒有玩家看得到的畫面提示——
專案目前沒有任何遊戲內的 toast／通知系統，加一個屬於另外的 UI 範圍，不在
issue #359 內。

> [!important] 擁有者是欄位，不是 id 的一部分
> `character_id` 選 UUID 就是選擇讓 id 不回答「這是誰的」。角色存檔要帶一個
> `owner` 欄位，但那要等真的有帳號概念才寫得出值 —— 現在沒有，所以先不放
> 空欄位佔位。這條界線的好處是帳號模型日後怎麼變都不必替 id 寫遷移。

正常重開時，`character_id` 跨場次穩定已不是阻礙：固定 NPC（Agent/Agent2）靠
`npc_schedule.json` 的 `identities` 表天生穩定，Player 的 id 額外持久化到
`user://saves/player_id.txt`（跟這裡的角色／世界存檔分開放，見
[[Character 基底與 Agent]]「id 生成第三層」，issue #399）。載入損壞存檔導致
`_ensure_unique_id()` 換掉 Player id 時，會透過 `_on_id_changed()` hook 同步
寫回 `player_id.txt`（同一則筆記，issue #438），不會造成每次重開都換 id。
角色庫投放的動態角色（`spawn_character()`）id 持久化屬於 [[角色庫與投放]]
的範圍，不在這裡。

## 序列化的規則

> [!important] 走訪 `Stats.SPEC`，不要手寫欄位
> `stats.gd` 已經是資料驅動的：SPEC 加一列，數值就自動多一項。
> 存檔照抄這個做法，SPEC 改了存檔不用改。
> 這跟 [[LLM 串接與 AI 服務層]] 的 payload 是同一條規則。

舊存檔缺欄位時用 `SPEC[key]["start"]` 補，不要當成錯誤 ——
SPEC 加一項是預期會發生的事，不該讓舊存檔讀不起來。

`Relationships.records` 直接存，它本來就是純資料，
而且 key 用 `character_id` 不用名字（名字可以改，拿它當 key 等於改名就失憶）。

## 記憶怎麼存

跟《03 事件評估與記憶》的四層架構對齊，但不是四層都要存：

| 層 | 要不要存 | 理由 |
| --- | --- | --- |
| L1 短期工作記憶 | **不用** | 每 tick 滾動、開場即可重建，本來就是暫時性資料 |
| L2 近期記憶 | **要** | 這次跟角色存檔一起做——記憶是「養一個有記憶的夥伴」的核心賣點 |
| L3 長期記憶庫（向量） | **要** | 含 embedding 向量一起存；讀檔回來若 embedding 是空陣列（例如舊存檔，或存檔時 embedding server 不可用）會重新排隊算一次，見 issue #571 |
| L4 核心記憶 | **要** | 同 L2，一起做 |

**序列化技術：JSON，不是 SQLite。** 走 `Stats.SPEC`／`Relationships.records` 同一套「走訪資料結構、不手寫欄位」規則，直接存進角色存檔檔案。單機、5 人村莊的規模，SQLite 的索引/查詢優勢用不到，量大到需要時再換不遲，跟《00》§3 一致。

> [!note] SQLite 不是排除，是還沒到需要的時候
> 真的長出「動態、需要查詢」的資料（例如事件記錄、跨世界社交關係、經濟交易歷史）才是 SQLite 該接手的部分，屆時是在存檔介面背後加一塊，不是重寫這裡的序列化規則。實作時存讀角色／世界都包成介面（不要讓呼叫端直接戳 `FileAccess`），就是為了讓這個之後可以換。

`03` 裡「推測待確認」的數值（衰減率、L4 上限 5 條、重要度分級門檻、酒精遺忘判定式）**先用文件裡的暫定值上線，不現在拍板**——這些是可調數值，不影響存檔的資料結構，之後實跑再校準（跟 `agent.gd` 那批仲裁常數同樣的處理方式）。

### 決策情境欄位：只留跨天的承諾

`current_goal`／`today_plan`／`appointment`／`last_action_result` 這四個是 06 定義的「決策情境」欄位，不是全部都要存：

| 欄位 | 要不要存 | 理由 |
| --- | --- | --- |
| `today_plan` | **要** | 角色當天的計畫，玩家重開遊戲後如果整個消失，「今天原本要幹嘛」的連續感就斷了 |
| `appointment` | **要** | 跨天的承諾——重開遊戲後憑空消失，會出現「對方在等你、你卻不記得」的違和 |
| `current_goal` | 不用 | 瞬時念頭，重開後歸零 |
| `last_action_result` | 不用 | 上一個動作的結果，跟目前情境無關，不需要跨重開留著 |
| `emotion`（#419 起才有這個欄位） | 待決（#444） | 同樣是瞬時狀態，沒存的話重開後回到中性，跟情緒自然到期時的狀態完全一樣，不會壞——但敘事連續性上跟 `current_goal` 是同一類問題，見下方 |

> [!warning] 「重開等於重新想」只是類比，讀檔當下沒有任何程式碼真的觸發重新決策
> 查證 #400（`main_scene.gd::_apply_continue()`）的讀檔流程後確認：讀檔迴圈只呼叫
> `character.load_save_data(data)`，跑完就結束，**沒有接著呼叫 `_request_next_decision()`
> 或 `_reevaluate()`**。
>
> `current_place`／`current_state` 讀檔後恢復的來源是**世界存檔**——
> `GameManager.get_world_save_data()`／`apply_world_save_data()` 那一層，不是
> `Character.get_save_data()`／`load_save_data()`。`Agent._tasks`（任務池）**完全不在
> 任何存檔資料裡**：讀檔不影響它，是 `_load_schedule()` 每次從 `npc_schedule.json`
> 排程資料重新建構的（CodeRabbit review 抓到：原本這裡寫成「維持存檔裡讀回來的
> `current_state`／任務池狀態」，把兩者都誤植成角色存檔的一部分）。角色讀檔後真正
> 會帶著空的 `current_goal`／中性的 `emotion`，直到下一次自然觸發（該遊戲分鐘的排程
> 重算、任務做完等）才會照平常那套邏輯走——跟平常任何一個 tick 沒有兩樣，不是讀檔
> 專屬的特殊步驟。技術上不會壞（`emotion` 讀檔後的中性狀態，跟情緒自然到期時
> `_tick_emotion()` 重設的狀態完全相同，`prompt_builder.gd` 讀取時也有安全預設值），
> 純粹是「重開等於角色重新想過一次」這句理由目前不是真的會發生的事，只是設計上的類比。
> 要不要補一個讀檔後的批次重新決策觸發、`emotion` 要不要跟著存，留給 #444 拍板。

**「離開」只有一種情境要處理**：世界存檔是一條時間線，只在主機開著世界時推進（見上面「併發與時間線」），所以真正觸發存檔/讀檔的只有「主機關閉世界」這一刻。連線玩家中途斷線不會讓世界停下來、不會觸發存檔——但這個分支這次也不會發生，因為 MVP 這次不做連線/多人。

## 併發與時間線

**一份世界存檔就是一條時間線**，而且只在有人開著它的時候推進 ——
不做離線託管，關掉世界它就停。所以時間不會有兩處各自前進、事後要對齊的問題。

要防的是**同一份角色存檔同時被兩份存檔寫入**：

| 問題 | 這一階段做什麼 |
| --- | --- |
| 兩個 process 開同一份存檔 | **已完成**（#23）—— 單一 session 鎖 |
| 同一份角色存檔被兩個世界同時寫 | **已完成**（#23）—— 鎖鎖在角色這一層 |

角色存檔跨世界共用，你的 agent 被帶進別人的村莊時，兩邊都會想改它的數值與關係。
鎖不能只鎖世界存檔。

### 鎖怎麼做（#23）

每份存檔配一個同名 `.lock`**目錄**當互斥閘門，但閘門不是「先建空目錄、
再補內容」——那個做法有洞：建立閘門跟寫入 `info.json`（`{ pid, acquired_at }`）
是兩個分開的步驟，剛贏得閘門的 process 若在寫完 `info.json` 前被排程延遲，
另一個 process 會看到「閘門存在但內容還沒出現」的中間態，不管用什麼超時
判斷都只能降低誤判機率、無法真正消除。

改成先把完整內容寫進一個只有自己看得到的私有暫存目錄，再用
`DirAccess.rename_absolute()` 一步發布成公開的固定名字：目的地已存在時
`rename_absolute()` 會直接失敗、不覆寫、不部分成功（實測驗證過），所以公開
名字底下要嘛不存在、要嘛一出現就是內容完整的——不會再有可能被誤判成孤兒
鎖的中間態，搶輸的人只是清掉自己的暫存目錄，不影響任何人。

因為鎖要防的是**兩個各自獨立的 Godot process**（而不是同一 process 內的事），
存活判定問系統的 process 清單（Windows 用 `tasklist`、POSIX 用 `kill -0`）——
`OS.is_process_running()` 只認得 `OS.create_process()` 自己開出來的子行程，
拿另一個獨立啟動的 Godot process 的 pid 去問一律回傳 `false`，用不上。

鎖只管**寫入**，不擋讀取：第一次成功 `save_character()`／`save_world()` 某個 id
時取得鎖，之後同一 process 重複寫同一個 id 一定成功（重入），直到 process 正常
結束（`_exit_tree()`）才釋放。別的活著的 process 想寫同一個 id 會被拒絕，
`push_error` 帶出持有者的 pid 與取得時間。

當機留下的鎖不會變死鎖——下一個來搶鎖的 process 發現閘門裡的 pid 已經不在跑，
會先把「這是死鎖」的判斷跟「移除它」合成同一個不可被插隊的步驟：用
`rename_absolute()` 把整個閘門搬到只有這次呼叫看得到的隔離目錄（來源不存在
時 rename 一樣會失敗，兩個 process 同時想搬走同一個閘門只有一個搬得走），
搬走之後才檢查內容——證實真的死了才清掉、重新發布接手；搬走後發現其實還
活著（代表在判斷死鎖到真正搬走這段極短的時間內，原本的死鎖已經被別的
process 清掉並發布了合法新鎖），原封不動搬回去，不動任何人的東西，這次
接手失敗。不能只是「先讀 pid 判斷、再直接刪除」——那樣兩個 process 都判斷
死鎖時，後刪除的那個會把先接手成功的人剛發布的新鎖也一起清掉，兩邊都以為
自己拿到手。

**已知殘留限制**：這整套只靠 `rename`／`mkdir` 的原子性做互斥，沒有真正的
作業系統鎖（`flock`／`LockFileEx`，GDScript 沒有介面能叫）。兩個 process
互搶（含死鎖接手）已經涵蓋，但三個以上 process 同時對同一個 id 搶死鎖接手
時，「搬回去」那一步理論上仍可能因為第三者插隊而失敗——單機、最多兩個
process 會碰同一份存檔，用不到為了這個機率去接原生擴充套件換真正的系統鎖。

實作在 `Ailley/scripts/save/json_save_service.gd`，鎖是 `JsonSaveService` 這個
後端自己的機制，不在 `SaveService` 抽象介面上——`SqliteSaveService` 之後真的
接上 CRUD 時，並行寫入保護會走 SQLite 自己的 transaction，不會重用這套鎖檔。

## SQLite 後端現況

### `select()`／`select_where()` 查詢失敗跟「成功但空結果」分不出來（issue #439）

`DatabaseManager.select()`／`select_where()` 在 `_require_ready()` 為 false 或
SQL 查詢失敗時都回傳空 `Array`，跟「查詢成功、真的沒有符合的資料列」無法
從回傳值本身分辨。`SqliteSaveService.has_character()`／`has_world()` 原本靠
`select().is_empty()` 判斷「這筆存檔存不存在」，這個歧義會讓查詢失敗被誤判成
「從沒存過」。

修法是在 `DatabaseManager` 加一個 `last_query_failed: bool`，`select()`／
`select_where()` 每次呼叫都會更新（成功清 false、`_require_ready()` 失敗或
`query_with_bindings()` 失敗都設 true），回傳值本身維持 `Array` 不變——`insert()`／
`update()／delete()` 有自己的 bool 回傳值，不受影響。單一 Godot process 對應
單一 db 連線，沒有並行呼叫，呼叫完緊接著檢查不會被別的查詢蓋掉。

只有 `has_character()`／`has_world()` 這兩個把 `is_empty()` 當存在判斷用的
呼叫端接了這個旗標：查詢失敗時額外 `push_error` 說明「無法判斷存不存在」，
`-> bool` 回傳值仍是 false（`SaveService` 介面沒有第三種狀態可以表達，見
`save_service.gd` 的 `has_character()` 註解）。`get_character()`／`get_world()`
等既有函式，以及 `DatabaseSeeder.gd`／`CharacterStatePersistence.gd` 裡其他
`select()`／`select_where()` 呼叫端沿用原本的 `is_empty()` 慣例，不在這次範圍——
這些是「有沒有資料要不要覆蓋」的判斷，查詢失敗當下呼叫已經 `push_error` 過，
不是這次要解決的「當成正常空狀態」問題。

《14》§4 的非阻塞平行開發，跟 JSON 路徑（#19–#23）分開推進。schema 在
`Ailley/scripts/database/schemas/`，`SqliteSaveService`（`scripts/save/sqlite_save_service.gd`）
的四個函式已接上真正的 `DatabaseManager` CRUD（issue #147）。

`DatabaseManager.DATABASE_PATH` 依這個 checkout 的 `res://` 絕對路徑算完整
sha256 雜湊接在檔名後（`user://game_<hash>.db`）——不截斷，截斷等於自己
削弱防撞名的效果。不同 worktree 各自落地成不同實體檔案，不會共用同一份
`game.db`（issue #334）。JSON 存檔（`SaveService`）還沒做這個隔離，見上面
「存哪」一節。

隔離前那份共用的 `user://game.db` 本身就是多個 worktree 用不同 schema
平行寫出來的產物，沒有單一乾淨版本可言。這裡不讀取、不複製、也不刪除它，
讓它變成孤兒檔案——往每個 checkout 複製只會把跨 worktree 的污染資料帶進
原本乾淨的隔離環境。真的要救資料或做版本化 migration，屬於下面
「schema 版本化 migration（issue #239）」的範圍。

`get_character`／`save_character` 對齊的是 `Character.get_save_data()` 現在
實際吐出來的形狀的其中一部分——`character_id`／`character_name`／
`stats`（11 項扁平數值）／`relationships`（`{ target_id: {met_count, appearance_cache} }`）
——不是《06》完整版那份 identity/hexaco/personality/economy/state.emotion，
後者現在沒有任何 Character 欄位在產生，接了也沒有呼叫端餵得進資料。

`Character.get_save_data()` 現在還會多產生一個 `memory` 欄位（L2/L4，見上面
「記憶已接進角色存檔」），但 `get_character`／`save_character` 目前**不讀寫
它**——schema 已有 `MemorySchema.gd`，只是這兩個函式還沒接上，SQLite
round-trip 之後整段記憶會遺失，不是靜默漏單一欄位。已知缺口：
`npc_state` 沒有 `mood`／`social`／`fun`（Stats.SPEC 有這三項），
`npc_relations` 沒有 `met_count`（Relationships.DEFAULT_RECORD 有）——
這兩項有 `Stats.load_save_data()`／`Relationships.load_save_data()` 本來就有的
「缺欄位用預設值補」機制吞掉，不是靜默漏資料。

`get_world`／`save_world` 對齊的是 `GameManager.get_world_save_data()`：
`day`／`allow_player_join`／`characters{ <npc_id>: {position, current_place?, current_state?} }`。
這一層原本在 schema 裡完全空白（P-37），issue #147 補上 `world`
（`world_id`／`day`／`allow_player_join`）與 `world_character_state`
（`world_id`＋`npc_id` 複合主鍵，`pos_x`／`pos_y`／`current_place`／`current_state`，
兩者都 FK 回各自的父表）兩張表。`location`／`item` 是靜態參考資料，
不屬於世界存檔，`get_world`／`save_world` 不碰它們。`world` 表沒有
`embodied_character_id` 欄位（#373 之後才新增，晚於 #147），SQLite
round-trip 目前會遺失這個欄位，是已知缺口，不是這次的範圍。

`npc_relations.target_id`／`world_character_state.npc_id` 都有 FK 指向
`npc(npc_id)`：整包覆蓋時如果目標角色還沒存過（例如 debug console `save`
迴圈裡還沒輪到），那一筆跳過並記警告，不讓整包寫入失敗——下次雙方都
存過之後這筆會自己補回來。

### schema 版本化 migration（issue #239）

`DatabaseSchema` 用 `PRAGMA user_version` 追蹤 schema 版本（`CURRENT_VERSION`
常數），`initialize()` 開機時讀出目前版本、依序套用 `MIGRATIONS` 裡版本
比目前新的項目、成功後把版本寫回去，整段跟原本的 `CREATE TABLE IF NOT
EXISTS` 一樣包在同一個 transaction 裡——任何一步失敗就整批回滾，不會
留下版本號跟實際 table 結構對不上的中間態。

`MIGRATIONS` 裡每個 entry 是 `{version, name, apply(db)->bool}`，只處理
「既有 table 的結構變更」（`ALTER TABLE`／重建搬資料／`DROP TABLE`）；
新增 table 交給 `CREATE TABLE IF NOT EXISTS` 自己處理，不需要另外寫
migration。目前有 7 項：version 2（issue #270／P-46 的 `water`／`ale`
腐壞數值 backfill）、
version 3（issue #446，見下方「既有資料庫補 `NOT NULL` 主鍵」）、
version 4（issue #382 的 `grave_epitaphs.content` 長度 CHECK）、
version 5（issue #512，`DROP TABLE` 移除 `npc_death`／`grave_highlights`
這兩張死碼表，見下方「墓碑欄位」一節）、
version 6（issue #511，`npc_action_history` 索引重建為
`(npc_id, game_day, game_minute, id)` 複合索引）、
version 7（issue #514，見下方「既有資料庫補 `NOT NULL` 主鍵」的
`world`／`item`／`npc_state`／`npc_emotion`／`npc_goal` 部分）、
version 8（issue #561，`npc`／`location` 與它們全部依附表，見下方同一節）。
之後再出現不相容 schema 變更時同樣加項、`CURRENT_VERSION` 加一即可。

### 既有資料庫補 `NOT NULL` 主鍵（issue #446／#514／#561／《99》P-55　已完成）

`memories`／`npc_appearance`／`npc_last_action`／`npc_occupation`／
`world`／`item`／`npc_state`／`npc_emotion`／`npc_goal`／`npc`／`location`
這 11 張目標主表，在 `*Schema.gd` 補上 `TEXT NOT NULL PRIMARY KEY` 之前
就已經被建過的既有資料庫，主鍵欄位仍允許 `NULL`——`CREATE TABLE IF NOT
EXISTS` 不會回頭改舊 table 的欄位定義。用標準 SQLite「舊表改名成暫存表
→ 呼叫對應 `*Schema.create(db)` 建回原名新結構 → 從暫存表複製資料 →
刪除暫存表」流程逐表重建，不在 migration 裡重複 `CREATE TABLE` SQL；
這套重建流程（`_migrate_rebuild_single_table()`／
`_migrate_rebuild_drop_stale_indexes()`／
`_migrate_rebuild_verify_column_shape()`）是版本無關的共用工具，函式名
不綁死版本號，migration 3／7／8 共用同一份。

`memories`／`memory_related_npcs` 兩張表一起重建：`memory_related_npcs`
外鍵指向 `memories(memory_id)`，改名 `memories` 時 SQLite 會把這個外鍵
定義自動改指向暫存表名，所以 `memory_related_npcs` 也要同步重建，讓它
的外鍵在刪暫存表之前先恢復指向新的 `memories`；兩個暫存表都建好、資料
複製完，才依「子表先、父表後」的順序 `DROP`——這個順序本身就避免了
`DROP` 觸發 FK cascade 波及對方，不需要在 transaction 中途切換
`PRAGMA foreign_keys`（SQLite 交易中途本來就不接受切換）。

migration 7（原編號 6，rebase main 時發現 6 已被 npc_action_history 複合索引
migration 佔用，改編為 7）的 5 張目標表分兩種情形。`npc_state`／`npc_emotion`／
`npc_goal` 沒有其他表外鍵指向它們（它們反過來外鍵指向 `npc`／
`location`，但那是它們依賴別人，不是別人依賴它們），單表重建即可，
跟 `npc_appearance` 等單表一樣直接呼叫 `_migrate_rebuild_single_table()`。

`world`／`item` 不是這種情形——`world_character_state` 外鍵指向
`world(world_id) ON DELETE CASCADE`，`npc_inventory`／`npc_home_storage`／
`item_transaction` 外鍵指向 `item(item_id) ON DELETE RESTRICT`。這是
review 階段（CodeRabbit）抓到的問題：原本的實作只重建 `world`／`item`
本身，沒有連帶重建這 4 張子表——改名 `world`／`item` 時 SQLite 一樣會把
子表的外鍵定義自動改指向暫存表名，子表沒有跟著重建的話，最後 `DROP`
舊 `world`／`item` 時，`CASCADE` 的 `world_character_state` 會被隱含
`DELETE` 連鎖清空（悄悄丟資料），`RESTRICT` 的 3 張子表則會擋下
`DROP`、讓整個 migration 直接失敗（只要那 3 張表任一張有資料）。

修法是新增 `_migrate_rebuild_table_group()`：接受一組「父表在前、子表
在後」排列的表，全部改名成暫存表 → 依父表在前的順序逐一 `create(db)`
建回新結構 → 依同一順序把資料搬回去（父表要先搬，子表的 FK 立即檢查
才能通過）→ 依反序（子表先、父表後）刪暫存表，原理跟 `memories`／
`memory_related_npcs` 的雙表協同重建一樣，只是推廣成可以處理任意張
子表，不只兩張。`world`＋`world_character_state`、`item`＋
`npc_inventory`＋`npc_home_storage`＋`item_transaction` 各呼叫一次。

踩過兩個坑：`ALTER TABLE ... RENAME TO` 會把表上的索引一起搬到暫存表、
名稱不變，SQLite 索引名稱在資料庫層級唯一，`schema.create(db)` 的
`CREATE INDEX IF NOT EXISTS` 因此靜默跳過，暫存表被砍掉後索引就跟著
消失——`schema.create(db)` 之前要先用 `_migrate_rebuild_drop_stale_indexes()`
清掉暫存表上的索引（`sqlite_autoindex_*` 跟著表本身生滅，不用手動處理），
讓名稱空出來給新表用。另外 `INSERT INTO x SELECT * FROM x_old` 是按欄位
順序複製，不是按名稱；這套重建流程只保證修好「既有資料庫欄位定義跟現行
`*Schema.gd` 一致、只缺 `NOT NULL`」這種情形，所以每次 `SELECT *` 之前
用 `_migrate_rebuild_verify_column_shape()` 比對暫存表跟新表的 `PRAGMA
table_info` 欄位名稱與順序，兜不起來就中止交給既有 `ROLLBACK` 機制，
不嘗試猜欄位怎麼對應。

migration 8（issue #561）補上最後剩下的 `npc`／`location`：`location`
有 7 張表外鍵指向它（`npc` 本身也是其中一張，透過 `home_location_id`），
`npc` 則有近 20 張表外鍵指向它，其中 `grave`／`memories` 還各自帶一張
自己的子表（`grave_epitaphs`／`memory_related_npcs`）。改名 `location`／
`npc` 時，SQLite 會把「全部」指向它們的外鍵定義自動改指向暫存表名，
不是 migration 7 那種 1-2 層——這裡兩層鏈（`grave`→`grave_epitaphs`、
`memories`→`memory_related_npcs`）的子表的子表也要跟著重建，不然它們
的外鍵會停留在暫存表名，最後 `DROP` 暫存表時 `CASCADE` 子表被隱含清空、
`RESTRICT` 子表擋下 `DROP`。做法是把 `location`／`npc` 兩張根表，
與全部直接或間接依附它們的 23 張表（含 #428 才新增、migration 6 重建過
索引的 `npc_action_history`）一起放進同一個 `_migrate_rebuild_table_group()`
（entries 共 25 個），依「父表在前」拓樸排序：
`location` → `npc` → `grave`／`memories`
（依附 `npc`／`location`）→ `grave_epitaphs`（依附 `grave`／`npc`，要在
`grave` 之後）／`memory_related_npcs`（依附 `memories`／`npc`，要在
`memories` 之後）→ 其餘只依附 `npc`（部分也依附 `location`）的表，
彼此順序無關。`repair_null_pk` 只給 `location`／`npc`（根表身分，跟
migration 7 的 `world`／`item` 同一套判斷）；其餘表要嘛主鍵是
`INTEGER PRIMARY KEY AUTOINCREMENT`（SQLite 不會真的存 `NULL` 進去），
要嘛主鍵已經在 migration 3／7 補過 `NOT NULL`，被掃進同一組重建純粹是
因為外鍵指向 `npc`／`location`，不是自己的主鍵有缺口。

`npc_inventory`／`npc_home_storage`／`item_transaction`／
`world_character_state` 這 4 張在 migration 7 已經因為 `world`／`item`
重建過一輪，migration 8 因為 `npc` 重建又再重建一次——不是重複勞動，
是兩次重建各自針對不同的父表（`item`／`world` vs. `npc`），沒有先後
可以合併的空間。

主鍵是 `NULL` 的舊資料列（issue #566／《99》P-69）：既有資料庫在補 `NOT NULL`
之前，理論上可能已經寫入過這種列，`INSERT INTO x SELECT * FROM x_old`
撞到會讓整個 migration 失敗。`_migrate_rebuild_handle_null_primary_keys()`
在 `INSERT` 之前先檢查，依主鍵是不是同時也是外鍵分兩種處理：`world`／
`item`／`memories`／`npc`／`location` 這類「根表」（主鍵是這張表自己的
獨立身分，不是外鍵）補一個新 UUID（`_migrate_rebuild_generate_uuid()`，演算法跟
`character.gd::generate_id()` 相同，這裡獨立一份避免資料庫層依賴場景層的
`Character`），保留列數與其他欄位資料；`npc_state`／`npc_emotion`／
`npc_goal`／`npc_appearance`／`npc_last_action`／`npc_occupation`／
`memory_related_npcs` 這類主鍵同時是外鍵（例如 `npc_state.npc_id` 指向
`npc(npc_id)`）的表，NULL 代表「不知道這筆屬於哪個父表資料」，這個資訊
已經遺失，補新 ID 對不到任何真實父表資料，直接中止 migration（交給既有
`ROLLBACK`），錯誤訊息列出表名與筆數。`_migrate_rebuild_single_table()`／
`_migrate_rebuild_table_group()` 的 entry 用 `repair_null_pk`（預設
`false`）決定走哪條路。

`initialize()` 開機時會先判斷這是不是「全新資料庫」——查 `sqlite_master`
有沒有任何應用程式 table，`user_version` 也還是 0——是的話直接跳過
`MIGRATIONS`：`CREATE TABLE` 陣列建的本來就是最新欄位，全新資料庫建完
就已經是 `CURRENT_VERSION` 的形狀。只有「有 table 但沒記錄過版本」的
既有資料庫（同樣 `user_version == 0`）才會真的跑 `MIGRATIONS` 裡的
`ALTER TABLE`——這條分界是必要的，否則之後隨便一個 migration 加了
`ALTER TABLE ... ADD COLUMN`，全新資料庫會因為 `CREATE TABLE` 已經
建過那個欄位、`ALTER TABLE` 想再加一次而直接撞欄位重複失敗。

`stored_version` 比 `CURRENT_VERSION` 還新時 `initialize()` 直接拒絕
開啟、不動 transaction也不改 `user_version`——這通常代表同一 checkout
切回了舊分支，但 `DATABASE_PATH` 指向的 hashed database 被新分支開過
（跨 checkout 已靠雜湊隔開，不會撞到別的 worktree）；繼續執行只會
把版本號誤降回舊分支認得的 `CURRENT_VERSION`，讓新分支的 migration
之後被重複套用。

> [!warning] `DatabaseManager.update()`／`delete()` 曾經會把外層交易提早關掉
> godot-sqlite 的 `update_rows()`／`delete_rows()` 呼叫完會把 `BEGIN TRANSACTION`
> 開的交易自動 COMMIT 掉（`insert_row()` 沒有這個毛病），用
> `db.get_autocommit()` 實測驗證過。後果是 `SqliteSaveService` 的
> `begin_transaction()` ... `commit_transaction()` 包不住 UPDATE／DELETE：
> 最後的 `commit_transaction()` 會拿到 `"cannot commit - no transaction is active"`
> 而回傳 `false`（即使資料其實正確寫入了），而且中途真正失敗時也救不回
> 已經被提早 COMMIT 掉的前面幾步。2026-08-18（issue #147）已修：
> `update()`／`delete()` 改用 `db.query_with_bindings()` 自己拼帶 `?` 佔位符的
> SQL，不再呼叫 `update_rows()`／`delete_rows()`，值一樣是綁定參數，
> 對外簽章沒變。

## 角色庫已接進世界存檔（issue #342）

`GameManager.character_library`（玩家自建角色及其 `deployed` 狀態，見
[[角色庫與投放]]）跟著 `get_world_save_data()`／`apply_world_save_data()`
整包存讀，不另立存檔層——這份清單套不進「角色存檔記一個節點的身分／
數值／關係」那個形狀，只能收在世界層。

`deploy_from_library()` 的投放人數是現場掃 `character_library` 算出來的，
不是另存的計數欄位，清單還原正確人數自然就對。

## 讀檔會重新生成場景裡缺席的角色（issue #344）

`main.tscn` 寫死 5 個 Agent 節點＋1 個 Player，只要世界的角色組成跟這份
清單不同——投放了新角色、角色庫（#342）還原之後投放狀態變了——場景裡就會
缺角色。`apply_world_save_data()` 分兩段：先套用場景裡目前找得到的節點
（既有邏輯），再對存檔 `characters` 裡有記載、但場景沒有對應節點的
`character_id`，呼叫 `GameManager._respawn_character()` 生出來再套用。

`get_world_save_data()` 存每個角色的 `type`（`"agent"`／`"player"`），
`_respawn_character()` 靠這個決定用 `agent.tscn` 還是 `player.tscn`。
實際上目前只有 `"agent"` 分支真的會被觸發——`main.tscn` 的固定 NPC 與唯一
的 Player 節點本身就不會缺席，這條路徑服務的是「角色庫投放後重開遊戲」。

`character_id` 在 `character_library` 查得到時，走跟 `deploy_from_library()`
同一套：設 `identity_assignments`（讓 `_ready()` 撿到正確人格）、套
`decision_source`／`model_name` 後呼叫 `rebuild_provider()`（投放後不可改
的欄位，時序坑跟 `deploy_from_library()` 相同，見該函式註解）。查不到時
退回只給 `character_id` 的最小身分並 `push_warning`。

反向情況（場景裡有節點、但存檔沒有記載）不處理，不會移除任何節點——
留給之後真的需要「收回角色」時再決定，這次只解決「該出現的沒出現」。
## 記憶已接進角色存檔

`Character.get_save_data()`／`load_save_data()` 現在會一併帶 `memory` 欄位
（`Ailley/scripts/character/character.gd`）。`Memory.get_save_data()`／
`load_save_data()`（`Ailley/scripts/character/memory.gd`）只走訪 `entries`
挑出 `level == 2` 或 `level == 4` 的項目，跟 `Relationships.get_save_data()`
同一套「直接吐內部資料，不另外包裝」規則。

`Character.load_save_data()` 讀 `memory` 這件事跟 `stats`／`relationships`
故意不同：後兩者存檔沒帶欄位就直接不呼叫，讀進來的角色保留原本的值；
`memory` 一律呼叫 `Memory.load_save_data()`，沒有 `memory` 欄位或格式不對
就傳空 Dictionary 進去——讀存檔要把角色重設成跟檔案內容一致，不能讓套用
到已經在場上跑過的角色（debug console `load` 就是這樣用）時，殘留讀檔前的
舊記憶。`l1` 沒有存檔，讀檔時一併清空，理由相同。`entries`／`_next_id` 驗證
完整份 `entries` 陣列（不是 Array、項目不是 Dictionary、`level` 不是 2/4 都
跳過該筆）後才一次替換，不會套用到一半。`_next_id` 接續讀進來的最大 id，
避免新記憶跟舊記憶撞號。

目前只有 `JsonSaveService` 走這條路徑——`SqliteSaveService`（見上面「SQLite
後端現況」）還沒接 `memory`，屬於已知缺口，不是這次的範圍。

## 墓碑欄位：三個已接進 `Agent` 存檔，第四個走 SQLite

《規格書 09》§4-2 墓碑四個內容欄位裡，`words_to_creator`／`last_words`／
`life_highlights` 是「一份墓一筆」的欄位，接進 `Agent.get_save_data()`／
`load_save_data()`（`Ailley/scripts/character/agent.gd`），只有 `Agent` 有——
真人角色（Player）死亡不留墓碑（見《09》§1-1），不需要這三個欄位。三個欄位
型別互不相同（string／string／array），直接手寫存讀，不套 `Stats.SPEC` 那種
走訪同型別數值的模式。

`words_to_creator` 舊存檔缺欄位時保留現有值（跟 `character_id`／`character_name`
同一套「缺就不動」規則）；`last_words`／`life_highlights` 缺欄位一律重置成空，
跟 `memory` 同一套「讀檔要讓角色狀態跟檔案內容一致」規則——避免套用到已經在
場上跑過的角色時殘留讀檔前的舊資料。

死亡狀態機還沒實作（#368 已於 2026-08-20 拍板架構與規則，見《規格書 09》），
這三個欄位目前沒有任何呼叫端會寫入，只是先把存讀路徑接上。第四個欄位
`epitaphs`（一對多）不在這裡，走 SQLite。

`Ailley/scripts/database/schemas/` 底下更早（#124 骨架）留下的 `GraveHighlightSchema.gd`／
`NPCDeathSchema.gd` 已經移除（issue #512）——兩者把 `life_highlights`／整個死亡狀態
整包放在 SQLite，跟這裡的 JSON 分工衝突，`SqliteSaveService` 完全沒有任何函式讀寫
它們，也沒有其他 schema 用外鍵指向它們當父表，純粹死碼。

`Ailley/scripts/database/schemas/GraveSchema.gd` 保留，不是死碼——`GraveEpitaphSchema.gd` 的 `grave_id` 外鍵指向
`grave(grave_id)`，`epitaphs`（第四個欄位，一對多，#382 決定沿用 `grave_id`＋
`npc_id` 複合唯一鍵的既有結構）需要 `grave` 當父表才寫得進資料。`grave` 表現在
只為了這個父表角色存在，但欄位仍留著 `death_cause`／`last_words`／`words_to_creator`
這些跟 JSON 重複的快照欄位——要不要瘦身只留 `grave_epitaphs` 真正需要的欄位，
留給之後評估，不影響現況。`epitaphs` 的 CRUD（`SqliteSaveService` 讀寫）還沒接，
等死亡系統真正落地、有呼叫端要寫入時再接。

### `database/` 目錄位置

`DatabaseManager.gd`／`DatabaseSchema.gd`／`DatabaseSeeder.gd`／`schemas/` 放在
`Ailley/scripts/database/`，對齊 `Ailley/CLAUDE.md`「腳本一律進 `scripts/<領域>/`」
規則。`DatabaseManager` 只透過 autoload 名稱、`DatabaseSchema`／各 schema 只透過
`class_name` 被引用；`DatabaseManager.gd` 內另有一處透過 `load()` 呼叫的硬編碼
字串路徑，指向 `res://scripts/database/CharacterStatePersistence.gd`——這種寫法
不會被 `.tscn` 引用掃描抓到，之後這批檔案再搬動要記得一併檢查。

## 開場讀檔（issue #343）

`SaveService` 介面（`Ailley/scripts/save/save_service.gd`）多了 `has_character(id)`／
`has_world(id)`：只判斷存不存在，不管讀不讀得出來。理由是 `get_character()`／
`get_world()` 對「從沒存過」跟「存過但 JSON 損毀／解析失敗」都回傳空 Dictionary，
呼叫端沒辦法只看回傳值分辨兩者——前者是新角色的正常路徑，後者要讓玩家知道
讀檔失敗，不能悄悄退回新遊戲讓他以為存檔憑空消失。兩個實作都補了：
`JsonSaveService` 查 `FileAccess.file_exists()`，`SqliteSaveService` 查對應資料表
有沒有那筆 row。

主選單（`scripts/ui/main_menu.gd`）`_ready()` 時用 `has_world(DEFAULT_WORLD_ID)`
決定要不要顯示「繼續遊戲」；`has_world()` 為 true 但 `SaveService.is_world_data_valid()`
沒過時，藏起按鈕並顯示 `UI_MENU_LOAD_ERROR` 明確提示讀檔失敗，不是單純沒有存檔。
`is_world_data_valid()` 除了頂層 `is_empty()` 之外，也要求 `characters` 這個 key
明確存在且是 Dictionary——完全缺這個 key（`get_world_save_data()` 一定會寫出它）
或型別不對，都算讀檔失敗，跟頂層解析失敗走同一條路徑；`main_scene.gd` 實際
套用前也呼叫同一個函式，兩邊對「這份存檔算不算讀得出來」的認定才會一致。

按下「繼續遊戲」只設定 `GameManager.continue_requested = true` 再換場景——世界／
角色存檔的實際套用要等 `main.tscn` 裡的角色節點都 `_ready()` 完成才能做（要先有
`character_id` 才能查表），所以套用邏輯在 `main.tscn` 根節點的
`scripts/core/main_scene.gd`，不是主選單自己做。`_ready()` 由下而上呼叫，
根節點的 `_ready()` 執行時場上角色一定都已經進了 `"characters"` 群組。套用邏輯
跟 debug console 的 `load` 指令（見上面「拆成哪些 issue」表格 #21）共用同一套
「只套用場景裡目前找得到的角色」規則，多一層 `has_character()` 判斷：
角色本身沒有存檔紀錄就跳過（正常——例如存檔當時場上還沒有這隻角色），
有紀錄但讀不出來才 `push_error`。按「開始遊戲」（新遊戲）則是
`continue_requested = false`，`main_scene.gd` 看到 false 直接略過，角色維持
場景預設狀態——新遊戲不會動到磁碟上既有的存檔檔案，舊存檔依然在，之後
還是能被「繼續遊戲」讀到。

`main_scene.gd` 檢查 `has_world()`／`is_world_data_valid()` 失敗時，不會留在
`main.tscn` 悄悄套用預設世界——兩者都直接 `change_scene_to_file()` 送回主選單，
讓 `main_menu.gd` 的 `_ready()` 重新跑一次同樣的驗證、顯示 `UI_MENU_LOAD_ERROR`。
主選單檢查跟實際套用中間有時間差（例如檔案在轉場過程中被刪除或損毀），
這條路徑才是讀檔失敗真正的出口，不能只是 `push_error` 完就讓遊戲照跑。

角色層也補了同一種一致性檢查：`get_character(character.character_id)` 查到的
資料裡 `character_id` 欄位一定要存在、是 String、且跟查詢用的 id 相等，
`get_save_data()` 永遠會寫入這個欄位，缺欄位／型別不對／對不上都代表這份
存檔內容跟檔名認定的角色對不起來（可能已損毀或被誤覆蓋）——套用下去會讓
`character.load_save_data()` 直接把場上角色的 id 改掉，跟已經套用的世界存檔
位置／關係對不齊。`main_scene.gd` 與 debug console 的 `load` 都在呼叫
`load_save_data()` 前擋掉這種情況，`push_error`／印出錯誤後跳過該角色。

`GameManager.continue_load_failed` 補的是另一種時間差：主選單檢查存檔有效
之後、`main_scene.gd` 實際套用之前，檔案在轉場過程中被刪除或損毀——這種情況
`main_scene.gd` 送回主選單前會設這個一次性旗標，`main_menu.gd::_ready()` 重新
驗證時優先讀它，顯示 `UI_MENU_LOAD_ERROR`，不會因為此時 `has_world()` 也查到
「不存在」而誤判成「本來就沒有存檔」。

套用邏輯是通用的，對場上每個 `"characters"` 群組成員一視同仁，不特別排除
Player。Player 的 `character_id` 已透過 `user://saves/player_id.txt` 持久化
（見上面「一個前置」一節與 [[Character 基底與 Agent]]）——這則 PR 自己的
驗證只涵蓋 NPC 與 `day`（見 PR 說明的驗證表），Player 這條路徑要等 id
持久化落地後再重新驗證。
