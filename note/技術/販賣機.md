# 商店（餐酒館／藥草鋪，issue #572）

站進餐酒館或藥草鋪這兩個地點的 `Area2D` 範圍按 E，開商品選單（見
`vending_menu.gd`／`player.gd`），花錢買東西。商店不是場景裡的實體物件，
是綁在**地點**本身的一份靜態資料（`world/shop.gd` 的 `Shop.CATALOGS`），
跟 [[工作站]] 那種需要走到一個特定 `StaticBody2D` 前的互動不一樣。

庫存與現金視為無限（規格書 08 §5 規則 #4，不做商鋪經營模擬）——好幾個
角色可以同時買，不用像 Workstation 那樣卡位。

依賴 [[物品欄]] 的金錢與背包 API（`spend()`、`add_item()`）。

## 觸發方式：跟地點互動，不是跟機台互動

`player.gd::_nearest_shop_place()` 對 `SHOP_PLACES`（`["tavern",
"herb_shop"]`）各檢查一次「玩家是否站進這個地點的 `Area2D` 矩形範圍內」
（`PlaceAnchors.is_within()`），回傳符合條件的地點名稱；都不在回空字串。
不要求面向——地點是站進去的區域，不是像工作站那樣站在外面面對的一個點
（issue #1022：地點在 #814 從 `Marker2D` 換成 `Area2D` 矩形後，舊的
「離錨點中心 `BUY_RANGE`(32px) 內＋面向錨點」判斷沒跟著換，矩形內大半範圍
反而被誤判成「太遠」或「沒面向」，商店幾乎按不進去）。

`_get_interact_candidates()` 的優先序是 workstation → 商店 → 可搭話的人
（跟拿掉機台前一樣），`E` 鍵按下時打到哪個由 `_unhandled_input()` 這套
比較邏輯決定；商店贏了就呼叫 `vending_menu.open(place, self)`。

> [!important] 商店沒有節點可以描邊高亮
> `workstation` 與可搭話對象靠近時，`player.gd` 會即時描邊提示「E 會打到
> 這個」（issue #81）。商店拿掉實體道具後沒有節點可以掛這個效果——玩家
> 走進商店地點的 `Area2D` 範圍就能按 E，沒有額外的視覺提示，跟純距離判斷的
> 其他地點行動（`eat`／`drink` 之類）體感一致。

AI（Agent）走的是另一條路徑：`_pursue_buy_task()` 直接把 `params.place`
（`"tavern"`／`"herb_shop"`）當目的地走到 `PlaceAnchors` 錨點，抵達後呼叫
`buy_from(place, item_id)`——這條路徑本來就不靠場景物件判斷，issue #572
落地前後行為沒變，只是拿掉了原本用來查價格的 `_find_vending_machine_at_place()`
節點查找，改直接查 `Shop.CATALOGS`。

## 買一件東西是兩件事，要一起成功

`spend(price)` 扣款成功之後，`add_item(item_id)` 還是可能因為背包滿了回
`ADD_NO_SPACE`——如果不處理，玩家會白付錢。`buy_from()` 用「扣款失敗就不買、
加入失敗就退款」的補償式寫法：

```gdscript
if price > 0:
	var spend_reason := inventory.spend(price)
	if spend_reason != Inventory.MONEY_OK:
		return spend_reason

var add_reason := inventory.add_item(item_id)
if add_reason != Inventory.ADD_OK:
	inventory.add_money(price)		# 退回剛剛扣的錢
	return add_reason
```

> [!important] `price > 0` 不是多餘的守衛：0 元商品不能送進 `spend()`
> `Inventory.spend()` 擋掉 `amount <= 0`（那道守衛是防呼叫端傳負數當加錢用），
> 所以免費商品送進去會拿到 `MONEY_INVALID_AMOUNT`——按鈕看得到、點下去永遠
> 買不成，而且回一個原因碼表上沒有的碼。`Shop.get_price()` 也是為了同一件事回
> `-1` 而不是 `0` 當「沒這項」的哨兵值：0 是合法價格。

沒有在買之前先用 `find_first_empty()` 猜背包放不放得下——同 `item_id` 可能
疊進既有格，不一定要空格，猜的話等於在 `buy_from()` 裡重算一次 `Inventory`
內部的堆疊規則（`_find_stackable_slot()` 是私有方法，本來就不該從外面猜）。
退款是更簡單可靠的做法，而且錯誤處理只要在一個地方做。

## 頭上飄的 `-N`

`MoneyPopup`（`player.tscn`／`agent.tscn` 各掛一個子節點，跟 `Bubble`／
`WorkProgress` 同一種「頭上飄一塊 UI」掛法，`position (0, -18)`）在買賣真的成立
才飄——`buy_from()` 只有在 `add_item()` 也成功、確定不會被退款之後才呼叫
`money_popup.show_change(-price)`。中途失敗退款的話淨變動是 0，飄出來只會
讓人以為扣了又加，很奇怪。

`show_change(amount)` 是通用的：正數綠色（Moss）、負數紅色（Ember），數字
用 `"%+d"` 格式化自動帶正負號。目前只有 `buy_from()` 在用（負數），`work_at()`
的報酬沒有接——issue 沒有要求，先不做。飄的動畫是 `Tween`：往上飄 12px、同時
淡出，0.8 秒後 `hide()` 收尾，呼叫端不用自己清狀態。

> [!important] 靜止位置由場景決定，腳本不可以寫死歸零
> `_ready()` 把 `position` 記進 `_rest`，`show_change()` 歸位與 tween 目標都
> 相對它算（`_rest.y - RISE_DISTANCE`）。寫死 `position = Vector2.ZERO` 的話
> 第一次購買就把場景給的 `(0, -18)` 永久洗掉，之後每次都在角色身體上飄。
> `Bubble` 與 `WorkProgress` 沒踩到這個坑，是因為它們根本不動 `position`。

## 失敗原因碼

`TOO_FAR`／`TARGET_NOT_FOUND` 是 `character.gd` 自己定義的（形狀比照
`TALK_*`／`WORK_*`），但扣款與加入的失敗**直接借用 `Inventory` 自己的原因碼**，
不重新取名：

| 碼 | 來源 | 意義 |
| --- | --- | --- |
| `TARGET_NOT_FOUND` | `character.gd` | 這個地點沒有商店，或場景找不到對應錨點 |
| `TOO_FAR` | `character.gd` | 不在地點的 `Area2D` 範圍內 |
| `ITEM_NOT_FOUND` | `character.gd` | 這間商店沒有賣這個 `item_id` |
| `NO_INVENTORY` | `character.gd` | 角色沒有掛 `Inventory` |
| `NOT_ENOUGH` | `Inventory.MONEY_NOT_ENOUGH` | 錢不夠 |
| `NO_SPACE` | `Inventory.ADD_NO_SPACE` | 背包滿了（已退款） |

## 選單：滑鼠點擊，不做數字鍵快捷

`VendingMenu`（`main.tscn` 的 `VendingMenu` CanvasLayer，跟 `StatusPanel`／
`InventoryPanel` 同一層級）用 `Button` 動態長出商品清單，點一項直接呼叫
`buyer.buy_from(place, item_id)`。標題用 `places.gd::display_name(place)`
（「餐酒館」／「藥草鋪」），同一份選單服務兩個地點，不是寫死的「販賣機」。

刻意不做數字鍵快捷選——`hotbar.gd` 的 `hotbar_1`-`hotbar_9` 也在監聽同一批
數字鍵，兩邊都是 `_unhandled_input`，誰先誰後不保證，容易「買東西的同時把
快捷欄也選到同一格」。商品目前只有 4 項，純滑鼠點擊不吃虧太多。

兩個因為「這是預期玩家一直點的面板」而跟其他面板不同的地方：

- **`Panel` 的 `mouse_filter` 是 `STOP`，不是 `IGNORE`。** `InventoryPanel`／
  `StatusPanel` 用 `IGNORE` 沒問題，因為它們是被動顯示；這裡用 `IGNORE` 的話，
  點在按鈕以外的地方（內距、標題列、按鈕之間的空隙）會穿透到 `selection.gd`，
  在選單背後選角色、畫點擊漣漪、還把鏡頭移過去。
- **`open()` 重建清單時先 `remove_child()` 再 `queue_free()`。** `queue_free()`
  是幀末才真的刪，只呼叫它的話重開選單那一幀 `ItemList` 同時掛著 4 個舊按鈕與
  4 個新按鈕，`VBoxContainer` 排 8 列會撐破固定尺寸的面板。

## 開關的職責切法

跟 `InventoryPanel` 用固定的 `Tab` 鍵開關不同，商店沒有一個固定的「開關鍵」——
`E` 是不是要開選單，得先判斷玩家在不在商店地點旁邊，這個判斷只有 `player.gd`
做得到（`VendingMenu` 不知道玩家在哪裡）。所以「開」跟「關」故意切給兩邊分別負責：

- **開**：`player.gd` 的 `_unhandled_input` 判斷玩家在商店地點旁才呼叫 `open()`
- **關**：`vending_menu.gd` 自己的 `_unhandled_input` 監聽 `interact`／`ui_cancel`

`player.gd` 在選單開著的時候會直接 `return`（不呼叫
`set_input_as_handled()`），讓同一個 E 事件繼續往下傳給 `vending_menu.gd`
自己處理——不然玩家在選單裡按 E 想關掉，會先被 `player.gd` 攔下來當成
「開始一個新的互動」。

還有第三條關法：**走出地點的 `Area2D` 範圍就自己關掉**。選單擋不住移動（方向鍵
照走），少了這段的話玩家可以邊開著選單邊走到地圖另一頭，價格照顯示、每次點
都回 `TOO_FAR` 而且只有 `push_warning` 看不到，同時 `player.gd` 又因為「選單
開著」放掉 E，等於整個卡住。`_process()` 用 `PlaceAnchors.is_within()` 判斷
玩家還在不在地點範圍內，跟 `buy_from()` 同一套判斷（issue #1022），
`open()` 開啟、`close()` 關掉——選單沒開的時候不跑。收法跟對話走遠自然散場
是同一種。

> [!warning] 這個 early-return 依賴的是「事件還沒被標記處理」，不是節點順序
> Godot 的 `_unhandled_input` 在同一批監聽者之間的呼叫順序不保證（`pause.gd`
> 的註解也提過同樣的事：Esc 目前有好幾個使用者、順序不可靠）。這裡故意不去賭
> 順序——`player.gd` 判斷選單開著就直接跳過、完全不碰這個事件，`vending_menu.gd`
> 才會照樣收得到同一個還沒被處理的事件，不管兩個節點誰先被呼叫。

## AI 動作白名單

`ALLOWED_ACTIONS` 本來就有 `"buy"`，**`IMPLEMENTED_ACTIONS` 沒有**，理由跟
[[工作站]] 的 `work` 一模一樣：沒有任何執行層把一筆 `{"action": "buy"}` 對應到
一次真的購買。`buy` 還多缺一個「買哪個 `item_id`」的來源——目前只有玩家從
`VendingMenu` 點得出來。列進去會變成「白名單宣稱做得到、實際靜默不做」。

## 買到的東西怎麼生效：[[進食與飲用|`eat()`／`drink()`]] 呼叫 [[物品欄|`Inventory.use_item()`]]

實際接到玩家/Agent 動作的消耗路徑是 `character.gd` 的 `eat()`／`drink()`，
找食物/飲品走 `ItemDatabase.get_item(item_id).category`，不是硬編碼白名單
（#84／#163）；找到之後取得 `item`，並呼叫 `Inventory.use_item(item_id, stats, item)`。
`Inventory.use_item()` 從傳入的 `item` 讀取 `data/items.json` 定義的 `effect_*` 欄位
（例如 `effect_satiety`／`effect_hydration`／`effect_alcohol`／`effect_wakefulness`；
key 跟著 `Stats.SPEC` 動態產生，不是寫死這四項），
不是靠 `item_id` 自己再查一次資料庫，套用成功才 `apply_personality_delta()`。
`ale`／`spirit` 喝下去會加 `alcohol`，`CONDITION_DRUNK` 是既有的通用門檻邏輯
（`alcohol > 30`），不用額外接。

## 這則不包含

- **販售（`sell`）。** 只做買
- 議價、`reputation < -50` 拒絕交易、`decay` 折價（規格書 08 §5，全部標了
  【推測待確認】）
- Agent 自己決定要去買東西——那是行程仲裁的事，跟 [[工作站]] 排除
  「Agent 自己決定要去工作」是同一個理由
- NPC／店員造型的商店互動——issue #572 拍板選單介面，不做對話式買賣
