# 販賣機

場上第二個可互動物件，沿用 [[工作站]]（#62）做出來的形狀：動作介面在
`character.gd`（Player 能做的，Agent 也要能做），`player.gd` 只負責 E 鍵
怎麼分派。#63 明講不做「一套通用的互動物件框架」——兩個物件不值得先蓋一層
抽象，`Workstation` 跟 `VendingMachine` 是兩個獨立的 `StaticBody2D` 腳本，
`character.gd` 也是分別各寫一個 `find_nearest_*()` / 對應動作，沒有共用基底。

依賴 [[物品欄]] 的金錢與背包 API（`spend()`、`add_item()`）。

## 跟工作站不一樣的地方

| | Workstation（#62） | VendingMachine（#63） |
| --- | --- | --- |
| 佔用 | `occupant` 卡位，一次一人 | 無限庫存/現金（規格書 08 §5 #4），誰都能同時買 |
| E 鍵行為 | 立刻執行動作（開始計時） | 開商品選單，動作在選單裡點下去才發生 |
| 動作時長 | 5 遊戲分鐘 | 即時 |

## 買一件東西是兩件事，要一起成功

`spend(price)` 扣款成功之後，`add_item(item_id)` 還是可能因為背包滿了回
`ADD_NO_SPACE`——如果不處理，玩家會白付錢。`buy_from()` 用「扣款失敗就不買、
加入失敗就退款」的補償式寫法：

```gdscript
var spend_reason := inventory.spend(price)
if spend_reason != Inventory.MONEY_OK:
	return spend_reason

var add_reason := inventory.add_item(item_id)
if add_reason != Inventory.ADD_OK:
	inventory.add_money(price)		# 退回剛剛扣的錢
	return add_reason
```

沒有在買之前先用 `find_first_empty()` 猜背包放不放得下——同 `item_id` 可能
疊進既有格，不一定要空格，猜的話等於在 `buy_from()` 裡重算一次 `Inventory`
內部的堆疊規則（`_find_stackable_slot()` 是私有方法，本來就不該從外面猜）。
退款是更簡單可靠的做法，而且錯誤處理只要在一個地方做。

## 頭上飄的 `-N`

`MoneyPopup`（`player.tscn`／`agent.tscn` 各掛一個子節點，跟 `Bubble`／
`WorkProgress` 同一種「頭上飄一塊 UI」掛法，`position (0, -18)`）在買賣真的成立
才飄——`buy_from()` 只有在 `add_item()` 也成功、確定不會被退款之後才呼叫
`money_popup.show_change(-price)`。中途失敗退款的話淨變動是 0，飄出來只會
讓人以為扣了又加，很奇怪。

`show_change(amount)` 是通用的：正數綠色（Moss）、負數紅色（Ember），數字
用 `"%+d"` 格式化自動帶正負號。目前只有 `buy_from()` 在用（負數），`work_at()`
的報酬沒有接——issue 沒有要求，先不做。飄的動畫是 `Tween`：往上飄 12px、同時
淡出，0.8 秒後 `hide()` 收尾，呼叫端不用自己清狀態。

## 失敗原因碼

`TOO_FAR`／`TARGET_NOT_FOUND` 是 `character.gd` 自己定義的（形狀比照
`TALK_*`／`WORK_*`），但扣款與加入的失敗**直接借用 `Inventory` 自己的原因碼**，
不重新取名：

| 碼 | 來源 | 意義 |
| --- | --- | --- |
| `TARGET_NOT_FOUND` | `character.gd` | 附近沒有販賣機 |
| `TOO_FAR` | `character.gd` | 超出 `BUY_RANGE`（32px = 2 格） |
| `ITEM_NOT_FOUND` | `character.gd` | 販賣機沒有賣這個 `item_id` |
| `NO_INVENTORY` | `character.gd` | 角色沒有掛 `Inventory` |
| `NOT_ENOUGH` | `Inventory.MONEY_NOT_ENOUGH` | 錢不夠 |
| `NO_SPACE` | `Inventory.ADD_NO_SPACE` | 背包滿了（已退款） |

## 商品表

`VendingMachine.CATALOG`（`{item_id: price}`）先寫死在腳本裡，價格抄
《規格書 08 物品與經濟》§3-1／§3-2 的售價欄——只挑食物與飲品，符合販賣機的
定位（刀、衣物那些隨身用品不放這裡賣）：

| item_id | 價格 |
| --- | --- |
| `bread` | 12 |
| `water` | 2 |
| `wild_fruit` | 8 |
| `ale` | 10 |

之後真的要資料驅動再搬進 `data/`，目前只有 4 項不值得。

## 選單：滑鼠點擊，不做數字鍵快捷

`VendingMenu`（`main.tscn` 的 `VendingMenu` CanvasLayer，跟 `StatusPanel`／
`InventoryPanel` 同一層級）用 `Button` 動態長出商品清單，點一項直接呼叫
`buyer.buy_from(machine, item_id)`。

刻意不做數字鍵快捷選——`hotbar.gd` 的 `hotbar_1`-`hotbar_9` 也在監聽同一批
數字鍵，兩邊都是 `_unhandled_input`，誰先誰後不保證，容易「買東西的同時把
快捷欄也選到同一格」。商品目前只有 4 項，純滑鼠點擊不吃虧太多。

## 開關的職責切法

跟 `InventoryPanel` 用固定的 `Tab` 鍵開關不同，販賣機沒有一個固定的「開關鍵」——
`E` 是不是要開選單，得先判斷附近有沒有機器，這個判斷只有 `player.gd` 做得到
（`VendingMenu` 不知道玩家在哪裡）。所以「開」跟「關」故意切給兩邊分別負責：

- **開**：`player.gd` 的 `_unhandled_input` 判斷附近有販賣機才呼叫 `open()`
- **關**：`vending_menu.gd` 自己的 `_unhandled_input` 監聽 `interact`／`ui_cancel`

`player.gd` 在選單開著的時候會直接 `return`（不呼叫
`set_input_as_handled()`），讓同一個 E 事件繼續往下傳給 `vending_menu.gd`
自己處理——不然玩家在選單裡按 E 想關掉，會先被 `player.gd` 攔下來當成
「開始一個新的互動」。

> [!warning] 這個 early-return 依賴的是「事件還沒被標記處理」，不是節點順序
> Godot 的 `_unhandled_input` 在同一批監聽者之間的呼叫順序不保證（`pause.gd`
> 的註解也提過同樣的事：Esc 目前有好幾個使用者、順序不可靠）。這裡故意不去賭
> 順序——`player.gd` 判斷選單開著就直接跳過，完全不碰這個事件，`vending_menu.gd`
> 才會照樣收得到同一個還沒被處理的事件，不管兩個節點誰先被呼叫。

## 場景

`vending_machine.tscn`：跟 `workstation.tscn`同構——`StaticBody2D`
（`VendingMachine` 腳本）+ `Polygon2D`（10×16 直立方形佔位視覺，Ash `#7E8A93`，
跟工作站的 Loam 棕色區分開）+ `CollisionShape2D`（`RectangleShape2D` 10×16，
純粹給 `NavGrid` 當障礙，跟互動判定無關）。

`main.tscn` 裡擺了一個實例在 `restaurant` 錨點附近（`Node2D/VendingMachine`，
position `(140, -20)`），一樣不掛在 `PlaceAnchors` 底下——理由跟工作站一樣，
它是實體物件不是純座標。

`VendingMenu` 的 `Panel` 重用 `InventoryPanel` 那塊 `Setting menu.png` 素面
9-slice（`region_rect (139, 12, 106, 122)`），沒有共用同一個 `SubResource`
實例（`node_set_property` 的內嵌資源語法會建一份新的），視覺上完全一致，
只是多一份幾乎不佔記憶體的資源。

## AI 動作白名單

`ai_schema.gd` 的 `IMPLEMENTED_ACTIONS` 加了 `"buy"`（`ALLOWED_ACTIONS` 本來
就有，#62 那次就確認過）。

## 這則不包含

- **販售（`sell`）。** 只做買
- **吃掉食物回復飢餓。** `inventory.gd` 目前沒有物品效果，買到的食物只會
  躺在背包裡，這是預期的——見 [[物品欄]] 的「未做」
- 議價、`reputation < -50` 拒絕交易、`decay` 折價（規格書 08 §5，全部標了
  【推測待確認】）
- Agent 自己決定要去買東西——那是行程仲裁的事，跟 [[工作站]] 排除
  「Agent 自己決定要去工作」是同一個理由
