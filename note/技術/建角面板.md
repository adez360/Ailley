# 建角面板

規格書 05 的完整流程（issue #122）：建角（分頁 1/2/3）→ 存檔驗證 → 角色生成
→ 存進角色庫 → 投放。版面約束見 [[UI 版面與素材規格]]。

## 三個分頁都做了

| 分頁 | 內容 | 狀態 |
| --- | --- | --- |
| 1 基本 | 姓名／年齡／性別／決策來源（本機／雲端／真人，兩段式，讀 `AIConfig`） | 已實作 |
| 2 個性 | 六維滑桿 + 自由文本 + 極端項計數（沒變） | 已實作 |
| 3 外觀 | 6 套造型組挑選，MVP 用編號＋純色塊佔位（規格書 05 §5-0，內容待《99》P-38） | 已實作（佔位） |

分頁切換是純顯示層：`_switch_tab()` 把三塊 Control 的 `visible` 互斥切換，
選中的分頁按鈕疊 Amber stylebox——跟六維滑桿一樣是表驅動生成
（`DIMENSIONS`／`GENDERS`／`DECISION_SOURCES`），增減選項只改表。

### 決策來源（規格書 05 §3-1）

兩段式：先選來源（三個按鈕），本機／雲端沒有可用 provider 時對應按鈕
`disabled`；選了本機或雲端才會出現下拉選單，列出 `AIConfig.providers` 裡
`valid == true` 且「base_url 指向本機」（`localhost`／`127.0.0.1`）相符的那批。
下拉選的是**型號字串**（`Provider.model`），不是 provider 的 key——這是刻意
的，也是查表方向要反過來的原因，見 [[LLM 串接與 AI 服務層]]
「`model_name` 存的是型號字串」那節。真人不需要選模型，第二段整個隱藏。

## 存檔後接去哪裡：`character_saved` → `GameManager`

面板本身**只負責蒐集資料**，這條原則沒變。`_on_save_pressed()` 驗證通過就
`character_saved.emit(collect())` 然後關閉面板；`_ready()` 時把這個訊號接到
`GameManager.receive_created_character()`（面板不知道存檔驗證之後發生什麼，
`GameManager` 也不知道面板長什麼樣）。

`receive_created_character()` 做規格書 05 流程圖 ①-⑤：組 `hexaco` →
`Personality.from_identity()` 一次拿到 `personality`＋`system_prompt`（這條
轉換管線已經在 #117 做完，這裡只是接上）→ 存進 `GameManager.character_library`
（容量 15）→ fire-and-forget 打一次 `words_to_creator`（新的第四種 AI 呼叫
類型，見 [[LLM 串接與 AI 服務層]]）。

## 角色庫首頁（`character_library.gd`）

獨立 `CanvasLayer`，跟建角面板同一種 `open()`/`close()`＋Esc 關閉的寫法。
沒有立繪縮圖與六維雷達圖——素材與繪圖元件都還沒有，MVP 用一行文字摘要
（`H50 E15 X15 A50 C85 O50` 這種縮寫）代替，跟 `hotbar.gd`／`status_panel.gd`
同一種「資料變動時動態長出 Row，不在場景裡手排」寫法。四個操作：

| 操作 | 行為 |
| --- | --- |
| 編輯 | 僅未投放者可按；呼叫 `character_create.edit(id)` 把既有資料灌回建角面板，存檔時原地覆蓋（`collect()` 帶 `id`）而不是新增一筆 |
| 刪除 | `GameManager.remove_from_library(id)` |
| 投放 | `GameManager.deploy_from_library(id)`，見下方 |
| 複製 | `GameManager.duplicate_library_entry(id)`，新 id、名字加「（複製）」、投放狀態重置 |

> [!warning] 列表刷新要先 `remove_child()` 再 `queue_free()`
> 只呼叫 `queue_free()` 的話要等到幀尾才真的刪，連續刷新兩次（例如刪除後
> 緊接著又投放）舊列還沒真的消失，新列就疊上去、列數變兩倍。同一個坑
> `vending_menu.gd` 踩過（見 [[販賣機]]），這裡照抄同一個解法。

## 投放：借用既有的 `identity_assignments` 查表機制

`GameManager.deploy_from_library()` 呼叫既有的 `spawn_character()`（#73）生成
節點，但**不改** `spawn_character()` 或 `Character._ready()` 一行——`_ready()`
本來就會用 `GameManager.get_npc_identity(name)`（節點名查表）組
`system_prompt`／`personality`，`deploy_from_library()` 只是在呼叫
`spawn_character()` **之前**，把這隻角色的完整身分（`hexaco`／`character`）
註冊進 `identity_assignments`、key 用即將指派的 `character_id`（`spawn_character()`
本來就會把節點名設成這個 id）。`_ready()` 不用改一行就會撿到真正的人格資料，
不是撿到空字典退回沒有人格的最小版 `system_prompt`。

`decision_source`／`model_name` 是 `agent.gd` 的 `@export` 欄位，投放時用
`get()`/`set()` 套進去（跟 `spawn_character()` 判斷 `schedule_template` 同一種
寫法，因為收到的是泛型 `Character`）。

> [!warning] 套完欄位要重建一次 provider，不然選擇不會生效
> `spawn_character()` 內的 `add_child()` 會同步觸發 `Agent._ready()`，那裡
> 會照 `@export` 當下的值（預設 `"local"`）建一次 `_provider` 並存起來
> （《06》「投放後不可改」，只建一次）。`deploy_from_library()` 是在
> `spawn_character()` **回傳之後**才套用建角面板選的 `decision_source`／
> `model_name`——這時 `_provider` 早就用舊值建好了，角色庫選的來源不會
> 生效（CodeRabbit review 抓到）。修法是 `agent.gd` 加一個公開的
> `rebuild_provider()`，套完兩個欄位後呼叫它重建 `_provider`。

> [!note] `human` 是已知的既有限制，不是這則的 bug
> `human` 目前沒有 `HumanInput` 實作，`_make_provider()` 會安靜退回
> `LocalLLMProvider`（見 [[LLM 串接與 AI 服務層]]）。`local` 分頁下拉選單選的
> 型號已經會真正生效（#288，`LocalLLMProvider` 跟 `RemoteLLMProvider` 一樣讀
> `model_name`）；`human` 選了會退回本機這件事還沒解，要等 `HumanInput`
> 落地（issue #156）才會有真正的行為可選，不屬於這則的範圍。

## 投放路由：「由我操控」走 `player.tscn`（issue #371）

`deploy_from_library(id, as_player)` 多一個 `as_player` 參數。`true` 時
`spawn_character()` 收到的是 `preload("res://scenes/player.tscn")`，不是
`agent.tscn`；`identity_assignments` 照樣註冊（六維人格保留當角色履歷/存檔
用途，不影響操作，見 issue #372）。`decision_source`／`model_name` 那段
`character.get("decision_source") != null` 的判斷式對化身者天生會是
`null`——`player.gd` 是 `extends Character`，不是 `Agent`，本來就沒有這兩個
`@export` 欄位，不用另外加 `as_player` 分支去跳過。

投放化身角色前，會先把場景裡既有的「player」分組節點清掉（`queue_free()`）
——不管那是設計時期在 `main.tscn` 擺的測試假人，還是先前已投放的化身角色。
同一時間只該有一個真人操控的身體；沒清掉的話 `get_first_node_in_group("player")`
（`hotbar.gd`／`follow_camera.gd`／`chat_input.gd`／`inventory_slot_button.gd`
全部靠這個查表）永遠撈到先加進場景的那個，新投放的等於白投，是編輯器裡實測
重現過的行為，不是預防性寫法。

只做了後端路由本身；面板上「由我操控」這個選項的按鈕/版面還沒做（見
issue \#374 的 hotbar/inventory 接線）。

## 化身者模式：決策來源分頁隱藏（issue #372）

`open(as_player)` 多一個參數，`true` 時把 `_embodiment_mode` 設起來；
`_refresh_all()`（既有「依實例狀態同步 UI 視覺」的唯一入口，跟
`_refresh_source_buttons()`／`_refresh_style_buttons()` 同一種寫法）多一行
把 `_decision_source_block()` 那個容器的 `visible` 設成
`not _embodiment_mode`。決策來源對化身者沒有意義（`deploy_from_library()`
本來就不會套用），藏起來即可，不用額外 disable。

六維人格滑桿刻意不動——滑桿保留當角色履歷/存檔用途（見上面 #371 那節），
不是這則要重新決定的範圍。`edit()` 一律強制 `_embodiment_mode = false`：
編輯既有角色庫項目走的一定是 AI 角色模式，`edit()` 沒有 `as_player` 參數。

目前沒有任何按鈕會呼叫 `open(true)`——跟 #371 同一種模式，UI 上「由我
操控」的選項按鈕/版面留給後續視覺任務。

讀檔不會自動接回化身：世界存檔的 `embodied_character_id`（issue #373）讀檔時
只還原這個值，跟場景裡實際的 player 節點不一致只 `push_warning`，不會自動
把身分套到別的節點——真正「讀檔後自動換身」依賴的就是這裡的投放路由，見
[[存檔]]「目前被誰操控，也屬於世界」。

## 開啟入口：debug 指令，不是 HUD 按鈕

規格書沒有定義任何 HUD 掛點能開這兩個面板。比照 #73 的 `spawn` 先例，走
debug 指令 `charnew`（開建角面板）／`charlib`（開角色庫首頁）打通管線，
不等一個像素風的開場選單——先例本身也是這樣講的：「之後有正式的建角
面板/角色庫 UI（#122）接上之後再收進正式指令表」，`help` 目前留空。

## 存檔驗證（規格 4-4，沒變）

極端項 = 滑桿 ≤25 或 ≥75。門檻**依 `character` 有沒有填而不同**：

| `character` | 需要的極端項 |
| --- | --- |
| 有填 | 2 ~ 4 |
| 留空 | 3 ~ 4 |

留空時要求更多，否則會產生一個既沒數值特徵也沒文字描述的空角色。分頁 1
的姓名（必填）與分頁 3 的造型組（必選）並列同一關：任一不通過，`儲存`
按鈕整體 `disabled`。

## 三個實作上的坑

**`TextEdit` 沒有 `max_length`。** 250 字上限只能在 `text_changed` 裡自己截，
而且截字會把游標彈到開頭，要先記下 `get_caret_column()` 再設回去。
`LineEdit`（姓名欄）不受影響——原生就有 `max_length`。

**極端狀態的紅色填充是 `add_theme_stylebox_override`，不是 theme variation。**
variation 必須註冊 base type，而那只有編輯器 UI 做得到（`theme_manage` 沒有對應的 op）。
`儲存` 按鈕的 Amber 底、分頁與造型組選中狀態同理。

**`HSlider` 的滑鈕是 icon 不是 StyleBox**，所以 `assets/ui/slider_grabber.png` 是必要的，
不是裝飾。目前是 5×11 的佔位圖（Bark 外框 + Cream 內芯），畫好真的直接覆蓋同一個檔名即可。
