# 物品欄

角色的物品容器，掛在 [[Character 基底與 Agent|Character]] 基底而不是 Player——
核心約束「Player 能做到的，Agent 也必須能做到」，Agent 沒有 UI 也要查得到背包。
資料形狀與堆疊規則照《規格書 08 物品與經濟》§1、§4。這則只做容器與 API，
不做物品定義檔、腐壞／耐久的 tick 計算、地上物品、商店交易。

## 槽位

`scripts/character/inventory.gd`（`class_name Inventory extends Node`），
`player.tscn`、`agent.tscn` 各掛一個 `Inventory` 子節點，
`character.gd` 用 `@onready var inventory := get_node_or_null("Inventory")` 取得。

快捷欄與主背包共用同一個陣列，不是兩個容器：

| 區段 | index | 常數 |
| --- | --- | --- |
| 快捷欄 | 0–8 | `HOTBAR_SIZE = 9` |
| 主背包 | 9–35 | `MAIN_SIZE = 27` |

「把快捷欄的東西丟進背包」因此是搬 index（`move_slot` / `swap_slot`），不是跨容器搬移。
分成兩個容器的話，這個最常見的操作會變成跨容器搬移，堆疊與空位判斷得寫兩份。

槽數一律讀常數，不要把 9 / 27 / 36 散進迴圈或版面計算。

> [!note] 規格書 08 §4 寫的是「隨身 8 格」，這裡是 36
> 那個「8」在規格書裡標了【推測待確認】，數字之後可能還會再動。
> 這則先蓋一個能用的容器，是否改規格書留到平衡階段連同物品清單（《99》P-18）一起拍板。

## 一格的資料

照 §1：`{item_id: String, count: int, decay: int, durability: int}`，空格是 `{}`。

`item_id` 這階段收任意字串，不查定義檔（定義檔不在這則範圍）。

> [!important] `durability` 用 `-1` 當「這格不追蹤耐久」的哨兵值
> 規格書 §2 把物品分兩類：`decay` 類（食物、獵物、採集品……）與 `durability` 類
> （`carry`，刀、樂器……），兩者互斥。定義檔還沒做，`add_item()` 目前靠呼叫端自己講——
> 傳 `durability >= 0` 就當這批是 `carry` 類。存進槽位時，decay 類一律寫 `durability = -1`，
> 而不是規格書範例裡看起來「順手」的 `100`：`-1` 落在合法的 0–100 之外，
> 程式判斷「這格有沒有在追蹤耐久」時不會跟一格真的耐久滿值的 carry 物品混淆。
> 等物品定義檔進來，這個哨兵值就是唯一要對齊的地方。

## 堆疊規則（§4）

`add_item(item_id, count, decay, durability)`：

1. `durability >= 0` → 視為 carry 類，不可疊，一件佔一格（`_add_unstackable`）
2. 否則視為 decay 類，找同 `item_id`、無 durability、`decay` 差距 ≤ `STACK_DECAY_TOLERANCE`(10)
   的既有格疊進去，取較差（較高）的 decay；沒有相容格就開一格新的（`_add_stackable`）
3. 兩種情況沒位置都回傳 `ADD_NO_SPACE`，且**不動任何格**——失敗是原子的，
   不會半途占掉一部分槽位又回報失敗

`remove_item()` 對稱：數量不夠回傳 `REMOVE_NOT_FOUND` 且不動任何格。

失敗原因碼比照 `character.gd` 的 `TALK_*`（`ADD_OK` / `ADD_NO_SPACE` /
`ADD_INVALID_COUNT`、`REMOVE_OK` / `REMOVE_NOT_FOUND` / `REMOVE_INVALID_COUNT`）——
計畫 §5.3 要求每個動作都要能講出為什麼失敗，AI 才有辦法重排。

### `count` 必須是正整數

`add_item()` / `remove_item()` 對 `count <= 0` 直接回 `*_INVALID_COUNT`，
`has_item(id, 0)` 回 `false`。這不是防禦性寫法，是因為放行會壞掉狀態：

- `_add_stackable(count=0)` 會寫出 `{count: 0}` 的格子。它非空，所以
  `find_first_empty()` 跳過；`count_item()` 又算成 0，所以 `remove_item()` 回
  `REMOVE_NOT_FOUND`——**這格永遠清不掉**。負數還會讓後續的加總被吃掉。
- `_add_unstackable(count=0)` 的蒐集迴圈永遠比不到 `empties.size() == count`
  （append 後 size 起跳就是 1），會把**整個背包**填滿該物品。

`has_item()` 一起擋是為了對齊：呼叫端常寫 `if has_item(id, n): remove_item(id, n)`，
`has_item` 對 `n <= 0` 回 true 就會走進一個必定失敗的 remove。

`count_item()` 比對前先跳過空格——空格的 `get("item_id", "")` 回空字串，
拿 `""` 去查會 match 到每一個空格，然後存取它們沒有的 `count` 鍵而崩掉。

## `move_slot` 與 `swap_slot` 是兩件事

`move_slot(from, to)` 只在目的地是空格時成功，不覆蓋；要交換兩個已佔用的格用
`swap_slot(a, b)`。UI 拖曳放到空格走前者，快捷欄重新排序走後者。

## 快捷欄選格

`get_selected_index()` / `set_selected_index()` 是資料層狀態，不是 UI 狀態——
UI 只是把這個值顯示出來，Agent 沒有 UI 也要有「手上拿著什麼」這個概念。
`set_selected_index()` 夾限在 `0..HOTBAR_SIZE-1`。

## Agent 查詢

`get_summary()` 回不含空格的密集陣列，每筆補一個 `slot` 索引，給行為判定與
日後的 AI payload 用；回傳的是副本，改它不會動到內部狀態。

## debug 指令

`debug_console.gd` 的 `inv` 指令（見 [[尋徑與 Debug 主控台]]）：

- `inv [name]` —— 列出該角色的背包，省略就看玩家自己
- `inv give <item_id> [count]` —— 塞測試物品給玩家，一律是 decay 類
  （durability 用預設 -1；要測 carry 類不可疊得直接呼叫 `Inventory.add_item()`）
