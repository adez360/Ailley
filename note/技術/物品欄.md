# 物品欄

角色的物品容器與錢包，掛在 [[Character 基底與 Agent|Character]] 基底而不是 Player——
核心約束「Player 能做到的，Agent 也必須能做到」，Agent 沒有 UI 也要查得到背包。
資料形狀與堆疊規則照《規格書 08 物品與經濟》§1、§4，金錢照《規格書 01 角色數值》§3-3。
這則只做容器與 API，不做物品定義檔、腐壞／耐久的 tick 計算、地上物品、商店交易。

## 槽位

`scripts/character/inventory.gd`（`class_name Inventory extends Node`），
`player.tscn`、`agent.tscn` 各掛一個 `Inventory` 子節點，
`character.gd` 用 `@onready var inventory := get_node_or_null("Inventory")` 取得。

快捷欄與主背包共用同一個陣列，不是兩個容器：

| 區段 | index | 常數 |
| --- | --- | --- |
| 快捷欄 | 0–8 | `HOTBAR_SIZE = 9` |
| 主背包 | 9–35 | `MAIN_SIZE = 27` |

「把快捷欄的東西丟進背包」因此是搬 index（`move_slot` / `swap_slot`），不是跨容器搬移。
分成兩個容器的話，這個最常見的操作會變成跨容器搬移，堆疊與空位判斷得寫兩份。

槽數一律讀常數，不要把 9 / 27 / 36 散進迴圈或版面計算。

> [!note] 隨身 36 格已定案，跟規格書一致
> 規格書《08》§4 已改採這裡的實作數字（隨身 36 格＝快捷欄 9 ＋主背包 27）。
> 家中儲存（50 格）與單一堆疊數量上限（30 個）已寫進《08》§4，但兩者都還沒實作——
> 目前的 `add_item`/`remove_item` 沒有堆疊數量上限，一格能疊到多少算多少。

## 一格的資料

照 §1：`{item_id: String, count: int, decay: int, durability: int}`，空格是 `{}`。

`item_id` 這階段收任意字串，不查定義檔（定義檔不在這則範圍）。

> [!important] `durability` 用 `-1` 當「這格不追蹤耐久」的哨兵值
> 規格書 §2 把物品分兩類：`decay` 類（食物、獵物、採集品……）與 `durability` 類
> （`carry`，刀、樂器……），兩者互斥。定義檔還沒做，`add_item()` 目前靠呼叫端自己講——
> 傳 `durability >= 0` 就當這批是 `carry` 類。存進槽位時，decay 類一律寫 `durability = -1`，
> 而不是規格書範例裡看起來「順手」的 `100`：`-1` 落在合法的 0–100 之外，
> 程式判斷「這格有沒有在追蹤耐久」時不會跟一格真的耐久滿值的 carry 物品混淆。
> 等物品定義檔進來，這個哨兵值就是唯一要對齊的地方。

## 堆疊規則（§4）

`add_item(item_id, count, decay, durability)`：

1. `durability >= 0` → 視為 carry 類，不可疊，一件佔一格（`_add_unstackable`）
2. 否則視為 decay 類，找同 `item_id`、無 durability、`decay` 差距 ≤ `STACK_DECAY_TOLERANCE`(10)
   的既有格疊進去，取較差（較高）的 decay；沒有相容格就開一格新的（`_add_stackable`）
3. 兩種情況沒位置都回傳 `ADD_NO_SPACE`，且**不動任何格**——失敗是原子的，
   不會半途占掉一部分槽位又回報失敗

`remove_item()` 對稱：數量不夠回傳 `REMOVE_NOT_FOUND` 且不動任何格。

失敗原因碼比照 `character.gd` 的 `TALK_*`（`ADD_OK` / `ADD_NO_SPACE` /
`ADD_INVALID_COUNT`、`REMOVE_OK` / `REMOVE_NOT_FOUND` / `REMOVE_INVALID_COUNT`）——
每個動作都要能講出為什麼失敗，AI 才有辦法重排。

### `count` 必須是正整數

`add_item()` / `remove_item()` 對 `count <= 0` 直接回 `*_INVALID_COUNT`，
`has_item(id, 0)` 回 `false`。這不是防禦性寫法，是因為放行會壞掉狀態：

- `_add_stackable(count=0)` 會寫出 `{count: 0}` 的格子。它非空，所以
  `find_first_empty()` 跳過；`count_item()` 又算成 0，所以 `remove_item()` 回
  `REMOVE_NOT_FOUND`——**這格永遠清不掉**。負數還會讓後續的加總被吃掉。
- `_add_unstackable(count=0)` 的蒐集迴圈永遠比不到 `empties.size() == count`
  （append 後 size 起跳就是 1），會把**整個背包**填滿該物品。

`has_item()` 一起擋是為了對齊：呼叫端常寫 `if has_item(id, n): remove_item(id, n)`，
`has_item` 對 `n <= 0` 回 true 就會走進一個必定失敗的 remove。

`count_item()` 比對前先跳過空格——空格的 `get("item_id", "")` 回空字串，
拿 `""` 去查會 match 到每一個空格，然後存取它們沒有的 `count` 鍵而崩掉。

## `move_slot` 與 `swap_slot` 是兩件事

`move_slot(from, to)` 只在目的地是空格時成功，不覆蓋；要交換兩個已佔用的格用
`swap_slot(a, b)`。UI 拖曳放到空格走前者，快捷欄重新排序走後者。

## 快捷欄選格

`get_selected_index()` / `set_selected_index()` 是資料層狀態，不是 UI 狀態——
UI 只是把這個值顯示出來，Agent 沒有 UI 也要有「手上拿著什麼」這個概念。
`set_selected_index()` 夾限在 `0..HOTBAR_SIZE-1`。

## 物品定義檔（`scripts/core/item_database.gd`）

`item_id` → 顯示名稱、分類、圖示的查詢介面，跟 `Inventory` 本身是分開的元件——
`Inventory.item_id` 仍然收任意字串不驗證（見上面「一格的資料」），這份定義檔只服務
顯示端。資料放 `data/items.json`，品項清單抄自《規格書 08 物品與經濟》§2、§3。

`ItemDatabase` 是靜態查詢類別（`class_name ItemDatabase extends RefCounted`），
第一次呼叫時讀檔快取，之後都是查記憶體裡的 Dictionary：

| 函式 | 行為 |
| --- | --- |
| `get_item(item_id)` | 查不到回空字典（`{}`），跟 `Inventory.get_slot()` 空格同一個慣例 |
| `has_item(item_id)` | 定義檔裡有沒有這個 id |
| `get_display_name(item_id)` | 查不到就退回 `item_id` 本身，不是空字串 |

`icon` 欄位目前全部是 `null`——專案還沒有任何物品圖示素材（`assets/ui/Sprite sheet
for Basic Pack.png` 是通用 UI 圖示如星星／獎盃，不是物品圖），先把欄位形狀定好，
等美術素材到位再填 `{"source": "res://...", "region": [x, y, w, h]}`。
`inventory_slot_button.gd` 還沒有改讀這份定義檔（見下面「格子上的文字」與 #84）。

## 格子上的文字（`inventory_slot_button.gd`）

`hotbar.gd`／`inventory_panel.gd` 的格子都是 `InventorySlotButton`（`TextureButton`
子類別），掛 `Inventory.changed` 重讀對應的 `Inventory.get_slot(slot_index)`，
非空格子印 `item_id` 前三碼＋數量（例如 `bread x3` 顯示成 `BRE` / `3`），
空格維持空白。

連線要等一幀（`await get_tree().process_frame`）才掛得上——`Hotbar`／
`InventoryPanel` 跟 `Player` 誰先 `_ready()` 由場景樹順序決定，第一幀不保證
找得到 player。目前沒有任何角色重生或 despawn 的路徑，所以連線只綁開場那一個
`Inventory`；真的做出重生時這裡要跟著重連。

這是暫時的示意畫法，不是正式的道具圖示系統（見上面「未做」的道具圖示那條）——
物品定義檔已有（見上面「物品定義檔」），但專案還沒有任何物品圖示素材可畫，
這裡先讓「格子裡有沒有東西、買到/拿到東西有沒有真的進背包」肉眼看得出來。
真正的圖示系統做出來之後這塊要整個換掉，不是拿去微調。

## `changed` 訊號

格子或金錢真的變了才發，而且**只在成功的異動上發**——失敗是原子的、什麼都沒動，
發出去只會讓顯示端白刷一次。發的地方是 `add_item()`／`remove_item()`／
`move_slot()`／`swap_slot()`／`add_money()`／`spend()` 的成功路徑。

不帶參數是刻意的：顯示端要的是「重讀一次」，不是「哪一格變了」。帶了的話每個
顯示端都得先判斷這則跟自己有沒有關係，而重讀 36 格本來就很便宜。

有這個訊號，UI 才不用每幀輪詢。36 個格子按鈕各自 `_process()` 重讀一次，
光是 `get_slot()` 內部的 `duplicate()` 在 60fps 下就是兩千多次配置／秒，
而資料只在買東西或工作時才變、背包面板關著也照跑。

## 金錢

`money` 跟背包放同一個元件。規格書 §3-3 把 `money` 與 `inventory` 都歸在 `economy`
底下，為了一個 int 另外開一個節點，換到的只是多一個 `get_node_or_null` 要防。
初始值 `DEFAULT_MONEY = 300`。

`_money` 是私有的，只能經由三個函式碰：

| 函式 | 行為 |
| --- | --- |
| `get_money()` | 讀 |
| `add_money(amount)` | 進帳，`amount <= 0` 回 `MONEY_INVALID_AMOUNT` |
| `spend(amount)` | 扣款，餘額不足回 `MONEY_NOT_ENOUGH` 且**一毛都不扣** |

> [!important] 收入與支出是兩個函式，不是 `add_money(±n)`
> 合成一個之後，「扣錢」就會走上一條沒有餘額檢查的路 ——
> `add_money(-500)` 會安靜地把餘額扣成負的，而且不會有任何地方報錯。
> 分成兩個，才講得出 `MONEY_NOT_ENOUGH` 這個原因碼——每個動作
> 都要能講出為什麼失敗。
>
> 同理，`_money` 不像 `slots` 那樣公開：公開欄位讓呼叫端寫得出
> `inventory.money -= price`，那條路一樣繞過檢查。

`spend()` 失敗是原子的，跟 `remove_item()` 一致 —— 呼叫端拿到原因碼就知道
這筆交易整個沒發生，不必自己回滾。買東西那種「扣款 + 進背包」要兩件事一起成功的
情況（[[#未做]]），靠的就是這個保證。

金錢會出現在 `Character.get_state_snapshot()` 的 `money` 欄（有掛 `Inventory` 才有）——
Agent 沒有 UI，查自己有多少錢只有這條路。**背包內容不進快照**：`slots` 是 36 格的
陣列，塞進每一次快照（含日後的 LLM payload）太貴，要看內容的呼叫端自己拿
`get_summary()`。

玩家看得到的地方：點角色跳出來的 `StatusPanel`（年齡那個面板）在 `AgeLabel` 底下
多一行 `MoneyLabel`，跟 `StatsBox` 一樣看角色有沒有掛 `Inventory` 決定要不要顯示；
數值是 `open()` 當下讀的一次性快照，不會跟著金額變動即時更新（跟 `Stats` 那幾行
同一種行為，面板得重新點開才會刷新）。

## Agent 查詢

`get_summary()` 回不含空格的密集陣列，每筆補一個 `slot` 索引，給行為判定與
日後的 AI payload 用；回傳的是副本，改它不會動到內部狀態。

## debug 指令

`debug_console.gd` 的 `inv` 指令（見 [[尋徑與 Debug 主控台]]）：

- `inv [name]` —— 列出該角色的背包，省略就看玩家自己
- `inv give <item_id> [count]` —— 塞測試物品給玩家，一律是 decay 類
  （durability 用預設 -1；要測 carry 類不可疊得直接呼叫 `Inventory.add_item()`）
- `money <amount>` —— 改玩家的錢，正數走 `add_money()`、負數走 `spend()`。
  沒有查詢用法，金錢已經在 `status` 的輸出裡，任何角色都查得到。
  兩個方向都能走是刻意的 —— 只能加錢的話，`MONEY_NOT_ENOUGH` 從主控台測不到
