# 村莊地圖

`main.tscn` 的 `Node2D/TileMapDual` 是真實村莊地圖（issue #154），
取代了原本拿來驗尋徑的方塊測試圖。地圖範圍 tile x:-11..18、y:-11..10（30×22）。

不是一整塊開闊地：外框有樹籬邊界，多數地點各自圈在一塊有樹籬圍籬、留一個
缺口當入口的院子裡，院子之間是沒種樹籬的空地，走起來就是連接各院子的路。
另外散置 4 叢 2×2 的裝飾樹籬（不圍院子，純打斷大草皮的視覺變化）。
`cemetery` 是例外——只有一顆裸錨點，沒有圍院子（issue #380 落地時只放了
錨點，場景美術留待之後）。院子座標（外框矩形，樹籬圍住內部可走的空地，
缺口方向見下表）：

| 家 | x:-10..-6, y:-6..-2 | 南側 `(-8,-2)` |
| `herb_shop` | x:-10..-4, y:3..7 | 北側 `(-7,3)` |

> 「一種地點、多個實例」（例如每人一間的家）不能只驗各自 `find_path()` 可達，
> 彼此的 pairwise 距離也要 > `character.gd::ACTUAL_PLACE_RADIUS`（32px，

> 會擋路」的 marker）在 `TileSetAtlasSource` 裡**都沒有畫任何 collision

> 可以啟用。也就是說地圖上看起來圍成院子、圍成外框的樹籬視覺**純粹是畫面**，

> 存在的 `StaticBody2D`（工作站、房屋等），不代表樹籬有擋人（issue #745
> 踩過這個坑：地圖曾經完全沒有邊界，角色能一路走出地圖範圍以外的空白區域）。

## 地圖邊界（`MapBoundary`，issue #745）

角色移動時真正擋住地圖邊緣的是 `Level` 根節點底下的 `MapBoundary`
（`StaticBody2D`，`collision_layer = 1`，跟 `Workstation` 等既有障礙物同一個
物理層），底下 `Top`／`Bottom`／`Left`／`Right` 四個 `CollisionShape2D`
（`RectangleShape2D`）圍成一圈邊框。實際牆框（四個 shape 的外緣）是
**x[-272, 432]、y[-272, 256]**（像素，tile 約 x:-8.5..13.5、y:-8.5..8），
**比 `TileMapDual.get_used_rect()` 小一圈**：`get_used_rect()` 是
tile `(-15,-15)` 到 `(24,13)`，換算像素是 x[-480, 800]、y[-480, 448]，牆框
到 used_rect 邊緣之間的外環地皮角色走不到，只是裝飾用的邊界草地，
不是可玩區域（PR #750 code review 更正：牆框座標以 `level.tscn` 內四個
`CollisionShape2D` 的實際 position/size 為準，不是貼著 used_rect 外緣）。

`FollowCamera._apply_limits()`（見下方「相關」）算鏡頭邊界用的是同一個
`get_used_rect()`，但兩者是各自獨立算的，不是同一份資料——地圖範圍改變時
兩邊都要重新算。也因此鏡頭的 `limit_*` 是 used_rect 那個更大的像素矩形，
鏡頭可以移出牆框、拍到牆外的空白外環；角色本身則被 `MapBoundary` 擋在牆內。

這是刻意選的做法，不是幫每一顆樹籬 tile 補碰撞多邊形：地圖範圍已經因為後續
的家戶／森林等擴建成長到遠超《規格書 07》原本規劃的院子範圍，樹籬圖塊在
整個地圖上散布超過 500 顆，逐顆補多邊形沒有必要——只要在遊玩區域最外圈擋
一圈整體邊界即可，院子內部的樹籬本來就只是視覺上的房子區隔，不需要
物理碰撞。

## PlaceAnchors 錨點

`Node2D/PlaceAnchors` 底下對應《規格書 07》的地點，錨點名稱就是
`Stats.SPEC`（`scripts/character/stats.gd`）與 `data/npc_schedule.json` 的
`place` 欄位直接引用的字串——**只有變更錨點名稱（識別字串）時**才需要這兩個檔案一起同步，
單純搬移 Marker2D 座標不會改變節點名稱、`resolve()` 也照常找到地點。
若未同步變更後的地點識別字串，`places.gd` 的 `resolve()` 會 `push_error` 且
靜默回傳 `Vector2.ZERO`。`loc_home_NN` 錨點是例外：`Stats.SPEC`／
`npc_schedule.json` 認的仍是抽象的 `"home"`，不直接對應這些節點名稱
——`places.gd` 的 `has_for()`／`resolve_for()` 依角色的 `home_location_id`
轉譯後才查到對應節點，而且錨點本身是執行期動態建立的（issue #825），
細節見《[[07_地點/家]]》。

家的錨點（`loc_home_NN`）不在下表——它們沒有畫進 `level.tscn`，由
`CharacterStatePersistence` 在角色進場時動態建立、離場時拆除，座標存在
`location.pos_x`／`pos_y`（issue #825，細節見《[[07_地點/家]]》）。

| 錨點 | 位置 | 對應 `location_id` |
| --- | --- | --- |
| `herb_shop` | `(-110, 90)` | `loc_herb_shop` |
| `tavern` | `(170, 50)` | `loc_tavern` |
| `pavilion` | `(70, -110)` | `loc_pavilion` |
| `god_stone` | `(20, 55)` | `obj_divine_stone` |
| `cemetery` | `(176, -112)` | `loc_cemetery` |
| `herb_field` | `(240, -112)` | `loc_herb_field` |

> [!note] 同一錨點多角色站位避讓（issue #657）
> `places.gd::resolve_for(character, place_name)` 會在錨點座標外加一個依角色
> id 雜湊算出的固定方向偏移（半徑 8px），不是回傳錨點原始座標本身。多個
> 角色被排到同一個地點（例如同時要去 `tavern` 吃飯）時因此會自然散開站，
> 不會完全疊在同一個像素上，也不需要引擎追蹤「這個地點現在站了幾個人」
> 這種主動式排位狀態。同一個角色每次呼叫都拿到同一個偏移（純函式、無狀態），
> 移動中的抵達判定才不會追著一個一直在動的目標跑。偏移產生後會用 NavGrid
> 驗證落點格可走，不可走就退回錨點座標——寧可重疊也不要走不到。
>
> 玩家不吃偏移：玩家站錨點原座標、NPC 固定偏移 8px 離開錨點，兩者距離恆
> 為 8px、永遠不會疊，也都在 TALK_RANGE 內。這包括 agent.gd 說服流程的
> waypoint indicator（`resolve_for(player, place)`，#415）——指標指向錨點
> 本身，引導玩家去「這個地點」，不是去某個 NPC 的偏移站位。手上沒有
> Character 的純座標查詢（debug 主控台、一次性座標查詢、販賣機選單距離
> 判斷）走不帶偏移的 `resolve()`。相近雜湊角度仍可能視覺貼近，屬已知取捨，
> 詳見 places.gd 的 `_overlap_offset()` 註解。

工作站見 [[工作站]]。商店（餐酒館／藥草鋪）綁在 `tavern`／`herb_shop` 這兩個
錨點本身，不是另外的場上物件，見 [[販賣機]]。涼亭（`Pavilion`）與天神之石
（`DivineStone`）目前是純視覺佔位（`Polygon2D`，無碰撞、無腳本），各自是
對應 `Marker2D` 的子節點、本地座標 `(0,0)`——座標只有錨點這一份，不會有
移動錨點時視覺物件沒跟著搬的問題。兩者在 MVP 的 `available_actions` 都是
泛用行動（`rest`／`talk`／`move`／`idle`），天神之石的話語輸入機制本身
另有 issue，不需要互動腳本就能滿足這則的範圍。

## TileMapDual 填色陷阱：atlas 座標不是任選的

`addons/TileMapDual` 是 dual-grid 自動拼接外掛。`TileMapDual`（world/隱藏層）
與其子節點 `Display`（實際可見層）是兩層——直接對 world 層呼叫低階的
`tilemap_set_cell`／`tilemap_set_cells_rect`（`tilemap_manage` MCP 工具）可以填，
但**填的 atlas 座標必須帶有效的 `terrain` 自訂資料**，否則 Display 完全不知道
怎麼畫，畫面會變成一片空白／viewport 底色。

查一顆 tile 的 `terrain` 值：

```gdscript
var td = tile_set.get_source(0).get_tile_data(Vector2i(col, row), 0)
td.terrain  # -1 = 無效（純視覺變體，不能拿來畫）／0／1 = 有效 marker
```

本專案這顆 16 格 atlas 只有兩顆是有效 marker，其餘 14 顆是自動拼接用的
視覺變體（邊界/轉角混色，terrain 皆為 -1，只會出現在 Display 層，不要拿來填 world 層）：

| atlas (col,row) | `terrain` | 意義 |
| --- | --- | --- |
| `(2,1)` | `1` | 有地形（草叢／樹籬視覺） |
| `(0,3)` | `0` | 空地（可走） |

**要開闊、全部可走的地面就填 `(0,3)`**；要畫樹籬/障礙的視覺才填 `(2,1)`——
但注意這兩顆圖塊在 `TileSetAtlasSource` 裡都沒有畫 collision polygon，
`(2,1)` 只是「看起來會擋路」，實際不會擋人，見上面「地圖邊界」那節。
踩過的坑：一開始誤填 `(0,0)`（`terrain=-1`）畫面全黑，改填 `(2,1)` 又把整塊
地填成滿版視覺障礙物——兩次都跑起來才發現。

## 改地圖／加錨點要開對場景檔：`main.tscn` 的 `Level` 是 `level.tscn` 的實例

`main.tscn` 裡的 `Node/Level` 是 `[node ... instance=ExtResource(...)]`，
本體定義在 `res://scenes/level.tscn`——`TileMapDual`／`NavGrid`／`PlaceAnchors`
全部是這個實例底下的節點。用 godot-ai MCP 直接對 `main.tscn` 開著的那份場景
操作 `/Node/Level/PlaceAnchors/...` 路徑（`node_create`／`tilemap_set_cell` 等）
看起來會成功、`scene_get_hierarchy` 也讀得到，但 `scene_save()` 存 `main.tscn`
時**不會把這些改動寫進磁碟**——它們是實例子節點的臨時記憶體狀態，
不是這個實例的 override，Godot 存外層場景時直接放棄未被登記為 override 的
實例內部改動。存檔呼叫回報成功、檔案大小/雜湊卻完全沒變，是這個問題的
症狀，容易誤判成別的環節出錯。

**正確做法：`scene_open("res://scenes/level.tscn")` 直接開本體場景來改**，
改完 `scene_save()` 存的是 `level.tscn` 自己，任何實例它的場景（目前只有
`main.tscn`）都會自動吃到新節點/新 tile，不用額外同步。
