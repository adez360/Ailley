# 記憶與睡眠反思

角色的記憶系統（《03 事件評估與記憶》L1-L4）與把「今天發生的事」轉成候選記憶的反思管線。設計依據見 [[api]] 的 `Memory`／`Agent` 條目，這則講整體資料流與設計理由。

`Memory` 子節點掛在共用場景本體 `scenes/agent.tscn`／`scenes/player.tscn` 上，
不是只手動擺在 `main.tscn` 那三隻測試角色身上（issue #209，2026-08-17 修正）——
`GameManager.spawn_character()` 直接 `instantiate()` 這兩個場景，場景本體缺了
這個節點的話，動態生成的角色 `character.gd::memory` 會是 `null`，
且不會有任何錯誤或警告，記憶系統對這種角色完全不會啟動。

## 資料流

```
角色做了某件事（對話結束／完成工作／第一次注意到陌生人）
        │
        ▼
Agent._push_daily_event(content)   純客觀事實句，不判斷正負面/重要性
        │  （DAILY_EVENTS_CAP=30，FIFO，睡前一次送出）
        ▼
Agent.request_sleep_reflection()
        │  PromptBuilder.build_reflection_envelope()
        │  → AIService.request(Policy.SCHEDULED)
        │  → AISchema.validate_reflection()
        ▼
逐筆 memory.add_candidate(content, importance, valence)
        │  importance 分級：<30 丟棄／30-59 L2／60-89 L3／90+ L4
        ▼
Memory.entries（L2/L3/L4，跨遊戲日走 decay_all() 衰減）
        │
        ▼
PromptBuilder._memory_block()：L2 依連結展開篩選、L4 固定全量帶進下一輪 dialogue／plan 的 context
```

## 為什麼 importance 由 LLM 評分，不是引擎算公式

《00》原則二：「引擎只給事件，不給情緒。引擎報告發生什麼，AI 決定這算不算一回事。」純物理強度公式（例如「流血量」「金額」）會讓記憶庫只記得住有具體數字可算的事件，社交/情感類事件永遠沒有數字撐得起分數——這違背「養一個有記憶的夥伴」的初衷。改成 LLM 在睡眠反思時自己評分，跟《03》§3「重要度評分——由 LLM 自行評分，引擎不做加權」一致。

同一個原則也決定了事件觸發點只寫客觀事實句（「你跟 X 講完話了」），不寫「你跟 X 度過了愉快的時光」這種帶主觀判斷的句子——valence／importance 完全留給反思階段的 LLM。

## 事件觸發點

都是「現在真的會觸發」的既有流程，不是為未落地系統預留的空接口：

- **對話結束**（`Agent.exit_conversation()`）：讀 `_conversation.target`/`initiator` 找出對方是誰，`super()` 清空 `_conversation` 前就要讀；`location_id` 用即時位置反查（`_resolve_actual_place()`，#426），不是 `current_place`——指名對話（direct-target talk）沒有 `current_place`
- **完成一段工作站工作**（`Agent._on_work_finished()`）：事件句刻意不寫賺了多少錢——這個鉤子在工作被提早中斷（半途走開）時也會觸發，那種情況沒有真的撥款（見 `character.gd` 的 `_run_work()`／`_end_work()`），寫死金額會變成不一定為真的事實句
- **第一次注意到陌生人**（`Agent._on_spotted()`）：只在 `!relationships.has_met()` 成立時觸發，跟「！」反應共用同一個判斷
- **被攻擊**（`Agent._on_attacked()`）：`location_id` 用 `_place_before_interrupt` 快照的即時位置反查（#426）——移動途中被攻擊時 `current_place` 是還沒走到的目的地，不是事發當下的實際位置
- **吃／喝**（`_pursue_eat_task()`／`_pursue_drink_task()`，#354）
- **給／收到物品**（`_pursue_give_task()`，雙向各記一筆，#354）
- **被說服／拒絕勸說**（`_resolve_pending_persuade()`，#354）
- **進入新的生理／社會 condition**（`Character._set_condition()`，#354；讀檔重建既有狀態時不記，只記新發生的）
- **搬運／被搬運、放開／掙脫搬運**（`Character.start_haul()`／`stop_haul()`，#354）
- **聽到天神之石的聲音**（`Agent.hear_god_stone()`）

## L1 跟 `_daily_events` 是兩回事

`Memory.l1` 是固定 8 條的滾動視窗（FIFO），`Agent._daily_events` 是「睡前都留著、反思完清空」的緩衝區，語意不同，不共用同一份資料。目前沒有任何呼叫端呼叫 `Memory.push_l1()`——L1 的實際使用時機（例如當作對話的短期上下文）留給之後需要的功能自然接上，這輪只確保這個函式本身正確。

## 觸發時機：角色入睡時自動觸發

`agent.gd::_reevaluate_once()` 偵測「這一輪重算進來時是不是在睡」跟「重算完是不是變成 `sleep`」這兩個時間點的落差（`_was_sleeping` → `current_state == "sleep"`），抓到剛入睡的轉換瞬間就清空 `Memory.l1`、呼叫 `request_sleep_reflection()`（fire-and-forget，不 await，避免同步函式卡在一次網路往返上）。`debug_console.gd` 的 `reflect <name>` 指令仍然保留，作為手動測試用途，但不再是唯一路徑。

## 記憶注入 prompt：只放 content，不放引擎內部欄位

`PromptBuilder._memory_block()` 給模型的只有 `content` 字串陣列（`recent`＝L2、`core`＝L4），不含 `valence`／`importance`／`decay_value`——模型只需要「記得什麼」，不需要知道引擎怎麼替這則記憶打分或衰減。L4 固定全量帶入（核心記憶永不遺忘）；L2 依連結展開篩選（#360，《13》§三 MVP-1）：`related_npcs` 跟呼叫端傳入的在場角色有交集，或 `location_id` 等於呼叫端傳入的目前所在地點，才帶入——兩個條件由呼叫端（`agent.gd`）整理好傳進來，這個檔案不伸進 `current_place`／`visible` 等內部欄位。地點比對只在呼叫端傳入的「目前所在地點」**非空**時才成立；傳入空字串（`talk`／追逐目標這類無地點任務，`current_place` 本來就是空的）時一律不比對地點，不會因為記憶的 `location_id` 剛好也是空字串就誤判成「同一個地點」而帶入。篩選端（讀取這一側）的「目前所在地點」刻意沿用 `current_place`，不是即時座標反查——`current_place` 是目前任務的目的地，跨場景一致比對才有意義（跟 `get_state_snapshot()` 送給 LLM 的 `place` 欄位同一個來源，不另外定義一套「現在在哪」）。改用真實座標反解出的地點來篩選，會讓大多數寫入時打的標籤（下面這段）跟讀取時比對的標準變成兩套不同語意，兩者對不上，比現在的覆蓋率落差更糟——這個決定跟寫入那一側（下面這段）各自獨立，兩者不必用同一個座標來源。

寫入記憶那一側（`_push_daily_event()` → 睡眠反思 → `add_candidate()`）的 `location_id`，多數呼叫端沿用 `current_place`；但 `_on_attacked()`（`_place_before_interrupt` 快照）與 `exit_conversation()` 改用即時座標反查 `Agent._resolve_actual_place()`（`PlaceAnchors.resolve_from_position()`，issue #426）——這兩處的 `current_place` 本身不可信：移動途中被攻擊時 `current_place` 是還沒走到的目的地，`exit_conversation()` 處理指名對話（direct-target talk）時 `current_place` 從頭到尾是空字串。這兩處記錄的是「事情發生當下人真正站在哪」，跟上一段篩選端維持 `current_place` 的決定不衝突：篩選端比對的仍是任務目的地語意的 `current_place`，多數記憶的 `location_id` 也是同一套語意，只有這兩個原本記錯或記不到地點的呼叫端換了資料來源，覆蓋率變好、沒有引入新的兩套系統互相對不上的問題。`Memory.mark_retrieved()` 只對真的被選中帶入的那幾條 L2 記憶呼叫，不是整桶。放在 `payload.context` 不放 `system`，因為 `system` 段要逐字元不變才能吃到 provider 的 prompt cache，記憶這種會隨事件變動的內容不該進 system。

記憶已接進角色存檔（#170）：`Memory.get_save_data()`／`load_save_data()`
只存 L2／L4，跟 [[存檔]]「記憶已接進角色存檔」是同一份設計，細節看那篇。

## 墓碑欄位 life_highlights（issue #384，《規格書 09》§4-2）

`Memory.get_life_highlights()` 從 L4 核心記憶彙整重大事件成一段文字陣列，
純資料格式化，不經 LLM 潤飾——L4 本來就是《03》定義的「重大事件」分級
（importance 90+，永不衰減，上限 `L4_CAP`），不需要另外維護一套「重大事件
流」判斷邏輯。依 `created_day` 由舊到新排序，格式化成「第 D 天，`<content>`」，
`content` 是 `add_candidate()` 存進來時就修剪過的原始事實句，這裡不做任何
語氣潤飾或摘要。

> [!note] 已實作彙整函式，尚未接上死亡流程
> `Agent.life_highlights`（#381）目前沒有任何呼叫端會寫入——`Character._die()`
> 沒有呼叫 `memory.get_life_highlights()` 把結果存進這個欄位。#384 範圍只涵蓋
> 「純資料彙整」這一半，死亡當下由誰、在哪個時間點呼叫並寫回 `life_highlights`
> 是待補的後續動作，尚未列入任何 issue。

## 不做（這輪範圍外）

- 向量檢索（《03》§7，完整版才需要，MVP 用 L2/L4 全量 + 標籤/關鍵字取代語意檢索）
- `personality_delta`（依賴 #117 人格資料，還沒接上，沒有東西可以調整）
- 酒精導致記憶模糊（《03》§6，另一則功能，這輪沒做）

## 已知的規格內部矛盾

《03》§3 分級表寫「L2：30-59...三日後若未被檢索則淘汰」，跟 §4-1 的衰減公式（基礎衰減率 3/天，100 分要約 33 天才歸零）數字對不上。已列入《99》P-15 待釐清，目前 `Memory.decay_all()` 只實作 §4-1 的衰減公式，沒有另外的「三日」規則。
