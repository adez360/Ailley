# 測試計畫

模組化手動測試計畫（issue #582，《99》P-61，《17》「模組化手動測試計畫」一節）。
由工程師手動測試玩法是否通順、功能是否正常，跟《[[自動化測試]]》互補、不是取代——
那邊抓「不需要活場景的純函式邏輯有沒有被弄壞」，這裡抓「遊戲真的跑起來時，順不順、
LLM 講話自然不自然、UI 對不對」，兩者環境限制不同，沒有一種測法能同時涵蓋。

## 模組怎麼劃分

依系統為主軸，分類直接沿用《[[自動化測試]]》「涵蓋範圍」表跟《17》MVP 範圍表已經在用
的同一組系統邊界（角色數值／記憶／地點行動／社交／經濟／UI／化身者與死亡系統），不是
另外發明一套分類——兩邊分類一致，之後有 bug 時比較容易判斷「這個洞該補自動化測試還是
只是這次手動抓到的一次性問題」。

**額外加一條「端到端流程」**，跟系統模組是不同軸線、服務不同目的：模組 checklist 抓的
是「這個系統的每個功能點有沒有正常運作」，測得再仔細也測不出銜接處的問題——例如死亡
流程本身沒 bug、對話回應本身沒 bug，但玩家在等 LLM 回應時等太久導致整段體驗卡頓，這種
「串起來玩順不順」的問題只有走一次完整流程才會浮現。兩條軸線都要，不是二選一。

此清單涵蓋《17》MVP 目標範圍內的功能；《17》裡標 ☐（尚未落地）的項目測試時直接略過，
不算未通過，等該功能真的做完再開始測。

## 各模組 checklist

### 1. 地基層——建角與存讀檔

- [ ] 建角面板三分頁（基本／個性／外觀）都能填完、送出後正確生成一個新角色
- [ ] 決策來源三選一（Local／Cloud／Human）各測一次，角色都能正常做出決策
- [ ] 玩一段時間後存檔、關遊戲重開，角色狀態／金錢／物品／記憶都還在
- [ ] 角色庫投放既有角色到世界，位置與狀態正確還原

### 2. 生理與心理層——數值與記憶

- [ ] 8 種情緒與生理衍生 `conditions`（見《02》）隨數值變化正確觸發／解除
- [ ] `eat`／`drink`／`sleep`／`nap`／`rest`／`wash` 各自對應的數值確實變化
- [ ] 睡眠反思後新增記憶、`personality_delta`（若有）有合理套用
- [ ] L1／L2 記憶（標籤／關鍵字／連結展開）能在後續對話或決策的 reasoning 裡看出被引用
- [ ] L3／L4 語意檢索尚未實作（見《17》），略過

### 3. 世界與行動層——地點與經濟

- [ ] MVP 8 個地點（家／藥草鋪／餐酒館／涼亭／天神之石／藥草叢／森林／墓園）都能移動
      抵達，`available_actions` 符合《07》定義
- [ ] 餐酒館／藥草鋪正式互動選單（issue #572）走一輪購買
- [ ] `gather`（採集）、`perform`（表演，含玩家打賞與 NPC 自主打賞兩條線）各測一次成功
      與一次失敗路徑（例如沒有 `instrument` 觸發表演門檻擋下）
- [ ] `hunt_small`／`hunt_large` 待落地後補測，目前尚未開工（見《17》），略過
- [ ] 物品 `decay`／`durability` 隨時間正確變化，跨過《08》§6 級距時效果符合定義
      （腐壞扣 health、耐久歸零自動移除）

### 4. 社交層

- [ ] `talk`／`give`／`persuade`／`shout`／`murmur` 各測一次成功與一次判定失敗
- [ ] `appointment` 約定：時間到雙方在場、事實句正確送達；一方爽約時的處理符合《10》§5.5
- [ ] 跟隨系統：跟隨中對象移動時正確跟走，主動停止跟隨後不再跟
- [ ] 群體對話尚未實作（見《17》），略過

### 5. UI 層

- [ ] 角色資訊面板三分頁（狀態／今日／物品）開關、切分頁、面板開著時換角色，資料都正確
      刷新（對照《15》§2-3／§2-5／§2-6）
- [ ] 天神之石輸入框送出後，範圍內角色有反應；地點事件記錄能看到歷史紀錄
- [ ] 六種玩家狀態小圖標尚未實作（見《17》P-68），略過

### 6. 化身者與死亡系統

- [ ] Player 操控走位正常，能觸發跟 Agent 相同的動作集合
- [ ] 昏迷 → 30 分鐘無人搬走 → 轉入死亡流程，全程符合《技術/昏迷狀態機制》
- [ ] `bury`／安葬、墓碑內容（含無名碑）正確顯示
- [ ] 復活：24 小時免費窗口內／超時付費兩條路徑各測一次

## 端到端流程通關

一次不中斷地玩過：**建角 → 日常行動（生理／經濟類動作至少各跑一次）→ 社交（至少一次
多輪對話）→ 死亡與復活其中一條路徑**。抓的是模組 checklist 測不出來的銜接處問題，不是
逐項功能覆蓋，走一次完整流程即可，不用每個分支都試。

## 執行頻率與負責人

- **各模組 checklist**：PR 改到該模組時，作者在請 review 前跑一次自己動到的模組，不需要
  每個 PR 都測全部模組——跟 `.claude/CLAUDE.md`「PR 產權人是作者」同一個邏輯，動到那塊
  的人最清楚要驗什麼。
- **端到端流程**：專題發表 demo 前至少跑一次（建議排在展示彩排前），任一工程師執行即可，
  不需要全員各自重跑。
- 一律**工程師本人手動執行**，不掛自動化、不假手他人代跑——這是跟自動化回歸測試互補的
  手動驗收層，重點是人的體感判斷（順不順、講話自然不自然），交給別人代跑會失去這一層
  存在的意義。

## 通過標準

| 面向 | 標準 |
| --- | --- |
| 功能面 | 沒有 crash／console 出現 script error／動作沒有預期效果（例如 `buy` 判定成功卻沒扣款、沒加物品） |
| 體驗面 | 操作起來順、LLM 輸出內容合理不跳戲、UI 沒有明顯卡頓或誤導性顯示 |

體驗面沒有量化標準，由執行者主觀判斷；覺得不順就記下來（哪個模組、什麼情境、哪裡卡），
不強求打分或量表。

## 跟其他驗收機制的分工

- **跟《[[自動化測試]]》**：那邊測不需要活場景／`GameClock` 的純函式邏輯（環境限制見該
  筆記），這裡測活遊戲裡跑起來的整體行為，兩者互補，同一個 bug 可能兩邊都測不到——這正
  是為什麼還需要這一層手動測試，不是自動化測試的替代品。
- **跟《16 打包與發布規格書》／《99》P-43 上架前 QA checklist**：那份管「打包出來的
  build 能不能正常安裝、跑起來、sidecar 連線」，假設遊戲邏輯本身沒問題，只驗證打包這層；
  這裡管「遊戲本身的功能與體感」，假設遊戲已經正常執行，驗證的是裡面的內容。兩者不重複，
  QA checklist 是上架前的最後一關，這份是開發過程中持續在跑的驗收。
