# 自動化測試

`Ailley/tests/*.gd` 底下的 `McpTestSuite` 子類，透過 godot-ai MCP 的 `test_run`
執行、`test_manage(op="results_get")` 拿結果（見 `Ailley/CLAUDE.md`）。

## 寫法慣例

繼承 `McpTestSuite`、加 `@tool`，覆寫 `suite_name()`，方法名 `test_*` 就會被
runner 收集執行。用 `track(obj)` 註冊手動建立的物件（`Character`／`Stats`／
`Inventory`／`CollisionShape2D` 等），runner 會在每個測試跑完自動釋放，不用
自己管生命週期。斷言方法見 `test_suite.gd`：`assert_true`／`assert_eq`／
`assert_gt`／`assert_has_key`／`assert_contains` 等。

角色類物件一律用 `Script.new()` 手動組（不 `add_child()` 進場景樹），需要的
子元件（`collider`／`inventory`／`stats`）手動塞值卡位——跟直接在編輯器裡
`instantiate()` 一份 `agent.tscn` 相比，這樣可以精準控制只測到目標函式本身，
不會因為場景相依的其他節點沒接好而混進不相關的失敗。

## 核心限制：這是編輯器工具環境，不是活的遊戲

`test_run` 執行在編輯器的 `@tool` 環境，**沒有活的 `SceneTree`、autoload 也
沒有實例化**。這代表三類東西測不到：

1. **直接讀 autoload 單例的函式**——`GameClock.day`／`GameClock.hour` 這類
   引用會解析到一個沒有被正常初始化的物件，一碰就是
   `SCRIPT ERROR: Invalid access to property 'hour' on a base object of
   type 'Node (GameClock.gd)'`（`test_corpse_decay.gd` 實測踩過）。
   例：`Character._die()`、`Memory.add_candidate()` 都直接讀 `GameClock.day`。
2. **需要查詢真實場景樹的函式**——`get_tree()`、`get_first_node_in_group()`、
   `Places.resolve()`、`Agent._find_vending_machine_at_place()` 這類在沒有
   場景打開時要嘛回傳空、要嘛直接噴錯。例：`Character.bury()` 的地點/墓碑
   格數判斷、`buy`／`work_at` 的 hard rule、`GameManager.deploy_from_library()`。
3. **`PackedScene.instantiate()` 生出來的非 `@tool` 腳本節點**——`test_run`
   的 `@tool` 環境下，`load(".tscn").instantiate()` 對場景裡任何沒標 `@tool`
   的腳本一律回傳 placeholder instance（`Invalid access to property`／
   `Attempt to call a method on a placeholder instance. Check if the
   script is in tool mode.`），**跟開哪個場景、有沒有 `add_child()` 掛進
   場景樹都無關**——`instantiate()` 那一刻就已經是 placeholder，實測過就算
   完全不掛進任何樹、只是呼叫完馬上存取屬性也一樣噴錯（issue #624，
   `test_shout_reaches_player.gd` 原本用 `player_scene.instantiate()` 踩到）。
   `Script.new()`（不透過 `PackedScene`）不受影響，回傳的是正常可用的實例——
   這正是上面「寫法慣例」一律用 `Script.new()` 手動組的另一個理由，不只是
   為了精準控制測試範圍。
   需要 `_ready()` 才會解析的 `@onready` 子節點（例：`Player.bubble`），改成
   `Script.new()` 建好角色後手動把子元件塞進對應欄位卡位；子元件自己內部
   若也有 `@onready`（例：`Bubble.box`／`Bubble.label`），一併手動塞值。
   **`_ready()` 裡對欄位的初始設定也要一併手動補上**，不能只補 `@onready`
   解析的部分——`Bubble._ready()` 把 `visible` 蓋成 `false`，跳過 `_ready()`
   的話 `visible` 會停在 `CanvasItem` 預設的 `true`，`Bubble.say()` 內部
   「還沒顯示才要渲染」的判斷會直接誤判成「已經在顯示」，訊息進了佇列
   但永遠不會真的被渲染出來——不是喊 `is_speaking()` 沒事就代表真的測到了
   渲染邏輯，這種情況下它會因為 `visible` 一開始就是 `true` 而巧合回傳
   對的答案，掩蓋掉 `label.text` 其實從沒被寫入的事實。

沒有計畫在 test_run 裡注入假的 GameClock 或假的場景樹——那類函式改用
`project_run` + `game_eval` 在編輯器裡對活的遊戲場景驗證，把驗證方式與結果
寫進該系統自己的技術筆記（例：[[記憶與睡眠反思]]、《規格書09》死亡系統），
不硬塞進 test_run 套件湊測試數量。這是 issue #387（corpse_decay）跟 #583
（擴大回歸測試覆蓋）都採用的既定做法。

## 涵蓋範圍（issue #583）

| 模組 | `Ailley/tests/*.gd` | 備註 |
| --- | --- | --- |
| 角色數值 | `test_stats.gd` | `Stats` 純數值函式（`_apply_drift`／`get_value`／`set_value`／存讀檔）不依賴場景，可測；`_ready()` 綁定 `GameClock.time_changed` 觸發漂移的那段不在涵蓋範圍（沒有場景樹，`_ready()` 不會跑） |
| 記憶 | `test_memory.gd` | `add_candidate()` 讀 `GameClock.day`，改用手動組 entry 繞過，測其餘邏輯；`add_candidate()` 本身見下方 game_eval 驗證 |
| 社交 | `test_persuade_pending.gd`、`test_give_attack_on_player.gd`、`test_shout_reaches_player.gd` | `try_record_pending_persuade()` 純狀態機；送達後的事實句注入依賴 `_now_minutes()`→GameClock，測不到。`test_shout_reaches_player.gd` 的 `Player` 與 `Bubble` 都改成 `Script.new()` 手動組＋手動塞值（見上方限制 3），不再 `instantiate()` `player.tscn` |
| 地點行動 | （無新增，見下方 game_eval 驗證） | `Places` 本身是場景節點、`buy`／`work_at` 的 hard rule 要查場景樹，改走 `project_run`＋`game_eval` |
| 化身者 | （無新增，見下方 game_eval 驗證） | `GameManager.deploy_from_library()` 是 autoload＋要真的 instantiate 場景，改走 `project_run`＋`game_eval` |
| 死亡系統 | `test_bury.gd`、`test_corpse_decay.gd`（既有）＋下方 `_die()` game_eval 驗證 | `_die()` 本身跟 `add_candidate()` 同一種 GameClock 限制 |

`test_run` 全套件跑過（main.tscn／main_menu.tscn 開哪個都一樣）：63 條全過。

## GameClock／場景相依部分的 game_eval 驗證（2026-08-27）

以下用 `project_run` + `game_eval` 對活的 `main.tscn` 場景實測過一輪，
結果符合預期：

- **`Memory.add_candidate()`**：importance 10（<30）回傳空字典（丟棄）；
  importance 40 進 level 2、`created_day` 正確蓋上當下 `GameClock.day`；
  importance 95 進 level 4。分級門檻與 `created_day` 蓋值都正確。
- **`Character._die()`**：呼叫後 `is_dead` 從 `false` 翻成 `true`、
  `death_cause`／`death_day`（＝當下 `GameClock.day`）正確寫入，
  `conditions` 清空只留 `petrified`，`corpse_decay` 歸零——跟《規格書09》
  §1 死亡流程圖一致。
- **`GameManager.deploy_from_library(id, true)`**：對一筆手動組的 library
  entry 呼叫，回傳值是 `Player` 型別、`character_id` 正確設定、entry 的
  `deployed` 旗標翻成 `true`，且場景裡「player」分組維持只有一個節點
  （舊的化身者正確被移出分組並釋放）——化身者的核心投放機制沒有壞掉。
- **`Places.resolve()`／`has()`**：對已知地點（`tavern`）回傳正確座標，
  對不存在的地點回傳 `false`／`Vector2.ZERO`。
- **`buy` 的 hard rule**（`Agent.resolve("buy", ...)` → 內部
  `_find_vending_machine_at_place()`）：站在販賣機旁呼叫，正確找到機器、
  依商品是否存在往下判斷（測試用的 `bread` 不在該機台商品清單，回傳
  「販賣機裡沒有這個商品」）；站在極遠處呼叫，正確回傳「找不到販賣機」——
  距離判定跟商品判斷是分開的兩關，都如預期運作。

這些不是 `Ailley/tests/*.gd` 裡的自動化測試（不會在下次 `test_run` 自動重跑），
是這次擴大回歸測試覆蓋範圍時，針對「框架測不到」的部分做的一次性活場景
驗證紀錄，跟 `test_corpse_decay.gd` 對死亡分支的既有處理方式一致。
