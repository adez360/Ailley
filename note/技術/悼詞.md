# 悼詞

玩家對已安葬角色留一句話（#385，《規格書09》§4-5）。issue 本身拆兩段做：這次只做表單邏輯與讀寫（「R 先做出功能版」），排版與視覺留給後續——目前沒有查看完整墓碑內容（`last_words`／`life_highlights`／既有悼詞列表）的面板，點擊已安葬角色只彈出一個輸入框。

## 觸發與面板

`PersistentUI/EpitaphInput`（`hud.tscn`）是獨立的 `CanvasLayer`（`Panel > TitleBg/TitleLabel/Input/StatusLabel`），版面數值抄自 `GodStoneInput`，但不是它的場景實例——一開始用 `node_manage(op="duplicate")` 複製節點省事，結果 `.tscn` 留了 `instance=ExtResource(god_stone_input.tscn)`，等於把跟悼詞無關的 `god_stone_input.tscn` 結構跟這裡耦合在一起（CodeRabbit review 抓到，PR #622）：god_stone_input.tscn 之後若改動節點結構，會不小心波及這裡。改成 `node_create` 逐個節點手動建立，數值照抄，不吃這個耦合。開關機制跟 `status_panel.gd` 同一套：`_input()` 而非 `_unhandled_input()`，不 `set_input_as_handled()`（空地點擊要繼續傳給 `selection.gd` 取消選取），共用 `selection.character_at()` 找點到誰——但只對 `is_buried == true` 的角色開面板，未安葬的屍體沒有墓碑可以留言（跟《規格書09》§4-3「未安葬不顯示遺言/生平」同一種「沒有墓碑」的語意，延伸到悼詞）。

`LineEdit.max_length = 40`，`text_submitted` 送出，`Esc` 或點面板外關閉。作者一律是操作者本人（玩家），不是任意角色——這個面板是玩家點擊觸發的，不是 AI 任務，NPC 目前沒有對應的 `epitaph` LLM 動作（不在 `IMPLEMENTED_ACTIONS`，是完全獨立的後續工作）。

`_on_submitted()` 只在真的要關面板的路徑（成功、或本來就沒東西可寫）才清空 `input`；`write_epitaph()` 回傳失敗原因時把送出的內容放回 `input.text` 並保留焦點，不清空（CodeRabbit review 抓到，PR #622）——原本一進來就 `input.clear()`，寫入失敗（例如 `grave_epitaphs` 的 40 字 `CHECK` 約束擋下）時面板留著開但玩家剛打的字已經沒了，得整句重打。

## 讀寫走 SQLite，不是 JsonSaveService

《99》P-50 已定案：`epitaphs` 是「一對多」，刻意留在 SQLite（`grave`／`grave_epitaphs` 兩張表），跟 `last_words`／`words_to_creator`／`life_highlights` 這些「一份墓一筆」欄位分開存（那些走 JSON）。`GraveEpitaphPersistence.gd`（`class_name`，但被 `epitaph_input.gd` 用 `preload()` 引用，不是靠全域識別字——見下方「godot-ai 踩坑」）：

- `ensure_grave_id(corpse)`：找 `grave.npc_id = corpse.character_id` 對應的 `grave_id`，沒有就建一筆。回傳 `-1` 代表失敗或未安葬。
- `write_epitaph(author, corpse, content)`：確保作者有 `npc` 記錄（呼叫 `CharacterStatePersistence.sync_character()`，玩家也會被收進 `npc` 表，不是只有 AI 角色才有），再 upsert 進 `grave_epitaphs`（`UNIQUE (grave_id, npc_id)`，每人對同一座墓限 1 條，覆寫後舊的不保留）。

> [!important] 稽查 #385 時發現：`grave`／`location` 兩張表在此之前完全沒被寫過
> `bury()`（character.gd）只改 Character 節點上的字串欄位（JSON 存檔），從沒有任何呼叫端 `INSERT INTO grave`——`grave.grave_id` 是 SQLite 自動遞增的 `INTEGER`，跟 `Character.grave_id`（`"grave_%s" % character_id` 字串哨兵值）完全是兩個獨立概念，只是剛好同名。`grave_epitaphs.grave_id` 外鍵需要一筆真的存在的 `grave` 列，所以這裡補上「第一次留悼詞時懶建立」（2026-08-27 拍板，不碰 `bury()`／`_die()`，改動範圍留在悼詞這條路徑本身）。
>
> 建 `grave` 列時又撞到第二層：`location_id` 外鍵指向 `location(location_id)`，但 SQL 的 `location` 表現況只有 `CharacterStatePersistence._resolve_home_location()` 懶建立的 `home_001` 佔位列——`loc_cemetery`（《規格書09》§6 寫的正式 id）從沒被建過，SQL 的 `location` 表根本沒有跟 `places.gd`／`PlaceAnchors` 的真實世界地點同步。照抄同一招：`GraveEpitaphPersistence._ensure_cemetery_location_id()` 找不到就懶建立一筆最小可用的佔位列。
>
> `grave` 表其餘欄位（`death_cause`／`last_words`／`words_to_creator`）故意不填：這幾欄跟 JSON 存檔重複、沒有任何讀取端使用（P-50 已定案），schema 本身都有 `DEFAULT`，不補值不影響功能。

## godot-ai 踩坑：`script_create` 有時回報成功卻沒真的寫到磁碟

開發這則時實測到：對 `epitaph_input.gd` 呼叫 `script_create`（含中文註解、無 `class_name`）連續兩次都回傳 `"committed": true`、`"diagnostics": []`，但檔案在磁碟上完全不存在（`ls` 查無此檔），導致後續 `script_attach` 一直報 `RESOURCE_NOT_FOUND`。換用 `filesystem_manage(op="write_text")` 寫同樣內容則正常落地。`GraveEpitaphPersistence.gd`（有 `class_name`）用 `script_create` 反而正常——目前無法穩定重現觸發條件，懷疑跟内容大小或連續呼叫的時序有關。**之後新增腳本檔案若 `script_attach`／`preload` 找不到檔案，先用 shell 確認檔案是否真的落地，別預設 `script_create` 回報成功就代表寫入成功**；`write_text` 目前實測更可靠。

## 驗證

用 godot-ai `game_eval` 端到端跑過（`project_run` → 切到 `main.tscn` → 直接呼叫 `_open()`／`_on_submitted()`，因為模擬滑鼠點擊事件在 `_input()` 收不到——`status_panel.gd` 的既有點擊機制用同樣的合成 `InputEventMouseButton` 測也一樣收不到，是這個測試環境的限制，不是新程式碼的問題；世界座標／畫面座標的換算與 `get_pick_rect()` 命中判定已經另外用純數學驗證過一致）：

- 已安葬角色 `_open()` → 面板正確開啟，讀到對應角色；場景改成獨立節點後重測一次，`Panel` 底下確實只有 `TitleBg/TitleLabel/Input/StatusLabel` 4 個子節點，沒有重複
- 送出悼詞 → `grave`／`grave_epitaphs` 兩張表都正確寫入（`grave` 懶建立成功，`location` 懶建立成功）
- 同一人對同一座墓再送一次 → `UPDATE` 覆寫既有列（`epitaph_id` 不變、`content`／`updated_at` 更新），不是新增一列
- 送出超過 40 字的內容（繞過 `LineEdit.max_length` 直接呼叫 `_on_submitted()`）→ `grave_epitaphs` 的 `CHECK (LENGTH(content) <= 40)` 正確擋下、`write_epitaph()` 回傳 `WRITE_FAILED`，面板留著開、`input.text` 保留剛才打的內容、資料庫裡的舊值沒被動到；接著送出一則合法長度的內容 → 正常寫入成功，確認失敗那次沒有讓後續寫入跟著壞掉
- 空白/純空白字串送出 → 面板關閉，不寫入、不報錯
- 點擊存活角色 → `is_buried == false`，面板不會開啟
