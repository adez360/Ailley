# changelog

AI 專用。**筆記庫裡唯一可以寫「原本是什麼」的地方。**

其他地方（`技術/`、`ai/api.md`、`交流/`）一律只寫現況：東西改了就把舊的那段刪掉，
不是在旁邊加註。被刪掉的決定如果日後可能有人再提一次，就記到這裡 ——
查資料的人不會讀到過期內容，吵完的事也不會繞回來。

## 記什麼

```
記   決定被推翻      （原本 X → 現在 Y → 為什麼換）
     方案被否決      （考慮過 X，因為 Y 不做）
     整篇被刪的筆記  （它裝過什麼、結論搬去哪）
不記 新增功能、修 bug、重構   → git log 就夠了
     還沒拍板的討論           → 那在 `交流/`
```

一則就是一個決定的來歷，日期倒序。**不要寫成每日工作日誌。**

## 2026-08-17

### 關係只留 `trust`，好感／熟悉／虧欠三維整個拿掉

- **原本**：`relations` 是 4 維數值（`affinity`／`trust`／`familiarity`／`debt`），
  理由是「單一好感度做不出『我討厭他，但我信任他的專業』」。
  `conversation.gd` 講完一場加 `affinity +3`，`DialogueLines` 依好感挑開場／收尾句，
  `prompt_builder.gd` 把 `affinity` 送進 LLM payload
- **現在**：只留 `trust`（persuade 讀它算成功率），另加 `appearance_cache`
  （《99》P-08 的外觀快取）。台詞不再分親疏，payload 送 `trust`，
  對話結束只記 `note_meeting()`
- **為什麼**：全庫查過一輪引擎消費者，那三維從沒被任何公式讀過，只被寫入再餵給
  AI 看，不符合《00》原則三。好感、熟悉、虧欠交給《03》記憶系統自己記自己判斷，
  不用另一組引擎數值重複做同一件事
- 連帶：`trust` 不拿來當親疏門檻——它是信任不是好感，混用等於把規格書
  刻意拆開的兩件事又併回去

## 2026-08-13

### Godot 端不再保留打 `poc_village_sim` 的接口

- **原本**：`poc_village_sim` 定位是 R&D／驗證，繼續開發但**保留 HTTP 接口給
  Godot 端**；Godot 這邊有 `village_sim_client.gd`／`village_sim_decision.gd`／
  `village_sim_locale.gd` 三支，`Agent` 上還掛著 `village_ai_enabled`／
  `poc_character_id` 兩個 demo 用的 `@export`，主控台有 `village_ai`、
  `village_ai_act` 兩個指令
- **現在**：Godot 這一端整條移除，LLM 一律走 `AIService`。
  `poc_village_sim` 本身不動，它是本機的獨立 Python 專案
- **為什麼**：那條線混在正式的角色與主控台程式碼裡，容易被誤認成正式機制；
  它繞過任務池／仲裁器直接動角色，跟行程表兩個機制互相覆蓋。
  出貨架構已拍板走 Godot ↔ Sidecar，這條線不會長成出貨的樣子
- **結論搬去哪**：`技術/LLM 串接與 AI 服務層` 只留下還在影響正式線的兩件事——
  Godot `Stats` ↔ poc `physiology` 的方向對照（GDScript 重寫要照著翻）、
  以及實測 2.5-4 秒的延遲與體感解法

## 2026-08-10

### 鏡頭不再掛在 Player 底下

- **原本**：`Camera2D` 是 Player 的子節點，跟隨靠父子關係達成，不用每幀腳本 ——
  這一點原本被當成優點寫在筆記裡
- **現在**：`Camera2D` 移到 `main.tscn` 的世界層，持有一個 `_target`，
  每個物理幀對齊它的座標
- **為什麼**：要讓鏡頭跟著「被選取的角色」。掛父子關係就得在執行期 reparent，
  而且**鏡頭會跟著對象一起被移除** —— 角色離場時鏡頭就沒了。
  改成持有參照之後，對象失效退回玩家是三行事
- **代價**：多一個每幀的座標指派。平滑仍然是 `Camera2D` 內建的，腳本不插值

### 滑鼠選取否決 physics object picking

- **考慮過**：`input_pickable` + `mouse_entered` / `input_event`，Godot 的內建做法
- **決定**：自己拿目前影格的矩形比對游標位置
- **為什麼**：角色的碰撞形狀只有腳下半徑 6 的小圓（還往下偏 6px），
  照它算**點頭部會落空**，而人本來就往頭上點。
  要修就得在 `player.tscn` 與 `agent.tscn` 各加一個 `ClickArea` 與一層新的碰撞層；
  更麻煩的是 `Vision` 是 `Area2D` 而它的 `input_pickable` 預設為 true，
  半徑 5 格的視野圈會先把游標吃掉，還得逐個關掉
- **代價**：沒有物理遮蔽判定 —— 但這個遊戲不需要「被牆擋住就點不到」

## 2026-08-08

### `character_id` 用 UUID，否決 `<owner>/<local_id>` 命名空間

- **考慮過**：`<owner>/<local_id>`（例如 `adez360/agent`）。可讀、擁有權不必查表、
  存檔 grep 得到、錯誤訊息與手寫 json 都不用改
- **決定**：UUID v4，擁有者改成角色存檔的一個欄位
- **為什麼**：唯一性的**來源**。命名空間把唯一性押在一個現在不存在、
  日後幾乎一定會被真實帳號系統取代的 `<owner>` 上 —— 那時所有既有 id 都要遷移。
  這跟 `relationships.gd` 早就寫下的理由同構：拿會變的東西當 key，改名就等於失憶；
  owner 也是會變的東西，把它塞進 key 只是把同一個錯誤往上搬一層
- **硬性理由**：Godot 節點名不接受 `/`，會靜默換成 `_`。
  `character.gd` 拿兩個 id 組 `Conversation_%s_%s`，
  `adez360/agent` + `bob/agent2` 與 `adez360/agent_bob` + `agent2` 會撞成同一個名字
- **代價**：id 不可讀。錯誤訊息與主控台顯示改用 `character_name`，
  `npc_schedule.json` 的 `assignments` 改用節點名當 key

> [!note] `owner` 欄位還沒放
> 決定是「擁有者是欄位不是 id 的一部分」，但現在沒有帳號概念，寫不出值。
> 等真的有東西產生它再加，不先放空欄位佔位。

### 取消主模式／AI 模式的區別

- **原本**：`主模式`（玩家操作）與 `AI模式`（觀察 agent 自主生活）兩個模式，
  共用角色存檔與世界存檔；已拍板「AI 模式裡玩家角色不存在，不可讀 player 存檔」
- **現在**：不分模式。世界之間唯一的差別是裡面有沒有 player。
  世界存檔多一個建立時決定的旗標「**允不允許 player 加入**」，允許也不強制在場
- **為什麼**：整個區別化簡下來就只有「有沒有 player」，不值得做成兩套東西
- **消失的問題**：「AI 模式跑掉 3 個遊戲日再切回主模式，時間線怎麼銜接」——
  一份世界存檔就是一條時間線，且只在被開著時推進，沒有另一邊要銜接
- **浮上來的問題**：角色存檔跨世界共用 → **鎖要鎖在角色這一層**，不只鎖世界存檔
- **待拍板**：那個旗標建好之後還能不能改（傾向能改）

> [!warning] 別把「有沒有 player」寫成載入時算一次的分支
> 玩到一半有人離線就壞了。世界層問的是「允不允許加入」；
> 「現在有沒有人在操作」是角色層的問題。
