# Test A 三次完整 2 遊戲日測試分析

本地測試專用（`worktree-test-decision-trace` 分支，未上 GitHub）。用新增的
`TestRunLogger`（掛在 `AIService.request()`／`agent.gd::_select()`／
`_log_task_ended()`／`Character.spoke` 四個既有出口）完整記錄三次獨立的
2 遊戲日測試，角色 TestA 全程單獨存在（`context.visible` 空），
`llm_decision_enabled=true`，真實 LLM 決策。

三份原始 JSONL 在同目錄：`test_a_run1.jsonl`（27 事件）、
`test_a_run2.jsonl`（59 事件）、`test_a_run3.jsonl`（57 事件）。

## 結果總覽

| | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| 真實 LLM 決策次數 | 9 | 12 | 12 |
| 最終 health | 100 | 51 | 55 |
| 最終 hydration | 80（未觸發危機） | 0 | 0 |
| 選中動作種類 | work, rest | follow, work, rest, talk×6 | eat×2, work, rest, talk×5, drink×1 |

三次最終狀態高度一致（health 51-55、hydration 見底、satiety 17-30），
不是隨機噪音，是穩定重現的行為模式。

## 決定性發現

**1. AI 沒有卡死不動，但是「社交需求蓋過生理需求」，不是「工作狂不吃飯」。**
Run 2、3 後半段連續多輪決策，`talk` 優先度給到 100-110（遠高於 eat/drink
通常給的 10），reasoning 一致是「整天沒人說話，好寂寞」。

**2. 最關鍵的證據**：Run 2、3 收尾前的決策，模型自己看到的數值是
「極度飢餓 80」「脫水 100（滿）」「睏到撐不住 100（滿）」——
**reasoning 完全沒提到這三個瀕死數值**，繼續說「缺乏社交讓心情低落，
需要找人聊聊」，選擇 talk。不是沒看到，是看到了但被社交敘事完全蓋過。

**3. `talk` 三次測試共 11 次，全部失敗。** 因為 TestA 單人測試、
`context.visible` 是空的，沒有合法對象，但模型仍硬選 talk，
`params.target` 出現：
- `"context.visible[0]"`——照抄 prompt schema 範例的字面文字，不是代入的名字
- `"TestB"`——幻覺出來、根本不存在的角色
- `"tavern"`／`"tavern keeper"`／`"路人"`／`"村民"`——地點或通用稱呼，不是角色名

「照抄範例字面文字」是真的 prompt 清晰度問題，值得修；但 talk 失敗率
本身很可能是單人測試場景的人為限制，多 NPC 環境不會這麼慘，不能直接
外推成「talk 機制本身故障」。

**4. `buy` 三次測試、33 次決策，一次都沒被選過。** eat/drink 總共只被選
3 次，其中 2 次 `params` 完全是空的 `{}`（連 item_id 都沒填），全部失敗。
唯一一次有填 item_id/place 的 drink（`{"item_id":"ale","place":"tavern"}`）
也失敗，因為沒有先 buy、庫存裡沒有這個東西。

**5. `sleep`／`nap` 從未被選過**，即使 wakefulness 已經到「睏到撐不住」
的滿值，全程只用 `rest` 恢復體力，從沒有真正睡過覺。

## 尚待決策

- 「模型忽略瀕死數值、被社交敘事綁架」要不要開 issue、怎麼修（prompt
  加強調權重？還是接受這是小模型能力限制？）
- 「talk target 填 schema 字面文字」的 prompt 清晰度問題
- 「sleep/nap 從未被選中」是巧合還是系統性傾向，需要更多樣本
- 這三次測試都是單人場景，`talk` 全滅的結論不能直接套用到多 NPC 環境，
  之後應該補一次「附近有其他角色」的對照測試
