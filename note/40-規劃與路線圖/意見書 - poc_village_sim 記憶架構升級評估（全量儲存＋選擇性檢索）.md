# 意見書：poc_village_sim 記憶架構升級評估（全量儲存＋選擇性檢索）

## 背景

使用者在規劃雲端模型接口時提出：現有記憶機制（`memory_store.py`）是不是不夠好，能不能
改成「全資料儲存＋精簡後記憶當預設＋模型依情況選擇性呼叫更多資訊量」的架構。

## 一、現有做法的實際短板

`memory_store.py` 目前只做**新近度（指數衰減）＋重要性**加權排序，固定取分數最高的
top_k=6 筆塞進 prompt，這是刻意的設計（見 [[POC 紀錄 - poc_village_sim 五人整合試跑（新版 AI 架構首測）]]
或 `memory_store.py` 檔頭註解：曾在 `poc_mode_a/dialogue_ping_pong_memory_embed.py` 測過
加入語意相關性（embedding）檢索，結果反而強化對話卡住/重複的傾向，沒有採用）。

真實限制：
1. **永遠被動塞固定量**——模型沒有辦法在決策當下說「這個情境資訊不夠，我要多看一點」，
   只能拿到我們預先決定好的 6 筆摘要。
2. **沒有語意相關性項**——這是已知取捨，不是遺漏，但代價是长期記憶容易被「常發生但不重要」
   的事件洗掉（跟論文原始設計的落差，[[POC 架構總覽與 Generative Agents 論文比對]] 已點名）。
3. **原始資料雖然都留著（transcript 本身是全量記錄），但沒有被設計成「可被模型主動查詢」
   的形式**——現在的原始資料只是拿來做事後稽核/分析用，不是給模型在決策當下用的。

## 二、提案的架構方向

三層式：
1. **完整原始資料**——已經有了，不用另外做（transcript／未來的資料庫記錄本來就是全量）。
2. **精簡摘要（現有 top-K）當預設**——平常呼叫用這個，成本低、跟現在行為一致。
3. **新增檢索工具（function calling / tool call）**——決策當下如果模型覺得資訊不夠，
   可以主動發起一次「查更多細節」的呼叫（例如：查某個人的完整互動歷史、查某天發生的
   完整事件序列），不是我們單方面決定要塞多少給它。

這個方向跟現代 agent 常見的「工具化 RAG」模式一致（模型自己決定何時檢索、檢索什麼），
比固定 top-K 更貼近論文原始設計裡「觀察→反思→行動」的動態性質。

## 三、可行性與風險（尚未驗證，需要花時間確認）

| 項目 | 現況 | 需要驗證的事 |
|---|---|---|
| **llama.cpp／llama-server 的 tool call 支援** | 較新版本的 llama-server 有支援 OpenAI 相容的 function calling，但我們目前完全沒用過這條路 | 要實際測：現在部署的版本（commit `aff6eb6`）支不支援、支援到什麼程度 |
| **tool call 跟現有 grammar 約束共存** | 現在的決策呼叫全程靠 GBNF grammar 硬鎖 JSON 結構 | tool call 通常需要額外的 schema/呼叫協議，要驗證能不能跟現有 grammar 機制疊加，不衝突 |
| **模型會不會真的在該查的時候去查** | 未知，是全新的行為，沒有測過 | 這本質上是另一個「模型有能力用工具，但會不會用」的決策層級問題——跟這幾天一直在測的
「有失敗原因也不換動作」是同一類疑慮，工具存在不代表模型會正確使用，可能還是需要
訓練介入（DPO）才能讓模型學會「什麼情境該多查一點」 |
| **雲端模型上的可行性** | OpenRouter／多數雲端 API 原生支援 function calling，技術上比本地更成熟 | 但雲端這條線本身還在規劃（見雲端接口那份工作），這個記憶升級如果要同時支援本地+雲端，
兩邊的 tool call 實作方式可能不同，要各自處理 |

## 四、建議的下一步（等使用者排時程再啟動）

1. 先花一次小規模驗證，確認本地 llama-server 版本是否支援 tool call、能不能跟 grammar 共存
2. 如果技術上可行，設計最小可行版本（例如只開放一種查詢：「查某個人完整的互動記錄」），
   不要一次做完整的檢索工具集
3. 驗證「模型會不會恰當使用這個工具」本身要當一個獨立的觀察指標，不能假設做了工具
   模型就會正確用

## 五、跟其他進行中工作的關係

- 跟雲端模型接口是**兩件不同的事**，不要因為都牽涉到「雲端」就綁在一起做——接口只是
  換底層呼叫對象，記憶升級是換整個資訊呈現/取用的架構，範圍大很多，值得獨立排時程。
- 跟 DPO 訓練方向可能有交集（「該不該查更多資訊」本身可能也要靠 DPO 教），如果之後
  真的要做，可以評估要不要跟 DPO 訓練資料收集一起設計。
