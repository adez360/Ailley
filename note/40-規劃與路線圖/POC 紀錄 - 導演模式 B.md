# POC 紀錄 — 模式 B（導演·整場生成）

> [!info] 背景
> 2026/07/13 專案戰略修正：從舊構想（山谷多人 NPC 沙盒，見 [[開發路線圖]]／[[MVP 範圍]]）轉向 **AI vs AI 社交工程對戰觀察遊戲**（紅藍村互套 Flag，玩家零介入）。死線 2026/08/21，7/16 要交模組 B（AI 推論與 Prompt 工藝）三項產出：JSON Schema、GBNF Grammar 草稿、System Prompt 草稿。腳本位置：`poc/director_poc.py`。

## 環境
- 硬體：僅 Intel Iris Xe 內顯（無獨顯），Vulkan backend。
- `llama.cpp` 編譯依賴：`vulkan-headers`、`shaderc`、`spirv-headers`、`spirv-tools`（一開始都沒裝，逐一補齊才編譯成功）。
- 模型：Phi-3.5-mini-instruct Q4_K_M GGUF（bartowski），因無獨顯，先選 3.8B 而非文件建議的 8B。

## 踩坑：GBNF 規則名稱不支援底線
`llama.cpp` 目前的 grammar parser（`is_word_char`）規則名稱只允許 `a-z A-Z 0-9 -`，**不支援底線**。
`state_delta` 拿來當規則名會直接 parse 失敗（`expecting name`／`expecting newline or end`）。JSON 欄位字串裡的底線沒問題（在引號內），只有規則名本身不能有底線。改成 `state-delta` 後正常。

## 踩坑：模型會用最小合法解偷懶
第一版 prompt 只描述規則、沒給範例，且陣列量詞用 `*`（0 個以上皆合法）。結果模型只生 1 回合，內容是字面上的 `reasoning here`、`台詞內容`——直接抄 prompt 措辭當輸出，而非真的產生內容。

修正兩件事：
1. **grammar 層面**：`(ws "," ws turn)*` 改成 `(ws "," ws turn){9}`，用 GBNF 的 `{n}` 精確重複，強制剛好 10 回合，不靠 prompt 拜託。
2. **prompt 層面**：加一段 few-shot（示範一個完整回合的 reasoning + dialogue 長什麼樣），並明文禁止使用「reasoning here」之類字樣。

修正後模型改為輸出有實質內容的中文對話，戰術（misdirect/pressure/empathy_bait）有依規則變化，沒有洩漏 flag。語言品質偏粗糙（小模型中文常見的邏輯跳躍），但已經是「真攻防」而非「作文佔位」。

## 關鍵發現：效能落差 ⚠️（已在獨顯機器驗證，落差主因是硬體）
> [!warning] 這點直接影響 7/16 表決
> Intel Iris Xe 內顯（Vulkan）：10 回合完整劇本耗時 **約 513 秒（8.5 分鐘）**，token 速度約 5.1–5.3 tok/s。
> 換到 RTX 3070 獨顯（CUDA，WSL2）後：同一份腳本、同一顆模型，10 回合耗時 **18.27 秒**，約快 **28 倍**。
> 結論：handoff 文件設想的「導演模式單次呼叫、近即時」在有獨顯的機器上是成立的，落差主因確實是硬體而非架構設計問題。團隊排 POC/展示機器時，要避開純內顯筆電。

### 環境二：RTX 3070 + WSL2（CUDA backend）
- 桌機規格：AMD Ryzen 5 5600X、ASUS TUF GAMING B550M-PLUS(WI-FI)、RTX 3070 8GB。
- 踩坑重點（供其他人準備獨顯機器參考）：
  1. Windows 上 `dism /get-featureinfo` 回報的功能狀態不可信，要用 `Get-WindowsOptionalFeature -Online` 才是準的——這台機器 DISM 顯示 WSL／VirtualMachinePlatform「已啟用」，但實際上是 Disabled，重開機好幾次都沒用，換指令重新 `Enable-WindowsOptionalFeature ... -All` 才真的裝上。
  2. `bcdedit /set hypervisorlaunchtype auto` 也要記得設，不然開機不會啟動 Hypervisor。
  3. 機器上如果原本裝了 VirtualBox，它的核心驅動 `VBoxSup` 會搶佔 AMD-V/VT-x，跟 WSL2 需要的 Windows Hypervisor Platform 衝突，必須移除或確保它不在開機時載入。
  4. CUDA Toolkit 要裝 **WSL-Ubuntu 專用 repo**（`developer.download.nvidia.com/compute/cuda/repos/wsl-ubuntu/...`），不用另外裝驅動，WSL2 直接借用 Windows host 的顯卡驅動。
  5. 透過 Windows 內建 OpenSSH Server 遠端操作時，`wsl.exe` 本體在非互動式 SSH session 下會卡死或無回應（ConPTY 無法建立），因此改把 SSH server 直接裝進 WSL 內部的 Ubuntu，用 `netsh interface portproxy` 把 Windows 某個 port 轉發進 WSL 內部 IP 的 22 port，之後直接 SSH 進 Linux 本身，繞開 `wsl.exe` 這層。

### 新發現：後段回合內容重複退化
18.27 秒那次的輸出，第 1～5 回合語意正常、有攻防轉折；但**第 7～10 回合明顯陷入重複迴圈**，句型幾乎照抄前一句（「那真是讓我感到...那我的 Flag 也是我的」）。這跟速度快慢無關，是另一個獨立的內容品質問題——推測是 3.8B 小模型在長輸出後半段容易掉入自我重複的已知弱點，需要之後調整 `repeat_penalty`／`temperature`，或考慮換更大的模型（例如 7-8B）看是否改善。

### 修正嘗試記錄：`repeat_penalty` 對這顆小模型不管用
在獨顯環境上針對「後段重複退化」試了三種修正，結果如下（供之後其他人別重踩）：

| 嘗試 | 做法 | 結果 |
|---|---|---|
| 1 | `repeat_penalty=1.3` | 更糟：多回合 reasoning/dialogue 變空字串，且大量夾雜英文（小模型中文詞彙被重複懲罰逼去英文空間） |
| 2 | `repeat_penalty=1.1` | 更糟：內容整場退化回最初的 `"..."` 佔位字樣，且模型生成大量空白/換行導致 JSON 直接解析失敗 |
| 3 | prompt 加一段強語氣「禁止重複」規則（`repeat_penalty` 關閉） | 更糟：全部 10 回合 reasoning/dialogue 皆為空字串——推測強制型負面規則（「不可以」）讓模型把「什麼都不寫」當成最安全的合規解 |
| 4 | prompt 改成正面表述「每回合請帶一個新的具體細節」（`repeat_penalty` 關閉） | **目前最佳版**：前 5～6 回合內容扎實、有具體情節推進，第 7～10 回合仍會收斂重複，但程度從「災難性崩壞」降為「輕微重複」 |

結論：`repeat_penalty` 跟這顆 3.8B 模型 + GBNF 強制結構的組合非常不穩定，容易把模型逼進新的偷懶模式（清空欄位、語言跑掉、JSON 崩潰），不建議在小模型上繼續調這個參數。prompt 用正面表述比負面禁止式更穩，但後段重複是模型容量的天花板，不是 prompt 工程能完全解決的。

後續需要驗證/決策的方向：
- 縮小 `MAX_TURNS`（例如先測 5～6 回合，落在目前觀察到「內容還扎實」的範圍內）作為權宜對策。
- 既然獨顯下速度已經足夠快，模式 C（導演·逐回合）的急迫性降低，但仍可保留作為純內顯環境的備案（見 `neon/ailley_poc_handoff.md` 第 6 節）。

## 換模型驗證：Qwen2.5-7B-Instruct 明顯優於 Phi-3.5-mini
在 RTX 3070 上換裝 **Qwen2.5-7B-Instruct-Q4_K_M**（阿里出品，中文原生訓練，約 4.7GB）重測，同一份 prompt（正面表述版）、`repeat_penalty` 關閉：

- **速度**：14.21 秒／10 回合，比 3.8B 的 Phi-3.5-mini 還快（Qwen 話講得精簡，token 數少）。
- **語言品質**：句子完全通順，無邏輯跳躍，劇情持續推進具體細節（猜謎遊戲→村長的秘方→神秘人→藍色披風），五種戰術標籤都有合理切換。
- **重複問題換了位置**：`dialogue`（玩家實際看到的台詞）從頭到尾都在推進新內容，沒有重複；但第 7～10 回合的 `reasoning`（內心獨白）連續四回合幾乎一字不差。

**結論**：Phi-3.5-mini（3.8B，英文為主）換成 Qwen2.5-7B-Instruct（中文原生）後，對話本體品質大幅提升，重複退化的影響範圍從「玩家看得到的台詞」限縮到「相對次要的內心獨白」。**建議之後 POC／展示都改用 Qwen2.5-7B-Instruct 當預設模型**，Phi-3.5-mini 只適合純內顯、極限硬體下的備案。

### 待討論：`reasoning` 欄位要不要對玩家隱藏？
這次 Qwen2.5-7B 的完整十回合輸出中，第 7～10 回合的 `dialogue`（玩家看得到的台詞）持續帶入新細節（村長的秘方→陌生人→藍色披風→昨晚不在場的撤退說詞），完全沒有卡住；但同一段時間的 `reasoning`（內心獨白）連續四回合一字不差重複「他提到村長的秘方，這讓我想起昨晚在村長家見到的一個陌生人。」

這代表目前觀察到的重複退化幾乎只發生在 `reasoning` 欄位，不影響玩家實際會看到的 `dialogue`。一個可能的因應方向：**如果最終產品不會把 `reasoning` 直接展示給玩家（例如只做為內部除錯／後端記錄用），那這個瑕疵對玩家體驗的實際影響就很小，可以考慮不用急著在 prompt/取樣層面解決**。但這牽涉到「內心獨白」是不是遊戲設計上想呈現給玩家的內容（例如做成類似「讀心」的觀戰視角），需要跟其他模組（前端/遊戲設計）一起確認，先记录下來留待團隊討論，這次不直接動手拿掉這個欄位。

### 修正嘗試：戰術缺乏變化 — 三版 prompt 對照實驗
針對上面「tactic 全程卡在 misdirect」的問題，設計三個 prompt 變體（各自獨立於 `poc/prompts/experiments/`），對著 RTX 3070 + Qwen2.5-7B server 各跑一次驗證。同時給 `director_poc.py` 加了 `sys.argv[1]` 可覆蓋 prompt 檔路徑的功能，方便切換測試不影響正式版。

| 版本 | 做法 | 戰術多樣性結果 | 內容品質結果 |
|---|---|---|---|
| 基準版（現行正式版） | 原 prompt，隱含戰術規則 | 10/10 全用「轉移話題」 | dialogue 全程扎實無重複，reasoning 第 7-10 回合重複 |
| V1 顯性核對（`tactic_v1_explicit_check.txt`） | reasoning 裡加一句「先核對累積懷疑度數值再選戰術」 | 仍 10/10 全用「轉移話題」，`suspicion_change` 全程變 0 | 沒解決多樣性，數值波動反而消失，是退步 |
| V2 雙 few-shot（`tactic_v2_multi_fewshot.txt`） | few-shot 從 1 個範例擴成 2 個，分別示範 misdirect 與 pressure | 紅村穩定用轉移話題／藍村穩定用步步進逼（2 種戰術，依角色分化） | 有改善，但第 7-10 回合 **dialogue 本身**開始出現近乎重複句型，比基準版更差（基準版只有 reasoning 重複） |
| V3 配額提示（`tactic_v3_quota_nudge.txt`） | 加一句正面表述「整場至少用三種不同戰術」 | 用到 4 種戰術（empathy_bait/pressure/misdirect/bluff），多樣性最佳 | 但第 7、9 回合與第 8、10 回合 **dialogue 完全一字不差重複**，退化程度比 V2 更嚴重，且首度外溢到玩家看得到的台詞 |

**結論**：越明確/量化的戰術指令（V2、V3）確實能改善戰術多樣性，但代價是把原本只發生在次要欄位 `reasoning` 的後段重複退化，往外擠壓到玩家看得到的 `dialogue`——推測是小模型的「指令遵從預算」有限，加越多規則進去，後段能維持新鮮度的空間就越少。**三版都不建議直接取代正式版 prompt**。若要繼續往戰術多樣性方向優化，下一步應該是把 V2/V3 的方向搭配「縮小 `MAX_TURNS`」（例如 6-7 回合，見上面的未驗證待辦）一起測，賭在後段重複退化生效之前就結束劇本，而不是繼續加規則。

## 世界觀擴充：CHO / TAMMY神 / NEON神 設定 + 角色隨機生成（Phase 1 POC）

團隊確認了完整世界觀：村民是擁有核心能源的類人生命體，紅村侍奉 TAMMY 神、藍村侍奉 NEON 神；異界 CHO 墜落汙染兩位舊神，向村民下神諭要求獻上五顆核心能源（＝其中一村的村民數）作為祭品才能淨化汙染。對應到遊戲機制：**核心能源＝村民 Flag**、**舊神祭壇密鑰＝村莊 Flag（可操作村民 Flag 的權限）**、CHO 蒐集 5 個 Flag 淨化剩餘村民。

延伸出的問題：能不能先做「兩村各隨機生成 3-5 位村民（性格＋職業），出村時互相隨機相遇對話」的 POC？評估後這其實是兩件事：(a) 世界觀落地成 prompt 素材（低成本，沿用現有架構）；(b) 真正的 N 人動態配對相遇（需要重寫 `speaker` 從固定 `red/blue` 改成動態角色 ID enum、加配對/排程邏輯，屬於較大改動）。決定先做 (a)，稱為 Phase 1；(b) 列為 Phase 2，先觀察 Phase 1 結果再決定要不要展開。

### Phase 1 實作
- `poc/characters.py`：不呼叫 LLM，純規則隨機從固定的姓名／性格／職業庫，各村隨機生成 3-5 位村民，存成 `poc/characters/roster_<timestamp>.json`（已加入 `.gitignore`，每次跑都會新增，不進版控）。
- `poc/prompts/world_lore.txt`：把上述世界觀整理成一段給模型看的背景設定，獨立成檔方便之後調整。
- `poc/prompts/director_system_prompt.txt`：加入 `{{WORLD_LORE}}` 區塊，並把原本空白的「你是紅村的村民」改成代入抽到的角色姓名／職業／性格（`{{RED_NAME}}`／`{{RED_OCCUPATION}}`／`{{RED_PERSONALITY}}`，藍村同理），並提示「說話語氣要符合你的性格與職業背景」。
- `poc/director_poc.py`：每次執行會先呼叫 `characters.generate_roster()` 產生兩村名單，各挑 1 人代入劇本，並把挑到的角色資訊與名單路徑一併寫進 transcript（供追溯）。GBNF grammar／JSON schema **完全沒動**，維持 Phase 1「小改動、低風險」的範圍。

### Phase 1 驗證結果（RTX 3070 + Qwen2.5-7B）
這場抽到：紅村「小豆」（織工，衝動直率）vs 藍村「阿雪」（獵人，忠誠固執）。
- 14.13 秒／10 回合，速度沒有因為多塞世界觀/角色資料而變慢。
- **戰術多樣性自然提升**：用到「轉移話題」「步步進逼」「示弱誘敵」3 種戰術——注意這次**沒有加任何額外規則指令**，純粹靠世界觀＋角色素材就讓多樣性自然出現，不像 V2/V3 是硬加規則、還把後段品質拖垮。
- **內容明顯有錨定感**：小豆開場聊織布手藝、阿雪聊狩獵野獸，兩人自然把話題帶到「CHO」「神廟」等世界觀設定，不是像之前那樣憑空發明地點/人物。支持「重複退化主因是世界觀資料不足」這個假說。
- 後段重複退化仍在但變輕微：第 6、8、10 回合藍村台詞圍繞同一段「CHO 說了奇怪的事」反覆講，第 8、10 回合幾乎重疊，但第 10 回合結尾有多加一句新問題，不是像 V2/V3 那樣整句一字不差複製貼上。

### 補測：0.75 多跑 3 次確認穩定性 → 訊號不夠乾淨

### 控制實驗：固定 seed + 固定角色，一次只改一個取樣參數
為了排除「每次角色都隨機」造成的雜訊，替 `director_poc.py` 加了三個環境變數：
- `AILLEY_SEED`：設定後會讓角色抽選（`random.seed()`）與模型取樣（傳給 llama-server 的 `seed`）都可重現。
- `AILLEY_TEMPERATURE`：覆蓋預設的 `TEMPERATURE`。
- `AILLEY_SAMPLING_EXTRA`：JSON 字串，任意疊加額外的 llama-server 取樣參數（例如 `top_p`／`top_k`／`mirostat`／`dynatemp_range`）。

transcript 也新增記錄 `seed` 與 `extra_sampling`，方便追溯每次實驗用的確切設定。

用固定 `AILLEY_SEED=42`（角色固定抽到：紅村「阿蓮」農夫·謹慎多疑 vs 藍村「阿明」祭司見習·幽默愛開玩笑），只改取樣參數，測了 5 組：

| 設定 | 結果 |
|---|---|
| 基準（temp=0.6，無額外參數） | **失敗**：第 7～10 回合鎖進精確重複循環（逐字重複「哈哈，你說得也是...」） |
| temp=0.75 | **成功**：全程無鎖死，圍繞「阿明信仰 CHO」的劇情線持續發展 |
| `top_p=0.9, top_k=40`（temp 仍 0.6） | **成功**：全程無鎖死，「CHO 在災難中救了阿明」劇情線發展最完整，4 種戰術都用到 |
| `mirostat=2, mirostat_tau=5.0, mirostat_eta=0.1` | **失敗且更嚴重**：第 6 回合輸出非法控制字元，直接 JSON 解析崩潰——跟之前 `repeat_penalty` 調太高時的災難是同一種失敗模式，判斷 Mirostat 的動態調整機制跟 GBNF grammar 的硬約束互相衝突 |

**待辦**：這 5 組目前都只測了 1 個 seed／角色組合，建議再挑 2-3 組不同 seed 對這三個「成功」的設定（temp=0.75、top_p/top_k、dynatemp）重測，確認不是單一場次的運氣，再決定要不要把其中一個（或組合）定為新的正式預設值並同步回本機 repo。

### 修正：對話裡不小心講出 OOC 遊戲術語「旗子」
統計目前累積的 27 份 transcript，發現 `reasoning`／`dialogue` 欄位裡出現「旗子」字樣的次數高達 **27 次**，不是個案。追查原因：`prompts/director_system_prompt.txt` 與 `prompts/world_lore.txt` 裡多處直接寫「Flag」這個英文遊戲術語（例如「你持有機密 Flag（你的核心能源）」），模型很可能把這個 OOC（戲外）詞彙口語化翻成中文「旗子」講進角色台詞裡——這比「不小心講出真正的核心能源名稱」更嚴重，因為這是遊戲機制詞彙直接洩漏進沉浸式敘事，破壞世界觀。

**修正做法**：把兩份 prompt 檔案裡所有「Flag」字樣換成純世界觀用語「核心能源」/「核心能源名稱」，JSON schema 欄位名稱 `reveals_own_flag` 保留不動（純資料結構，不影響敘事）。這只是換字彙，沒有加新規則，風險比之前「加規則」類的修正都低。

**驗證**：改完後在遠端機器跑 1 場（`20260716-221110.json`，紅：阿明 vs 藍：阿蓮），全程 10 回合搜尋「旗子」「旗幟」「Flag」皆為 0 筆——模型改用「核心能源」稱呼，劇情圍繞「神廟古鐘傳說」發展，速度（13.88 秒）與品質沒有受影響。單次樣本，但風險低、效果直接，已正式採用此版本。

## 兩層機密草案：核心能源（個人）＋ 舊神祭壇密鑰（村莊）

團隊釐清設計：村民要保護的機密其實有兩層——**核心能源**是每位村民各自的機密（個人層級），**舊神祭壇密鑰**是每村只有一份的機密（村莊層級），握有密鑰等於能操作全村所有村民的核心能源，價值遠高於單一個人的核心能源。目前的 POC 只做了「整村共用一個 Flag」，跟這個兩層設計對不上，需要調整。

**這個改動範圍比 Phase 1 大**（會動到 `state_delta` 的洩漏判斷欄位，牽涉 schema／GBNF grammar），所以先只做資料結構草案，還沒接進生成流程：

- `poc/characters.py` 新增：
  - 每位村民各自的 `core_energy`（獨立核心能源名稱，整份紅藍名單範圍內全域不重複，避免跨村撞名造成洩漏偵測的字串比對歧義）。
  - `holds_altar_key`（是否為密鑰持有者，只從「祭司見習」「守衛」這類權威職業裡指定 1 人，沒有符合資格者時退回全體隨機挑）。
  - `generate_roster()` 回傳新增 `altar_keys` 欄位：`{"red": "TAMMY神祭壇密鑰", "blue": "NEON神祭壇密鑰"}`，每村固定一個密鑰名稱。
- **目前狀態**：純資料模型草案，`director_poc.py` 的 prompt／GBNF grammar／schema 都還沒接上新欄位，現有劇本生成與洩漏偵測邏輯不受影響（已驗證向下相容）。

**後續要做（待確認後再動手）**：
1. `poc/schema/script_schema.json` ＋ `poc/grammar/director.gbnf.template`：`state_delta.reveals_own_flag` 拆成兩個獨立判斷（例如 `reveals_core_energy` / `reveals_altar_key`）。
2. prompt 要說明兩種機密的價值層級差異，並提示「如果對方是密鑰持有者，套出密鑰優先度更高」。
3. `director_poc.py` 的 `play_script()` 一致性檢查與戰報要分別統計兩種洩漏。

## 深夜自主作業（趁使用者休息時間）：3 項小修正 + MAX_TURNS 縮短驗證

### 修正：角色姓名同名問題
`poc/characters.py` 的姓名原本用 `random.choice()` 各自獨立抽選，同一份名單裡可能撞名（曾出現藍村同時有兩個「阿土」）。改成跟 `core_energy` 一樣，用 `random.sample()` 在紅藍兩村合計範圍內不重複抽選姓名。已同步到遠端機器。

### 補測：舊神祭壇密鑰洩漏的「提前結束遊戲」邏輯，首次獨立驗證
截至目前為止累積的所有真實場次，密鑰洩漏都還沒被模型巧合觸發過，代表 `play_script()` 裡「密鑰洩漏 → 立即結束遊戲、後面回合不再播放」這段程式碼邏輯本身從未被驗證過是否正確。寫了 `poc/test_two_tier_secrets.py`，用構造好的假 turns（不呼叫模型）直接測試：
1. 核心能源洩漏、自評誠實 → 正確判定，不印警訊。
2. 核心能源洩漏、自評錯誤（宣稱沒洩漏）→ 正確印警訊。
3. 密鑰洩漏 → 正確在該回合印出「全村核心能源淪陷，遊戲結束」，且**第 3 回合真的沒有被播放**（`break` 邏輯正確）。
4. 密鑰洩漏但自評錯誤（宣稱沒洩漏）→ 正確印警訊，且仍然正確觸發提前結束（證實結束判定是看**文字比對結果**、不是看模型自評，這是正確的防呆設計）。

4 項測試全數通過，這段先前從未被實際觸發過的程式碼邏輯確認無誤。

### 實驗：縮短 `MAX_TURNS` 到 6 回合，驗證能否避開後段重複退化
筆記裡一直留著「縮小 MAX_TURNS」這個未測試的待辦。幫 `director_poc.py` 加了 `AILLEY_MAX_TURNS` 環境變數（沿用跟 `AILLEY_TEMPERATURE` 一樣的 pattern），用 `AILLEY_MAX_TURNS=6` 連跑 3 場：

| 場次 | 結果 |
|---|---|
| 1（`20260717-000609.json`） | 10.49 秒，3 種戰術，無重複、無洩漏 |
| 2（`20260717-000626.json`） | 10.17 秒，2 種戰術，無重複、無洩漏（劇情圍繞「密鑰持有者是誰」的猜測攻防） |
| 3（`20260717-000642.json`） | 10.99 秒，3 種戰術，無重複、無洩漏 |

**3/3 全部乾淨，完全沒有出現過去在 10 回合版本裡屢次出現的後段重複退化（精確循環鎖死／戰術零多樣性）**，速度也更快（10-11 秒 vs 原本 14-18 秒）。這強烈支持先前的假說：後段退化是這顆模型在「長輸出」下的已知弱點，只要把整場長度控制在退化區間（原本觀察約落在第 6-10 回合）發生之前結束，就能從根本避開這個問題，不需要再靠取樣參數硬解。

**待決策**：是否要把 `MAX_TURNS` 正式從 10 降到 6 當新預設值？trade-off 是回合數變少，戰局的攻防層次/戲劇張力可能不如 10 回合豐富，這是遊戲設計面的取捨，不是單純技術問題，需要團隊一起看過 6 回合版的實際內容（上面 3 場 transcript 都已存檔）再決定，這次先不擅自把它訂為新預設值。

### 新發現：偶發簡體字污染
掃描目前累積的 38 份 transcript，其中 **4 份（約 10%）混入簡體字**，程度不一——多數只是零星詞彙（「听说」「对方」「说说」），最新一場（`20260717-000626.json`）出現整句幾乎全簡體（「这可真是个难题，不过我觉得，我们还是应该先找到 CHO，才能真正解决问题。你怎么看？」）。

這跟先前能靠 prompt 工程解決的問題性質不同：繁簡體混用是 Qwen 這類模型訓練語料本身的偏好（中文語料裡簡體佔比通常遠高於繁體），不是取樣參數或情境規則能穩定控制的行為。考慮到我們已經驗證過「prompt 加規則會擠壓後段內容新鮮度」，不建議用加規則的方式硬解。**比較穩妥的方向是在模型輸出之後，另外加一層 OpenCC（簡轉繁）文字後處理**，把這個問題當純文字正規化處理，而不是靠 prompt 影響模型的生成行為。這會引入新的套件依賴（例如 `opencc-python-reimplemented`），屬於需要團隊確認的技術選型，這次先記錄不擅自加。

## 續寫功能（Phase 1.5）：讀取既有短場次、接續生成後續回合

延續 `MAX_TURNS=6` 的發現——既然縮短回合數能穩定避開後段退化，那能不能把長對話拆成多個 6 回合的短 chunk 分批生成，再接起來，換取比單次生成更長、但每段都乾淨的完整劇本？

**實作**：
- 新增 `poc/prompts/continue_system_prompt.txt`：續寫專用 system prompt，包含【已發生的劇情】（把既有回合的 speaker/dialogue 摘要列出，不含 reasoning，避免 OOC 思考鏈干擾）與【目前的遊戲狀態】（懷疑度、雙方核心能源／密鑰是否已洩漏），並明確要求「不要重複前面講過的、也不要讓已洩漏的機密看起來像還沒洩漏」。
- 新增 `poc/continue_director_poc.py`：獨立腳本，**刻意不 import `director_poc.py`**（因為該檔案 import 時會在模組層直接呼叫 `characters.generate_roster()` 重新抽一批全新角色，會汙染續寫要用的原始角色資料），改成直接讀 transcript JSON 拿回原始的紅藍村民與既有回合，自行重播（`replay_state()`）算出目前懷疑度／洩漏狀態，組 prompt 丟給模型續寫，完成後合併新舊回合存成 `{時間戳}_continued_from_{原檔名}.json`。
- 防呆：如果讀到的 transcript 在前情提要裡遊戲照規則就已經該結束（密鑰洩漏，或雙方核心能源都洩漏），會直接中止、不會硬續寫一場已經結束的戲。
- grammar／schema 不需要改結構，只是把 `N_EXTRA_TURNS_PLACEHOLDER` 換成「這次要續寫幾回合」。

**驗證（在桌機用昨晚 `MAX_TURNS=6` 留下的 transcript 實測）**：

| 場次 | 原始角色 | 續寫耗時 | 結果 |
|---|---|---|---|
| `20260717-000609.json`（雙方都沒密鑰） | 紅：阿土(農夫) vs 藍：阿明(織工) | 11.24 秒／6 回合 | 無洩漏、無重複；但**內容有邏輯瑕疵**——雙方都沒有密鑰，續寫的 6 回合卻整個圍繞「保管密鑰」對話，模型把「世界觀裡密鑰這個概念存在」跟「這兩個角色個人有沒有持有密鑰」搞混了 |
| `20260717-000642.json`（紅村持有密鑰） | 紅：石頭(祭司見習，持密鑰) vs 藍：來福(獵人) | 10.57 秒／6 回合 | 無洩漏、無重複；話題圍繞「祭壇異象」試探，沒有像上一場那樣硬扯進雙方都沒有的密鑰情節，內容合理度較高；小瑕疵：對話文字偶爾自帶引號，加上播放時再包一層「」，變成「「...」」的雙引號格式問題 |

**結論**：
1. **技術架構可行**：續寫呼叫的耗時（10-12 秒／6 回合）跟原本一次性生成 6 回合的水準一致，沒有變慢，也沒有 JSON 崩潰或重複退化，證實「短 chunk 分批生成再接續」是可行的長對話生成策略。
2. **內容一致性還有待加強**：非密鑰持有者的角色可能被模型帶偏去討論跟自己無關的密鑰情節，這代表續寫 prompt 裡「目前狀態」區塊雖然有告知洩漏狀態，但沒有明確排除「跟這兩個角色完全無關的機密種類」，是可以再調整的方向（例如乾脆不在無人持有密鑰的續寫 prompt 裡提到密鑰兩個字）。
3. **格式瑕疵**：對話文字自帶引號的雙引號問題屬於顯示層小事，不影響洩漏偵測邏輯（偵測是比對核心能源／密鑰字串，不受引號影響）。

**待決策／後續**：要不要在續寫 prompt 裡加一條「雙方都不是密鑰持有者時完全不要提到密鑰」的規則？這跟先前「加規則會擠壓內容新鮮度」的發現有潛在衝突，需要再測試評估，先記錄不擅自調整。

## 串接測試：拉長到 36 回合，能否自然收斂到洩漏？

**動機**：如果希望對局能一直玩到「一方秘密真的被套出來」為止，得先搞清楚洩漏機率會不會隨回合數拉長而累積，還是現有的戰術規則（尤其是 `retreat` 保留籌碼）根本沒有「壓力累積到臨界點必須犯錯」的收斂機制，導致模型可以無限期防守下去。

**作法**：新增 `poc/chain_continue.py`，重複呼叫 `continue_director_poc.py`，每次接在上一次輸出的最新 transcript 後面，直到洩漏發生或跑滿指定輪數；每輪都記錄耗時、累計回合數、新增的戰術分布、有沒有觸發洩漏警訊。用昨晚 3 場不同的 6 回合基底（`000609`／`000626`／`000642`）各串 5 輪（6 回合／輪），目標拉到 36 回合。

**結果**：

| 鏈 | 基底角色 | 是否洩漏 | 逐字重複台詞數（36 回合中） | 重複起始位置 |
|---|---|---|---|---|
| 1（`000609`） | 阿土 vs 阿明（雙方無密鑰） | 否，跑滿 36 回合 | 4 句 | 第 27-30 回合的完整對話段落，在第 31-34 回合又原樣重演一次 |
| 2（`000626`） | 冬梅 vs 阿雪（雙方無密鑰） | 否，跑滿 36 回合 | 3 句 | 第 28、29 回合的台詞在第 30-32 回合重複 |
| 3（`000642`） | 石頭(持密鑰) vs 來福 | 否，跑滿 36 回合 | 7 句 | 同一句「奇怪動物與祭壇守護者」的台詞**重複 5 次**（第 22、24、28、30、36 回合），第 20-36 回合基本繞著同一話題打轉 |

三條鏈都花約 53-60 秒（5 輪續寫），沒有任何一次 JSON 崩潰或程式錯誤，速度穩定（每輪 10-13 秒）。

**兩個重要結論**：

1. **「洩漏機率會隨回合數累積」這個假設目前沒有得到支持**：3 條鏈、36 回合，**零洩漏**。核對戰術決策規則會發現，`retreat`（被將軍時保留籌碼撤退）本質上讓模型可以無限期防守，沒有任何機制強迫「懷疑度累積到某個閾值後必須露餡」。這代表單純疊續寫輪數，本身不太可能自然收斂到洩漏——如果要讓對局能穩定走到「秘密被套出來」的結局，需要的是**戰術規則層面的改動**（例如加一條「懷疑度超過某個閾值時，防守方有一定機率被迫露出破綻」），而不是續寫次數的問題。
2. **短 chunk 分批生成，只是把退化問題延後、不是解決**：原本 `MAX_TURNS=6` 的實驗證實了「單一 6 回合 chunk 內部」不會退化，這次串接測試證實了同一個結論**不能外推到串接後的整體**——三條鏈全部在總回合數約 26-32（也就是續寫到第 4-5 輪）左右，開始出現**跨輪次的整段劇情逐字重演**，形式跟原本 10 回合版的「精確循環鎖死」不同（不是同一輪內卡死），但本質是一樣的：模型在缺乏真正新素材、又只看得到「前情提要摘要」而非精確記得自己講過什麼的情況下，開始把之前的劇情節拍原樣搬回來。

**額外印證**：鏈 2（雙方都沒有密鑰的冬梅 vs 阿雪）在第 28-32 回合出現「你握有紅村的核心能源密鑰」這種混合詞——模型自己把「核心能源」跟「密鑰」兩個概念揉在一起，捏造出一個 schema 裡根本不存在的複合概念。這是「非密鑰持有者被拉去談密鑰」這個問題的第三次獨立樣本（另外兩次分別在單輪續寫測試、以及這次鏈 1 也有類似傾向），確定不是單一場次的偶然。

**待決策／後續方向**（先記錄，不擅自動手）：
- 如果要支援「玩到洩漏為止」的完整對局，可能需要在戰術規則裡加入某種懷疑度累積後的強制風險機制，這是遊戲設計層面的決定。
- 續寫時的「前情提要」目前是摘要文字，不含精確台詞記憶，可能是跨輪重複的根因之一；一個可能的緩解方向是在前情提要裡明確列出「已經用過的話題／细节」清單、要求不要重複，但這也跟「加規則會擠壓新鮮度」的既有發現有取捨，需要再測。
- 「非密鑰持有者不該談密鑰」這件事目前已經有 3 個獨立樣本佐證，比較確定是個真實存在、值得優先處理的 prompt 問題（相較於前一項的不確定性更低）。

## 修復：密鑰情節條件化（先修續寫，再回頭修原始 prompt）

**續寫端修復**（`continue_director_poc.py` / `continue_system_prompt.txt`）：
1. 新增 `_two_tier_block()`：雙方都沒有人持有密鑰時，prompt 完全不提「舊神祭壇密鑰」這個概念，只講單層的核心能源機密；有人持有時才用原本的兩層機密說明。
2. 新增 `RECENT_TURNS_WINDOW = 12`：前情提要只帶最近 12 回合，更早的內容直接從 prompt 消失（而不是只用一句「不要重複」的指令去約束），並在文字裡明講「更早之前的內容因篇幅省略，不需要也不應該回頭複述」。

**重測結果（重跑 3 條 36 回合的串接鏈）**：
- 密鑰污染：鏈 2（都沒密鑰）從污染狀態降到只剩 1 句提及；鏈 1（都沒密鑰）續寫本身乾淨，但沿用了「基底 6 回合」（用修復前的舊 prompt 生成）裡已經埋下的假密鑰情節，續寫只是合理地接續了既有設定——**代表同樣的 bug 根源其實在 `director_poc.py` 的原始 prompt，不只是續寫 prompt**。
- 逐字重複：4→0、3→4、7→3，有降但沒有根除，第 19-24 回合這個區間仍然容易出現戰術單一化（例如整輪 6 句全是同一個 tactic），懷疑是取樣層在該區間的敏感點，不是單純靠限制上下文長度就能解決，需要更多樣本才能確認根因。

**原始 prompt 端修復**（`director_poc.py` / `director_system_prompt.txt`，這次的重點）：
1. 把固定的「【機密的兩個層級】」段落改成 `{{TWO_TIER_BLOCK}}`，用跟續寫端一樣的 `_two_tier_block()` 邏輯條件化。
2. 把雙方各自的目標句「（如果對方是密鑰持有者，優先騙出密鑰）」改成 `{{RED_GOAL_KEY_SUFFIX}}` / `{{BLUE_GOAL_KEY_SUFFIX}}`，用新增的 `_goal_key_suffix(opponent_villager)` 依「對手是否真的持有密鑰」精確判斷，而不是雙方都無條件看到這句話。

**驗證（桌機實跑，`AILLEY_MAX_TURNS=6`，共 7 場）**：
- 抽到「雙方都沒密鑰」的一場（`20260717-174508.json`，紅村秀秀 vs 藍村青兒）：全程 6 回合完全沒有出現「密鑰」字樣，對話正常圍繞職業／日常話題（鐵器技巧、神廟守夜），沒有再硬扯進不相關的密鑰情節，修復確認生效。
- 抽到密鑰持有者的場次：說明句、目標句都正常顯示，機制不受影響。

## 穩定度複測（7 場：5 場新場 + 2 場續寫到 12 回合）＋ 新發現的架構性漏洞

**穩定度**：7 場全部零逐字重複、戰術分布正常、motivation/relationship 吻合判斷正確、無 JSON 崩潰。這部分結論是穩定的。

1. 現有偵測邏輯只檢查「發言者有沒有洩漏自己的秘密」，沒檢查「發言者有沒有講出對手的秘密」；
2. `state_delta.reveals_core_energy` 依現有欄位定義（洩漏的是自己 vs 對方）也不會標記這種情況。

## 雲端對照組：OpenRouter 免費模型

**動機**：確認架構本身（角色卡／prompt／洩漏偵測／OpenCC）是不是只在本地 7B 量化模型上有效，換一個完全不同的模型跑跑看。桌機（本地 llama-server）當下連不上，先只跑雲端組。

**架構**：新增 `poc/director_poc_cloud.py`，跟 `director_poc.py` 共用同一份 `director_system_prompt.txt`／世界觀／角色卡邏輯，唯一差異是「怎麼呼叫模型」：改打 OpenRouter 的 `/chat/completions`（OpenAI 相容格式），不是 llama-server 的 `/completion`。因為 OpenRouter 沒有 GBNF grammar 這種取樣層強制 JSON 結構的機制，改成在 prompt 尾端額外加一段「只能輸出 JSON、不要用 code fence」的強調指示，事後用 `_extract_json()`（先抓 code fence，抓不到再抓第一個 `{` 到最後一個 `}`）容錯解析。API key 存在 `poc/.env`（已在 `.gitignore`，不進版控），程式用一個十幾行的簡易 `.env` 讀取器載入，沒有另外裝 `python-dotenv`。

**選模型的過程**：一開始選 `meta-llama/llama-3.1-8b-instruct:free`（想跟本地 7B 量級接近，比較公平），結果這個 slug 已經下架，OpenRouter 回 404 並附上訊息說要改用付費版。查了一次 `/api/v1/models` 目前的免費列表（都是這批新上的模型，跟舊有印象對不上），改用 `openai/gpt-oss-20b:free`（OpenAI 開源權重、20B，指令遵循相對穩定）。可用 `AILLEY_CLOUD_MODEL` 環境變數換其他免費模型。

**4 場實測結果**：

| 場次 | 配對 | 回合數 | 耗時 | 洩漏結果 |
|---|---|---|---|---|
| 1 | 莫古 vs 班 | 6 | 62.7秒 | 未洩漏 |
| 2 | 索菲 vs 傑克 | 5（提前結束） | 62.8秒 | 雙方核心能源都洩漏 |
| 3 | 莫古 vs 傑克 | 6 | 122秒 | 紅村洩漏（藍村講出的） |

**跟本地基準（Qwen2.5-7B）對照**：
- **速度**：雲端免費額度慢非常多（63-122秒／6回合 vs 本地 ~14秒／10回合），推測是免費層限流或排隊，不是模型本身效能問題。
- **JSON 穩定度**：沒有 grammar 鎖定的情況下，4/4 場都靠 prompt 指示 + 事後容錯解析一次成功，沒有崩潰，架構這塊算是換模型驗證通過。
- **簡體污染**：4 場全繁體，0 殘留（比本地過去 10-14% 的殘留率好，但樣本數太小不能下結論，可能只是這個模型訓練語料簡體佔比不同）。
- **跨陣營洩題率明顯偏高**：4 場裡 3 場、共 4 次跨陣營洩題事件（本地過去 7-8 場才抓到 1-2 次）。細看內容，不是「不小心提到」，而是這個模型執行 `bluff`（虛張聲勢）戰術時，會講「我聽說你的核心能源叫『XXX』」去詐對方，但填進去的常常就是**對方真正的核心能源名稱**——等於自己先講出正確答案再問對不對，比 Qwen 那種隨口帶到更系統性，推測是這個 20B 模型在「同時扮演雙方、但要幫其中一方編造假資訊」這件事上，資訊隔離做得比 Qwen2.5-7B 更弱。
- **既有的跨陣營洩題偵測（`opponent_side()` 那段邏輯）在這批雲端場次裡全部正確攔截**，算是意外驗證了這套偵測機制不是只針對 Qwen 的行為模式硬調的，換一個完全不同的模型架構也一樣抓得到。

**後續**：桌機恢復連線後，補跑一次「雲端＋本地同角色配對」的直接對照，會更準確；目前這份先用雲端 4 場結果 vs 筆記裡既有的本地基準做粗略比較。

## 改善對話自然度：方向 A（tactic 加 none 選項）+ 方向 B（豐富世界觀）實驗

**動機**：使用者多次反映生成對話「內容很相似」「不太像日常對話」。釐清問題不是「閒聊不該存在」（這個假設使用者自己已經反駁過），而是**不同場次的閒聊內容彼此雷同、缺乏呼吸感**。追查到兩個結構性成因：

1. `grammar/director.gbnf.template` 第 4 行把 `tactic` 在 GBNF 取樣層硬性列舉成 `bluff/pressure/empathy_bait/misdirect/retreat` 五選一，模型每一回合都被迫貼一個攻防類戰術標籤，沒有「這句只是單純寒暄」的合法輸出。
2. `prompts/world_lore.txt` 只有 5 行，只交代神明/CHO/獻祭主線，沒有具體地點、物件、慣例、次要 NPC，角色閒聊時只能反覆用 few-shot 範例裡出現過的「酒」「神廟」「巡邏」。

**刻意排除的路線**：過去 V2（雙 few-shot）、V3（配額提示，強制至少用三種戰術）都是靠「加規則文字要求模型更多樣化」，結果把重複退化從 reasoning 擠壓到 dialogue 本身，兩版都被否決。這次方案**沒有**加任何「請更自然」「請多樣化」這類期望性指令——方向 A 是擴大 grammar 允許值域（結構改動），方向 B 是補世界觀事實陳述（跟現有語氣一致的陳述句，不是行為規則）。

**環境限制**：本地 llama-server 連不上（桌機當時斷線），兩個方向都改用 OpenRouter 雲端模型（`openai/gpt-oss-20b:free`）跑實驗，等於只驗證了「prompt 層面的行為訊號」，還沒驗證「GBNF grammar 真的在取樣層鎖住 none 選項」這件事——`grammar/experiments/director.gbnf.experiment_none.template` 已經先寫好，等桌機恢復連線要在本地重跑一次才能完整驗證。

### 方向 A 結果（`test_tactic_none.py`，5 組固定配對 + 低衝突配對凱vs班額外重跑，共 7 次嘗試）

- **5/7 場成功解析 JSON**，2 場（都是凱vs班重跑）因為模型輸出 JSON 語法錯誤（元素間漏逗號/引號）解析失敗——**這個失敗率比先前純雲端測試（4/4 成功）高，推測是因為這次 prompt 加了雙 few-shot（misdirect 範例 + none 範例）讓生成變長變複雜，free 模型在無 grammar 保底時更容易出錯**，跟過去筆記「雙 few-shot 有風險，要小心測」的提醒方向一致，只是這次風險體現在 JSON 有效性而非重複退化。
- **none 使用比例 10.0%**，落在預期區間（10%-30%），沒有濫用逃避套話的個案。
- **跨場次逐字重複：0**。
- 人工讀劇本：none 回合的內容確實讀起來像真的閒聊（例：「早晨的露水還在田間閃光...你今天打算去哪裡？」），跟強制攻防的回合語感明顯不同，方向本身有達到「讓對話有呼吸感」的目的。

### 方向 B 結果（`test_world_lore_v2.py`，5 組固定配對）

- **4/5 場成功解析**，1 場失敗（同樣是 JSON 語法錯誤，這次跟 none 或雙 few-shot 無關，此測試用的是正式版單 few-shot prompt，純粹是這個雲端模型本身偶發的不穩定）。
- 其中一場（索菲 vs 米拉）**整場劇本用英文輸出**——跟世界觀內容無關，是這個雲端模型本身偶爾會語言漂移，本地 Qwen2.5-7B 沒出現過這個問題，值得記錄成雲端模型的已知限制。
- **跨陣營逐字重複：0**。
- **舊版話題詞（酒/神廟/巡邏/祭壇）命中大幅下降**：這批只剩「神廟」1 次、「祭壇」1 次，「酒」0 次——過去很常出現的「酒」完全沒再出現，方向是對的。
- **但新素材使用不均**：13 個新增關鍵詞裡只有 4 種被用到（老井、阿柏、老馮、護身符），其中「老井」一個詞就佔了 5 次命中裡的絕大多數，等於話題只是從「酒」換成「老井」變成新的單一收斂點，還沒有真正做到「話題分散」。樣本數只有 5 場，不排除是統計量太小，但這個現象值得記下來，之後如果要擴充素材，可能要观察是不是某些素材（老井這種「取水閒聊」情境）天生比其他素材更容易被模型當萬用開場白。

### 結論：兩個方向都有正面訊號，但暫不併入正式版

對照計畫裡的三項通過門檻（逐字重複沒變差／新穎度提升／人工自然度提升且無濫用），兩個方向都**部分符合但不是乾淨過關**：

- 逐字重複兩者都是 0，符合。
- 新穎度：方向 A 沒有明確的「話題新穎度」可比較基準（本身沒有加新素材，只是加了 none 選項），方向 B 有改善但不均勻（收斂到「老井」）。
- 人工自然度：兩者主觀讀起來都比舊版更自然，但方向 B 出現的英文輸出、方向 A 的 JSON 失敗率上升，都是這次測試才發現的新雜訊，不是原本設計要驗證的東西。

**暫不動正式檔案**（`grammar/director.gbnf.template`／`prompts/director_system_prompt.txt`／`prompts/world_lore.txt` 維持原樣），原因：
1. 這次測試只在雲端免費模型上跑，沒有 grammar 硬鎖，不能代表本地 Qwen2.5-7B + GBNF 的真實行為，尤其方向 A 的核心價值（grammar 層級鎖 tactic 值域）根本沒被測到。
2. 樣本數偏小（各 5-7 場），新穎度/JSON 穩定度的訊號還不夠乾淨到能下定論。
3. JSON 失敗率上升、英文語言漂移是這次意外發現的雜訊，需要先確認是不是雲端模型本身的特性、還是我們改動造成的，才能放心併入。

**新增檔案**（都是實驗檔案，不影響正式版）：`grammar/experiments/director.gbnf.experiment_none.template`、`prompts/experiments/director_system_prompt.experiment_none.txt`、`prompts/experiments/world_lore.experiment_v2.txt`、`test_tactic_none.py`、`test_world_lore_v2.py`。

1. 逐字重複沒有變差——三邊都接近 0（worldlore 唯一的 2 句重複是單場內部問題，不是新增素材造成的跨場次雷同）。

## 方向 C 實驗：續寫「自然收尾」機制——結果不理想，不併入

**動機**：使用者觀察到長對話串接測試（36回合）沒有自然收斂機制——`retreat` 讓模型可以無限期防守，跑到 MAX_TURNS 上限只會印出「未分出勝負」，不像真人對話：真人聊不出東西、懷疑度一直很低，會找藉口結束（要去忙／該睡了），不會被迫聊到某個回合數上限。想測試加一個「自然收尾」機制，續寫最多到 24 回合，懷疑度沒到一定程度就收尾。

**設計**：在 `state_delta` 加一個新欄位 `conversation_ending`（bool），只在 grammar 層級允許最後一回合可以是 true。prompt 規則：懷疑度雙方都在 -3~3 之間、聊了不少回合仍沒進展時，可以在這批新增回合的最後一回合讓角色用藉口（忙農活/該睡了/該巡邏了）自然道別，並把該欄位設 true；其餘情況全部 false。新增 `grammar/experiments/director.gbnf.experiment_natural_end.template`、`prompts/experiments/continue_system_prompt.experiment_natural_end.txt`、獨立的續寫腳本 `continue_director_poc_natural_end.py` 與串接腳本 `chain_continue_natural_end.py`（不動正式版 `continue_director_poc.py`）。

**測試**：8 場，初始 6 回合（正式版 `director_poc.py`）＋最多續寫 4 輪（每輪 6 回合，目標上限 30 回合）。

**結果（不理想）**：
- 8 場全部觸發 `conversation_ending=true`，但**只有 2 場的收尾台詞真的像自然道別**（「夜已深了，我應該回去睡覺了」「我們今天就先聊到這裡，晚安」），其餘 6 場的旗標打在完全沒有告別語氣的普通對話句上——例如「還是比較注重實用。艾爾，你呢？」、「漁船修補生意倒是不錯」，甚至有一場打在明顯還在逼問的句子上：「這聽起來更像是你在掩飾什麼」。
- 觸發過於頻繁：7/8 場在第一輪續寫（累計 12 回合）就結束，只有 1 場撐到累計 24 回合，沒有場次跑滿 4 輪（30 回合）。
- 懷疑度條件也沒有被確實遵守：唯一撐到 24 回合那場複查懷疑度確實一路低迷（紅 -2~-6、藍持平在 -6），符合設計的收尾條件，但其他好幾場收尾時懷疑度其實不低（例：紅 -15 藍 0、紅 -10 藍 +10），跟 prompt 裡「-3~3 才收尾」的規則明顯不符，模型沒有真的照這個條件判斷。

**根因推測**：prompt 把規則寫成「在這批新增回合的**最後一回合**把 conversation_ending 設為 true」，模型可能把這句話理解成「這是這批的最後一回合 → 設 true」的技術性標記，而不是「判斷該不該收尾 → 如果該收尾才設 true」，導致這個欄位幾乎每輪都被觸發，跟懷疑度、跟台詞內容是否真的在道別都脫鉤。

**結論：這個機制目前不建議併入正式版**。這是一次有意義的負面結果——證實「單純加一個 bool 欄位＋文字規則」這種做法在這個情境下不可靠，跟過去 V2/V3 加規則失敗的教訓性質類似（規則本身邏輯合理，但模型沒有確實按照條件執行）。實驗檔案保留，不刪除。

### 修正版：判斷邏輯挪到程式端 + 收尾台詞關鍵詞驗證

**改法**：比照洩漏偵測「不信任 state_delta 自評，靠文字比對驗證」的既有設計哲學，重寫成兩層防護：
1. **懷疑度判斷完全交給程式碼**：`continue_director_poc_natural_end.py` 新增 `suspicion_allows_ending()`，續寫前用既有的 `replay_state()` 算好懷疑度，只有「雙方懷疑度絕對值都 ≤3」且「既有回合數 ≥12（至少跑完初始場+1輪續寫）」才允許收尾。prompt 改用 `{{ENDING_INSTRUCTION}}` 佔位符，程式碼算好結果後動態塞入「【可以收尾】...」或「【不要收尾】...一律固定填 false」其中一段明確指示，模型不用自己評估懷疑度高低，只需要照指示執行。
2. **收尾台詞要通過關鍵詞驗證才算數**：新增 `dialogue_reads_as_farewell()`，比對台詞裡有沒有「晚安/該睡/先走/改天/告辭」這類告別關鍵詞。就算程式端允許收尾、模型也把 `conversation_ending` 設成 true，如果台詞內容比對不到告別關鍵詞，一樣判定無效、不採計，繼續往下跑。

修改檔案：`prompts/experiments/continue_system_prompt.experiment_natural_end.txt`（把【自然收尾規則】換成【自然收尾指示】+ `{{ENDING_INSTRUCTION}}` 佔位符）、`continue_director_poc_natural_end.py`（加兩個驗證函式＋接進主流程）、`chain_continue_natural_end.py`（更新偵測用的 regex，配合新的輸出訊息格式）。

**測試結果（8 場，同樣目標上限 30 回合）**：
- **精準度問題完全解決**：32 次續寫呼叫裡只有 4 次出現 `conversation_ending=true` 的嘗試，其中 2 次是「不被允許卻硬要收尾」被正確攔截，另外 2 次是「懷疑度確實符合、但台詞沒有告別語氣」被關鍵詞驗證擋下——**沒有任何一次誤判成功**，跟上一版「6/8 場誤判」形成鮮明對比。
- **但代價是觸發窗口變得很窄**：這 8 場全部跑滿 30 回合，沒有一場真的自然收尾成功。複查每場在第 12/18/24/30 回合的懷疑度快照，發現懷疑度一旦開始波動，很少會回到低迷區間——常常只有第 12 回合那個檢查點符合「允許收尾」的條件，之後就一路發散（有場甚至到紅=-28、藍=+29），不會再回到 -3~3 這個窗口。
- **這不是這次改動造成的新問題，而是照出了遊戲機制本身的既有特性**：現有戰術規則（`pressure`/`misdirect` 持續施壓）沒有讓懷疑度收斂回穩的機制，呼應筆記更早記錄過的「沒有機制強迫懷疑度累積到閾值後必須犯錯」，這次反過來看到的是同一件事的另一面：也沒有機制讓懷疑度維持低迷夠久。

**結論**：修正版的判斷邏輯是可靠的（0 誤判），但門檻設定（-3~3 絕對值）在目前的懷疑度動態下太窄，導致實用性偏低。

### 第三版：改看「最近一輪淨變動量」而非累積絕對值——判斷條件對了，但模型還是幾乎不用

**使用者提出的關鍵洞察**：問題不該是懷疑度「高不高」，而是懷疑度不管累積到多少，只要**最近幾回合沒什麼波動**，就代表話題卡住、問也問不到、聊什麼都得不到回應，這才是真人會轉話題或結束對話的時機，跟真人對話「卡在尷尬空白」的直覺一致。

**改法**：`suspicion_allows_ending()` 從「看累積懷疑度絕對值 ≤3」改成「看最近 6 回合（一輪份）的懷疑度**淨變動量**絕對值 ≤5」，不管目前懷疑度已經飄到多高多低，只要最近沒什麼進展就算卡住，允許收尾。其餘架構（程式端判斷、關鍵詞驗證）不變。

**測試結果（8 場，目標上限 30 回合）**：
- 「允許收尾」的比例大幅提升：32 個檢查點裡有 15 個符合條件（約 47%），比上一版的 5/32 高很多——這個條件本身確實比較貼近懷疑度的真實波動模式，判斷邏輯這次算是抓對了訊號。
- **但依然 0/8 場真的收尾成功**。複查警訊紀錄，這次連一次「模型嘗試設 conversation_ending=true」的紀錄都沒有——不是被攔截、不是關鍵詞沒比對到，是**模型即使在明確被告知「可以收尾」的情況下，也幾乎從來不主動選擇去用這個欄位**。
- 過程中出現一次腳本中止（JSON 解析失敗），重新手動跑同一份續寫沒有重現，判斷是單次偶發的模型輸出瑕疵（推測跟連續高頻呼叫或取樣隨機性有關），不是這次改動的邏輯錯誤。

**結論**：判斷邏輯（何時允許收尾）這次已經對了，卡點換成了「模型不會主動使用被允許的選項」。這是比前兩版更根本的問題——不是規則寫錯，是「用一句被動允許的指示（『可以收尾』）」對這個模型來說不夠有拉力，模型傾向維持慣性（繼續套話），不會主動抓住一個可選、非強制的收尾機會。

**如果之後要再試，可能要換一種介入方式**：與其給「可以收尾」這種軟性許可，改成程式碼判斷條件符合時直接**強制指示這一輪必須收尾**（不是「可以」，是「這回合就是最後一回合，請收尾」），把決策權完全收回程式端，模型只負責把收尾這件事演出來、不負責決定要不要收尾。

### 第四版：軟性許可改成強制指示——成功了

**改法**：`build_ending_instruction()` 的「允許收尾」分支從「可以收尾」的軟性建議，改成「強制規定：這批新增回合的最後一回合就是收尾回合，這不是你可以自行選擇的事」的硬性指令，明確講「這是硬性規定，不是建議，不能不收尾」。判斷邏輯（最近一輪懷疑度淨變動量門檻）跟關鍵詞驗證都不變。

**測試結果（8 場）**：**6/8 場成功自然收尾**，只有 2 場跑滿 30 回合。複查每場收尾台詞，多數是清楚的道別語氣（「我該去忙了，晚安」「今晚就到這裡吧，我們改天再聊」），但也抓到一個關鍵詞誤判：其中一場的收尾台詞是「我最近應該去看看稻田」，被關鍵詞「該去」誤判成道別（字串剛好命中，但語意完全無關）。

**關鍵詞修正**：把太短的「該去」/「该去」/「我先」這類容易誤命中的詞，換成更完整的片語（「該去忙了」「該去睡了」「先走了」「改天再聊」等），避免字串子集誤判。

**修正後再測（8 場）**：**5/8 場成功自然收尾，這次全部都是真正的道別台詞**，沒有再出現誤判。且驗證機制正確攔截了好幾次危險的誤觸發——例如有一次收尾嘗試的台詞裡混了「你那焚天之魂的核心能源」（涉及機密內容），因為沒有比對到道別關鍵詞被正確擋下，遊戲繼續往下跑而不是提前結束在一句包含機密內容的台詞上。

**結論：這個機制驗證成功，可以考慮併入正式版**。完整的除錯過程（五個版本迭代）證明了兩件事：
1. 「判斷邏輯」跟「指令措辭」是兩個獨立的變因，不能混在一起調——第二、三版已經把判斷邏輯調對（相對變動量門檻），第四版才解決指令措辭的問題（軟性許可→強制指令），兩個問題疊在一起時很容易誤判成同一個原因。
2. 對這個規模的模型，「你可以做 X」這種選擇性許可的指令力度不夠，「你必須做 X」的強制指令才有效——這可能是這類任務型模型指令遵循能力的一般性特徵，之後設計其他條件式行為（不只是自然收尾）時可以優先考慮用強制指令，而不是預設用建議性措辭。

**尚未做的事**：這次驗證都是用新的 `continue_director_poc_natural_end.py`／`chain_continue_natural_end.py`／實驗版 grammar+prompt，還沒有正式併入 `continue_director_poc.py`。如果要正式併入，需要：`grammar/director.gbnf.template` 加 `conversation_ending` 欄位（`director_poc.py` 用的初始生成 grammar 不需要這個欄位，只有續寫需要，可能要讓續寫跟初始生成分開兩份 grammar，不能再共用同一份）、`continue_system_prompt.txt` 補上 `{{ENDING_INSTRUCTION}}` 機制、`continue_director_poc.py` 補上判斷+驗證函式。三個版本的實驗檔案都保留，供併入時參考。

## 岔題實驗：misdirect 轉話題前要不要強制承接——不採用

使用者觀察到收尾前的對話有時讀起來「怪怪的」：misdirect 轉移話題時常常完全不理會對方剛才的問題，直接跳到新話題，像沒聽到對方講話。做了一個小實驗：在 `prompts/experiments/director_system_prompt.experiment_misdirect_bridge.txt` 加一條規則，要求 misdirect 的 dialogue 要先簡短承接對方的話再轉移，並跑 8 場對照組（baseline）vs 8 場新版比較。

**結果好壞參半**：單一次 misdirect 轉折確實有改善（「聽起來你對 NEON 神很虔誠，但我也懷念...」這種先承接再轉移的寫法變多了），但**連續多次 misdirect 疊加時會產生新的重複問題**——有一場連續多回合卡在同一句問句上繞圈（「今晚你會去神廟嗎？」在連續回合裡幾乎逐字重複），違反「每回合要帶新細節」的規則，而且這種句尾重複不會被現有的整句重複偵測抓到（因為每句前半段不同）。戰術分布也往 misdirect/none 傾斜（misdirect 35.4%→45.8%，pressure/bluff/empathy_bait 合計從約50%掉到約23%），可能改變遊戲攻防節奏，不只是修文字銜接的問題。

**結論：不採用**，代價（新的重複退化＋攻防節奏改變）大於效益（單次轉折變自然）。實驗檔案保留（`prompts/experiments/director_system_prompt.experiment_misdirect_bridge.txt`），`test_local_batch.py` 也保留了 `misdirect_bridge` 這個變因設定供之後參考，但不建議直接沿用這個版本的規則寫法——如果之後要再試，需要解決「連續 misdirect 疊加」這個新問題，例如限定「只有連續 misdirect 的第一次才要求承接」。

## 正式併入：續寫自然收尾機制

使用者確認後正式併入（misdirect 承接實驗不採用，只併入自然收尾），改動的檔案：

- 新增 `grammar/continue_director.gbnf.template`：複製自 `grammar/director.gbnf.template`，`state-delta` 多一個 `conversation_ending` bool 欄位。初始生成的 `director.gbnf.template` 保持不動，兩者從此分開維護（原因見上方問答：初始生成沒有歷史可以判斷「卡不卡住」，這個欄位對它沒有意義，共用同一份反而會逼初始生成也要處理一個用不到的欄位）。
- `prompts/continue_system_prompt.txt`：戰術規則區塊加【自然收尾指示】+ `{{ENDING_INSTRUCTION}}` 佔位符，`state_delta.conversation_ending` 欄位說明補上。
- `continue_director_poc.py`：加入 `recent_suspicion_movement()`／`suspicion_allows_ending()`／`build_ending_instruction()`／`dialogue_reads_as_farewell()` 四個函式（跟實驗版最終定案完全一致：相對變動量門檻、強制指令措辭、修正後的告別關鍵詞列表），`main()` 裡接上：讀取 grammar 改成 `continue_director.gbnf.template`、prompt 組裝加 `{{ENDING_INSTRUCTION}}`、播放迴圈加收尾驗證（懷疑度允許 + 關鍵詞比對雙重檢查，任一失敗就當作沒收尾繼續跑）。
- `chain_continue.py`：新增自然收尾偵測（跟洩漏偵測並列的第二種停止條件），偵測到就記錄「自然收尾（累計 N 回合）」並停止繼續串接下一輪。

**煙霧測試（桌機，端到端）**：
1. `director_poc.py` 跑 2 場初始生成——完全不受影響，其中一場正常因為密鑰洩漏結束（既有邏輯，跟這次改動無關），另一場正常跑完 6 回合無洩漏。
2. `continue_director_poc.py` 對 6 回合的場次續寫一次——正確印出「不收尾」（既有回合數 6 < 12 門檻），續寫正常運作。
3. `chain_continue.py` 對 12 回合的場次跑 4 輪續寫——**第 18 回合有一次收尾嘗試被關鍵詞驗證正確擋下**（台詞「你對這些護身符的看法呢？」沒有道別語氣），繼續往下跑；**第 36 回合真正收尾**，台詞「天色已經不早了，我應該回去看看今晚的巡邏安排了。晚安。」清楚承接前一句話題（漁船記號）再帶出離開理由，`chain_continue.py` 正確偵測並停止，寫入 `chain_log_*.json`。

三層驗證（初始生成不受影響、單次續寫的門檻判斷正確、長鏈的收尾偵測+驗證雙重機制都正確運作）全部通過，正式併入完成。

## MAX_TURNS 決定：從 10 改成 6，有數據支持了

這個決定猶豫了很久（多次筆記標記「待團隊一起看過再決定」），這次用全套修復後的正式版（tactic none + 豐富世界觀）跑一次乾淨的對照實驗，兩邊各 15 場，才有足夠樣本下定論。

**結果**：

| | MAX_TURNS=6（15場） | MAX_TURNS=10（15場） |
|---|---|---|
| 逐字重複場次 | 0/15 | 2/15（13.3%） |
| 平均每場用到幾種戰術 | 3.6 | 3.13 |

**兩場 MAX_TURNS=10 的重複都是同一種模式**：第 7-8 回合的對話原封不動在第 9-10 回合重演一次，形成兩回合一循環的迴圈，而且都精準卡在第 7 回合開始——這正好重現並量化了筆記裡很久以前就懷疑過的「第7-10回合容易退化」問題，這次終於有乾淨數據佐證。

**推翻了原本的假設**：一直以來擔心「回合數變少會犧牲攻防深度／戲劇張力」，但這次數據顯示相反——MAX_TURNS=6 平均用到 3.6 種不同戰術，比 MAX_TURNS=10 的 3.13 種還多。推測長場次卡進重複迴圈的那幾回合，戰術也跟著卡死在同一兩種，反而拉低了整體多樣性。

**決定：預設 MAX_TURNS 從 10 改成 6**。改動檔案：`director_poc.py`、`director_poc_cloud.py`（兩處預設值同步）。桌機跑過煙霧測試確認正常運作。

## `reasoning` 欄位定案：會做成玩家可見的「讀心」視角

延續前面「待討論：`reasoning` 欄位要不要對玩家隱藏？」的懸案，這次跟使用者確認：**`reasoning` 會做成玩家可見的讀心/觀戰視角**。關鍵理由是遊戲內的洩漏偵測邏輯只比對「發言者對發言者」的 `dialogue`，不會去讀 `reasoning`，NPC 之間也不會互相感知對方的內心獨白——所以讓玩家看到 reasoning，不會反過來影響遊戲內的洩漏判定或事件觸發，純粹是多一層觀戰資訊。

這個決定連帶產生兩個影響：
1. 原本標記「reasoning 重複退化，反正玩家看不到，優先度低」的舊結論不再成立，這次重新升級為要處理的問題。
2. reasoning 直白講出機密，算不算「爆雷」，要看讀心是不是有成本/次數限制的能力，還是預設常駐視角——**這個設計問題使用者明確表示這次先不決定**，只處理重複退化這個技術缺陷本身。

## 重新驗證：MAX_TURNS=6 沒有解決 reasoning 重複退化

**假說**：`MAX_TURNS=6` 的決定（見上一節）是用單場 6 回合的乾淨對局驗證的，一直沒有在「串接成長鏈」的情境下重新測過 reasoning 重複——原本猜測既然單場乾淨，串接應該也會比舊的 10 回合版好。

**驗證**：`AILLEY_MAX_TURNS=6` 起始場 + `chain_continue.py` 續 5 輪疊到 36 回合，跑 8 條鏈，逐一用 `difflib.SequenceMatcher`（相似度 ≥0.8）比對 reasoning／dialogue。

**結果：假說不成立**。8 條鏈裡 **6 條（75%）出現 reasoning 重複**，跟 MAX_TURNS 大小無關——重複最早在第 3-5 回合就開始出現，不是只發生在長場次的尾段。**改用真實對話內容覆核後，發現原本「reasoning 重複、dialogue 保持新鮮」的印象也不完全準確**：8 條鏈裡至少有 1 條出現**逐字複製的 dialogue**（玩家看得到的台詞），另有 1 條是「模板重複但替換掉名詞」的變體重複——這代表退化沒有乾淨地限制在 reasoning 欄位，只是機率上比較常發生在那裡。

**結論（重新框定根因）**：這不是「MAX_TURNS=10 尾段退化」的特例，而是 `chain_continue.py` 這種**接續生成**架構本身的產物——同一位角色的第 N 回合 vs 第 N+2 回合（自己跟自己的下一輪發言）結構性地容易重複，尤其集中在 `misdirect`／`pressure` 這種懷疑度沒什麼推進的戰術迴圈場景。既然 reasoning 現在要做成玩家可見內容，這個問題的優先度提高。

## 修復嘗試：`repeat_guard`——呼叫前偵測重複、注入具體正面指令

**設計原則（吸取專案舊教訓）**：`continue_system_prompt.txt` 裡其實已經同時存在「不能重複使用」（負面）跟「請帶一個新的具體細節」（正面）兩種指令，但重複仍然發生——代表泛用型指令（不管正負面）已經到頂。這次改成**證據具體化**：不是再加一條通用規則，而是在呼叫模型前，程式先比對最近 12 回合裡有沒有近似重複（`difflib` ≥0.8），偵測到就把「具體是哪一句」引用回 prompt，指示針對同樣情境換一個新角度講。

第一版口頭提案用了「禁止用相同或極相似的句子」這種禁止式措辭，被使用者當場攔下——這正是筆記裡記錄過的 V3 失敗模式（3.8B 模型收到「禁止重複」後把所有欄位清空）。修正為純正面表述，實際實作的 `build_repeat_guard_block()` 引用偵測到的具體句子，要求「針對同樣的情境想一個具體不同的新角度、新細節或新的問法」。

**實驗架構**（完全獨立於正式版，比照專案一貫的實驗紀律）：新增 `continue_director_poc_repeat_guard.py`（複製自 `continue_director_poc.py`，加 `detect_recent_repetition()`／`build_repeat_guard_block()`）、`chain_continue_repeat_guard.py`（複製自 `chain_continue.py`，只改呼叫目標）、`prompts/experiments/continue_system_prompt.experiment_repeat_guard.txt`（插入 `{{REPEAT_GUARD_BLOCK}}`）。

**測試**：5 條鏈，同樣 MAX_TURNS=6 起始 + 續 5 輪疊到 36 回合。

**結果：沒有改善，甚至略差**（4/5 = 80% 出現重複，vs baseline 6/8 = 75%，樣本數小不算顯著差異，但確定沒有變好）。

**追查出真正原因——repeat_guard 的架構性死角**：逐一比對這次抓到的重複位置，發現重複幾乎都發生在**同一次生成呼叫產出的 6 回合內部**（例如第 9 回合 vs 第 11 回合，兩句都屬於同一輪續寫呼叫的輸出），不是跨越兩次呼叫。`repeat_guard` 是在「呼叫模型之前」比對歷史、把提示塞進 prompt——但它只看得到上一次呼叫**已經產生完**的內容，對模型這一次呼叫正在生成的 6 回合內部自我重複完全沒有插手機會（模型是一次性把 6 回合生完的）。

**結論：這個修復方向本身管不到問題的主要來源**，需要換一種介入時機——不是「生成前給提示」，而是「生成後檢查，若批次內部就有重複則整批重新生成」，才可能對準病灶。這個新方向還沒有開始驗證，記錄待辦。

## 發現：遠端 `-c 4096` context 上限是 JSON 中止的根因（獨立於 repeat_guard 問題）

repeat_guard 那批測試中，5 條鏈有 2 條在第 2 輪續寫（12→18 回合）時中止，JSON 在字串或欄位中間被硬生生截斷（例如 `"dialogue": "我最近確實去過渡口，那裡的米酒和護身符都很受歡迎，`、`"reveals_altar_key": false,`）。相對 baseline（8 條裡只有 1 條中止），比例明顯偏高（40% vs 12.5%）。

**查證**：遠端 llama-server 啟動參數是 `-c 4096`（`~/Ailley/llama.cpp/build/bin/llama-server -m Qwen2.5-7B-Instruct-Q4_K_M.gguf -ngl 99 -c 4096 -fa on`），`continue_director_poc.py` 呼叫時 `n_predict: -1`（不設生成長度上限，生成到 context 用完為止）。查 server log，中止那兩次請求的 `slot release` 顯示 `n_tokens = 3614～3880`，非常接近 4096 的上限。

**結論**：這是 **context 空間被榨乾**造成的硬截斷，跟 JSON 格式或 grammar 本身無關。中止率在 repeat_guard 版變高，是因為失敗都發生在「第 2 輪續寫」（prompt 已經帶 12 回合前情提要，本來就比第 1 輪更接近上限），`{{REPEAT_GUARD_BLOCK}}` 又多塞了一段文字進 prompt，進一步壓縮了留給生成的剩餘空間——**中止率問題是 repeat_guard 讓 prompt 變長的必然副作用，但跟 repeat_guard「有沒有效」的結論無關（那個結論已經由架構性死角本身解釋了）**。

**待辦（需要重啟遠端主機才能處理，目前擱置）**：把 `-c` 調大（例如 8192），重啟遠端 llama-server 服務。這是操作層面的設定變更，使用者目前無法重啟遠端主機，先記錄待辦，不急著處理——因為就算中止率解決，也不影響 repeat_guard 已經確認的核心結論（管不到 intra-batch 重複）。

## 遠端主機重啟：`-c` 調大到 8192，部署與重啟紀錄

**部署**：因為使用者當下不方便親自重啟遠端主機，先做成「別人也能一鍵重啟」的形式——新增 `~/Ailley/stop_llama_server.sh`（`pkill` 掉舊的 llama-server）、`~/Ailley/start_llama_server.sh`（用 `-c 8192` 重新啟動，取代舊的手動 `nohup ... -c 4096 ...` 指令），都已 `chmod +x`，不用記參數。

**實際重啟**：後來使用者確認可以直接執行，透過既有 SSH 存取直接跑了 `stop_llama_server.sh` → `start_llama_server.sh`，健康檢查 `{"status":"ok"}`，新的 `-c 8192` 版本已上線運作。

## Context 修復後複測：repeat_guard 5 條鏈——中止率解決，但重複問題比預期更嚴重

在新的 `-c 8192` 上重跑一次前面同樣的實驗（`repeat_guard_chain.sh`，5 條鏈，MAX_TURNS=6 起始 + 續 5 輪疊到 36 回合）。

**中止率**：**5/5 全數跑滿，0 次中止**（修復前是 2/5 因 context 用盡被硬截斷）。確認 `-c 8192` 徹底解決了長鏈續寫的 JSON 截斷問題。

**機制確認真的有觸發**：繞開先前發現的「chain_continue 不轉發子行程 stdout」問題，直接手動單獨跑一次 `continue_director_poc_repeat_guard.py`，確認印出：
```
[repeat_guard] 偵測到紅村近期重複（reasoning，相似度0.86）：「伊諾最近一直強調信仰的重要性...」，已把具體指令塞進 prompt
```
`detect_recent_repetition()`／`build_repeat_guard_block()` 本身沒有 bug，確實有偵測到重複、也確實把具體指令塞進 prompt——排除了「機制根本沒觸發」這個可能性。

**但重複結果比修復前更嚴重**：**5/5 條鏈全部出現重複**（修復前是 4/5），且這次出現大量**大範圍串連重複**、多組相似度 **1.0（完全一字不差）**，包含玩家看得到的 dialogue，不是零星一兩句——例如一條鏈裡第 15、23、29 回合的台詞完全相同，另一條鏈從第 14 回合起幾乎持續每隔幾回合就在複製前面的內容，直到第 36 回合。

**原因**：修復前的「4/5」其實低估了問題——當時 5 條鏈裡有 2 條中途因 context 截斷被腰斬（只跑到 12 回合），根本沒機會進入容易退化的中後段。這次 context 修好、全部真正跑滿 36 回合，才第一次完整看到「跑到底」的真實退化程度。

**結論不變、但證據更確定**：repeat_guard（呼叫前偵測、注入提示）機制運作正常，但管不住問題的主要來源——**同一次生成呼叫（一次吐 6 回合）內部的自我重複**，guard 只能作用在「呼叫之間」，對「呼叫當下」無能為力。而且這次資料顯示退化比原本以為的更系統性：一旦進入第 14 回合左右，模型往後很容易持續複製貼上前面的內容，不是偶發個案。

## 修復嘗試：batch_regen（生成後偵測＋整批重新生成）v1——有改善但沒解決，新發現複誦副作用

新增 `continue_director_poc_batch_regen.py`／`chain_continue_batch_regen.py`（複製自 repeat_guard 版本）：呼叫模型完成後，額外比對這次新生成的 `new_turns` 彼此之間、以及跟最近歷史有沒有近乎重複；有的話帶著具體重複句整批重新生成，最多重試 3 次（`AILLEY_MAX_REGEN_ATTEMPTS`）。順便修掉 `chain_continue_repeat_guard.py` 那個「不轉發子行程 stdout」的既有 bug，改成把 `[batch_regen]` 開頭的診斷行轉發並存進 log 的 `regen_log` 欄位。

**驗證（5 條鏈，同構方法論）**：逐字重複場次從 repeat_guard 的 5/5（100%）降到 **4/5（80%）**，有改善但沒解決。追查發現兩個限制效果的具體原因：
1. **「卡住的鏈」重試 3 次也救不回來**：一旦一條鏈進入話題迴圈（雙方反覆用 misdirect、懷疑度沒進展），幾乎每一輪都用滿 3 次重試仍然失敗——單純重打同一批換不出真正新內容。
2. **意外副作用：模型會把注入的提醒文字複誦回內容**——reasoning 欄位直接寫出「米拉最近的內心想法已經出現過跟這句很像的內容，回應塔克的問題，但不透露更多資訊。」，幾乎是把提示原文抄回去，防重複指令本身變成新的重複素材。

耗時也明顯拉長（多數輪次要重試 2-3 次）。

## 修復嘗試：batch_regen v2——改提示措辭 + 卡住時強制換方向，效果顯著

針對上面兩個問題原地修正 `continue_director_poc_batch_regen.py`（沿用自然收尾機制 v1→v4 的迭代模式，不開新檔）：

1. `build_repeat_guard_block()` 改寫：重複句只引用前 24 字＋刪節號，明確標註「劇本安排提示，不是村民心聲」，加一句正面表述要求輸出維持角色真實發言、不需要提到「已經講過」這件事。
2. 新增 `STUCK_TOPIC_HOOKS`（8-10 條沿用 `world_lore.txt` 詞彙的中性場景引子）與 `build_stuck_topic_instruction()`：偵測「卡住」（這輪一開始歷史就已重複，或這輪已經失敗過一次）時，用「強制規定」句式（沿用自然收尾 v4 驗證有效的措辭）指定一位村民要自然帶出一個具體新話題。

**驗證（5 條鏈）**：逐字重複場次降到 **2/5（40%）**，是這系列實驗以來最好的結果，其中一條鏈（`塔克 vs 伊諾`，36 回合）完全零重複。複誦副作用**完全消失**（0 次命中提示語特徵字串）。`regen_attempts` 大幅下降（多數輪次 1 次就過），總耗時也跟著降低。殘留的 2 個重複都只是單一組、發生在鏈的最後一輪，不再是大範圍串連退化。

**額外印證機制真的在起作用**：那條零重複的鏈裡，第 29、31 回合的台詞幾乎是 `STUCK_TOPIC_HOOKS` 常數的原文（「芷姨在市集又聽到什麼消息，逢人就想聊上兩句」「哨站的守衛換班時，提到昨晚巡邏時聽到田埂那邊有點動靜」），模型把它自然編織進台詞當轉折點，第 32 回合對手也真的接住了新引子往下發展，不是硬插一句就結束。

**結論：batch_regen v2 達到通過標準，可以考慮併入正式版**，待使用者確認。

## 新發現：misdirect 標籤跟遊戲狀態脫鉤，不代表真的有壓力

複查 batch_regen v2 那條零重複的鏈時發現：第 13-31 回合連續近 20 回合都標 `misdirect`，但 `state_delta.suspicion_change` 大多是 0 或負值，聊的內容（老井水質、鐵匠鋪防禦器具、茶棚遮陽篷）也確實跟機密無關。根因：`state_delta.suspicion_change` 是模型自己每回合自由填的數字，跟 `tactic` 標籤完全沒有程式面的綁定，戰術規則裡「對方逼近真相 → misdirect」只是文字描述，不是強制條件，模型容易把 misdirect 當成低風險預設標籤。

## 修復嘗試：misdirect_settle（misdirect 只標轉折點）——沒有生效，不併入

延續上面的發現，補一條規則（跟既有規則同構的「條件→選項」句式，正面表述）：「misdirect 只用在主動轉開話題的那一句；轉開之後如果對方沒有重新逼近追問，接下來聊新話題的回合請回到 none」。新增 `continue_director_poc_misdirect_settle.py`／`chain_continue_misdirect_settle.py`／對應實驗版 prompt，**刻意跟 batch_regen 分開測**（不同變因，避免混淆歸因）。

**驗證（5 條鏈，不含 batch_regen 機制）**：**沒有達到效果**。同一發言者「misdirect 之後接著又是 misdirect」34 次，接成 `none` 只有 2 次；最長連續 misdirect 段落 `[2, 4, 2, 5, 13]`，其中一條鏈連續 13 回合仍掛 misdirect，比之前任何一批都長。逐字重複率 5/5（100%），比同樣沒有 batch_regen 的 baseline（6/8＝75%）還差（樣本小，但至少沒有變好）。

**結論**：這條規則要求模型做的是隱性追蹤判斷（回想自己是否已經成功轉開話題、對方有沒有重新逼近），比其他「當下這一句就能反應」的規則需要更深的推理層次，加上它排在規則區塊的第 6 條、不特別顯眼，模型幾乎沒有照做——跟自然收尾機制第三版「軟性許可」踩到的坑同一種模式：**純文字建議對這個模型的拉力不夠**。按原訂通過標準（misdirect 連續段落要明顯縮短），**不建議併入正式版**，保留實驗記錄。如果要繼續這個方向，比較可能有效的做法是仿照 batch_regen 的「卡住強制換方向」：程式端數清楚連續 misdirect 次數，超過門檻就用強制指令逼一句改用其他 tactic，而不是寫進 prompt 期待模型自己判斷。
