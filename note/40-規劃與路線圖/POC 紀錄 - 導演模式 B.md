# POC 紀錄 — 模式 B（導演·整場生成）

> [!info] 背景
> 2026/07/13 專案戰略修正：從舊構想（山谷多人 NPC 沙盒，見 [[開發路線圖]]／[[MVP 範圍]]）轉向 **AI vs AI 社交工程對戰觀察遊戲**（紅藍村互套 Flag，玩家零介入）。死線 2026/08/21，7/16 要交模組 B（AI 推論與 Prompt 工藝）三項產出：JSON Schema、GBNF Grammar 草稿、System Prompt 草稿。腳本位置：`poc/director_poc.py`。

## 環境
- 硬體：僅 Intel Iris Xe 內顯（無獨顯），Vulkan backend。
- `llama.cpp` 編譯依賴：`vulkan-headers`、`shaderc`、`spirv-headers`、`spirv-tools`（一開始都沒裝，逐一補齊才編譯成功）。
- 模型：Phi-3.5-mini-instruct Q4_K_M GGUF（bartowski），因無獨顯，先選 3.8B 而非文件建議的 8B。

## 踩坑：GBNF 規則名稱不支援底線
`llama.cpp` 目前的 grammar parser（`is_word_char`）規則名稱只允許 `a-z A-Z 0-9 -`，**不支援底線**。
`state_delta` 拿來當規則名會直接 parse 失敗（`expecting name`／`expecting newline or end`）。JSON 欄位字串裡的底線沒問題（在引號內），只有規則名本身不能有底線。改成 `state-delta` 後正常。

## 踩坑：模型會用最小合法解偷懶
第一版 prompt 只描述規則、沒給範例，且陣列量詞用 `*`（0 個以上皆合法）。結果模型只生 1 回合，內容是字面上的 `reasoning here`、`台詞內容`——直接抄 prompt 措辭當輸出，而非真的產生內容。

修正兩件事：
1. **grammar 層面**：`(ws "," ws turn)*` 改成 `(ws "," ws turn){9}`，用 GBNF 的 `{n}` 精確重複，強制剛好 10 回合，不靠 prompt 拜託。
2. **prompt 層面**：加一段 few-shot（示範一個完整回合的 reasoning + dialogue 長什麼樣），並明文禁止使用「reasoning here」之類字樣。

修正後模型改為輸出有實質內容的中文對話，戰術（misdirect/pressure/empathy_bait）有依規則變化，沒有洩漏 flag。語言品質偏粗糙（小模型中文常見的邏輯跳躍），但已經是「真攻防」而非「作文佔位」。

## 關鍵發現：效能落差 ⚠️（已在獨顯機器驗證，落差主因是硬體）
> [!warning] 這點直接影響 7/16 表決
> Intel Iris Xe 內顯（Vulkan）：10 回合完整劇本耗時 **約 513 秒（8.5 分鐘）**，token 速度約 5.1–5.3 tok/s。
> 換到 RTX 3070 獨顯（CUDA，WSL2）後：同一份腳本、同一顆模型，10 回合耗時 **18.27 秒**，約快 **28 倍**。
> 結論：handoff 文件設想的「導演模式單次呼叫、近即時」在有獨顯的機器上是成立的，落差主因確實是硬體而非架構設計問題。團隊排 POC/展示機器時，要避開純內顯筆電。

### 環境二：RTX 3070 + WSL2（CUDA backend）
- 桌機規格：AMD Ryzen 5 5600X、ASUS TUF GAMING B550M-PLUS(WI-FI)、RTX 3070 8GB。
- 踩坑重點（供其他人準備獨顯機器參考）：
  1. Windows 上 `dism /get-featureinfo` 回報的功能狀態不可信，要用 `Get-WindowsOptionalFeature -Online` 才是準的——這台機器 DISM 顯示 WSL／VirtualMachinePlatform「已啟用」，但實際上是 Disabled，重開機好幾次都沒用，換指令重新 `Enable-WindowsOptionalFeature ... -All` 才真的裝上。
  2. `bcdedit /set hypervisorlaunchtype auto` 也要記得設，不然開機不會啟動 Hypervisor。
  3. 機器上如果原本裝了 VirtualBox，它的核心驅動 `VBoxSup` 會搶佔 AMD-V/VT-x，跟 WSL2 需要的 Windows Hypervisor Platform 衝突，必須移除或確保它不在開機時載入。
  4. CUDA Toolkit 要裝 **WSL-Ubuntu 專用 repo**（`developer.download.nvidia.com/compute/cuda/repos/wsl-ubuntu/...`），不用另外裝驅動，WSL2 直接借用 Windows host 的顯卡驅動。
  5. 透過 Windows 內建 OpenSSH Server 遠端操作時，`wsl.exe` 本體在非互動式 SSH session 下會卡死或無回應（ConPTY 無法建立），因此改把 SSH server 直接裝進 WSL 內部的 Ubuntu，用 `netsh interface portproxy` 把 Windows 某個 port 轉發進 WSL 內部 IP 的 22 port，之後直接 SSH 進 Linux 本身，繞開 `wsl.exe` 這層。

### 新發現：後段回合內容重複退化
18.27 秒那次的輸出，第 1～5 回合語意正常、有攻防轉折；但**第 7～10 回合明顯陷入重複迴圈**，句型幾乎照抄前一句（「那真是讓我感到...那我的 Flag 也是我的」）。這跟速度快慢無關，是另一個獨立的內容品質問題——推測是 3.8B 小模型在長輸出後半段容易掉入自我重複的已知弱點，需要之後調整 `repeat_penalty`／`temperature`，或考慮換更大的模型（例如 7-8B）看是否改善。

### 修正嘗試記錄：`repeat_penalty` 對這顆小模型不管用
在獨顯環境上針對「後段重複退化」試了三種修正，結果如下（供之後其他人別重踩）：

| 嘗試 | 做法 | 結果 |
|---|---|---|
| 1 | `repeat_penalty=1.3` | 更糟：多回合 reasoning/dialogue 變空字串，且大量夾雜英文（小模型中文詞彙被重複懲罰逼去英文空間） |
| 2 | `repeat_penalty=1.1` | 更糟：內容整場退化回最初的 `"..."` 佔位字樣，且模型生成大量空白/換行導致 JSON 直接解析失敗 |
| 3 | prompt 加一段強語氣「禁止重複」規則（`repeat_penalty` 關閉） | 更糟：全部 10 回合 reasoning/dialogue 皆為空字串——推測強制型負面規則（「不可以」）讓模型把「什麼都不寫」當成最安全的合規解 |
| 4 | prompt 改成正面表述「每回合請帶一個新的具體細節」（`repeat_penalty` 關閉） | **目前最佳版**：前 5～6 回合內容扎實、有具體情節推進，第 7～10 回合仍會收斂重複，但程度從「災難性崩壞」降為「輕微重複」 |

結論：`repeat_penalty` 跟這顆 3.8B 模型 + GBNF 強制結構的組合非常不穩定，容易把模型逼進新的偷懶模式（清空欄位、語言跑掉、JSON 崩潰），不建議在小模型上繼續調這個參數。prompt 用正面表述比負面禁止式更穩，但後段重複是模型容量的天花板，不是 prompt 工程能完全解決的。

後續需要驗證/決策的方向：
- 縮小 `MAX_TURNS`（例如先測 5～6 回合，落在目前觀察到「內容還扎實」的範圍內）作為權宜對策。
- 既然獨顯下速度已經足夠快，模式 C（導演·逐回合）的急迫性降低，但仍可保留作為純內顯環境的備案（見 `neon/ailley_poc_handoff.md` 第 6 節）。

## 換模型驗證：Qwen2.5-7B-Instruct 明顯優於 Phi-3.5-mini
在 RTX 3070 上換裝 **Qwen2.5-7B-Instruct-Q4_K_M**（阿里出品，中文原生訓練，約 4.7GB）重測，同一份 prompt（正面表述版）、`repeat_penalty` 關閉：

- **速度**：14.21 秒／10 回合，比 3.8B 的 Phi-3.5-mini 還快（Qwen 話講得精簡，token 數少）。
- **語言品質**：句子完全通順，無邏輯跳躍，劇情持續推進具體細節（猜謎遊戲→村長的秘方→神秘人→藍色披風），五種戰術標籤都有合理切換。
- **重複問題換了位置**：`dialogue`（玩家實際看到的台詞）從頭到尾都在推進新內容，沒有重複；但第 7～10 回合的 `reasoning`（內心獨白）連續四回合幾乎一字不差。

**結論**：Phi-3.5-mini（3.8B，英文為主）換成 Qwen2.5-7B-Instruct（中文原生）後，對話本體品質大幅提升，重複退化的影響範圍從「玩家看得到的台詞」限縮到「相對次要的內心獨白」。**建議之後 POC／展示都改用 Qwen2.5-7B-Instruct 當預設模型**，Phi-3.5-mini 只適合純內顯、極限硬體下的備案。

### 待討論：`reasoning` 欄位要不要對玩家隱藏？
這次 Qwen2.5-7B 的完整十回合輸出中，第 7～10 回合的 `dialogue`（玩家看得到的台詞）持續帶入新細節（村長的秘方→陌生人→藍色披風→昨晚不在場的撤退說詞），完全沒有卡住；但同一段時間的 `reasoning`（內心獨白）連續四回合一字不差重複「他提到村長的秘方，這讓我想起昨晚在村長家見到的一個陌生人。」

這代表目前觀察到的重複退化幾乎只發生在 `reasoning` 欄位，不影響玩家實際會看到的 `dialogue`。一個可能的因應方向：**如果最終產品不會把 `reasoning` 直接展示給玩家（例如只做為內部除錯／後端記錄用），那這個瑕疵對玩家體驗的實際影響就很小，可以考慮不用急著在 prompt/取樣層面解決**。但這牽涉到「內心獨白」是不是遊戲設計上想呈現給玩家的內容（例如做成類似「讀心」的觀戰視角），需要跟其他模組（前端/遊戲設計）一起確認，先记录下來留待團隊討論，這次不直接動手拿掉這個欄位。

### 修正嘗試：戰術缺乏變化 — 三版 prompt 對照實驗
針對上面「tactic 全程卡在 misdirect」的問題，設計三個 prompt 變體（各自獨立於 `poc/prompts/experiments/`），對著 RTX 3070 + Qwen2.5-7B server 各跑一次驗證。同時給 `director_poc.py` 加了 `sys.argv[1]` 可覆蓋 prompt 檔路徑的功能，方便切換測試不影響正式版。

| 版本 | 做法 | 戰術多樣性結果 | 內容品質結果 |
|---|---|---|---|
| 基準版（現行正式版） | 原 prompt，隱含戰術規則 | 10/10 全用「轉移話題」 | dialogue 全程扎實無重複，reasoning 第 7-10 回合重複 |
| V1 顯性核對（`tactic_v1_explicit_check.txt`） | reasoning 裡加一句「先核對累積懷疑度數值再選戰術」 | 仍 10/10 全用「轉移話題」，`suspicion_change` 全程變 0 | 沒解決多樣性，數值波動反而消失，是退步 |
| V2 雙 few-shot（`tactic_v2_multi_fewshot.txt`） | few-shot 從 1 個範例擴成 2 個，分別示範 misdirect 與 pressure | 紅村穩定用轉移話題／藍村穩定用步步進逼（2 種戰術，依角色分化） | 有改善，但第 7-10 回合 **dialogue 本身**開始出現近乎重複句型，比基準版更差（基準版只有 reasoning 重複） |
| V3 配額提示（`tactic_v3_quota_nudge.txt`） | 加一句正面表述「整場至少用三種不同戰術」 | 用到 4 種戰術（empathy_bait/pressure/misdirect/bluff），多樣性最佳 | 但第 7、9 回合與第 8、10 回合 **dialogue 完全一字不差重複**，退化程度比 V2 更嚴重，且首度外溢到玩家看得到的台詞 |

**結論**：越明確/量化的戰術指令（V2、V3）確實能改善戰術多樣性，但代價是把原本只發生在次要欄位 `reasoning` 的後段重複退化，往外擠壓到玩家看得到的 `dialogue`——推測是小模型的「指令遵從預算」有限，加越多規則進去，後段能維持新鮮度的空間就越少。**三版都不建議直接取代正式版 prompt**。若要繼續往戰術多樣性方向優化，下一步應該是把 V2/V3 的方向搭配「縮小 `MAX_TURNS`」（例如 6-7 回合，見上面的未驗證待辦）一起測，賭在後段重複退化生效之前就結束劇本，而不是繼續加規則。

## 世界觀擴充：CHO / TAMMY神 / NEON神 設定 + 角色隨機生成（Phase 1 POC）

團隊確認了完整世界觀：村民是擁有核心能源的類人生命體，紅村侍奉 TAMMY 神、藍村侍奉 NEON 神；異界 CHO 墜落汙染兩位舊神，向村民下神諭要求獻上五顆核心能源（＝其中一村的村民數）作為祭品才能淨化汙染。對應到遊戲機制：**核心能源＝村民 Flag**、**舊神祭壇密鑰＝村莊 Flag（可操作村民 Flag 的權限）**、CHO 蒐集 5 個 Flag 淨化剩餘村民。

延伸出的問題：能不能先做「兩村各隨機生成 3-5 位村民（性格＋職業），出村時互相隨機相遇對話」的 POC？評估後這其實是兩件事：(a) 世界觀落地成 prompt 素材（低成本，沿用現有架構）；(b) 真正的 N 人動態配對相遇（需要重寫 `speaker` 從固定 `red/blue` 改成動態角色 ID enum、加配對/排程邏輯，屬於較大改動）。決定先做 (a)，稱為 Phase 1；(b) 列為 Phase 2，先觀察 Phase 1 結果再決定要不要展開。

### Phase 1 實作
- `poc/characters.py`：不呼叫 LLM，純規則隨機從固定的姓名／性格／職業庫，各村隨機生成 3-5 位村民，存成 `poc/characters/roster_<timestamp>.json`（已加入 `.gitignore`，每次跑都會新增，不進版控）。
- `poc/prompts/world_lore.txt`：把上述世界觀整理成一段給模型看的背景設定，獨立成檔方便之後調整。
- `poc/prompts/director_system_prompt.txt`：加入 `{{WORLD_LORE}}` 區塊，並把原本空白的「你是紅村的村民」改成代入抽到的角色姓名／職業／性格（`{{RED_NAME}}`／`{{RED_OCCUPATION}}`／`{{RED_PERSONALITY}}`，藍村同理），並提示「說話語氣要符合你的性格與職業背景」。
- `poc/director_poc.py`：每次執行會先呼叫 `characters.generate_roster()` 產生兩村名單，各挑 1 人代入劇本，並把挑到的角色資訊與名單路徑一併寫進 transcript（供追溯）。GBNF grammar／JSON schema **完全沒動**，維持 Phase 1「小改動、低風險」的範圍。

### Phase 1 驗證結果（RTX 3070 + Qwen2.5-7B）
這場抽到：紅村「小豆」（織工，衝動直率）vs 藍村「阿雪」（獵人，忠誠固執）。
- 14.13 秒／10 回合，速度沒有因為多塞世界觀/角色資料而變慢。
- **戰術多樣性自然提升**：用到「轉移話題」「步步進逼」「示弱誘敵」3 種戰術——注意這次**沒有加任何額外規則指令**，純粹靠世界觀＋角色素材就讓多樣性自然出現，不像 V2/V3 是硬加規則、還把後段品質拖垮。
- **內容明顯有錨定感**：小豆開場聊織布手藝、阿雪聊狩獵野獸，兩人自然把話題帶到「CHO」「神廟」等世界觀設定，不是像之前那樣憑空發明地點/人物。支持「重複退化主因是世界觀資料不足」這個假說。
- 後段重複退化仍在但變輕微：第 6、8、10 回合藍村台詞圍繞同一段「CHO 說了奇怪的事」反覆講，第 8、10 回合幾乎重疊，但第 10 回合結尾有多加一句新問題，不是像 V2/V3 那樣整句一字不差複製貼上。

### 補測：0.75 多跑 3 次確認穩定性 → 訊號不夠乾淨

### 控制實驗：固定 seed + 固定角色，一次只改一個取樣參數
為了排除「每次角色都隨機」造成的雜訊，替 `director_poc.py` 加了三個環境變數：
- `AILLEY_SEED`：設定後會讓角色抽選（`random.seed()`）與模型取樣（傳給 llama-server 的 `seed`）都可重現。
- `AILLEY_TEMPERATURE`：覆蓋預設的 `TEMPERATURE`。
- `AILLEY_SAMPLING_EXTRA`：JSON 字串，任意疊加額外的 llama-server 取樣參數（例如 `top_p`／`top_k`／`mirostat`／`dynatemp_range`）。

transcript 也新增記錄 `seed` 與 `extra_sampling`，方便追溯每次實驗用的確切設定。

用固定 `AILLEY_SEED=42`（角色固定抽到：紅村「阿蓮」農夫·謹慎多疑 vs 藍村「阿明」祭司見習·幽默愛開玩笑），只改取樣參數，測了 5 組：

| 設定 | 結果 |
|---|---|
| 基準（temp=0.6，無額外參數） | **失敗**：第 7～10 回合鎖進精確重複循環（逐字重複「哈哈，你說得也是...」） |
| temp=0.75 | **成功**：全程無鎖死，圍繞「阿明信仰 CHO」的劇情線持續發展 |
| `top_p=0.9, top_k=40`（temp 仍 0.6） | **成功**：全程無鎖死，「CHO 在災難中救了阿明」劇情線發展最完整，4 種戰術都用到 |
| `mirostat=2, mirostat_tau=5.0, mirostat_eta=0.1` | **失敗且更嚴重**：第 6 回合輸出非法控制字元，直接 JSON 解析崩潰——跟之前 `repeat_penalty` 調太高時的災難是同一種失敗模式，判斷 Mirostat 的動態調整機制跟 GBNF grammar 的硬約束互相衝突 |
| `dynatemp_range=0.5, dynatemp_exponent=1.0` | **成功**：全程無鎖死，「老友」背景故事線持續發展 |

**這是目前訊號最乾淨的一組實驗**（固定角色＋種子，只變取樣參數）：`temperature`、`top_p/top_k`、`dynatemp` 三個方向都成功解決了基準版的鎖死問題，**`mirostat` 應直接排除**，不建議在這個模型 + GBNF grammar 的組合上使用。

**待辦**：這 5 組目前都只測了 1 個 seed／角色組合，建議再挑 2-3 組不同 seed 對這三個「成功」的設定（temp=0.75、top_p/top_k、dynatemp）重測，確認不是單一場次的運氣，再決定要不要把其中一個（或組合）定為新的正式預設值並同步回本機 repo。

### 修正：對話裡不小心講出 OOC 遊戲術語「旗子」
統計目前累積的 27 份 transcript，發現 `reasoning`／`dialogue` 欄位裡出現「旗子」字樣的次數高達 **27 次**，不是個案。追查原因：`prompts/director_system_prompt.txt` 與 `prompts/world_lore.txt` 裡多處直接寫「Flag」這個英文遊戲術語（例如「你持有機密 Flag（你的核心能源）」），模型很可能把這個 OOC（戲外）詞彙口語化翻成中文「旗子」講進角色台詞裡——這比「不小心講出真正的核心能源名稱」更嚴重，因為這是遊戲機制詞彙直接洩漏進沉浸式敘事，破壞世界觀。

**修正做法**：把兩份 prompt 檔案裡所有「Flag」字樣換成純世界觀用語「核心能源」/「核心能源名稱」，JSON schema 欄位名稱 `reveals_own_flag` 保留不動（純資料結構，不影響敘事）。這只是換字彙，沒有加新規則，風險比之前「加規則」類的修正都低。

**驗證**：改完後在遠端機器跑 1 場（`20260716-221110.json`，紅：阿明 vs 藍：阿蓮），全程 10 回合搜尋「旗子」「旗幟」「Flag」皆為 0 筆——模型改用「核心能源」稱呼，劇情圍繞「神廟古鐘傳說」發展，速度（13.88 秒）與品質沒有受影響。單次樣本，但風險低、效果直接，已正式採用此版本。

## 兩層機密草案：核心能源（個人）＋ 舊神祭壇密鑰（村莊）

團隊釐清設計：村民要保護的機密其實有兩層——**核心能源**是每位村民各自的機密（個人層級），**舊神祭壇密鑰**是每村只有一份的機密（村莊層級），握有密鑰等於能操作全村所有村民的核心能源，價值遠高於單一個人的核心能源。目前的 POC 只做了「整村共用一個 Flag」，跟這個兩層設計對不上，需要調整。

**這個改動範圍比 Phase 1 大**（會動到 `state_delta` 的洩漏判斷欄位，牽涉 schema／GBNF grammar），所以先只做資料結構草案，還沒接進生成流程：

- `poc/characters.py` 新增：
  - 每位村民各自的 `core_energy`（獨立核心能源名稱，整份紅藍名單範圍內全域不重複，避免跨村撞名造成洩漏偵測的字串比對歧義）。
  - `holds_altar_key`（是否為密鑰持有者，只從「祭司見習」「守衛」這類權威職業裡指定 1 人，沒有符合資格者時退回全體隨機挑）。
  - `generate_roster()` 回傳新增 `altar_keys` 欄位：`{"red": "TAMMY神祭壇密鑰", "blue": "NEON神祭壇密鑰"}`，每村固定一個密鑰名稱。
- **目前狀態**：純資料模型草案，`director_poc.py` 的 prompt／GBNF grammar／schema 都還沒接上新欄位，現有劇本生成與洩漏偵測邏輯不受影響（已驗證向下相容）。

**後續要做（待確認後再動手）**：
1. `poc/schema/script_schema.json` ＋ `poc/grammar/director.gbnf.template`：`state_delta.reveals_own_flag` 拆成兩個獨立判斷（例如 `reveals_core_energy` / `reveals_altar_key`）。
2. prompt 要說明兩種機密的價值層級差異，並提示「如果對方是密鑰持有者，套出密鑰優先度更高」。
3. `director_poc.py` 的 `play_script()` 一致性檢查與戰報要分別統計兩種洩漏。

## 深夜自主作業（趁使用者休息時間）：3 項小修正 + MAX_TURNS 縮短驗證

### 修正：角色姓名同名問題
`poc/characters.py` 的姓名原本用 `random.choice()` 各自獨立抽選，同一份名單裡可能撞名（曾出現藍村同時有兩個「阿土」）。改成跟 `core_energy` 一樣，用 `random.sample()` 在紅藍兩村合計範圍內不重複抽選姓名。已同步到遠端機器。

### 補測：舊神祭壇密鑰洩漏的「提前結束遊戲」邏輯，首次獨立驗證
截至目前為止累積的所有真實場次，密鑰洩漏都還沒被模型巧合觸發過，代表 `play_script()` 裡「密鑰洩漏 → 立即結束遊戲、後面回合不再播放」這段程式碼邏輯本身從未被驗證過是否正確。寫了 `poc/test_two_tier_secrets.py`，用構造好的假 turns（不呼叫模型）直接測試：
1. 核心能源洩漏、自評誠實 → 正確判定，不印警訊。
2. 核心能源洩漏、自評錯誤（宣稱沒洩漏）→ 正確印警訊。
3. 密鑰洩漏 → 正確在該回合印出「全村核心能源淪陷，遊戲結束」，且**第 3 回合真的沒有被播放**（`break` 邏輯正確）。
4. 密鑰洩漏但自評錯誤（宣稱沒洩漏）→ 正確印警訊，且仍然正確觸發提前結束（證實結束判定是看**文字比對結果**、不是看模型自評，這是正確的防呆設計）。

4 項測試全數通過，這段先前從未被實際觸發過的程式碼邏輯確認無誤。

### 實驗：縮短 `MAX_TURNS` 到 6 回合，驗證能否避開後段重複退化
筆記裡一直留著「縮小 MAX_TURNS」這個未測試的待辦。幫 `director_poc.py` 加了 `AILLEY_MAX_TURNS` 環境變數（沿用跟 `AILLEY_TEMPERATURE` 一樣的 pattern），用 `AILLEY_MAX_TURNS=6` 連跑 3 場：

| 場次 | 結果 |
|---|---|
| 1（`20260717-000609.json`） | 10.49 秒，3 種戰術，無重複、無洩漏 |
| 2（`20260717-000626.json`） | 10.17 秒，2 種戰術，無重複、無洩漏（劇情圍繞「密鑰持有者是誰」的猜測攻防） |
| 3（`20260717-000642.json`） | 10.99 秒，3 種戰術，無重複、無洩漏 |

**3/3 全部乾淨，完全沒有出現過去在 10 回合版本裡屢次出現的後段重複退化（精確循環鎖死／戰術零多樣性）**，速度也更快（10-11 秒 vs 原本 14-18 秒）。這強烈支持先前的假說：後段退化是這顆模型在「長輸出」下的已知弱點，只要把整場長度控制在退化區間（原本觀察約落在第 6-10 回合）發生之前結束，就能從根本避開這個問題，不需要再靠取樣參數硬解。

**待決策**：是否要把 `MAX_TURNS` 正式從 10 降到 6 當新預設值？trade-off 是回合數變少，戰局的攻防層次/戲劇張力可能不如 10 回合豐富，這是遊戲設計面的取捨，不是單純技術問題，需要團隊一起看過 6 回合版的實際內容（上面 3 場 transcript 都已存檔）再決定，這次先不擅自把它訂為新預設值。

### 新發現：偶發簡體字污染
掃描目前累積的 38 份 transcript，其中 **4 份（約 10%）混入簡體字**，程度不一——多數只是零星詞彙（「听说」「对方」「说说」），最新一場（`20260717-000626.json`）出現整句幾乎全簡體（「这可真是个难题，不过我觉得，我们还是应该先找到 CHO，才能真正解决问题。你怎么看？」）。

這跟先前能靠 prompt 工程解決的問題性質不同：繁簡體混用是 Qwen 這類模型訓練語料本身的偏好（中文語料裡簡體佔比通常遠高於繁體），不是取樣參數或情境規則能穩定控制的行為。考慮到我們已經驗證過「prompt 加規則會擠壓後段內容新鮮度」，不建議用加規則的方式硬解。**比較穩妥的方向是在模型輸出之後，另外加一層 OpenCC（簡轉繁）文字後處理**，把這個問題當純文字正規化處理，而不是靠 prompt 影響模型的生成行為。這會引入新的套件依賴（例如 `opencc-python-reimplemented`），屬於需要團隊確認的技術選型，這次先記錄不擅自加。
