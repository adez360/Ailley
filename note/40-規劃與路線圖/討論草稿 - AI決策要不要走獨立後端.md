## 討論：AI 決策要不要走獨立後端

目前專案裡並存兩種串接 LLM 的方式：

1. **遊戲端直接呼叫 LLM provider**，拿到回應後在遊戲端做格式驗證與白名單檢查。
2. **遊戲端呼叫一個獨立的決策後端，後端再去呼叫 LLM**，後端額外負責文法層級的輸出約束、決策排程、記憶檢索。

這兩種目前都有程式碼在推進，但方向不一致，建議趁還沒定型先討論清楚，不然之後要花力氣調和。

### 這兩種方式實際差在哪

|  | 方式一：遊戲端直打 | 方式二：走獨立後端 |
| --- | --- | --- |
| 輸出格式保證 | 生成後檢查，不合格式就重打 | 生成當下就用文法鎖住合法輸出，機率上更穩 |
| 額外延遲 | 沒有中間跳點 | 多一段本機呼叫（通常遠小於模型生成本身的時間） |
| 決策排程／記憶檢索 | 需要在遊戲端重新設計實作 | 目前已經有一份跑過多輪測試、調整過的實作 |
| 對雲端模型是否有差 | 雲端 API 本來就不支援文法層約束，兩種方式在雲端情境下差異會縮小 | 同左 |
| 維運複雜度 | 較單純，少一個要啟動/維護的服務 | 多一個需要一起啟動、監控的後端服務 |

### 一個常見誤解先澄清

文法層級的輸出約束（GBNF）是**推論伺服器本身的功能**，不限定用什麼語言呼叫——技術上遊戲端也能直接呼叫推論伺服器、拿到一樣的約束效果，不是「一定要透過某個特定語言的後端」。

真正的問題不是「能不能」，是：**現在「怎麼組文法規則」「怎麼排程決策」「怎麼檢索記憶」這幾套邏輯，只寫在一份程式碼裡（獨立後端那份），還沒有人搬到遊戲端。要不要重寫第二份，這才是要決定的事。**

### 重寫一份給遊戲端會付出什麼代價

- **兩份邏輯會分岔，而且這類問題已經真實發生過一次**：這些規則目前還在持續被調整（這幾天就改了好幾輪），一旦分成兩份程式碼，每次調整都要記得兩邊都改，忘了改哪一邊就會悄悄產生行為差異。專案裡已經有過一次真實案例——某支腳本原本自己維護一份設定值副本，跟真正的來源分開修改，兩邊改了一個沒改另一個，資料悄悄跟現實脫鉤，是後來才發現修掉的。邏輯分成兩份本質上就是在製造這類「哪一份才是真的」的問題，只是規模更大、影響更廣。

- **現有的快速實驗／驗證方法論會失效**：目前要驗證「某個設計改動有沒有用」，是寫一支獨立腳本、不用開遊戲、幾分鐘內拿到具體數據直接看結果，才能一輪一輪快速調整、驗證。這套方式建立在邏輯集中在一份程式碼裡、可以單獨呼叫測試。邏輯搬進遊戲端之後，要嘛在遊戲引擎裡重建一套一樣的實驗工具（工程量不小，遊戲引擎的生態圈也沒有對應的文字處理/統計工具那麼方便），要嘛以後測任何行為調整都得真的把遊戲跑起來看，回饋速度會慢很多，等於拖慢後續所有行為調校的迭代速度。

- **決策排程這塊不是照著原邏輯翻譯過去就好**：現有排程用的是事件佇列＋優先權中斷這套離散事件模擬模型，這幾天光是修一個欄位語意就修過幾次，過程中踩過不少坑。遊戲引擎的執行模型是幀迴圈／訊號驅動，跟離散事件模擬本質上是兩種思維方式，這不是把語法翻譯過去就好，是要重新設計一遍——等於重新走一次已經在原本那邊踩過坑、修過的過程，新的坑會出現在新的地方，而且沒人能保證行為完全一致。

- **記憶檢索如果真的走向量資料庫，遊戲端會遇到兩層問題，其中一層是硬限制**：記憶檢索要拆成兩個動作看——①把文字轉成向量（embedding），②在一堆向量裡找出最相關的幾條（相似度搜尋）。②其實不難，量級小的話遊戲端自己寫迴圈就能做；**①是硬限制**：這是要跑神經網路推論的動作，遊戲引擎的腳本語言本身沒有做矩陣運算、載入模型權重的能力，這件事天生只存在於專門的推論程式裡（不管用哪顆模型都一樣），遊戲端叫用不了，一定要透過某個具備推論能力的服務。就算換一顆更準的專門 embedding 模型，也只解決「準不準」，不會讓這個硬限制消失。

  除了硬限制之外，就算把整條記憶流程（寫入、衰減計算、相似度搜尋、睡眠反思壓縮）搬進遊戲端，也會有幾個實際拖累品質的問題，不只是「重寫要花時間」：
  - **會佔用遊戲的每幀運算預算**：現在這些運算跑在獨立的服務裡，跟畫面渲染完全不搶資源；搬進遊戲端就是在跟渲染／物理／動畫搶同一份主執行緒時間，像「每遊戲日重算一次全員記憶衰減」這種批次運算，沒特別處理（拆多幀、丟背景執行緒）會直接造成明顯頓格
  - **向量運算沒有加速工具**：現在的語言環境有成熟的向量化數學函式庫，同時對整批資料運算；遊戲端沒有對應工具，得自己寫迴圈一條一條算，量一大會真的變慢，不只是「感覺比較慢」
  - **持久化儲存要靠不是引擎原生支援的第三方套件**：規格書要求的儲存方式，現在的語言環境內建就有、成熟穩定；遊戲引擎沒有原生支援，得裝社群維護的擴充套件，可靠度是不同等級
  - **背景執行緒更容易出錯**：為了避免頓格把運算丟到背景執行緒，遊戲引擎很多 API 不是執行緒安全的，資料要小心在執行緒間傳遞，容易產生難以重現的當機或資料錯亂，這在現在的架構下完全不會遇到

- **懂這套調校邏輯的人，跟寫遊戲端程式碼的人可能不是同一群**：這些細節（某個提示句該怎麼寫、某種分類方式為什麼會讓行為變差、重試上限該設多少）都是需要反覆做行為實驗才調出來的，不是一次寫死就對的規則。邏輯搬過去之後，之後每次要調整，要嘛原本懂這套的人去改遊戲端的程式碼，要嘛把每個細節完整交接給寫遊戲端的人——兩種都有溝通與維護成本。

### 想討論的問題

- 是否需要生成階段的硬性格式保證？如果可以接受偶爾重試，這個保證的必要性可能沒那麼高，成本結構會不一樣。
- 決策排程與記憶檢索，要沿用現有已驗證的實作，還是重寫一份？重寫的話，上面列的幾項代價要不要接受？
- 未來如果本地模型與雲端模型都要能切換使用，兩種串接方式在雲端情境下的差異其實會縮小，這點可以納入判斷。

希望在還沒定型前先對齊方向，避免兩條線各自往前跑、之後要花更大力氣調和。
