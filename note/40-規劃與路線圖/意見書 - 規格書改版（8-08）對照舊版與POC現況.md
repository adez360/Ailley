## 一、最重要的發現：04 正式定義的架構，跟 main 分支現有 Godot 程式碼衝突

新版《04》明確畫出系統架構：

```
Godot（世界模擬/擲骰/存檔） ── HTTP+JSON ── AI 後端（Python：Prompt組裝＋GBNF＋DES排程＋Vector DB記憶檢索） ── HTTP ── llama-server
```

**這完全是你現在 `poc_village_sim` 在做的事**——Python 後端、GBNF grammar、DES
排程，規格書等於是把你的架構正式定案了。

**但這跟 main 分支現有的 `Ailley/scripts/ai/ai_service.gd` 衝突**（見上次對話的
分析）：`ai_service.gd` 是 Godot client 直接打 OpenRouter，走 OpenAI chat
completions 格式，沒有 GBNF、沒有 Python 中介後端、沒有 DES 排程。新規格書要求
的是「Godot 呼叫一個獨立的 Python AI 後端」，跟已經寫好、且今天才修過 P0 的
`ai_service.gd` 是兩條不同的路。

**這是本輪最需要立刻跟 Ru/夏／寫 `ai_service.gd` 的人對的一件事**：規格書已經
定案要有 Python AI 後端，那 `ai_service.gd` 這條直打雲端的路要退場、改造，還是
兩者並存（例如 `ai_service.gd` 未來改成打你的 `/tick` 而不是打 OpenRouter）？
再不講，`ai_service.gd` 可能會照著舊方向繼續長。

## 二、`04` 給出了具體 API 契約，直接解答上次「欄位缺什麼」的疑問

新協定不是單一角色的 `/decide`，是**批次**端點：

| 端點 | 方法 | 用途 |
| --- | --- | --- |
| `/health` | GET | 檢查模型就緒 |
| `/tick` | POST | **一次送全部 5 個 NPC**，要決策 |
| `/event` | POST | 天神之石事件推送 |
| `/generate/words` | POST | 建角時生成 `words_to_creator` |
| `/memory/reflect` | POST | 睡眠反思、記憶壓縮 |

跟你現在 `server.py` 的 `/decide`（單一角色、每次一問一答）差很多，要改成批次
處理 5 個 NPC 一次進來。

**回應上次的欄位缺失疑問**：`/tick` 的 request 裡確實包含大部分你缺的欄位——
`fact_lines`（＝你的 `recent_event`概念）、`last_action_result`、`present_npcs`
（＝你的 `visible`）、`current_goal`、`today_plan` 都有了。**但沒有
`recent_memory` 這個欄位**——規格書的設計是記憶檢索**由 AI 後端自己內部查
Vector DB**（依 `npc_id`），不是 Godot 傳文字進來。這代表你 `server.py` 現有
「呼叫端傳 `recent_memory` 字串」的設計，跟規格書期待的「後端自己維護每個
npc_id 的記憶庫並自己檢索」不一樣，要嘛後端自己養一份記憶庫，要嘛跟 Ru 談
「這階段先由 Godot 傳文字近似值」。

GBNF 約束範圍（§8）跟你 `rts.build_grammar_for_call()` 現有做法幾乎一致
（靜態 enum：action/emotion/speech_volume；動態產生：target/location_id）——
這塊不用改設計，是既有驗證的加強確認。

`01-3` 的兩條硬規定也直接對上你已經驗證過的東西：「數值一定要附中文形容詞」
＝ `hunger_tier_text` 那套；「一定要回報上一動作失敗原因」＝你的
`FEASIBILITY_*` 提示句設計。**這兩項不用等團隊決定，可以當作已經被規格書
正式認可的既有做法。**

## 三、動作／地點清單整個換了一版，8/7 才做完的 `enums.py` 對齊要重新核對

新《07》的行動清單跟《99》確認的地點清單，**跟 8/5 版差異很大**：

**行動**：8/5 版是 38 個動作（跟現有 `enums.py` 逐一對齊過）；新版《07》§2
只列了約 **20 個**，四大類重分（溝通／工作消費／動作移動／敵對）。8/5 版裡的
`whisper`／`handshake`／`hug`／`give_money`／`marry`／`divorce`／`rob`／
`break_item`／`arrest`／`heal`／`run_to`／`crouch`／`cover_head`／`raise_hand`／
`scream`／`throw_item`／`blow_kiss`／`follow`／`show_item`／`patrol`／
`surrender` 這些**新版都沒出現**；新增了 `persuade`（說服，`enums.py`
完全沒有）、`nap`（打盹）、`wash`（清潔）、`rest`（休息，跟 `idle` 分開了）。
`give_item` 改名成單純 `give`。

**地點**：新版變成 15 項（`loc_home`／`loc_well`／`loc_board`／`loc_reform`／
`loc_cemetery` 是新的），但 **`village_square`（村莊廣場）不見了**——8/5
版跟 `enums.py` 現有的 `square` 在新清單裡找不到對應。`洗心革面所` 的英文
`location_id` 也從你 8/7 對齊的 `jail` 改成規格書自己寫的 `loc_reform`。

> ⚠️ 這兩份都還標著「含推測，未經團隊確認」（《99》P-17），不是定案，
> 但既然差異這麼大，8/7 那次「小範圍命名對齊」現在跟最新規格書已經對不齊了，
> **建議先不要急著再動一次 `enums.py`，等 07 真的定案（P-17 有人簽名）再對，
> 不然可能要改兩次。**

## 四、記憶檢索的衝突：條件變了，不是消失了

上次記錄的衝突是「規格書 03 §B-5 檢索公式語意相關度佔 50%，跟你們
`memory_store.py` 實測『相關性檢索會讓對話卡住重複』的結論衝突」。

新版《03》§7 **拿掉了那條加權公式**，只寫「檢索來源 L3、每次取回 3~5 條、
向量資料庫【待確認】」，而且新增了**檢索觸發時機限制**：不是每個 tick 都查，
只在「遇到未見過的角色／抵達新地點／天神之石事件／睡眠反思」這幾種情境變化
時才觸發。

這**不代表衝突解除**——語意檢索（embedding-based）這個方法本身還是規格書
的既定方向，向量資料庫要用哪個也還沒定（《99》P-15 #8）。但觸發頻率大幅降低
（不是每次決策都跑），可能已經部分緩解你們實測到的「反覆卡在同一件事」問題
——**這點值得在跟 Ru/夏 談的時候一併提**，也許現在的方案 B（只在情境變化時
檢索）已經不會踩到你們原本擔心的那個坑，衝突範圍比原本想的小。

## 五、其他值得注意的變動

- **成功率公式定案（01-2）**：`成功率 = 基礎成功率 + 人格係數修正 + 體力修正
  - 傷勢懲罰 - 醉酒懲罰 - 環境風險`，夾制 5%~95%。這是規格書 04 職責切分
  原則的具體化——**擲骰與數值變更一律在 Godot 端**，AI 後端只能回傳意圖，
  不能直接改任何數值。你現在 `run_des_sim.py` 的成敗判定邏輯（如果有算在
  AI 後端這邊）之後要搬到 Godot 端，或至少邏輯上要對齊「只有 Godot 能擲骰」
  這條硬規定。
- **P-06 提出一個值得注意的問題**：`morality`／`greed`／`honesty` 三項人格
  參數目前**沒有任何引擎消費者**，規格書自己在問「要不要乾脆刪掉」。跟你
  8-1 節做的人格維度對照表有關——如果這三項真的被砍，你之後對齊 10 維人格
  就不用真的做到 10 維，可能只需要 7 維。**建議先不要急著補這三項到角色卡，
  等 P-06 決定了再動。**
- **P-11 問了一個直接關係到你們串接方式的問題**：「玩家自行串接雲端模型時，
  是否共用同一組端點？」——這題目前規格書自己也還沒答案，跟第一節「
  `ai_service.gd` 直打雲端 vs 走 Python 後端」是同一個問題的另一種問法，
  可以一起提出來問。
- **99 這份追蹤表本身很好用**：以後每次規格書再改版，可以直接對這份表的
  「決策紀錄」區塊，看團隊實際定案了哪些、日期是哪天，比每次重新全文比對
  快很多。
