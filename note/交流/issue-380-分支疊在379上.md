# issue #380 分支疊在 #379 上（2026-08-24）

## 現況

`feat/cemetery-burial-action`（worktree `.claude/worktrees/feat+cemetery-burial-action`）
是 #380（墓園地點機制）的工作分支，用 `gh issue develop 380 -n feat/cemetery-burial-action
--base feat/death-trigger-state-machine` 從 #379 的分支尖端（PR #551，2026-08-24 當時
tip 是 `c96e3fd`）切出來，**不是從 main 切的**。

**原因**：#380 的實作要用到 Character 上的 `is_dead`／`death_cause`／`corpse_decay`／
`is_buried`／`grave_id`／`CONDITION_PETRIFIED` 這些欄位，全部是 #379 加的，main 上還沒有
（#551 尚未合併）。直接從 main 切會拿不到這些欄位，寫不出能動的安葬邏輯；照搬一份等於
重做 #379 的骨架，見《技術/平行 Worktree 與 Godot MCP》「平行跑有相依關係的 issue」那節
明講不要這樣做。

**這代表**：

- `feat/cemetery-burial-action` 目前的 diff 對 main 而言會**包含 #379 的全部改動**，
  不是乾淨的「只有安葬機制」的 diff。開 PR 時要在說明裡講清楚「疊在 #551 上，
  #551 合併前不要合併這則」，PR 的 base branch 也要設成 `feat/death-trigger-state-machine`
  而不是 main（`gh issue develop --base` 已經設定成這樣，`gh pr create` 應該會沿用）。
- `feat/death-trigger-state-machine` 之後若因為 code review 又推新 commit（實測 2026-08-24
  當下已經比舊的 `feat+graveyard-location-mechanics` worktree 記錄的 `2107d20` 新，變成
  `c96e3fd`），這條分支要跟著 rebase。
- #551 真正合併進 main 後，`feat/cemetery-burial-action` 要 rebase 到新的 main，
  屆時 diff 會自動收斂成只剩 #380 自己的改動。

## 開發過程中發現並修掉的 #379 遺留問題

`feat/death-trigger-state-machine`（`c96e3fd`）在真的用編輯器打開、跑 `test_run` 前
沒被發現的一個編譯錯誤：`agent.gd` 還留著 #381 時期的 `var last_words := ""`，
跟 #379 新加在 `character.gd` 的 `last_words: Variant`（Player 也需要，故往上提升到
base class）撞名，GDScript 判「member 已存在於 parent class」直接編譯失敗，
整個專案（包含跟死亡無關的腳本）連帶炸掉。已在這個分支一併移除 Agent 那份殘留宣告與
對應的 `get_save_data()`/`load_save_data()` 重複處理，`last_words` 現在完全交給
`Character`（`super()`）處理。這個修法之後 rebase 到合併後的 main 時大機率會需要重新確認
一次（#551 那邊自己也可能已經修，屆時看 rebase 衝突的內容決定要不要保留這份）。
