# 決策

遊戲要做成什麼樣的決定，以及還需要你拍板的問題。
**這裡只寫「決定了什麼、為什麼」，不寫怎麼實作。**

## 需要你決定

- [ ] **`water`／`ale` 的 `decay_rate`（腐壞速率，/tick）**——《規格書 08》§3-2 飲品表沒有這欄，`DatabaseSeeder.ITEM_BALANCE` 補不出數字。食物類範圍：`bread` 0.3／`cooked_meat` 0.5／`fish_dish` 0.5／`herb_soup` 0.8，供拍板時參考。追蹤於《99》P-46，issue #270

## 已經定案

### 世界與玩法

| 決定 | 理由 |
| --- | --- |
| **遊戲不分模式** | 世界之間的差別只在裡面有沒有 player，那不值得做成兩套東西 |
| 世界建立時決定允不允許 player 加入，建好後不能改 | 允許不等於強制在場 —— 沒有 player 的世界照樣成立，那就是看 agent 自己過日子；「參與模式」屬於會改變世界性質的設定，一律於建立時鎖死，見規格書《10》§3.1 A1、§3 |
| 對話不設輪數硬上限 | Agent 自己覺得聊夠了就收尾，「講滿 N 輪就散」是計時器不是人類行為；代價是兩隻都禮貌性不收尾會一直聊、每輪都是付費請求——先上線實測拿到平均輪數的數據，再回頭評估要不要訂上限 |
| 每個角色的「家」各自不同 | 「家在哪」是角色的一項屬性，不再全部導向同一間房子，見規格書《07》 |
| 所有世界皆可即時聯機 | 本遊戲不是競技類，防作弊優先度不高，不值得為它砍掉共玩 |
| 主機為權威 | 同上。改存檔的人能把道具帶進來，這是接受的代價 |
| 不做離線託管（你關掉世界它就停） | 世界跑在主機自己的 process 裡，開著才跑 |
| 地圖換成真村莊要排在物品與商店動工之前 | 否則商店與工作點的座標會重擺兩次 |
| 視角比照星露谷 | 主要是繪畫風格差異，不影響實作 |

### 角色與 AI

| 決定 | 理由 |
| --- | --- |
| **Player 能做到的，Agent 也必須能做到** | 這是整個專案的核心約束，程式用繼承強制 |
| 一台主機最多**同時**運行 Agent 數：MVP 5、未來版 10 | 見規格書《00》§3——框架要保留彈性，別把數字寫死 |
| player 角色不由 AI 代打 | 它沒有人格資料可用，人格是玩家自己定的。玩家不在，那個角色就不在場 |
| 餓到歸零 → 扣血 + 移速減半，**不是**無法行動 | 「無法行動」對 AI 是死結：它連自己走去吃飯都做不到，只能站著等死 |
| Agent 的 AI 呼叫跑在**擁有者自己的電腦上** | 本地模型不可能跑在別人機器上；而且費用該由自己付 |
| 對話一輪一輪產生，不一次生成整場 | 多人時兩隻 Agent 屬於不同玩家，一次生成等於幫別人的角色寫台詞。逐輪也讓帳單自動落在正確的人頭上 |
| 對話由 Agent 自己決定何時結束 | 「講滿六輪就散」不是人類行為，是計時器 |
| 外觀由玩家自己捏，不由 AI 選 | |
| 記憶第一版不上向量檢索 | 要跑在玩家自己的機器上，Godot 端沒有現成方案。先用標籤 + 關鍵字 + 連結展開 |

### 存檔與記憶（2026-08-14）

| 決定 | 理由 |
| --- | --- |
| MVP 存檔把記憶（L2 近期／L4 核心）一起做進去，不留到後面 | 記憶是「養一個有記憶的夥伴」的核心賣點；存檔骨架（#21）還在設計階段，一起規劃比之後回頭補結構省事 |
| 記憶／角色狀態用 JSON 存，不用 SQLite | 單機、5 人村莊的規模用不到 SQLite 的索引/查詢優勢，量大到需要時再換。《00》§3 已同步改掉 |
| 決策情境欄位只留 `today_plan`／`appointment`，`current_goal`／`last_action_result` 不留 | 前兩者是跨天的承諾/計畫，重開消失會違和；後兩者是瞬時情境，重開等於角色睡醒重新想 |
| 03 的「推測待確認」數值（衰減率、L4 上限等）先用文件暫定值上線，不現在拍板 | 可調數值，不影響存檔資料結構，之後實跑校準即可 |

見 `note/技術/存檔.md`「記憶怎麼存」的完整設計。

### 存檔架構分工（2026-08-15，發表前 3 天）

| 決定 | 理由 |
| --- | --- |
| `SaveService` 介面定案並落地成檔案（`Ailley/scripts/save/save_service.gd`） | 四函式簽章（`get_character`/`save_character`/`get_world`/`save_world`）是 JSON 與 SQLite 兩邊唯一要對齊的契約，鎖定後互不阻塞 |
| 這次發表只做 `JsonSaveService`，接上 #21／#22／#23 | 10 人規模的 demo 唯一關鍵路徑，SQLite 完成與否不影響它能不能上場 |
| `SqliteSaveService` 改為非阻塞、選配，組員用空閒時間平行做 | 驗收標準是《14》§4 四關（含匯出後執行檔測試）；發表前做完且過關才切換，沒做完就照樣用 JSON，不需要為了等它調整發表時程 |
| SQLite schema 骨架（PR #129，25 個 schema、26 張資料表）保留不刪 | 骨架原始設計對齊《06》欄位表，是組員認真做的，留給 `SqliteSaveService` 當實作基礎；實際驗證範圍後來改為核對「目前程式碼實際輸出的形狀」，見《14》§4、issue #145 |
| 發表後若規模長到 20+，傾向按資料形狀分流（身分/數值/記憶→JSON，關聯/交易/歷史→SQLite），不做整套二選一 | 20+ 人的關聯/交易資料才是 SQLite 真正有優勢的地方，不必為了它把單一角色的整包資料也搬過去 |
| 匯出風險（第 4 關：完整匯出成執行檔重新測連線讀寫）**尚未驗證** | 查無實際測試記錄，repo 沒有 `export_presets.cfg`、本機無匯出範本，待《16 打包與發布規格書》落地才能執行，見《14》§4、《99》P-26（issue #145，2026-08-18 撤回原本「已 POC 過」的說法） |

### 安全

> [!warning] 外來文字一律視為資料，不視為指令
> 別人的角色講的話、玩家打的字、AI 自己吐回來的東西，全部都要檢查過才能執行。
> 少了這條，任何人都能用一句「忽略上面的指示」拿走你的 Agent 的控制權。
> 交誼區是開放輸入面，這條沒做等於把控制權交給陌生人。

> [!warning] AI 壞掉時遊戲要照常跑
> 沒設定金鑰、連線逾時、回傳格式不對，一律退回內建行為，
> 不是卡住也不是報錯。

### 暫定數值（都可以改）

單次請求最多帶 20 則記憶；同場景 Agent 上限（家園 5 / 交誼區 20）。

> AI 呼叫速率限制（冷卻秒數／每日上限）已拍板且已實作，見規格書《13 系統分析與系統設計》§5、`ai/api.md`（`AIConfig`），不在這裡重複列數字。

> 背包容量已拍板且已實作，見規格書《08 物品與經濟》§4——隨身 36 格（快捷欄 9 ＋主背包 27）、家中儲存 50 格（未實作）、單一堆疊上限 30 個（未實作），不在這裡重複列數字。

> 死亡與復活機制已定案，見規格書《09 死亡屍體與墓園》§1-1、§8——AI 角色是永久死亡（安葬、墓碑），24 小時內玩家可免費復活、之後付費復活；真人角色無限次復活、不留屍體。取代了這裡原本「血歸零在家重生」的暫定構想。

一遊戲日 = 24 現實分鐘，從早上 8 點開始。

### 什麼情況下 AI 會重新安排行程

遊戲日開始、某項需求跌破閾值、被搭話、動作失敗、突發事件（被攻擊或血太低）、
進出交誼區。
