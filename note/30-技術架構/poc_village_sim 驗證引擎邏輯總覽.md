## 一、整體流程

```
main()
 └─ 讀取 5 份 prompt／grammar 檔案（一般行動、睡眠反思、重要性評分）
 └─ 迴圈跑 N 次獨立模擬（run_one_simulation），每次結果各自存一份 transcript json
     run_one_simulation()
      └─ 讀角色名單／好感矩陣，算出地點清單（公用地點＋每人的家）
      └─ 初始化 5 人的 state（生理/人格/記憶/是否存活…全部從角色卡複製一份）
      └─ 迴圈跑 N 個 tick：
          1. 對這個 tick 開始前的狀態拍一張快照（state_at_tick_start）
          2.【決策階段】5 人平行呼叫 LLM（ThreadPoolExecutor），
             每人只讀快照、不寫共用狀態
          3.【套用階段】序列處理 5 人的決策結果，依序寫回 state：
             情緒衰減計數 → 生理數值（飢餓/口渴/體力）→ 攻擊/治療/睡覺的專屬效果
             → 生命值（流血/重傷/恢復）→ 死亡判定 → 無聊度 → 位置/上一動作結果
             → 睡眠反思（條件觸發）
          4. 換日時重置「今天做過的事／去過的地方／互動過的人」
      └─ 回傳這次模擬的完整 log ＋ 每人最終人格／記憶／死亡 tick
```

一個 tick 內，**決策永遠只看 tick 開始前的快照**，不管序列或平行執行都一樣——5 人是
「同時」決策的語意，不會因為 Python 迴圈或執行緒的執行順序而有先後之分。詳細討論見
[[POC 紀錄 - poc_village_sim 五人整合試跑（新版 AI 架構首測）]] 的「平行運算」一節。

## 二、各項數值機制與公式

### 飢餓／口渴

| 觸發 | 數值 |
|---|---|
| 每 tick 基礎流逝 | 飢餓 +2、口渴 +2 |
| `吃飯` | 飢餓 −40（單次，不檢查背包裡有沒有食物） |
| `喝酒` | 口渴 −35（單次，不檢查背包裡有沒有飲品） |

### 體力

| 觸發 | 數值 |
|---|---|
| 高消耗動作（打獵/搶劫/抓捕/破壞樂器/奔跑） | −8/tick |
| 中消耗動作（表演/移動/跟隨/巡邏/偷竊） | −4/tick |
| 其他所有動作（含發呆、說話類、需同意互動類、消費類） | −1/tick |
| `睡覺` 且人在自己家 | +4/tick |
| `睡覺` 但不在自己家（打盹） | +1/tick |
| `攻擊`（不管有沒有打中） | −2~−4/tick（隨機） |

### 生命值（跟體力分開的獨立欄位，0-100）

| 觸發 | 數值 |
|---|---|
| `bleeding=True` | −1/tick |
| `severe_injury=True` | −3/tick（可與流血疊加） |
| `治療` 且在藥草鋪且錢≥40 | 一次性 +50，扣 40 元，清除流血/重傷/扭傷/割傷；若血量仍<100 進入「治療中」 |
| `recovering=True`（治療中） | +1/tick，回滿 100 自動解除 |
| `攻擊`（攻擊方，不管打中與否） | −1（固定） |
| `攻擊` 命中（目標） | −1~−3（隨機） |
| 生命值 ≤0 | **死亡**，`alive=False`，不再參與模擬、不出現在別人視野裡 |

### 攻擊判定

| 項目 | 規則 |
|---|---|
| 命中率 | 固定 60%，不受人格數值影響 |
| 命中後流血機率 | 15%（跟命中判定各自獨立擲一次） |
| 攻擊方代價 | 不管有沒有打中都要付：生命 −1、體力 −2~−4 |
| 目標代價 | 只有命中才套用：生命 −1~−3，15% 機率流血 |
| 前提 | `action == "攻擊"` 且 `target` 不是 null（沒有目標時只走通用的低消耗體力，沒有其他效果） |

### 無聊度（Specify2 §7.3）

| 觸發 | 數值 |
|---|---|
| 每 tick 基礎 | +2 |
| 這次動作跟上一次相同 | 額外 +3 |
| target 是今天第一次互動的對象 | −25 |
| 這次地點是今天第一次去 | −15 |
| 這次動作類型是今天第一次做 | −10 |
| 視野內有人做了「事件類」動作（表演/攻擊/搶劫/偷竊/破壞樂器/抓捕/舉報/大叫） | −10 |

### 情緒

同一個情緒連續維持滿 5 tick 沒變，下一輪顯示給 LLM 的 `last_emotion` 重置回 `neutral`
（LLM 仍可自己選擇重新宣告同樣情緒，這只是「不主動告訴他還在生氣」，不是強制切換）。

### 六維人格（只有睡眠反思會動）

單項變動範圍 −3~3（grammar 鎖死），單晚（一次反思）總變動絕對值總和上限 6，超過會等比例
縮小。人格一旦被動過，之後的 prompt 改用數值套表產生的敘述，不再用角色卡手寫的
`personality_text`。

## 三、睡眠與睡眠反思

| 規則 | 說明 |
|---|---|
| 有效睡眠 | `action == "睡覺"` 且 `location` 是自己的家（`"XX家"`） |
| 觸發反思的時機 | 只在**一段連續睡眠的第一個 tick**觸發一次（用 `is_sleeping` 旗標追蹤上一個 tick 在不在睡），不是每個睡覺的 tick 都觸發 |
| 反思輸入 | 從「上次睡覺（或模擬開始）到現在」的原始 tick 記錄組成時間序列文字（方案 C 的「當日 log」，只在這裡用完，不進記憶檢索） |
| 反思輸出 | `reflection`（1-2句反思）／`personality_delta`（六維各自變動）／`long_term_memory`（一句精簡記憶） |
| 記憶檢索 | `long_term_memory` 存進角色的記憶清單，之後每個 tick 用「新近度（0.95 指數衰減，以 tick 數為時間軸）＋重要性（另一次 LLM 呼叫評 1-10 分）」排序，撈最相關的 6 筆塞進 Snapshot |

## 四、Grammar 動態產生（不是全部寫死在 .gbnf 檔案裡）

`turn.gbnf.template` 本身**不包含** `target-value`／`location-value` 這兩條規則的定義，
每次呼叫前才由 `build_grammar_for_call()` 現場組出來附加在後面：

- `target-value`：`"null"` + 當下視野內每個人的名字——保證不可能選到視野外的人、幻覺
  人名，或把「沒有對象」寫成字面字串 `"null"`（跟真正的 JSON null 搞混）。
- `location-value`：公用地點（`SHARED_LOCATIONS`）+ 依角色名單現場算出的每人的家
  （`"XX家"`）——換角色名單時會自動跟著變。

`action`／`emotion`／`speech_volume` 則是寫死在 `.gbnf` 檔案裡的靜態封閉 enum。

## 五、可靠性機制

| 機制 | 說明 |
|---|---|
| JSON 解析失敗重試 | 最多重打 3 次（原本 2 次，2026-07-28 遇到長批次逾時後改成跟連線重試共用同一個迴圈） |
| 連線層級重試 | 逾時／SSH tunnel 瞬斷會重試，間隔 3 秒，3 次後放棄回傳失敗（不會讓整支腳本崩潰，但救不回真的死掉的連線） |
| 死亡後的處理 | 不再被呼叫、不出現在別人視野裡，但角色資料保留在 `state` 裡供最終結果查詢 `death_ticks` |

## 六、平行運算架構

決策階段用 `ThreadPoolExecutor`（5 個 worker）同時發出 5 人的請求，套用階段維持序列處理
避免 race condition。需要搭配遠端 `llama-server` 開 `--parallel 5`，且 `-c`（總 context）
要夠大（目前用 16000，每 slot 分到 3328 token，太小會導致 prompt 把 slot 塞爆、輸出被
截斷）。實測 30 tick × 5 次批次：序列 11.4 秒/tick → 平行 7.48 秒/tick，約 1.53 倍加速。
詳細的優劣勢分析、VRAM 用量見 [[POC 紀錄 - poc_village_sim 五人整合試跑（新版 AI 架構首測）]]。

## 七、已知限制（規劃新架構時要注意）

- 沒有真正的 guardrail 成功/失敗判定系統（除了攻擊命中率、治療地點檢查這幾個有明確判定
  的動作，其他動作宣告了就直接算數，`last_action_result` 只會顯示「已宣告，未經完整
  guardrail 判定成功與否」）
- 背包沒有任何動作會真的增減內容物
- 舉報／抓捕／洗心革面所完全沒有機制效果
- 沒有物品分級定價／耐久度系統
- 「延遲一拍」的互動模型（A 這 tick 做的事，B 要下一 tick 才會知道）是刻意設計，不是
  bug，但如果新架構要做到同 tick 即時互動，需要額外的雙輪呼叫機制（呼叫量翻倍）
