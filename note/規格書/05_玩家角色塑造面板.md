## 3. 分頁 1：基本資料

| 欄位 | 元件 | 限制 |
| --- | --- | --- |
| `name` | 文字輸入 | 上限 12 字，必填 |
| `age` | 數字輸入或滑桿 | 16–70，預設 30 |
| `gender` | 三選一按鈕 | `male` / `female` / `other` |
| `decision_source`／`model_name` | 三選一（Local／Cloud／Human）＋模型下拉 | 選 Cloud 時**不收 API 金鑰**，下拉只列既有 `ai/api.md`《`AIConfig`》裡已設定好的 provider（2026-08-16）；投放後不可改（同《00》「已投放角色不可編輯」規則）。UI 細節見 §3-1 |

### 3-1 決策來源欄位

對應《12》的 `DecisionProvider` 三種 MVP 實作（《13》§三：`RemotePlayer` 留到多人階段）。
欄位定義見《06》`decision_source`／`model_name`。

**兩段式**：先選來源，再選模型。第二段的內容由第一段決定。

| 來源按鈕 | `decision_source` | 第二段顯示什麼 |
| --- | --- | --- |
| 本機 | `local` | 下拉列 `AIConfig.providers` 裡 `base_url` 指向本機的 provider，選中後 `model_name` 取該 provider 的 `model` |
| 雲端 | `cloud` | 下拉列 `AIConfig.providers` 裡其餘的 provider，同上 |
| 真人 | `human` | 第二段整段隱藏，`model_name` 存空字串 |

三選一按鈕的選中樣式沿用分頁按鈕：Amber `#C96C23` 底 + Ink `#1A1512` 字。

**下拉只列 provider 名字，不收任何連線設定。** 金鑰、`base_url`、逾時全部在
`user://ai_config.json`（見 `ai/api.md`《`AIConfig`》），建角面板讀它、不寫它——
金鑰有它自己的儲存規則（存 `user://`、不進版控、log 一律遮蔽，見《13》§5），
建角面板多開一個輸入口等於多一個洩漏點。

| 狀況 | 面板行為 |
| --- | --- |
| `AIConfig` 讀不到（設定檔不存在或解析失敗） | 「本機」「雲端」兩顆按鈕 `disabled`，下方小字提示去哪設定；「真人」照常可選 |
| 讀得到但該類別下沒有任何 provider | 只 `disabled` 那一顆 |
| 下拉尚未選 | 顯示 `—`（佔位規則見《15》§1-1），且**擋下存檔**——沒有 `model_name` 的角色投放後不知道要打去哪 |

預設值：`decision_source = local`，模型取 `AIConfig.default_provider`。
一鍵隨機（§6）**不隨機這一欄**——驅動來源是玩家的成本決定（雲端會產生帳單），
不是角色設定的一部分。

> ⚠️ 投放後不可改（§7-1）。UI 上的表現是：已投放角色的角色庫項目裡，這兩欄唯讀顯示，
> 不是隱藏——玩家要看得到自己這隻是誰在驅動的。

## 4. 分頁 2：個性

### 4-1 六維滑桿

| 中文 | 英文欄位 | 0% 端標籤 | 100% 端標籤 |
| --- | --- | --- | --- |
| 誠實謙遜 | `hex_honesty` | 狡猾自私 | 真誠無私 |
| 情緒起伏 | `hex_emotionality` | 冷酷無情 | 敏感多愁 |
| 外向性 | `hex_extraversion` | 孤僻自閉 | 社交狂熱 |
| 友善性 | `hex_agreeableness` | 充滿敵意 | 溫和包容 |
| 嚴謹性 | `hex_conscientiousness` | 散漫衝動 | 嚴密自律 |
| 開放性 | `hex_openness` | 傳統保守 | 獵奇創新 |

**UI 要求**：

- 預設 50，最小刻度 5
- 兩端標籤必須同時顯示，玩家才知道推向哪邊是什麼
- **滑桿進入極端區（≤25 或 ≥75）時要有視覺回饋**：滑桿本身變色（2026-08-16 拍板）

### 4-2 極端項計數器

面板需即時顯示：

```
個性強度：●●○○     2 / 4
提示：再推 0 個滑桿就達標了
```

| 狀態 | 顯示 |
| --- | --- |
| 未達下限 | 紅字「再把 N 個滑桿推向兩端，這個角色才有個性」 |
| 達標（2~4） | 綠字「這個角色有個性了」 |
| 超過 4 | 黃字「推太多了，人設會互相打架。請減少 N 個」 |

### 4-3 `character` 文本框

| 項目 | 規格 |
| --- | --- |
| 型別 | 多行文字框 |
| 上限 | 250 字 |
| 必填 | 否 |
| 即時字數 | 顯示 `47 / 250` |

placeholder：

```
崩塌前是機房維修員，獨自活過三次斷電。
說話很短，不耐煩時會發出鼻音。
最在乎自己的東西不被別人碰。
```

下方小字：「寫外表、口癖、過去經歷、他最在乎什麼都可以。不要寫能力或數值。」

### 4-4 存檔驗證

定義：**極端項** = 該滑桿 ≤ 25 或 ≥ 75。

| 情況 | 極端項數量要求 |
| --- | --- |
| `character` 有填 | 2 ≤ n ≤ 4 |
| `character` 留空 | 3 ≤ n ≤ 4 |

未達標時**擋下存檔**。

## 5. 分頁 3：外觀

**MVP 做 §5-0（造型組挑選），§5-1~§5-4 是完整版的 slot 系統，MVP 不做**（《13》§三、《99》P-01）。
兩者不是互斥的兩套資料：造型組展開後就是 §5-1 的 `appearance[]`，見下。

### 5-0 MVP：造型組挑選

外觀不拆 slot，改提供**固定 6 套**造型組整套挑選（《13》§三，2026-08-16 核過）。

#### 版面

2 列 × 3 欄，6 個縮圖格。選中的那格疊 Amber `#C96C23` `modulate`——
跟快捷欄選中格、分頁按鈕同一個顏色語意（見《[[UI 版面與素材規格]]》）。

| 項目 | 值 |
| --- | --- |
| 縮圖格 | 角色 sprite 尺寸 16×16，格框沿用 `Sprite sheet for Basic Pack.png` 的 `Rect2(11, 59, 26, 28)` |
| 每格下方 | 造型組名字，字級 11 |
| 必選 | 是。未選時**擋下存檔**，跟 §4-4 的極端項門檻並列，兩條都要過 |
| 預設 | 不預選。預設選第一套的話，六套裡會有一套變成「懶得選的人都長這樣」 |

> [!warning] 素材是佔位的，6 套現在長得一樣
> `assets/characters/` 目前只有一套 16×16 sprite sheet。6 個格子在真素材進來之前
> **顯示編號與名字，圖位放純色塊**，不要拿同一張圖 `modulate` 成六個顏色充數——
> 那會讓玩家以為造型組的差別只有顏色，而實際上它們的差別是 `label` 文字
> （那才是餵給 `system_prompt` 的東西）。

#### 資料怎麼存

**不新增欄位。** 每套造型組展開成一組固定的 `appearance[]`（§5-1 的形狀），存進角色。

這樣 MVP 與完整版共用同一份資料契約：完整版的 slot 系統做出來之後，
造型組只是「一鍵填好 8 個 slot」的預設集，不是要拆掉重存的另一種格式。
`build_appearance_text()`（§5-3）也不用分兩條路。

投放後鎖定，MVP 沒有換裝功能（《99》P-01 #3、P-16 決策紀錄）。

#### 6 套的內容

各套的 `appearance[]` 實際內容（`item_id` 與 `label` 文字）**待填**，見《99》P-38。
`label` 會被 `build_appearance_text()` 串進 `system_prompt` 常駐段，
所以那 6 段文字寫得好不好會直接影響角色的自我描述，不是純美術決定。

### 5-1 已確定的部分

- 資料為陣列 `appearance[]`，可儲存多筆
- 每筆含 `slot`（部位）／`item_id`（素材編號）／`label`（中文短句 ≤20 字）
- 存檔時由 `build_appearance_text()` 把所有 `label` 串成一段自然語言
- 產生的文字寫入 `system_prompt` 常駐段

### 5-2 提案 slot 清單　【推測待確認】

| `slot` | 中文 | 可存筆數 | 必填 | 備註 |
| --- | --- | --- | --- | --- |
| `body` | 體型 | 1 | ✔ | 精瘦／壯碩／嬌小… |
| `hair` | 髮型髮色 | 1 | ✔ |  |
| `face` | 臉部特徵 | 1 | ✗ | 疤痕、雀斑、鬍子 |
| `eyes` | 眼睛 | 1 | ✔ |  |
| `top` | 上衣 | 1 | ✔ |  |
| `bottom` | 下著 | 1 | ✔ |  |
| `shoes` | 鞋 | 1 | ✗ |  |
| `accessory` | 配件 | 最多 3 | ✗ | 手套、眼鏡、項鍊… |

### 5-3 組句規則　【推測待確認】

`build_appearance_text()` 依固定順序串接：

```
體型 → 髮型 → 眼睛 → 臉部特徵 → 上衣 → 下著 → 鞋 → 配件
```

**輸出範例**：

```
你身形精瘦，剪得很短的灰髮，一雙灰藍色的眼睛，左眼下方有一道舊疤，
穿著一件磨損的皮外套與深色工作褲，左手戴著皮手套。
```

- 空的 slot 整段略過，不輸出「無」
- 連接詞由固定模板組裝，不呼叫 LLM

## 7. 角色庫與投放

### 7-1 角色庫

| 項目 | 規格 |
| --- | --- |
| 顯示內容 | 立繪縮圖、姓名、六維雷達圖、是否已投放 |
| 可執行操作 | 編輯（僅未投放者）、刪除、投放、複製 |
| 容量上限 | **15 個**（2026-08-16 拍板） |

> ⚠️ **已投放的角色不可編輯**。`personality` 在遊戲中會因反思變動，回頭改滑桿會造成資料不一致；
> `decision_source`／`model_name` 套用同一條規則，投放後不可中途換驅動來源或模型。

### 7-2 投放機制

| 項目 | 規格 |
| --- | --- |
| 預設上限 | 5 人（《10》B21） |
| 房主可下修 | 全域上限 5，房主可設為 1（《10》B22） |
| 逾額 | 需付費，金額待定（見《99》P-20） |
| 投放時機 | 隨時可加入，包含世界進行中（《10》B24，已定案） |
| 投放後 | 生成該世界的肉體副本，進入世界，開始跑決策循環（《00》§7） |

### 7-3 靈魂與肉體

角色庫本質上是**靈魂庫**：靈魂永久保存、不會死亡；投放才會生成該世界專屬的**肉體**副本，只有肉體會經歷生老病死。完整定義見《10》§8。

| 情境 | 規則 |
| --- | --- |
| 投入新世界 | 記憶清空，全新開始（《10》§8.2） |
| 撤回 | 玩家可手動抓離世界；世界內包裝為「被天神召喚」（《10》§8.4） |
| 離開後再回到同一世界 | 取回該世界的封存記憶（《10》§8.2） |
| 在某世界死亡 | 該角色不得再進入該世界；靈魂本體不受影響，可投入其他世界（《10》§8.3） |

**角色履歷介面**【待規劃，見《99》P-16】：需陳列該角色待過的世界（世界名稱、進行中／已封存、留下的紀錄、是否可再次進入），細節見《10》§8.5。UI 呈現方式待設計，本節僅落規則本身。
