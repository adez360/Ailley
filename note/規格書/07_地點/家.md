# 家（`loc_home`）

**用途**：睡眠（回復量最大）、家中儲存
**容量上限**：1（《99》P-17 #2 已定案，先開工、實測後再調）

**每個角色各自一間**：`loc_home` 不是單一地點，是每個角色的 `home_location_id`（《01》§1-1）
指到的其中一筆。AI 決策時仍只看到抽象的 `loc_home`（跟其他地點一樣用 `location_id`），
引擎收到目標為 `loc_home` 的動作時，依發起角色的 `home_location_id` 解析成實際座標——
角色之間互不相通，A 的家不是 B 的家。

**地圖上放固定幾間房子，建角時系統自動分配**（2026-08-16）：玩家不用選。

**間數的產生規則**（2026-08-20 拍板，見 issue #370）：房子間數 = 房主建立世界時設定的人數
上限 N，不是寫死的數字。**MVP／Phase 2 階段這個 N 是固定 5**，不會有「房子不夠用」的情境。
系統不會依任意 N 動態生成房子——若房主未來把人數上限調高到超過目前地圖手動佈置的間數
（例如 10），屬於地圖動態擴張的範疇，MVP／Phase 2 不支援，見下方 P-58。

> [!warning] 目前地圖只有 1 個 `home` 錨點，5 個 `loc_home_01`～`loc_home_05` 是實作待辦
> 《[[村莊地圖]]》目前的 `PlaceAnchors` 只有單一 `home` 錨點對到 `loc_home`（CodeRabbit
> review 查證確認）。這則只拍板規則本身，把場景錨點、資料庫 fallback 列與 `places.gd`
> 解析規則同步成 5 間房各自獨立的 `loc_home_01`～`loc_home_05`，是合併規則後的實作前置
> 工作，不在這則規格 PR 範圍內。
>
> 同一個實作待辦也要處理既有存檔相容：目前程式碼的 fallback 邏輯認的是 `home_001`
> （單一寫死值，CodeRabbit review 查證確認），不是這裡新訂的 `loc_home_01`～`loc_home_05`。
> 要不要把既有 `home_001` 資料 deterministic 遷移到新命名、還是直接標記舊存檔不相容、
> 要求先跑過 migration 才能用新配置，留給那則實作 issue 一併決定，這裡不先猜。

**分配方式（round-robin）**：5 間房子各自的 `location_id` 命名為 `loc_home_01`～`loc_home_05`
（這裡新訂，供《[[腳本地圖]]》`PlaceAnchors` 對應時採用），依字典序排成固定順序表，系統維護
一個「下一個嘗試分配的索引」游標。建角時從游標位置沿固定順序找第一間
空房分配，游標移到該房屋的下一個位置（mod N）。**角色刪除**：騰出的房屋標記為空，游標不
回退，下次巡覽自然會再排到它，避免同一間房子被連續重複塞爆。**讀檔**：游標本身要存檔（跟
房屋佔用狀態一起存），讀檔時直接恢復，不能靠「已佔用房屋中最大索引 + 1」反推——刪除角色
會在佔用序列中留下空洞，最大索引不等於真正的游標位置（例：佔用 0/1/3，游標其實停在 2，
最大索引反推會算成 4）；世界裡沒有任何角色時「最大索引」本身也沒有定義。沒有游標欄位的
舊存檔，讀檔時預設游標為 0。

地圖動態擴張（人數上限中途調高）與同居功能（多角色共用一間房子）不在這次拍板範圍內，
留到 Phase 3/4，見《[[99_待規劃項目清單]]》P-58。

## 地點結構

`danger: 0` / `resources: []` / `regen: {}`（2026-08-16 拍板）——家沒有環境危險，也沒有可採集
的資源，欄位定義見《[[07_地點與行動]]》地點資料結構。

`desc: "籬笆圍出的小院子，南邊出口正對著藥草鋪的門，走幾步就到。"`（依《[[村莊地圖]]》實際佈局：
`home` 院子南側缺口 `(-8,-2)` 與 `herb_shop` 院子北側缺口 `(-7,3)` 幾乎同一條垂直線上，
兩院子入口互相正對）

## 可用行動
