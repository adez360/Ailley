# 15_遊戲內 UI 規格

# 15｜遊戲內 UI 規格

**閱讀對象**：前端組・視覺組
**前置閱讀**：《00 設計原則與架構》、《13 系統分析與系統設計》§三

本文件定義**世界跑起來之後**畫面上的 UI。建角、角色庫、投放那一段在《05》，兩者不重疊：
《05》是「把角色送進世界之前」的介面，本文件是「角色已經在世界裡」之後看到的介面。

> [!note] MVP 範圍
> MVP-1 需要三個 in-game UI：天神之石輸入框、今日摘要面板、身上物品面板，
> 三者均已實作（見《13》§三「UI 補齊」列），本文件定義三者的完整規格。
> 快捷欄（`hotbar.gd`）與主背包（`inventory_panel.gd`）已實作但**是給 player 用的**，
> MVP-1 還沒接 player，那兩個在 MVP-1 用不到，本文件不重複定義它們。

## 1. 共通約束

版面數值、字級、調色盤、素材尺寸一律依《[[UI 版面與素材規格]]》，本文件不重抄，只列會被反覆引用的三條：

| 約束 | 值 | 影響到本文件的什麼 |
| --- | --- | --- |
| 視窗 | 640 × 360，`stretch/scale_mode = integer` | 面板寬度上限。280 已經是螢幕的 44%，再寬會蓋掉世界 |
| 字級 | 全 UI 統一 11 | 一行約 12 個中文字（`bubble.gd` 的 `MAX_LINE_WIDTH = 132` 量出來的） |
| 面板底板 | `Setting menu.png` 九宮格，`texture_margin_top = 28` 那格帶標題列 | 有標題的面板用左格，素面用右格 |

### 1-1 佔位規則

**資料還沒接上的欄位一律顯示佔位字元 `—`，不留空白也不顯示假數值。**
沿用 `status_panel.gd` 的 `AGE_PLACEHOLDER := "—"` 做法（《13》§三明列這條）。

空白會讓人以為「這個角色沒有這項資料」，`0` 會讓人以為「這個角色的值是零」——
兩者都是錯的訊息。`—` 講的是「還沒接上」，這是實話。

「資料還沒接上」與「這個角色沒有這項能力」是兩回事，處理方式也不同：
沒掛 `Inventory` 的角色，金錢那一列是**整列隱藏**，不是顯示 `—`（`status_panel.gd`
的 `has_money` 已經是這個做法）。

### 1-2 這些面板不注入 prompt

本文件定義的所有面板都是**給人看的**。面板上的任何整理過的資料——今日摘要、
行動紀錄、物品清單——**都不得回頭注入 AI 的 prompt**。

理由是角色能想起什麼由《03》記憶四層架構決定，有自己的重要度與衰減規則。
UI 為了給玩家看而整理出來的「今天做過這些事」是一份沒有衰減、沒有遺漏的完美紀錄，
接進 prompt 等於繞過《03》偷渡一份完美記憶給角色。

## 2. 角色資訊面板

點角色彈出的面板。有四個分頁：**狀態**、**今日**、**物品**、**內心**（皆已實作）。

### 2-1 為什麼是一個面板多分頁，不是各自獨立的面板

《13》§三把「角色狀態面板」「今日摘要面板」「身上物品面板」列成三項，那是**工作項目**的分法；
內心分頁是之後（#736）依同一個理由追加的第四個切面。呈現上合成一個面板，理由有三：

| 理由 | 說明 |
| --- | --- |
| 都是同一個問題的切面 | 都在回答「我點的這個角色，現在是什麼狀況」。分成多個面板，玩家要開多次、記多個鍵位 |
| 640×360 放不下多個並存的面板 | `StatusPanel` 150×175、`InventoryPanel` 280×160，兩個都置中，同時開會直接互相蓋住 |
| 選取機制只有一套 | 資料來源都是「當下選中的那個角色」。分開做等於各自維護一份選中狀態，都要處理角色死亡/離場 |

分頁列沿用 `character_create.gd::_tabs()` 既有做法：`HBoxContainer` 排 `Button`，
選中的那頁套 Amber 底 + Ink 字，未選中的維持預設。

### 2-2 版面

| 項目 | 值 |
| --- | --- |
| 位置 | 螢幕置中 |
| 尺寸 | 280 × 208 |
| 底板 | `Setting menu.png` 帶標題列那格（`region_rect = Rect2(11, 12, 106, 122)`） |
| 標題列 | 角色名字。做法沿用 `status_panel.gd`：`TitleBg`（ColorRect `#DCB98A`）蓋掉素材烤進去的 "SETTINGS" 字樣，`TitleLabel` 疊上去 |

**兩個數字都是物品分頁決定的。** 物品分頁的 36 格是三頁裡唯一尺寸固定、又剛好最大的內容，
拿它定框最省事；狀態頁比這個框小，今日頁比它大所以自己捲（見 §2-5 末）。
三個分頁各自算尺寸的話，切分頁時面板會跳動。

| 方向 | 怎麼算出來的 |
| --- | --- |
| 寬 280 | 9 欄 × 26px 格 + 8 × 3px 間距 = 258，加左右各 10px 內距 = 278，進位到 280。跟 `inventory_panel.gd` 現值同源 |
| 高 208 | 標題列 32（`status_panel.gd` 的 `VBox` `offset_top`）+ 分頁按鈕 20 + 間距 6 + 4 列格子 121（4×28 + 3×3）+ 間距 6 + 提示列 14 + 底部 8 = 207，進位到 208 |

> [!note] 這些是 2026-08-17 在 640×360 執行期量出來的，不是估的
> 11px 字型下 `Label` 高 14、`Button` 高 20、`LineEdit` 最小高 22，格子 26×28、
> 9 欄 grid 實寬 258。要改字級或換 theme 樣式的話這幾個數字全部要重量。

### 2-3 開啟與關閉

| 操作 | 行為 |
| --- | --- |
| 點角色本體 | 開啟，切到**狀態**分頁 |
| 點分頁按鈕 | 切分頁，面板不關 |
| 點空白處 / Esc | 關閉 |
| 面板開著時點另一個角色 | 換成新角色的資料，**維持當前分頁** |

點擊偵測沿用 `world/selection.gd` 的 `character_at()`，不自己查物理碰撞形狀
（`status_panel.gd` 的註解寫過理由：角色的碰撞形狀只有腳下那個小圓，物理查詢點頭部會落空）。

「維持當前分頁」是刻意的：玩家連續點三個角色比對物品時，不該每次都被踢回狀態頁。

### 2-4 分頁一：狀態　**已實作**

`status_panel.gd`，現況即規格：姓名（標題列）、年齡、金錢，加上 `Stats.SPEC` 的全部數值。

數值列是 `_ready()` 時依 `Stats.SPEC` 動態長出來的，`SPEC` 加一項這裡自動多一行。
**不要改成固定節點**——那會讓每次新增數值都要回頭改場景。

年齡讀 `Character.age`（建角面板收集、經角色庫投放寫入節點，見《01》§1-1）；
固定寫在場景裡的 NPC 沒有這項資料，`age` 維持 -1 的哨兵值，顯示
`AGE_PLACEHOLDER`，不是假造一個數字。

### 2-5 分頁二：今日

回答「這個角色今天打算做什麼、實際做了什麼」。上下兩段，**上段是意圖，下段是紀錄**。

```
┌─ 角色名字 ────────────────────┐
│  [狀態] [今日] [物品]          │
│                               │
│  今天打算                      │
│   ✓ 去藥草鋪買藥               │
│   ・ 找鐵匠聊聊                │
│                               │
│  做過什麼                      │
│   10:30  搭話 → 小美（失敗）    │
│   09:02  工作                  │
│   08:14  移動 → 餐酒館      ▓  │
│                             ░  │
│  點空白處或按 Esc 關閉          │
└───────────────────────────────┘
```

右側那條是捲軸——這一頁的內容一定超過可視高度，見本節末。
`做過什麼` 由新到舊，所以最上面那筆永遠是這個角色現在在做的事。

#### 刷新時機（issue #661，2026-08-31 拍板）

**開啟面板、切到這個分頁、或面板開著時換選中角色，重新讀一次 `today_plan`／
`today_log` 並重繪整頁；停留在這個分頁不動的期間不即時更新**，跟這個角色同時
做的其他事（新增一筆 `today_log`、`update_plan` 改動 `today_plan`）不會反映在
畫面上，要玩家重新切一次分頁或重選一次角色才看得到最新內容。

這跟 §2-6 物品分頁「掛 `Inventory.changed` 訊號、不逐幀輪詢」刻意不同——物品分頁
能做到即時更新，是因為 `Inventory.changed` 訊號本來就存在、是給 `hotbar.gd`／
`inventory_panel.gd` 用的既有基礎設施，這裡只是多接一個訂閱者，成本趨近於零；
`_today_plan`／`_today_log` 目前沒有對應的變動訊號，要做到即時更新得先在
`agent.gd` 新增訊號並讓每個寫入點（`_apply_today_plan()`／`_push_today_log()`／
約定併入等多處）都補發送，是一筆新的實作成本，不是「差不多免費就能做」的等級，
MVP 階段不做。跟狀態分頁（§2-4，同樣是開啟／切分頁時重讀，沒有即時訂閱）維持
同一種行為，物品分頁才是這個面板裡的例外。

之後如果要接即時更新，比照物品分頁的做法在 `agent.gd` 補一個 `today_changed`
訊號、`status_panel.gd` 依樣連線／斷線即可，不是這裡先天做不到，只是這輪不做。

#### 上半：今天打算（`today_plan`）

資料來源是 `Agent._today_plan`，`Array[Dictionary]`，每筆 `{id, text, is_done}`
（見《[[LLM 串接與 AI 服務層]]》「今日計畫」、`NPCDailyPlanSchema.gd`）。

| 顯示 | 規則 |
| --- | --- |
| 順序 | 照陣列原順序，不重排。順序是模型自己寫的，重排等於竄改它的表述 |
| `is_done: true` | 行首 `✓`，字色 Loam `#5D4A38`（壓下去，讓未完成的那幾項跳出來） |
| `is_done: false` | 行首 `・`，字色 Bark `#2F2522` |
| 空陣列 | 顯示 `—`（見 §1-1）。世界開場、剛睡醒都會是這個狀態，是正常的 |
| 筆數 | **不限**（《10》§5.4：可變動增加、不限筆數）。版面不預設項數，全部渲染，靠 §2-5 末的捲動處理 |

> [!warning] `is_done` 是模型自我回報，不是引擎核實過的
> 唯一會寫 `is_done` 的地方是模型自己的 `update_plan` 回應。引擎的 `_tasks`
> （真的執行的排程）跟 `_today_plan`（自我回報的意圖）之間沒有任何連結。
>
> **UI 不得自己補上這個連結**：不要拿下半的行動紀錄去比對上半的計畫項目，
> 也不要顯示「計畫達成率」之類的彙總。那等於引擎替模型的自我陳述做真偽定性，
> 而這裡沒有任何機制能判定「移動→餐酒館」算不算完成「找鐵匠聊聊」。
> 兩段各講各的，讓玩家自己看出落差——那個落差本身就是可看的東西。

#### 下半：做過什麼（`today_log`，**新增機制**）

引擎目前**沒有**這份資料。`_current_task` 只有當下那一筆，做完就被換掉，
`last_action_result` 是瞬時情境、《[[存檔]]》明講不留。所以這個分頁需要新增一份紀錄。

| 項目 | 規格 |
| --- | --- |
| 位置 | `Agent`／`Character` 上的 `_today_log`，`Array[Dictionary]` |
| 一筆的形狀 | `{minute: int, action: String, target: String, ok: bool}` |
| `minute` | 遊戲分鐘，取 `GameClock`。顯示時格式化成 `HH:MM` |
| `target` | 動作的對象（地點名、角色名、物品 id）。沒有對象的動作填空字串，顯示時整個省略，不印「無」 |
| `ok` | 引擎判定這次動作成不成立。`false` 時行尾加「（失敗）」 |
| 寫入時機 | **動作執行結束時**由引擎寫，不是決定時。決定了但沒做到的不算做過 |
| 保留上限 | 50 筆，超過從最舊丟（issue #518／《99》P-38：一筆是四個欄位的小 Dictionary，記憶體成本可忽略，寧可抓寬鬆一點，避免早上的事傍晚就被擠掉） |
| 清空時機 | `GameClock` 跨日時整份清空。這是「**今日**摘要」，昨天的不留 |
| 顯示順序 | **由新到舊**。最上面那筆就是「當前行動」，§2-8 靠的是這一點 |

#### 這一頁裝不下，所以整頁可捲

面板高度是物品分頁定死的（§2-2），這一頁的內容量不受它限制：`today_plan` 不限筆數，
`today_log` 上限 50 筆，兩者加起來一定超過可視高度。

| 項目 | 值 |
| --- | --- |
| 容器 | `ScrollContainer`，只捲直向 |
| 可視高 | **122**＝面板 208 − 標題列 32 − 分頁列 20 − 間距 6 − 提示列 14 − 間距 6 − 底部 8 |
| 一次看得到 | 約 8 列（11px 下 `Label` 高 14）。扣掉「今天打算」「做過什麼」兩個小標題，實際約 6 列資料 |

**兩個小標題跟著一起捲，不釘住。** 釘住兩條標題要吃掉 28px，可視區只剩 94、約 6 列，
換到的只是捲到一半時知道自己在看哪一區——而兩區之間本來就有明顯的空行分隔。

不截斷、不加「還有 N 筆」的省略號：這一頁的重點就是讓玩家看完整份落差。

`ok` 是該動作判定流程跑完的最終結果，不是對動作性質的定性——技能／體力／運氣類由
引擎擲骰（《00》原則一），心智判斷類（如 `persuade`）由被說服者的模型裁定
（《01-2》§3-1、《00》原則四），`ok` 記的都是這條判定出來的結果，寫進紀錄沒有違反
原則二。紀錄裡**不放**動機、評價、關係影響之類的欄位：那些是《00》原則二點名不該由
引擎貼的標籤。

`today_log` 是 UI 專用的，不進 prompt（見 §1-2），也**不進存檔**——重開遊戲後這一欄
從空的開始。跟 `today_plan` 不同：`today_plan` 是跨天的承諾，《[[存檔]]》已定要存；
`today_log` 是當天的流水，重開遊戲時「今天」這個概念本身就重新開始了。

### 2-6 分頁三：物品

回答「這個角色身上有什麼」。

| 項目 | 規格 |
| --- | --- |
| 資料來源 | 該角色的 `Inventory`（掛在 `Character` 基底，Agent 也有，見《[[物品欄]]》） |
| 格數 | 36 格，4 列 × 9 欄。對應 `Inventory.SIZE`（快捷欄 9 + 主背包 27） |
| 第一列 | index 0–8，即快捷欄。**手持格**（`get_selected_index()`）疊 Amber `#C96C23` `modulate` |
| 其餘三列 | index 9–35，主背包 |
| 格子素材 | `Sprite sheet for Basic Pack.png` 的 `Rect2(11, 59, 26, 28)`，跟 `hotbar.gd`／`inventory_panel.gd` 同一格 |
| 格內顯示 | 沿用 `inventory_slot_button.gd`：中文名稱（`ItemDatabase.get_display_name()`，最多 2 字），數量 > 1 才多印一行。專案還沒有物品圖示素材，文字是暫時的示意畫法 |
| 沒掛 `Inventory` 的角色 | 整個分頁按鈕 `disabled`，不是顯示 36 個空格 |
| 更新 | 掛 `Inventory.changed` 訊號，不逐幀輪詢 |

**不做拖放、不做點擊換手持。** 這是觀察用的面板：玩家看的是別人的背包，
`set_selected_index()`（換手持物品）是那個角色自己的決定，不是玩家可以代按的。
Player 自己的背包操作走既有的 `hotbar.gd`／`inventory_panel.gd`，跟這裡是兩條路。

快捷欄那一列跟其餘三列**在視覺上要分得出來**（列間距加大，或加一條 Clay `#75593C` 分隔線）：
手持格的概念只對第一列成立。

### 2-7 分頁四：內心狀態

回答「這個角色現在心裡／身體是什麼狀況」（#736）。唯讀，只顯示現況，不顯示剩多久。

| 項目 | 規格 |
| --- | --- |
| 情緒 | `Character.emotion.type`（AI 自行宣告，見《02》§1）。`neutral` 顯示 `—`（§1-1），其餘顯示中文名稱＋強度，例如「開心（強度 60）」 |
| 生理狀態 | `Character.conditions` 陣列（引擎依門檻判定，見《02》§2-2），逐筆列出中文名稱。空陣列顯示 `—` |
| 不顯示 | `emotion.duration_left`——這頁給玩家看的是「現在是什麼狀況」，剩多久是引擎內部排程細節，不是狀況本身 |

情緒與生理狀態都是唯讀顯示，不做任何加工或評價：情緒的中文名稱只是
`EMOTION_TYPES` 的翻譯表，生理狀態沿用 `Character._get_condition_display_name()`
既有的翻譯，都不新增判斷邏輯。

### 2-8 這個面板就是 MVP 版的「內心視窗」

《10》§9.1 定義了內心視窗的欄位分級。本面板是它的 MVP 子集：

| 《10》§9.1 恆公開欄位 | MVP 做不做 | 在哪 |
| --- | --- | --- |
| 當前行動 | ✔ | 分頁二下半最新一筆 |
| 當前目標（`today_plan`） | ✔ | 分頁二上半 |
| 情緒狀態 | ✔ | 分頁四（§2-7） |
| 對在場者的好感度 | ✘ 不做 | 《10》§9.1 這一列指的 `affinity` 已於 2026-08-16 隨《01》§3-1 一起移除（沒有引擎消費者），`trust` 也已於 issue #601 同理拿掉，`relations` 現在只剩 `met_count`／`appearance_cache`，沒有評價數值可顯示。關係網 UI 也不在《13》§三的 MVP-1 清單裡 |
| 內心獨白 | ✘ 留到之後 | 需要決策迴圈先把模型的推理過程留下來，目前沒有存 |

> [!important] `prompt` 一律不得出現在任何面板上（《10》B5）
> prompt 裡有引擎餵給該角色的所有事實句，其中包含玩家不該知道的其他角色資訊。
> 要看 prompt 走 debug 主控台，那是開發用的，跟遊戲內 UI 是兩回事。

## 3. 天神之石輸入框

玩家對世界投放話語的唯一介面。機制規則在《10》§7 與《[[07_地點/天神之石]]》，
本節只定義 UI。

> [!important] MVP-2 化身後鎖住，只有純觀察者能用（2026-08-20 拍板，見 issue #369）
> 玩家一旦化身（操控一個世界內的角色），就不再是「純觀察者」，天神之石的
> 說話功能鎖住、無法再點擊開啟輸入框——化身代表成為世界的一員，不該同時保留
> 「跟世界外對話」的天神視角特權。純觀察者（含純 AI 模式——沒有玩家化身的世界，
> 觀察者永遠處於純觀察狀態）維持完整使用權，不受影響。
>
> 化身後走到石頭旁改成能查看一份「地點事件記錄」，見 §3-5——這不是拿掉功能，
> 是把「發話」換成「回顧」。

> [!note] 現況（2026-08-23）：地圖上已有天神之石
> issue #154（真村莊地圖）已關閉，`Ailley/scenes/main.tscn` 的 `god_stone` 錨點與
> `Ailley/scripts/world/god_stone_input.gd`／`Ailley/scenes/god_stone_input.tscn` 已實作，見《[[07_地點/天神之石]]》。

### 3-1 開啟方式：點地圖上的石頭

不給快捷鍵，也不放常駐按鈕。**點石頭才開**。

理由是《10》§7 明講「位置性須保留⋯⋯不得以全村廣播之類的功能優化掉」。
入口綁在石頭本體上，玩家每次投放話語都要先在畫面上找到那顆石頭。

**玩家恆知真實座標，不受搬運影響**（2026-08-20 拍板，見《[[07_地點/天神之石]]》、
issue #369）：石頭被搬走後找不到的資訊落差只發生在**角色**身上（《99》P-33），
UI 上會有指標指向真實位置，玩家不會真的「找不到」。

點擊偵測沿用 `world/selection.gd` 的做法，跟角色的 `character_at()` 平行。

> [!note] 位置性約束的是村民，不是玩家的滑鼠
> 「要走到石頭旁邊」是**村民**才有的限制（6 格內才聽得到）。玩家在 MVP-1 是觀察者，
> 沒有身體、沒有站位，鏡頭移得到就點得到。不要因為「位置性」四個字就要求玩家角色
> 走過去——MVP-1 根本沒有玩家角色。MVP-2 化身後這個入口整個鎖住（見上方 §3 開頭），
> 不是變成「要走過去才能點」，這題《99》P-38 §3 原本待確認的兩個選項到此已有答案：
> 兩者都不是，是鎖住＋換成 §3-5 的記錄查看。

### 3-2 版面

| 項目 | 值 |
| --- | --- |
| 位置 | 螢幕置中 |
| 尺寸 | 260 × 84 |
| 底板 | `Setting menu.png` 帶標題列那格 |
| 標題 | 「天神之石」 |
| 輸入 | `LineEdit`，寬 240，`max_length = 40` |
| 狀態列 | 輸入框下方一行小字，Loam `#5D4A38`。內容見 §3-4 |

| 方向 | 怎麼算出來的 |
| --- | --- |
| 寬 260 | `LineEdit` 要 240（跟 `chat_input.tscn` 的 `Input` 同寬，實測 240×22），加左右各 10px 內距 = 260 |
| 高 84 | 標題列 32 + `LineEdit` 22（11px 下的最小高，見《[[UI 版面與素材規格]]》「聊天輸入框靠 `grow_vertical = 0` 才不會長回快捷欄上」那條）+ 間距 6 + 狀態列 14 + 底部 8 = 82，進位到 84 |

輸入框寬度跟聊天框對齊是刻意的：兩處都是「打一句話出去」，同樣的框寬讓玩家對
「一行能打多少字」的手感一致，不用重新抓。**面板本身**比聊天框寬 20，那是九宮格內距，不是輸入區變寬。

**不沿用 `chat_input.tscn` 的底部置中位置。** 那個位置的語意是「你的角色正在說話」，
而天神之石的話語**不屬於任何角色**（《10》B19：不署名、村民與其他玩家皆不知來源）。
擺在同一個位置會讓玩家以為那是自己角色講的。

`max_length = 40` 跟 `chat_input.gd` 同值，理由也一樣：話語要冒成氣泡，
`bubble.gd` 的 `MAX_LINE_WIDTH = 132` 下 40 字已經是三行多，再長會蓋掉畫面。

### 3-3 送出後會發生什麼

| 步驟 | 行為 |
| --- | --- |
| 1 | 輸入框關閉 |
| 2 | **石頭本體**冒氣泡（沿用 `bubble.tscn`），不是玩家角色頭上 |
| 3 | 氣泡顯示 5 秒（《10》B18 的話語顯示冷卻） |
| 4 | 6 格內的角色收到一句事實句（《07》§3 的天神之石半徑，引擎端，不是 UI 的事） |
| 5 | 冷卻 5 秒內再點石頭，輸入框照開，但 `LineEdit` `editable = false`，狀態列顯示剩餘秒數 |

送出空字串（或只有空白）時直接關閉，不冒氣泡、不進冷卻——跟 `chat_input.gd`
的 `line.is_empty()` 同一個處理。

`words_to_creator` 的擲骰觸發（25%，情緒強度 ≥70 時 40%，見《01-3》§1 的注入分級註解、
《01》§1-4 與《99》P-10）
是引擎收到話語之後的事，**UI 不參與、也不顯示有沒有觸發**。玩家不該知道自己這句話
有沒有戳中誰——那是要在遊戲裡看出來的。

### 3-4 狀態列顯示什麼

| 情況 | 顯示 |
| --- | --- |
| 可以送出 | 「說吧。附近的人聽得到。」 |
| 冷卻中 | 「還在迴盪⋯⋯（N 秒）」，N 每秒更新 |
| 排隊中（多人） | `—`（見 §1-1）。MVP-1 單機只有一位玩家，排隊制（《10》B18 間隔 2 秒換下一位）沒有可顯示的內容，但版面先留著，接多人時不用重排 |

**不顯示「範圍內有幾個角色聽得到」。** 那會讓玩家先數人頭再決定講不講，
把「走到石頭前」的戲劇性換成一個效率計算。要知道誰在附近，自己看畫面。

### 3-5 地點事件記錄（2026-08-20 拍板，見 issue #369）

可以查看一份事件記錄——記錄透過天神之石說過的話，不是角色對天神之石的反應。
查看入口依身分不同：**化身玩家**要走到天神之石旁（跟村民的位置性限制同一套，見
§3 開頭說明）；**純觀察者／純 AI 模式**沒有身體、沒有站位（同樣見 §3 開頭），
入口是鏡頭移到石頭後點選，不是走過去——這是方便回顧的檢視功能，不是專門補償
被鎖住的輸入權限。

**綁定天神之石這個物件，不綁定座標**（2026-08-20 拍板，回應 CodeRabbit review）：
天神之石 `carryable: true`，可能被搬離原始座標（見《[[07_地點/天神之石]]》「可搬運
與已知位置」）。記錄跟著石頭本體走，不跟著座標——玩家在石頭「目前」所在位置查看的
永遠是同一份完整記錄，不會因為搬運而分裂成好幾份、也不會留下查不到的孤兒記錄。

**多人世界共享同一份，不署名、不分玩家**（2026-08-20 拍板，回應 CodeRabbit review）：
《10》B17／B19 已拍板天神之石全世界共用一顆、話語「不署名，村民與其他玩家皆不知
來源」——這份記錄延續同一條規則，不是「每位玩家各自的個人記錄」。任何走到石頭旁的
觀察者（不論哪位玩家）看到的都是同一份，內容只有「什麼時候、說了什麼」，不標示是
哪位玩家送出的。這樣單機與多人世界的呈現規則完全一致，也不需要另外設計「誰能看到
誰的話」這層存取控制。

**收錄範圍擴充：手勢事件（2026-08-30 拍板，見 issue #752／PR #759）**：
本節原本只收「透過天神之石說過的話」。自 2026-08-30 起，角色對天神之石的四種手勢——
吐口水（`spit_at_stone`）、攻擊（`attack`，`target` 填保留字 `"god_stone"`）、
膜拜（`worship_stone`）、讚美（`praise_stone`）——也寫進同一份記錄，面板顯示邏輯
不變（新到舊、保留 20 筆），行動定義見《[[07_地點與行動]]》§2-5。

**署名規則分兩種，是刻意的**：手勢是目擊得到的公開行為，記錄**帶角色名**
（「阿明 攻擊了天神之石。」）；石頭話語維持《10》B19 不署名。同一份面板從此混合
匿名（石頭話語）與署名（手勢）兩種條目，不是其中一邊違反 B19——B19 約束的是
「話語來源不可知」，手勢不是話語、本來就是旁人看得到的公開行為。

> [!warning] 跟 `words_to_creator` 是兩回事，不要混在一起做
> 《09》§7 明文規定角色的 `words_to_creator` 只有在該角色死亡後才會被收錄進圖書館、
> 提前揭露會牴觸這條已拍板的延遲揭露設計。這份地點事件記錄**不揭露任何角色的內心
> 反應**，只回顧說過什麼、做過什麼手勢、什麼時候。
>
> 也不是圖書館的一部分——圖書館是跨局永久保存的成就／回顧檔案，只在世界結束或
> 角色死亡這類固定敘事節點寫入（見《10》§10、《09》§7）；這份記錄是綁定天神之石、
> 當局有效的即時歷史，資料模型與寫入時機都不一樣，各自獨立，不要合併實作。

具體版面、保留筆數等留待實作 issue 補（本則只拍板功能定位與資料邊界）。
