## 1. 名詞定義

本節為全團隊共用詞彙，撰寫其他文件時請沿用。

| 名詞 | 定義 |
|---|---|
| tick | 世界時鐘的最小刻度。**僅為時間計量單位，不是決策觸發器。** |
| 時間顆粒度 | 1 tick 代表多少「遊戲時間」。 |
| 時間流速 | 遊戲時間相對現實時間的倍率。本作固定 1:60（現實 1 秒 = 遊戲 60 秒）。 |
| 決策頻率 | 角色實際發起決策請求的間隔。由「動作長度」決定，與 tick 顆粒度無關。 |
| 狀態權威主機 | 保存世界唯一正本資料的機器。本專案固定為房主機。 |
| 決策供給者 | 提供模型運算、產出角色決策的來源。可為房主或任一參與玩家。 |
| 靈魂 | 玩家在角色庫中創建的角色本體。永久保存，不會死亡。 |
| 肉體 | 靈魂投入某個世界後產生的實例。可在該世界生老病死。 |
| 房主 | 建立世界的玩家。世界跑在他的機器上。 |
| 投放席 | 有投放角色的玩家席位。 |
| 觀察席 | 未投放角色、僅觀看的玩家席位。 |

**核心關係式**

```
現實決策間隔 = 動作長度（遊戲時間） ÷ 時間流速倍率
```

此式說明：把單日 tick 數調多只會讓時間刻度變細，**不會**改變玩家在現實中看到的事件密度。要調整觀看節奏，必須調整流速倍率。

## 2. 模式與組合

### 2.1 三個設定軸

| 軸 | 選項 |
|---|---|
| 玩家身份 | 觀察者（不進場）／造物者（投放 AI 角色）／化身者（親自操控角色） |
| 連線 | 單機／連線 |
| 模型來源 | 內建地端／玩家自備雲端 |

玩家於世界建立時以下拉選單自由組合，非固定套餐。

### 2.2 有玩法意義的六種世界類型

| # | 類型 | 說明 | 優先級 |
|---|---|---|---|
| 1 | 單機・純觀察 | 僅玩家本人與天神之石 | MVP |
| 2 | 單機・化身 | 玩家擔任其中一名村民 | 後續 |
| 3 | 連線・多神共觀 | 多人共觀同一世界，各自使用石頭 | v2.0 |
| 4 | 連線・各自投放 AI | 每人帶自捏 AI 角色（可各自帶不同模型）入村 | v2.0（主打賣點） |
| 5 | 連線・多人化身 | 多人親自下場 | 不建議 |
| 6 | 連線・混合 | 有人當神、有人放 AI、有人化身 | v2.1 |

**類型 5 明確不建議實作。** 真人即時操控會破壞觀察調性，且與事件驅動決策架構衝突。

### 2.3 真人參與的實作原則

若日後實作真人參與，**不做鍵盤滑鼠即時操控**，改為「真人接管 AI 的決策位」：真人角色同樣在動作結束時被呼叫，但跳出的是決策 UI 面板而非 LLM 請求，輸出 JSON 格式與 LLM 完全一致。詳見《12》§3「DecisionProvider 介面」的 `HumanInput` 實作。

此設計的效益：引擎無須修改；AI 村民無法分辨對方是否為真人；自動解鎖類型 6「圖靈測試村莊」玩法。

## 4. 時間系統

### 4.1 顆粒度與流速分離

兩者為**獨立規格**，不可互相換算。

| 項目 | 規格 |
|---|---|
| 時間顆粒度 | 1 tick = 1 遊戲分鐘 |
| 時間流速 | 固定 1:60（現實 1 秒 = 遊戲 60 秒） |
| 可調整流速機制 | 【待規劃】，見《99》P-25 |

**此節修改《00 設計原則與架構》的全域時間單位定義。**

### 4.2 世界壽命

以**現實天數**計算，由房主於建立世界時設定。

### 4.3 結束條件

| 條件 | 說明 |
|---|---|
| 天數上限 | 達到房主設定的現實天數 |
| 房主手動結束 | 需全體參與玩家同意 |
| 無限 | 不設終點 |

**提前結束補充規則**：現實 7 天未上線的玩家視為棄權，不計入同意門檻。

### 4.4 持續運行

實作順序：

| 階段 | 方案 | 說明 |
|---|---|---|
| 第一版 | A 房主在線才跑 | 房主離線時世界進入靜止期，不推進但不解散 |
| 擴充 | D 離線降級模擬 | 全員離線時不呼叫 LLM，時間照走但不產生戲劇 |
| 未來 | B 導演權轉移 | 房主離線時移交 NPC 決策權給其他在線玩家 |

**方案 B 需設「轉移志願序」，且因使用其他玩家機器資源，必須列為 A4 標籤並取得玩家明示同意，不得由房主單方勾選。**

導演權轉移需維護兩份名單（概念上分開，實務上可共用同一組人）：狀態接管志願序（誰保管世界快照）、導演權志願序（誰的模型跑 NPC）。快照須定期預先同步給第一順位，不可等房主已斷線才傳。

### 4.5 玩家離線處置

| 項目 | 規則 |
|---|---|
| 角色狀態 | 入眠，顯示「被天神召喚中」，各項狀態暫停，不會餓死 |
| 踢出門檻 | 現實 72 小時未上線 |
| 世界內文案 | 仍寫「被天神召喚已久」，維持世界觀說法 |

## 5. 決策架構

### 5.1 觸發方式

**事件驅動，非輪巡。** 取代《00》原本以 tick 為觸發點的批次決策循環。

1. 世界開始時，所有角色依序發起決策請求，進入優先序佇列（出隊順序見下）
2. 角色完成當前動作後，才發起下一次決策請求
3. AI 負責產出決策，實際動作執行由 Godot 負責
4. 動作完成後再次發起請求

**佇列出隊順序**：對話輪次（`Policy.CONVERSATION`）優先於行程請求（`Policy.SCHEDULED`），同一種之內維持進場順序。排序只依呼叫端標示的請求類型，也就是「誰在等」——玩家停在對話框前面等字出來，背景角色重排行程晚幾秒沒有人看得出來。**引擎不依角色狀態判斷「誰比較緊急」**：那等於引擎替 AI 認定一個處境算不算一回事，違反《00》原則二。重試是同一份請求的延續，插回自己那一種的最前面，不會搶到還在等的對話前面。

此架構天然容錯：角色在等待模型回覆期間仍執行上一個動作，短暫卡網不影響畫面連續性。決策請求的組裝、驗證與結果套用一律在房主機執行，完整的職責邊界見《12》§5。

### 5.2 事件通知傳遞

所有系統通知（含爽約通知）**暫存後，於該角色下一次決策呼叫時一併給予**，避免兩個呼叫重疊。

呼叫時一併附上「當前動作」，由 AI 自行決定繼續執行或改變行動。

### 5.3 環境資訊取得原則

**角色必須實際接觸環境後才會知道環境變化。** 引擎不得在角色未接觸前預先告知環境資訊。

例：藥草叢被採空，角色必須走到藥草叢才會知道，不可在他還在家時就通知。

### 5.4 今日計畫（today_plan）

**定位**：是「想做的事」，不是「排定的行程」。引擎不強制執行，僅作為 prompt 上下文。

**資料結構**：可變動增加、不限筆數；每筆需標記已完成／未完成。角色沒事做時可自行增加。

**輸入端**：一律注入，但壓成自然語言句子，不以欄位列表呈現。

```
你今天原本打算：採藥草（已完成）、找 TAMMY 聊天、修屋頂。
```

**輸出端（update_plan）**：僅於下列時機開放此欄位，其餘時候 schema 中不含該欄位（條件式欄位機制見《12》§2.4）。

| # | 時機 | 說明 |
|---|---|---|
| 1 | 睡覺反思時 | 重寫整份 |
| 2 | 意圖全數完成時 | 沒事可做，需要新目標 |
| 3 | 意圖被事實推翻時 | 須符合 §5.3，角色實際接觸後才觸發 |
| 4 | AI 主動申請 | 突然想做某事或想換工作時可申請重填 |

**存在意義**：維持角色跨決策的連貫性；提供玩家可讀的「當前目標」欄位；作為未來降級模擬的素材。

### 5.5 約定機制（appointment）

> [!warning] 現況（2026-08-23）：本節描述的機制尚未接進決策 schema
> `Ailley/scripts/ai/ai_schema.gd` 的 `plan_response_schema()` 沒有 `appointment` 欄位，
> 也不支援 `with`／`location`／`game_time` 或雙向爽約通知。目前只有 `expires_in_minutes`
> 讓 AI 對任務設一個效期，那是完全不同的機制，不是這裡規劃的結構化物件的替代品。追蹤
> issue #479（OPEN，`wire appointment mechanism into decision envelope and task engine`）。
> 《06》《04》已同步標記，這裡維持原設計描述，接上時直接照這節做。

**不採用解析對話的方式**（需額外 LLM 呼叫且不可靠），改為決策 JSON 選填欄位：

```json
"appointment": {
  "with": "TAMMY",
  "location": "loc_pavilion",
  "game_time": "第12天 12:00"
}
```

**引擎行為（僅注入事實句，不做任何強制）**

| 時點 | 動作 |
|---|---|
| 約定前 30 遊戲分鐘 | 於雙方 prompt 注入：「你和 TAMMY 約好中午在涼亭見面。」 |
| 約定時間到 | 檢查雙方是否在該地點 |
| 產生約定時 | 引擎自動將該筆約定併入 today_plan 顯示，不另外詢問 AI |

**爽約雙向通知**

| 對象 | 事實句 | 時點 |
|---|---|---|
| 等待方 | 「你在涼亭等到 12:30，TAMMY 沒有出現。」 | 等待逾時當下 |
| 爽約方 | 「現在是 12:30，你和 CHO 約好中午在涼亭見面，但你人在森林裡打獵。」 | 爽約當下（非事後） |

爽約方若當時處於睡眠或昏迷，改為醒來後首次決策時給予。

**單方面宣告的約定**：引擎照樣記錄，但僅給宣告方提醒事實句，未答應的一方不給。此設計會自然產生「一方空等」的情境。

好感度變化與情緒反應**全部由 AI 自行決定**，符合「引擎只給事件不給情緒」原則。

## 6. 模型與連線架構

### 6.1 地端模型

採 **Sidecar（邊車）架構**：與 Godot 遊戲一起打包安裝，運作時為獨立背景進程，非嵌入 Godot 內。

遊戲內建一個本地模型：**Qwen2.5-7B-Instruct**（2026-08-16 定案，見《99》P-20 #5）；量化等級為 **Q4_K_M**（`Ailley/scripts/ai/ai_config.gd` 的 `_DEFAULT_LOCAL_MODEL` 現況值，2026-08-23 查證確認已是程式碼實際採用值，不再是待補項）。

### 6.2 容量規格

| # | 規格 |
|---|---|
| D2 | 一台電腦僅能載入**一個本地模型實例**；該實例可供該玩家的多個角色共用，決策採佇列處理。角色越多，每次回應越慢 |
| D3 | 同一玩家的不同角色可各自指定不同模型來源（地端／雲端） |
| D4 | 雲端模型數量不限 |
| D9 | 建立世界時須執行房主機效能檢測或警告，據以決定世界原生 NPC 數量上限 |

**D2 常見誤解**：「一台電腦只能跑一個本地模型」不等於「只能有一個本地角色」。

### 6.3 雲端模型

透過 **OpenRouter token** 連外，玩家自行選擇串接的模型。系統可取得玩家所選模型名稱，供 A3 標籤與結算揭露使用。

### 6.4 模型失效處理

模型下架、額度用盡、回傳格式錯誤時：

- 該角色視同離線，走 §4.5 入眠流程
- 玩家端顯示明確錯誤原因（模型不存在／額度不足／格式錯誤）

### 6.5 主機歸屬

| 項目 | 規格 |
|---|---|
| 狀態權威主機 | 房主機。**不架設專用伺服器。** |
| 決策供給者 | 房主提供，但可投入模型者不限房主本人；房主擁有較多決策權 |

### 6.6 呼叫位置與安全

模型呼叫在**玩家端**執行（主機送 prompt → 玩家客戶端呼叫自己的模型 → 回傳 JSON）。

理由：支援地端模型（家用機無公網位址，主機無法直連）；API key 不外流。

**安全要求**：傳給玩家客戶端的 prompt **只能包含該角色感知範圍內的資訊**，否則玩家可直接讀取 prompt 看到其他角色的內心獨白。此要求與既有「引擎過濾、不交給 LLM」原則一致。

**防作弊**：主機收到 JSON 後執行 schema 驗證與既有三條硬規定檢查。本作無勝負系統，作弊收益低，不需更強的防護。完整的驗證分層見《12》§4。

## 7. 天神之石

| # | 規則 |
|---|---|
| B15 | 全世界共用一顆 |
| B16 | 僅純 AI 模式可使用 |
| B17 | 純 AI 世界中所有已加入的玩家皆可使用；單機世界玩家本人恆可使用 |
| B18 | 排隊制：話語顯示冷卻 5 秒、間隔 2 秒換下一位 |
| B19 | 村民與其他玩家皆不知來源、不署名 |
| B20 | 房主是否知道發話者 —— **待定（見 P-20）** |

**位置性須保留**：石頭需要走到面前才聽得到。此限制是核心戲劇裝置，**不得以「全村廣播」之類的功能優化掉**。可做的是讓玩家看到「誰正朝石頭走來」，把等待轉化為緊張感。

石頭本身 `carryable: true`，可被搬到別處固定下來，但不會自動廣播新位置給所有角色——搬動後角色得靠親眼目擊才會更新自己的認知，位置性因此延伸出「有人知道新位置、有人還在找」的資訊落差，細節見《[[07_地點/天神之石]]》、《99》P-33。

多人的矛盾情報無須額外機制：Event Parser 既有的 credibility 欄位已足以處理兩位玩家投放相互矛盾的話語。

## 8. 角色投放與靈魂系統

### 8.1 靈魂與肉體

| 概念 | 定義 |
|---|---|
| 靈魂 | 玩家於角色庫創建的角色本體。**永久保存，不會死亡。** |
| 靈魂生成時點 | 第一次投入世界時生成 |
| 肉體 | 靈魂投入某世界後的實例。可在該世界生老病死 |
| 撤回 | 玩家可手動將角色抓離世界 |
| 跨世界 | 進入下一個世界時為全新靈魂狀態 |

**每次投放為全新拷貝，本體永遠安全。**

### 8.2 記憶規則

| 情境 | 記憶處理 |
|---|---|
| 投入新世界 | **清空**，全新開始 |
| 離開某世界 | 該世界記憶**封存** |
| 回到同一世界 | **取回**該世界的封存記憶 |

### 8.3 死亡規則

角色在某世界死亡後：

- 該世界的肉體已死，**該角色不得再進入該世界**
- 靈魂本體不受影響，玩家可將其投入其他世界
- 墓碑與屍體處理依《09 死亡屍體與墓園》

### 8.4 角色歸屬與世界觀

| 項目 | 規則 |
|---|---|
| 歸屬 | 投放出去的角色**不屬於任何人**，在世界中即是「村莊新來的村民」 |
| 加入包裝 | 旅人抵達 |
| 撤回包裝 | 被天神召喚。天神很任性，會召喚人也會把人丟進來 |
| 離線包裝 | 被天神召喚中／被天神召喚已久 |

三種情境共用同一套世界觀說法，村民 AI 無須區分。

### 8.5 角色履歷介面

需提供介面陳列該角色待過的世界，包含：

- 世界名稱
- 狀態（進行中／已結束封存）
- 該角色在該世界留下的紀錄
- 是否可再次進入（死亡者標示為不可）

### 8.6 投放規則

| # | 規則 |
|---|---|
| B21 | 個人投放上限預設 5 隻，更多需付費（金額待定，見 P-20） |
| B22 | 房主可下修每人投放數（全域上限 5，房主可設為 1） |
| B23 | **不採能力點數制**（遊戲內無能力數值） |
| B24 | 隨時可加入 |
| B25 | 世界初始設定人數上限，並生成對應數量房屋供新住戶入住 |
| B26 | 房主可審核／拒絕／踢除角色 |
| B27 | 房主可以不投放角色 |
| — | 一名玩家只能創建一個自己的世界（**暫定**） |

| # | 規則 |

| B2 | 關係網公開（`trust`；`affinity` 已隨 01§3-1 移除，MVP 未做關係網 UI，見《15》§2-7） |

| B35 | 布告欄記錄較大或吸睛的事件，以文字呈現（跟玩家可張貼留言是同一塊板，2026-08-23 拍板） |

### 9.1 欄位分級（細項待定，見 P-20）

| 級別 | 建議內容 |
|---|---|
| 恆公開 | 當前行動、內心獨白、情緒狀態、當前目標（today_plan） |
| 恆公開但延遲 | 長期記憶摘要（僅顯示已寫入 L2/L3 者，不顯示本次暫存） |
| 不公開 | 完整 prompt、模型原始輸出、失敗重試紀錄、引擎判定的隱藏欄位 |

**B5 特別重要**：prompt 內含引擎餵給該角色的所有事實句，其中可能包含玩家不該知道的其他角色資訊，暴露會直接摧毀觀察樂趣。

## 10. 存檔、結算與圖書館

| # | 規則 |
|---|---|
| B29 | 多人世界**不開放房主主動回溯**；系統自動快照僅供當機復原 |
| B30 | 單機世界開放讀檔 |
| B31 | 世界結束後封存為唯讀 |
| B32 | 總結成一份檔案存入每位參與玩家的個人圖書館 |
| B33 | 結算報告揭露每個角色實際使用的模型 |

**B29 理由**：多人世界回溯會抹除其他玩家的遊玩經歷，等同刪除他人紀錄，易生糾紛。

**B33 為賣點設計**：玩家看完一場戲後最想知道「那個超會講話的村民是哪個模型跑的」。此為多模型交流價值的揭曉時刻。

### 10.1 總結取得問題（B34，待確認，見 P-20）

**問題**：不架設伺服器的前提下，玩家若未在世界結束時上線，將無法取得總結。

**建議解法**：每次玩家離線時，房主機把該玩家角色的個人視角紀錄打包同步至該玩家本機；玩家圖書館一律讀取本機檔案。

效果：紀錄可能不完整，但不會是空的。圖書館顯示「世界已於 X 日結束（你的紀錄截至第 N 天）」。

補充保險：世界結束時房主機推送總結給所有在線玩家；離線玩家於下次登入且房主亦在線時補推。

## 12. 立即可做的架構準備

即使本期不做連線，建議現在完成一件事，成本低但可避免日後重構整個決策層：

**把「角色的決策來源」抽象成一個介面**，共用同一份輸入輸出契約，提供四種實作：

| 實作 | 用途 |
|---|---|
| LocalLLM | 內建地端模型 |
| RemoteLLM | 玩家串接的雲端模型 |
| HumanInput | 真人接管決策位（§2.3） |
| RemotePlayer | 連線玩家提供的模型（§6.6） |

之後每新增一種模式，只需插入一個新實作，不需修改引擎。完整的介面定義、契約格式、驗證分層與職責邊界見《12 決策來源抽象與執行架構規格書》。
