# 14_存檔資料存取層規格書

# 14｜存檔資料存取層規格書

本文件補充《00 設計原則與架構》§3「資料儲存」，定義角色／世界資料的存取抽象層，讓儲存後端（JSON／SQLite）可以獨立於遊戲邏輯決定與替換。跟《12 決策來源抽象與執行架構規格書》是同一種手法——把「誰在背後做事」抽成介面，呼叫端不需要知道背後是誰。

**適用對象**：遊戲邏輯組、後端組、負責存檔實作的組員。
**本期是否實作**：`SaveService` 介面與 JSON 實作建議本期完成；SQLite 實作由組員平行開發，是否採用待 §3 驗證關卡結果決定。

---

## 1. 背景與動機

專案 5 天後要發表，角色／世界的存讀檔系統目前完全空白——`Ailley/scripts/` 沒有任何存讀檔實作，只有兩個靜態設定檔（`ai_config.json`、`npc_schedule.json`）用 `FileAccess` 讀取。

儲存後端本身還沒定案：

- 已有評估：單機、5 人村莊規模用不到 SQLite 的索引／查詢優勢，《00》§3、《技術/存檔》原本傾向純 JSON
- 但專案未來確定要撐 20+ 角色的規模，屆時查詢/索引優勢會變得需要；組員已經手刻一份 schema，且已跟《06 資料欄位對應表》對齊
- SQLite 版本目前**未經驗證**：GDExtension 是否跟目前 Godot 版本相容、匯出成執行檔後原生函式庫是否正常運作，都還沒有實測證據；完成時間也不確定，可能超過原先預估

在後端未定案、時程又緊的情況下，讓遊戲邏輯直接綁定某一種後端是最大的風險——不管最後選哪邊，中途要換都要動到所有呼叫端。**解法是抽一層介面，遊戲邏輯只認介面，後端可以後補、可以替換。**

## 2. 介面設計：`SaveService`

### 2.1 介面定義

```gdscript
class_name SaveService

## 讀一個角色的完整資料，找不到回傳空 Dictionary
func get_character(id: String) -> Dictionary:
    push_error("SaveService: get_character 未實作")
    return {}

## 寫入一個角色的完整資料（整包覆蓋，不做局部欄位更新）
func save_character(id: String, data: Dictionary) -> bool:
    push_error("SaveService: save_character 未實作")
    return false

## 讀一個世界的完整資料
func get_world(id: String) -> Dictionary:
    push_error("SaveService: get_world 未實作")
    return {}

## 寫入一個世界的完整資料
func save_world(id: String, data: Dictionary) -> bool:
    push_error("SaveService: save_world 未實作")
    return false
```

呼叫端（角色生成、睡眠反思寫回、debug console 等）一律只呼叫這四個函式，**不直接使用 `FileAccess` 或任何資料庫 API**。這條界線比照《12》§5.3「驗證不得寫在 Godot 操控層」的精神——存取邏輯只能在 `SaveService` 的實作裡。

介面已落地為 `Ailley/scripts/save/save_service.gd`，上面的程式碼是說明用，實際簽章以該檔案為準。

### 2.2 粒度：整包讀寫，不是局部欄位

跟《06》全欄位對應表、《00》§4 的 L0~L3 分層一致：一次讀寫一個角色或一個世界的完整資料，不支援「只改一個欄位」這種局部更新。理由：

- MVP 規模（5～10 人）下整包讀寫沒有效能問題
- 局部更新是關聯式資料庫才有優勢的操作；現在就設計局部更新介面等於預先假設 SQLite 會是最終後端，違背「後端未定案」的前提
- 之後真的需要局部更新，是介面要擴充的問題，不影響呼叫端已寫好的整包呼叫（可以先用整包讀、改欄位、整包寫回頂著用）

### 2.3 兩個實作

```
SaveService（基底，定義介面）
    ├── JsonSaveService     每個角色／世界各自一個 JSON 檔
    └── SqliteSaveService   組員實作，內部走 SQLite
```

遊戲啟動時決定要用哪個實作、指派給全域的 `SaveService` 參照，呼叫端不需要知道也不需要判斷目前是哪一個。

## 3. 兩種後端對照

| 面向 | JSON（`JsonSaveService`） | SQLite（`SqliteSaveService`） |
| --- | --- | --- |
| 依賴 | Godot 內建 `FileAccess`／`JSON`，無外部依賴 | `godot-sqlite`（GDExtension，原生函式庫） |
| 匯出風險 | 無——內建 API 隨引擎一起打包 | **有**——需確認 export_presets 有把對應平台的 `.dll`／`.so` 一起包進去，這是最容易在發表前一天才炸掉的坑 |
| 版本相容性 | 無風險 | GDExtension 綁定特定 Godot 版本，需先驗證能否載入 |
| 序列化模式 | 走訪資料結構直接寫檔（跟 `Stats.SPEC`／`Relationships.records` 同一套模式） | 需要 schema，組員已建好。schema 骨架原始設計對齊《06》完整版欄位表，但實際驗證（見下）改核對「目前程式碼實際輸出的形狀」，兩者不是同一件事，見 §4 |
| Atomic write | 引擎不內建，要自己刻（先寫暫存檔，`DirAccess.rename()` 換名） | SQLite 本身有 transaction，天生具備 |
| 除錯 | 純文字檔，可直接開檔案看、可 `git diff` | 二進位格式，需另裝 DB Browser for SQLite 之類工具 |
| 10 人規模效能 | 沒有問題 | 沒有問題，也沒有優勢 |
| 20+ 人規模查詢（例如名聲排行） | 要自己刻迴圈全讀出來找 | 原生支援，SQL 語法糖 |
| 目前驗證狀態 | 未開始寫，但技術上無不確定性 | 四關驗證前三關已過（併入 repo／連線讀寫／schema 核對，見 §4），**第 4 關匯出後行為尚未測試** |

## 4. 決策與分工

**MVP（3 天內發表，10 人規模）**：`SaveService` 介面已定案並落地（`Ailley/scripts/save/save_service.gd`），主力開發者這 3 天只做 `JsonSaveService` 實作，接上 #21／#22／#23，不等 SQLite。這條路徑技術風險趨近於零，唯一成本是工時。

**SQLite 平行開發，非阻塞**：組員用自己的空閒時間實作 `SqliteSaveService`，不佔用發表衝刺的時程、不需要主力開發者為它調整進度。驗收標準是下列四關（建議一天為停損線），現況：

1. **已過**——把外掛併入 `Ailley/` repo，確認能載入、跟目前 Godot 版本相容。PR [#129](https://github.com/adez360/Ailley/pull/129)（`fix/pr127-review` → `main`，2026-08-15 merge，commit `18c5296`）：`Ailley/` 底下實際跑起來，log 顯示 `Godot Engine v4.5.1.stable.official.f62fdbde1`，25 個 schema 建表成功、無 script error／DB error
2. **已過**——連線、寫入一筆假資料、讀回來。PR [#289](https://github.com/adez360/Ailley/pull/289)（`feat/fill-sqlite-save-service-crud` → `main`，2026-08-18T08:03 merge，commit `826c66d`）：編輯器 Play 模式下用 `game_eval` 對 `get_character`/`save_character`、`get_world`/`save_world` 做新建、update 覆蓋、關係讀回、transaction rollback 測試，全數通過
3. **已過（範圍有調整）**——schema 逐欄位核對《06》欄位表。實作時發現骨架 TODO 原定對齊《06》完整版（identity/hexaco/personality/economy/state.emotion/memory），但這些欄位目前沒有任何呼叫端會產生資料，跟 `Character.get_save_data()`／`GameManager.get_world_save_data()` 實際吐出的形狀對不上；PR #289 改成**核對「目前程式碼實際輸出的形狀」**，經 wendy 確認採用此範圍。已知 schema 缺口（`npc_state` 缺 `mood`／`social`／`fun`，`npc_relations` 缺 `met_count`）記在 `sqlite_save_service.gd` 檔尾與 `note/技術/存檔.md`，round-trip 時用預設值頂著，不算靜默漏資料
4. **尚未驗證**——完整匯出成執行檔，重新測一次連線讀寫（**編輯器內測試不算數**，這是全部風險中最關鍵的一項）。查無任何 commit／PR／log 記錄實際測過；repo 裡目前沒有 `export_presets.cfg`，本機也沒有安裝 Godot 匯出範本，這一關的基礎建設要等《16 打包與發布規格書》（PR #294，尚未合併）落地後才能真正執行，見《99》P-26

發表前四關全過 → 切換到 `SqliteSaveService`；沒做完或任何一關卡住 → 發表沿用 `JsonSaveService`，不影響交付。**兩種結果都不會拖垮 demo**，因為呼叫端從頭到尾只認介面。目前第 4 關尚未驗證，發表沿用 `JsonSaveService`。

**發表後**：20+ 角色的規模需求、要不要正式導入 SQLite、`SaveService` 是否要擴充支援局部更新／查詢，是獨立的後續評估，不卡這次發表。

### 4.1 可維護性與接線可行性：已對照專案實況覆核

對照 `note/` 全部相關文件與 `Ailley/scripts/`、`Ailley/addons/`、`project.godot` 的實際內容驗證過：

- **可維護性判斷成立**：Repository/DAO 模式對應「後端未定案、組員時程不確定」這個具體情境，不是過度設計；跟《12 決策來源抽象與執行架構規格書》的 `DecisionProvider` 是同一種手法，專案裡已經用過一次；直接避開《技術/行程佇列與任務仲裁》點名過的反例「不要保留兩套資料再合併」
- **全域接線可行**：`project.godot` 的 `[autoload]` 已有 `GameManager`／`GameClock`／`AIService` 三個先例，`SaveService` 比照同樣方式掛，不需要新設計
- **工作量釐清**：`SaveService` 介面本身（4 個 stub 函式的 base class）成本趨近於零；真正的工時在 `JsonSaveService` 背後要接的資料模型（`Character`／`Stats.SPEC`／`Relationships.records`／L2+L4 記憶），對應《技術/存檔》#21／#22／#23——這塊不論是否採用 `SaveService` 都要做，工作量不會因為多這層介面而變多或變少
- **唯一剩餘卡點**：§4 的 SQLite 四關驗證結果尚未跑完，是本文件目前唯一未解決的不確定性

## 5. 風險說明

- **這層介面不會降低 SQLite 整合本身的技術不確定性。** GDExtension 版本相容性、匯出後原生函式庫能否正常運作，仍然只有實際測試才能確認，不會因為多一層介面就自動變得比較可能成功。
- **介面真正防住的是後果，不是風險本身。** 如果 SQLite 驗證失敗，因為呼叫端沒有直接綁定 SQLite，直接維持 `JsonSaveService` 照樣能上場——介面把「SQLite 會不會成功」從「一票否決全專案」降級成「不影響 demo，只影響能不能用到 SQLite 這個加分項」。
- **GDScript 沒有強制介面機制**，靠命名慣例與 base class 維持紀律，需要 code review 擋住任何呼叫端繞過 `SaveService` 直接操作檔案或資料庫（`ai_config.gd` 已有直接使用 `FileAccess` 的先例，是既有的個案，不是這層要處理的範圍，但新程式碼不應再增加這種例外）。
- **兩個實作的資料形狀必須對齊**——欄位缺值怎麼處理、ID 怎麼給，兩邊沒對齊，切換後端時一樣要重新調整。這塊已因 schema 對齊《06》而部分處理，但仍需在整合時實際核對。

## 6. 對其他規格書的影響

- 《00》§3「資料儲存」目前寫「JSON」，待本文件與驗證結果定案後，改為「經 `SaveService` 介面存取，MVP 實作為 JSON，SQLite 為候選後端，見《14》」
- 《06 資料欄位對應表》不受影響——介面讀寫的仍是同一組欄位，欄位定義的權威來源不變
- 《技術/存檔》後續補上 `SaveService`／`JsonSaveService` 的實作細節時，需與本文件的介面定義保持一致
