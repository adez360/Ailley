## 死亡與昏迷的關係（2026-08-20 拍板，見 issue #368）

昏迷不再是「取代」死亡的 MVP 簡化，而是死亡流程的**前置狀態**：`health ≤ 0` 一律先觸發
昏迷，不會直接死亡。昏迷時長不再是固定 30 分鐘，改成依傷勢嚴重程度計算（面板顯示倒數
計時，具體公式待實作 issue 訂）；逾時仍未獲救治，才轉入本文件描述的真正死亡流程。純觀察
模式下，天神可以主動介入：點按昏迷中角色，可直接觸發送醫（等同原本「自動送藥草鋪治療」
的路徑），不必等倒數結束。

餓死／渴死／老化與瞬間死亡（Flag 觸發）不經過昏迷，直接進入死亡流程——這兩類死因本來就
不是「health 歸零」，昏迷這個前置狀態對它們沒有意義。

實作細節（昏迷倒數公式、送醫介入的 UI／操作）留給後續實作 issue，本節只拍板兩套機制的
關係。逾時未獲救治現在會轉入本文件描述的死亡流程（issue #379 已落地，見文首「實作
現況」），取代原本 MVP-1 的「固定 30 分鐘＋自動送醫」；固定 30 分鐘門檻改成依傷勢動態
計算、天神主動介入送醫兩者都還沒實作。

本文件涵蓋單一世界內的死亡流程。跨世界層面的規則（角色死亡後不得再進入該世界、靈魂本體不受影響可投入其他世界）見《10 模式連線與世界設定規格書》§8.3。

## 1. 死亡流程

```
                ┌──────────────────┐
                │  死亡條件成立     │  昏迷逾時未獲救治
                └────────┬─────────┘  或餓死／渴死／老化／瞬間死亡 Flag
                         ▼
            ┌────────────────────────┐
            │ ① 記錄 last_words       │  臨終遺言，可為 null
            │ ② 記錄 death_cause      │  死亡原因
            │ ③ conditions 清空       │
            │    只留 petrified       │
            └────────────┬───────────┘
                         ▼
            ┌────────────────────────┐
            │   石化・停留原地        │
            │   本體變成灰色          │
            │   屍體開始 decay        │
            └────────────┬───────────┘
                         │
        ┌────────────────┴────────────────┐
        │ 他人偵測到                       │ decay 達 100
        ▼                                  ▼
┌────────────────────┐          ┌────────────────────┐
│  AI 自行決定是否搬運 │          │  自動立「無名碑」   │
│  （不強制）          │          │  確保死亡必被記錄   │
└─────────┬──────────┘          └────────────────────┘
          │ 決定搬運
          ▼
┌────────────────────┐
│  搬運至墓園         │  loc_cemetery
│  loc_cemetery       │
└─────────┬──────────┘
          ▼
┌────────────────────┐
│      已安葬         │
│  墓碑面板完整開放    │
└────────────────────┘
```

### 死亡觸發頻率

日常觀察模式下，死亡觸發為**溫和／低頻**（意外、老化為主），避免博弈感過重影響調性。

### 1-1 真人角色（Player）跟 AI 角色共用同一套死亡流程

（2026-08-20 拍板，見 issue #368）真人角色（Player，即化身者親自操控的角色，見《10》§2.1）
死亡時，本節以下 §2~§8 描述的死亡、屍體、墓碑、復活規則**全部比照 AI 角色（Agent）辦理**，
不再做特殊處理：一樣石化原地、留下屍體、可被安葬立墓碑、復活走同一套 24 小時免費窗口＋
超時付費（見 §8）、死亡地點原地重生。

**唯一還保留的不對稱**：真人玩家死亡後**不會**被禁止再進入該世界——AI 角色「死亡後不得再
進入該世界」（見《10》§8.3）不適用於真人玩家。理由不變：AI 角色的死亡要有重量，但真人玩家
的死亡不該變成永久拒絕遊玩。

## 2. 死亡相關欄位

```json
{
  "is_dead": true,
  "death_tick": 8642,
  "death_day": 60,
  "death_at": "2026-08-20T19:04:33Z",
  "death_cause": "在森林被大型獵物所傷，失血過多",
  "death_location_id": "loc_forest",
  "last_words": "早知道就不該一個人去。",
  "corpse_decay": 34,
  "is_buried": false,
  "grave_id": null
}
```

以上欄位是 `Character.get_save_data()` 存檔頂層的其中一段（跟其他非死亡欄位平鋪同一層，
不是巢狀在 `death` 物件底下），這裡只是為了方便閱讀而挑出來列。

| 欄位 | 型別 | 誰寫 | 說明 |
| --- | --- | --- | --- |
| `is_dead` | bool | 引擎 |  |
| `death_tick` | int | **引擎** | 遊戲內 tick（死亡當下的 GameClock tick） |
| `death_day` | int | **引擎** | 遊戲內天數 |
| `death_at` | timestamp | **引擎** | UTC 時間戳（ISO 8601），2026-08-20 拍板新增（見 issue #451 CodeRabbit review）——`death_tick`／`death_day` 是遊戲內時間，世界關閉、暫停、或調整時間流速（《99》P-25）都會讓「遊戲內經過多久」跟「現實經過多久」對不上，§8 的 24 小時免費復活窗口必須用這個真實時間戳判斷，不能靠遊戲內 tick 換算 |
| `death_cause` | string | **引擎** | 中文自然語言，由引擎彙整，**不讓 LLM 潤飾** |
| `death_location_id` | string | **引擎** | 死亡地點，見《07》 |
| `last_words` | string\|null | **LLM** | 臨終遺言，可為 null（來不及說） |
| `corpse_decay` | float | 引擎 | 0–100，每 tick +0.7（見 §3-4），達 100 自動立無名碑；存檔型別用 REAL，INTEGER 會把小數進度捨掉 |
| `is_buried` | bool | 引擎 | 是否已安葬 |
| `grave_id` | string\|null | 引擎 | 墓碑 ID，尚未安葬時為 null |

### `last_words` 產生規則（2026-08-20 拍板，見 issue #368）

| 死因 | 是否有機會留遺言 |
| --- | --- |
| 餓死／渴死／老化 | ✔ 有，死亡前一 tick 詢問 AI |
| 昏迷逾時未獲救治（轉死亡） | ✔ 有，轉死亡當下詢問 AI |
| 瞬間死亡（Flag 關鍵字觸發） | ✔ 有，但性質不同——來不及開口說，是「心裡想著、沒能說出口的話」，墓碑上仍會顯示，但呈現語氣要跟其他死因的口白式遺言區分（不用引號對白格式），具體文案由實作時定稿 |

## 3. 屍體處理

### 3-1 石化本體

- 死亡後角色本體**停留原地變成灰色**，不消失
- 其他角色移動經過時可偵測到
- **屍體佔用該地點的容量**（2026-08-20 拍板，見 issue #368）：跟活人一樣算進地點
  `capacity`，符合現實——沒人搬走的屍體會實際擠佔空間，可能導致該地點顯得擁擠或滿員

### 3-2 搬運

| 項目 | 規格 |
| --- | --- |
| 誰能搬 | 任何偵測到屍體的角色 |
| 是否強制 | **否**。由 AI 自行決定要不要搬 |
| 所需人數 | 單人即可搬運 |
| 同時搬運人數上限 | 2 人。單人已足夠，上限只是避免多名角色同時選取同一具屍體為搬運目標，無速度或成功率加成 |
| 搬運目的地 | `loc_cemetery` 墓園 |
| 搬運耗時 | 【待填】 |
| 搬運時可否被中斷 | ✔ 可以（2026-08-20 拍板，見 issue #368）：跟現有 `haul` 動作一樣，可被更高優先度事件打斷，屍體留在半路原地 |

> 💡 「有人死在路邊，村民各自決定要不要理他」本身就是高觀察價值的橋段。**絕對不要做成自動搬運。**

### 3-3 容量在搬運各階段怎麼轉移（2026-08-20 拍板，見 issue #451 CodeRabbit review）

屍體牽涉兩種不同的容量，不要混在一起算：**一般地點 `capacity`**（《07》§1-1「同時容納人數上限」，活人與未安葬屍體共用）跟**墓園墓碑格數**（本文件 §6 的「容量 6」，只有安葬完成、變成墓碑後才佔用）。

| 階段 | 一般地點 `capacity` | 墓碑格數（§6） |
| --- | --- | --- |
| 死亡、尚未被搬 | 佔用死亡地點 1 格 | 不佔用 |
| 搬運中（`haul` 進行中） | **不佔用任何地點**——屍體跟著搬運者移動，不是靜態佔用某個地點的一格 | 不佔用 |
| 搬運被中斷、屍體留在半路 | 若中斷地點落在某個有 `location_id` 的地點範圍內，重新佔用該地點 1 格；若落在地點之間的移動路徑上（沒有 `location_id`），不涉及容量機制——那種地方本來就沒有容量概念 | 不佔用 |
| 抵達墓園、尚未安葬 | 佔用墓園（`loc_cemetery`）1 格一般 `capacity` | 不佔用 |
| 安葬完成（`bury` 執行） | **釋放**——屍體不再是佔位的物理實體 | 佔用墓碑格數 1 格 |

這樣中斷搬運不會有容量重複計算或憑空消失的問題：屍體在任一時刻最多只計入「一般地點 capacity」或「墓碑格數」其中一項，搬運途中兩者都不計。

### 3-4 屍體腐壞

```text
每 tick：corpse_decay = clampf(corpse_decay + 0.7, 0, 100)（2026-08-20 拍板，
見 issue #368；100 / 0.7 除不盡，寫入前一定要 clamp，不然某個 tick 算出
100.1 會撞資料庫 CHECK(BETWEEN 0 AND 100) 寫入失敗，見 issue #451 CodeRabbit
review）

corpse_decay >= 100 且 is_buried = false 且 grave_id 仍是 null（避免每個
超過 100 之後的 tick 都重複建立 grave）
        ↓
自動立「無名碑」
```

**無名碑**的意義：墓園未滿格時（滿格行為見 §6），確保**每一個死亡都會被記錄**，即使沒有人願意搬他。無名碑上不顯示遺言與生平，只有一行「無人知曉他是誰」與死亡日期——但這是**顯示規則**，不是資料規則：自動立碑時，`name`／`last_words`／`life_highlights` 照樣從 `npc_death` 與角色紀錄整份寫進 `grave`（§4-1），只是 `is_anonymous` 設成 `true` 讓面板不顯示。資料從沒被清空過，見 §4-4「擦拭墓碑」。

## 4. 墓碑

### 4-1 結構

```json
{
  "grave_id": "grave_007",
  "npc_id": "npc_017",
  "name": "TAMMY",
  "is_anonymous": false,
  "buried_tick": 8698,
  "buried_by": "npc_003",
  "death_cause": "在森林被大型獵物所傷，失血過多",
  "last_words": "早知道就不該一個人去。",
  "words_to_creator": "你把我設計成連話都懶得講，那你現在是想聽什麼？",
  "life_highlights": [
    "第 12 天，第一次採到藥草",
    "第 29 天，和 NEON 在廣場起了衝突",
    "第 41 天，救了溺水的 CHO"
  ]
}
```

### 4-2 三個內容欄位

| 欄位 | 來源 | 規則 |
| --- | --- | --- |
| `last_words` | **死者的 LLM** | 臨終遺言，可為 null |
| `words_to_creator` | **死者的 LLM**（建角時生成） | 對造物主的一句吐槽，見《01》§1-4 |
| `life_highlights` | **引擎彙整** | 由 L4 核心記憶與重大事件流產出，**絕不讓 LLM 潤飾** |

> ⚠️ `life_highlights` 由引擎彙整是刻意的設計。讓 LLM 潤飾會產生美化過的假履歷，失去「這是真的發生過的事」的重量。

### 4-3 顯示規則

| 狀態 | 墓碑面板顯示 |
| --- | --- |
| **未安葬** | **不顯示** `last_words` 與 `life_highlights`。只有死亡原因與日期 |
| 已安葬 | 全部顯示 |
| 無名碑 | 只有「無人知曉他是誰」與死亡日期 |

> 未安葬時不顯示遺言與生平——這給了「搬運」這個行為實質的意義：**沒有人願意搬他，他的一生就沒有人知道。**

### 4-4 擦拭墓碑（2026-08-21 拍板）

| 項目 | 規格 |
| --- | --- |
| 誰能做 | 任何抵達墓園的角色，不限跟死者的關係 |
| 次數限制 | 無 |
| 效果 | 把該墓碑的 `is_anonymous` 設回 `false`。`name`／`last_words`／`life_highlights` 這幾個欄位在無名碑立碑當下就已經整份寫進去了（見 §3-4），擦拭不是「找回」資料，只是讓面板重新顯示已經在那裡的資料 |
| 適用對象 | 只對 `is_anonymous == true` 的墓碑有意義；已具名的墓碑本來就全部顯示，擦拭沒有額外效果 |

## 5. 死亡對其他角色的影響　【推測待確認】

| 事件 | 效果 |
| --- | --- |
| 目擊死亡 | 中斷當前行動；該事件 `importance` 通常會被 AI 評高分，進 L4 |
| 發現屍體 | 引擎送出事件，**不指定情緒**，AI 自行反應 |
| 死者是關係密切者 | 引擎不做特別處理——關係數值已在 prompt 裡，AI 自己知道 |
| 全村死亡 | 世界結束，進入完結總結（文字呈現） |

**發現屍體時得知的資訊**：符合《10》§5.3「角色必須實際接觸環境後才會知道環境變化」原則——AI 角色的屍體帶有死亡標籤，**只有實際靠近／偵測到的角色**才會收到：死亡狀態、身分（是誰）、外觀。不會有任何角色在沒接觸過的情況下就知道「某人已經死了」。

> 依《00》原則二，引擎只送出「你看到 TAMMY 倒在森林裡，他已經死了。」這樣的事實句，不送任何情緒或關係變動。悲傷、冷漠、還是鬆一口氣，由 AI 自己決定。

## 6. 墓園地點

| 項目 | 規格 |
| --- | --- |
| `location_id` | `loc_cemetery` |
| 可執行行動 | 通用行動（見《07》§5：`move`／`idle`／`talk`）＋ `bury`（安葬）／`wipe`（擦拭墓碑，見 §4-4） |
| 墓碑格數 | **6**（2026-08-20 拍板，見 issue #368）。**這不是《07》§1-1 的一般「同時容納人數」capacity**——安葬前的屍體算一般 capacity，安葬後變成墓碑才算這裡的墓碑格數，兩者不疊加，見 §3-3 |
| 滿格時的處理（Phase 2，2026-08-21 拍板） | **拒絕**——`bury` 與 §3-4 的自動立無名碑都直接失敗，屍體／狀態留在原地繼續佔一般 capacity，直到有格子空出來。已知限制：目前設計上唯一會釋放墓碑格的機制是復活（§8：已下葬者復活時墓園佔用格數全部釋放，見《99》P-24 #3），而復活需由玩家對屍體選單觸發才會發生，長期無人復活仍可能滿格；Phase 3 的動態擴張＋合併方案上線後才真正解決，方向已拍板但不在這次範圍內，見《99》P-57 |
| 玩家互動 | 點擊墓碑查看完整內容 |

## 8. 復活機制

**AI 角色與真人角色共用同一套規則**（2026-08-20 拍板，見 issue #368；§1-1 已取消原本的
不對稱設計）。

| 項目 | 規格 |
| --- | --- |
| 免費復活窗口 | 死亡後 **24 現實小時內**，該角色的擁有玩家可免費復活——判斷依據是 §2 新增的 `death_at`（真實 UTC 時間戳），不是 `death_tick`／`death_day`（2026-08-20 拍板，見 issue #451 CodeRabbit review）：世界關閉、暫停、或調整時間流速都不影響這個判斷，`now_utc - death_at ≤ 24h` 即可 |
| 超過窗口 | 復活需付費，**由該角色的擁有玩家自己支付**，固定金額（不隨時間遞增、不隨角色地位浮動）：未下葬 **50**、已下葬 **100**（2026-08-27 拍板暫定值，見《08》§5 money 預設 300 與物品售價區間定的低風險佔位數字，待經濟數值實測後可調整，調整不影響機制本身） |
| 復活後的自覺 | 角色會知道自己是被天神復活的；此事實會傳給 AI（比照《01-3》§3 事實句機制，作為一行注入文字，例如「你剛剛死而復生，你知道是天神把你救回來的。」） |
| 已下葬（`is_buried = true`）者可否復活 | **復活資格與流程相同，不分別處理**（2026-08-20 拍板）——僅超過免費窗口後付費時，依 `is_buried` 選擇一般或較高固定費用，兩者是**互斥的二選一**，不是疊加。Phase 3 方向（2026-08-22 拍板，見《99》P-24 #2）：不新增「掘墓」動作——現有復活本來就是擁有玩家在復活流程裡直接付費的既有模式，不是角色在遊戲世界裡執行的動作，`is_buried = true` 時改收另一個更高的固定金額即可 |
| 復活後角色的重生位置 | **死亡地點原地重生**（2026-08-20 拍板，跟 §1-1 真人重生位置同一題、同一個答案，AI／真人不分） |
| 復活後屍體／墓碑如何處理 | **2026-08-27 拍板**：`is_buried = false`（下葬前）——移除石化節點，角色就地重新變回可操作狀態，`death` 相關欄位全部清空。`is_buried = true`（已下葬）——墓碑節點、墓園佔用格數全部釋放，墓地格供其他角色安葬使用，不保留任何歷史紀錄（墓碑欄位依 2026-08-28 拍板不含 epitaphs，見 #652） |
