# 01-3｜Prompt 注入與資料傳送

**閱讀對象**：AI 組・後端組
**文件性質**：決定「每次呼叫 LLM 要餵什麼進去」的規格。
**前置閱讀**：《00 設計原則與架構》原則二、原則三

---

## 1. 注入分級

| 級別 | 內容 | 頻率 | 估計 token |
| --- | --- | --- | --- |
| **System**（固定） | 行為準則 2~4 條 ＋ `character` ＋ 外觀文字 | 建角後不變，可命中 KV 快取 | ~250 |
| **Tier 0**（常駐） | 生理 8（附形容詞）＋ `emotion` ＋ `conditions` ＋ `current_goal` ＋ `today_plan` ＋ `last_action_result` ＋ 事實句 | 每 tick | ~300 |
| **Tier 1**（情境） | 在場角色的 4 維關係、在場物品、可用行動清單 | 依情境 | ~350 |
| **Tier 2**（按需） | 完整庫存、指定對象完整關係、記憶檢索、地點細節 | AI 要求才給 | ~300 |
| **不注入** | `personality` 10 項、`hexaco_input` 6 項、`words_to_creator` | — | 0 |

> `words_to_creator` 平時不注入。它是角色對「自己被設定成這樣」的一句吐槽，角色本人不會反覆想起它。
**唯一例外**：玩家用天神之石對它說話且觸發擲骰成功時，該次 prompt 會額外注入一行「你突然很想說出這句話：『…』」，由 AI 自行決定要不要真的說出口。詳見《01》§1-4。
> 

## 2. 既有注入原則

| # | 原則 |
| --- | --- |
| 1 | **固定筆數的資料全給**（生理 8、L1 記憶 8 條、L4 核心記憶） |
| 2 | **不定筆數的才過濾**（`conditions` / L2、L3 記憶 / 在場人物 / 事件 / 可用行動） |
| 3 | 過濾一律由**引擎**判斷，不交給 LLM |
| 4 | **狀態不可靜默省略**。若省略，必須加兜底句 |

### 兜底句範例

| 省略了什麼 | 兜底句 |
| --- | --- |
| `conditions` 為空 | 你身上沒有值得一提的異常。 |
| 在場無人 | 這附近沒有其他人。 |
| 記憶檢索無結果 | 你想不起相關的事。 |

## 3. 事實句

引擎在組 prompt 時依條件產生**陳述句**，不設欄位、不指定情緒。這是取代 `stress` / `loneliness` / `satisfaction` 的機制。

| 觸發條件 | 注入文字 |
| --- | --- |
| 距上次社交 ≥ 18 tick（3 小時） | 你已經三個小時沒和任何人說過話了。 |
| 距上次社交 ≥ 36 tick（6 小時） | 你已經半天沒和任何人說過話了。 |
| 距上次社交 ≥ 144 tick（1 天） | 你整整一天沒有和任何人說過話。 |
| `current_goal` 連續 36 tick 未達成 | 你想做的那件事已經拖了很久還沒完成。 |
| 該地點首次造訪 | 你以前沒有來過這裡。 |
| 連續 3 次同一行為失敗 | 這件事你已經連續搞砸三次了。 |

### 撰寫規則

| ❌ 不要 | ✅ 要 |
| --- | --- |
| 「距離上次社交：36 tick」 | 「你已經半天沒和任何人說過話了。」 |
| 「你覺得很孤單」 | （不寫感受，只寫事實） |
| 「孤獨度 72」 | （不寫數值化的感受） |

> 本地小模型對過於中性的平述句反應偏弱。事實句要口語化、有畫面，但**絕不能替角色下結論**。
> 

### 資料來源（不新增任何 NPC 欄位）

| 事實句 | 來源 |
| --- | --- |
| 多久沒說話 | `last_social_tick`（引擎全域狀態） |
| 目標拖延 | `goal_set_tick`（引擎全域狀態） |
| 首次造訪 | 該角色的地點造訪紀錄 |
| 連續失敗 | `last_action_result` 歷史 |

## 4. 分層傳送機制　【待決策】

**問題**：每 tick 全量注入約 1,100~1,300 token。5 村民 × 144 tick／日 ≈ 80 萬 token／遊戲日。本地模型 context 16000 單次沒問題，但**速度與 AI 注意力聚焦度**是真正的成本。

### 4-1 三個方案

|  | **A：固定全量** | **B：情境預測式** | **C：兩段式按需** |
| --- | --- | --- | --- |
| 誰決定給什麼 | 不決定，全給 | **引擎**依地點與上一動作決定 | **AI** 自己要求 |
| 呼叫次數 | 1 次 | 1 次 | 1~2 次 |
| token 降幅 | — | 約 40~60% | 約 50~70% |
| tick 延遲 | 基準 | 不變 | 最壞情況翻倍 |
| 需改 GBNF | 否 | 否 | **是**（新增 `request_info`） |
| 需改 DES 時序 | 否 | 否 | **是** |
| 實作成本 | 無 | 中（維護對照表） | 高 |
| 風險 | AI 注意力分散 | 引擎誤判導致缺資料 | 小模型濫用或不會用 |

### 4-2 方案 B 運作方式

```
當前情境 ──► 查對照表 ──► 決定 Tier 1 內容

┌──────────────────┬────────────────────────────────┐
│ 情境              │ 帶入的 Tier 1 資料              │
├──────────────────┼────────────────────────────────┤
│ 在商店 / 交易中   │ 金錢、完整庫存、商品清單         │
│ 有他人在場        │ 在場者 4 維關係、可社交行動      │
│ 在森林 / 獨處     │ 地點資源、可工作行動（不帶關係） │
│ 剛被攻擊 / 目擊   │ 對象關係、可用防禦行動           │
│ 睡醒第一個 tick   │ today_plan 模板、昨日摘要        │
└──────────────────┴────────────────────────────────┘

缺資料時 ──► 加兜底句（符合 §2 原則 4）
```

### 4-3 方案 C 運作方式

```
Pass 1：Tier 0 + Tier 1 + 一個 request_info 欄位
   │
   ├─ AI 回傳 request_info: []            ──► 直接進判定
   │
   └─ AI 回傳 request_info:
        ["inventory", "relation:npc_003"]  ──► 引擎補 Tier 2
                                           ──► Pass 2（上限 1 次）
                                           ──► 進判定
```

### 4-4 建議

**採 B 為主線，C 列入迭代二。**

理由與死線直接相關：B 是純引擎邏輯，不動 LLM 介面，對照表可漸進調整、隨時回退全量；C 需要改 GBNF grammar 與呼叫流程，且會影響 DES 佇列時序，在 8/21 前導入風險偏高。

決策追蹤於《99》P-03。

## 5. 不需決策、建議直接做的優化

`system_prompt` 段固定不變 → 在 llama-server（`--parallel 5`）下每個 slot 各自的 KV cache 可直接命中。

**條件**：system 段永遠排在 prompt 最前面且**逐字元一致**（含空白與換行）。

這一項純收益、沒有取捨，建議直接列入實作。

### 組裝順序（固定不可調換）

```
┌─────────────────────────────────┐
│ ① System 段（永不變，可快取）    │  行為準則 + character + 外觀
├─────────────────────────────────┤
│ ② Tier 0（每 tick 變）           │  生理 + 情緒 + 目標 + 上次結果 + 事實句
├─────────────────────────────────┤
│ ③ Tier 1（依情境）               │  在場關係 + 可用行動
├─────────────────────────────────┤
│ ④ 輸出格式指示                   │  GBNF 已約束，此段可精簡
└─────────────────────────────────┘
```

## 6. 輸入格式的兩個必要條件

| # | 條件 | 為什麼 |
| --- | --- | --- |
| 1 | **數值一定要附中文形容詞** | `hunger: 62` 對模型沒有基準，「飢餓 62（很餓）」才有 |
| 2 | **一定要回報上一個動作的失敗原因** | 沒有原因，AI 會重複同一個錯誤直到永遠 |
