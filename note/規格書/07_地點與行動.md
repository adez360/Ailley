### 1-1 地點資料結構

所有地點筆記共用下列格式，範例取自 [[森林]]（目前唯一填滿實際數值的地點）：

```json
{
  "location_id": "loc_forest",
  "name": "森林",
  "desc": "樹影很密，聽得到不知名的動物聲。",
  "capacity": 4,
  "danger": 20,
  "resources": ["small_game", "large_game"],
  "available_actions": ["hunt_small", "hunt_large", "move"],
  "regen": { "small_game": 36, "large_game": 144 }
}
```

| 欄位 | 說明 |
| --- | --- |
| `desc` | 一句話環境描述，注入 prompt 用 |
| `capacity` | 同時容納人數上限，滿員則無法進入 |
| `danger` | 環境危險度 0–100，扣減行為成功率 |
| `resources` | 該地點可產出的資源 |
| `regen` | 資源再生所需 tick 數。`herb` 已拍板**不做**資源再生／冷卻（見《99》P-18 #9）；`small_game`／`large_game` 再生與否待拍板（見《99》P-71），上例數值為暫定 |
| `carryable` | 選填，預設 `false`。`true` 表示這是可被 `haul` 搬走的物件而非固定地點，目前僅 [[天神之石]] 為 `true`（見《99》P-27） |

## 2. 行動清單

行為的成功率公式與參數見《01-2》。本節定義**有哪些行動**與**分類規則**。溝通類（A）的行動與社交規則獨立在《[[11_人際互動與社交行為]]》，不在本節。

### 2-1 四大類

| 類別 | 特性 | 是否需要對方同意 |
| --- | --- | --- |
| **A 溝通類** | 對他人說話 —— 見《[[11_人際互動與社交行為]]》 | 依行動而定 |
| **B 工作與消費類** | 產出或消耗資源 | 否 |
| **C 動作與移動類** | 改變自身狀態或位置 | 否 |
| **D 敵對類** | 對他人造成損害 | 否 |

> [!note] 現況（2026-08-29 拍板；2026-08-30 隨 issue #753 同步）：本節列的動作不是全部已可被 AI 選到
> `Ailley/scripts/ai/ai_schema.gd` 的 `IMPLEMENTED_ACTIONS` 白名單目前有：`move_to`／`talk`／`sleep`／
> `wash`／`idle`／`eat`／`drink`／`buy`／`murmur`／`give`／`shout`／
> `haul`／`struggle`／`attack`／`persuade`／`bury`／`gather`／`follow`／`perform`／`work`／
> `spit_at_stone`／`worship_stone`／`praise_stone`（§2-5 天神之石手勢類，issue #752）／
> `hunt_small`／`hunt_large`／`wander`。
> 這份白名單**只管兩件事**：(1) `prompt_builder.gd` 組 LLM 選單時只端出這些動作、
> (2) `agent.gd::_select()` 只擋 `source == "llm"` 的任務——`source` 是 `schedule`／`reflex`
> 的任務不經過這道檢查，理論上仍可能呼叫到白名單外的執行邏輯，不宣稱這份清單擋住所有路徑。
> 另一個白名單管不到的缺口：`wander` 沒有 `place`，目的地是 `_pursue_wander_task()`
> 開跑時用任務 id 比對才挑一次的隨機座標——schedule 來源的任務 id 恆為
> `schedule_%d`、跨日重用，同一筆第二天再被選中時比對會失效，所以
> `agent.gd::_select()` 會在 wander 任務起跑時重置 `_wander_task_id`（與
> `_buy_pursuit_task_id` 同款處理），讓每次被選中都重新挑一趟的目的地；
> llm 來源每次決策 id 都是新的，不依賴這個重置。
> 下面 B／D 兩類列出的 `fish`／`sell`／`steal`
> 三個動作還沒在白名單裡，LLM 選不到；`fish`／`steal`
> 的成功率公式已經在 `Ailley/scripts/character/agent.gd::SUCCESS_PARAMS`
> 裡備好（見《01-2》§3），只是還沒有東西會真的呼叫到；`sell` 連公式都
> 還沒排。這份清單描述的是**規格**（要做哪些行動），不是目前的實作進度，沒有對應
> 追蹤 issue 的三個動作視同「規格已定、待實作」。

### 2-3 C 動作與移動類

| `action` | 中文 | 說明 |
| --- | --- | --- |
| `move`（**現況：程式碼實際 action id 為 `move_to`，params 用 `place` 不是 `location_id`——`ai_schema.gd` 自己的註解說明是刻意保留舊命名，改名要動多處引用不值得冒險，這裡沿用規格書原命名，只標明對應關係，不逐篇改字**） | 移動 | 需指定目的地；一律用基礎速度 `SPEED = 60.0`（`Ailley/scripts/character/character.gd`，2026-08-24 從 80 調降，PR #569，見 §4／《99》P-04 #9）。跑步（速度提升、額外耗體力）延後到 MVP 之後，見《99》P-29 |

| `idle` | 發呆 | **系統兜底用**，AI 逾時或失敗時執行 |
| `wander` | 閒晃 | 沒有目標、沒有 `place`，在 NavGrid 目前所在格附近以方形取樣（半邊長 6 格、邊長 13 格）隨機挑一個可走的格子走過去，抵達即結束。2026-08-30 issue #753 拍板，見 `note/ai/決策紀錄.md` |

### 2-4 D 敵對類

| `action` | 中文 | 說明 |
| --- | --- | --- |
| `steal` | 偷竊 | 含被目擊獨立判定，見《01-2》§4 |
| `attack` | 攻擊 | **必中**，MVP 不做閃避／格擋；每次命中：`health` -15、`injury` +20（見《99》P-28）；`injury ≥ 20` 時自動出現 `bleeding`（門檻自動，見《02》§2-2，不是攻擊另外觸發的旗標）；關係大幅下降；`health ≤ 0` 觸發昏迷（見《99》P-27） |
| `haul` | 搬運 | 目標須 `carryable: true`（物件，如[[天神之石]]）或為任意角色。速度為一般移動的 50%、每 tick 額外 -3 體力，是長動作，套用《02》§3 固定間隔檢查點（可中斷，中斷原地放下），見《99》P-27。**昏迷角色**：單人即可搬，不會掙扎。**清醒角色**：檢查點觸發時被搬運者只收引擎內部通知 `on_dependent_checkpoint()`，引擎不代問；要不要掙脫由被搬運者自己的下一次決策選 `struggle`（即時動作，不限檢查點時機，見《01-2》§3），`shout` 呼救、`idle` 不反抗也都在他的決策選項裡。單人搬運時 `struggle` 才有機會成功，雙人同時搬運則完全無法掙脫。`haul` 本身不自動改變 `relations`，不論目標清醒、昏迷或物件——搬運清醒角色的動機可能天差地遠（善意、玩鬧、挾持），引擎不預先替這個動作的性質定性（見《00》原則二），關係要不要變、變多少交給雙方當事人接下來的行為自己決定。清醒角色被搬運中，會收到一句環境事實（見《01-3》§3），只告知「正在被搬運」這個物理狀態，不歸因是誰、為什麼 |
| `struggle` | 掙脫 | 僅被強制搬運中的清醒角色可選（被搬運者自己的決策選項，即時動作）；成功率見《01-2》§3，雙人搬運時必定失敗；成功則立即掙脫，對方的 `haul` 中斷、原地放下 |

## 5. 地點與可用行動的對應

`available_actions` 由 Godot 端依「地點 ＋ 角色狀態 ＋ 持有物」過濾後給 AI（見《04》§4-2）。

```
地點的 available_actions
        │
        ├─ 減去：角色狀態不允許的（力竭時不能打獵）
        │
        ├─ 減去：缺少前置物品的（沒有食物就沒有 eat）
        │
        └─ 加上：全地點通用的（move / idle / talk）
                │
                ▼
        送給 AI 的 available_actions
```

> ⚠️ 過濾一律由引擎判斷，不交給 LLM。AI 只能從清單裡選，選不在清單裡的視為失敗。
> `rest`／`nap` 不在通用行動裡：LLM 只選 `sleep`，`rest`／`nap` 由引擎依睡眠需求內部分級（見 §2-3 `sleep`）。
> 

**特殊情形**：被強制搬運中的清醒角色，`available_actions` 一律覆蓋成 `struggle`／`shout`／`idle`，不套用下面的一般過濾規則（見《99》P-27）。

**過濾（拿掉選項）只用於角色狀態不允許／缺前置物品**——這兩種是「客觀上做不到」，AI 看不到這個選項不算少自由度。**社會性限制（名聲過低、被禁止進入的地點等）不走過濾**：選項仍留在 `available_actions` 裡，AI 能選，由引擎判定失敗並給理由，貼近《00》原則一「LLM 決定想做什麼，引擎決定做不做得到」——AI 保有「明知可能被拒也要去試」的自由。範例見《08》§5「交易規則」#3。
