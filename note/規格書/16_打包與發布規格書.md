# 16_打包與發布規格書

# 16｜打包與發布規格書

**閱讀對象**：後端組・遊戲邏輯組・負責發布的組員
**文件性質**：定義遊戲從原始碼到玩家手上這段流程的架構與分工。跟功能開發解耦——匯出設定（平台目標、resource include/exclude、sidecar 打包規則）一次設好通常很穩定，只有新功能帶來「需要隨版本一起發布的外部檔案」時才需要回頭補 include 規則，不會每加一個功能就要重做一次打包流程。
**前置閱讀**：《10 模式連線與世界設定規格書》§6（模型與連線架構，Sidecar 決策）、《14 存檔資料存取層規格書》§3（匯出風險對照表）

## 1. 已拍板的架構決策

| # | 決策 | 理由 |
| --- | --- | --- |
| B1 | 目標平台：Windows／macOS／Linux 三平台都要 | 涵蓋最廣的玩家與開發機組合 |
| B2 | 發布通路：Steam | 需要 Steamworks SDK／depot 整合 |
| B3 | 本地模型（Qwen2.5-7B-Instruct，`llama-server` sidecar）**全部塞進安裝包**，不做「首次啟動另外下載」 | Steam 對大檔案沒有容量限制（SteamPipe 常態處理 50GB+ 遊戲）；Qwen2.5 系列 Apache-2.0 授權允許再散布；塞進安裝包玩家下載完即可用，不用額外的首次啟動下載流程 |
| B4 | 模型檔獨立於遊戲本體 depot 之外，另開一個 Steam depot，但**預設隨遊戲一起安裝**，不做成選配／DLC 式的可選 depot | 之後遊戲更新玩家只重抓變動的遊戲本體 depot，模型那個大檔不會因為改一行 GDScript 就要重新下載；「獨立 depot」只是更新粒度的切分，不是要玩家自己選要不要裝模型——那樣會違反 B3「全部塞進安裝包」的初衷 |
| B5 | Sidecar（`llama-server` 獨立背景進程）架構不受 Steam 平台規則限制 | Steam 技術審查不禁止遊戲另開背景進程，反外掛／語音／疊加層工具都是同一套模式；唯一要注意的是簽章/公證與防毒誤判，屬於打包工程項目，不是平台禁令 |
| B6 | 本輪（MVP 打包骨架）**不**投資簽章／公證憑證，內部測試用未簽章版本即可 | Windows code signing 與 Apple Developer Program（年費 $99）留到真的要對外發布前再辦 |
| B7 | 本輪**不**申請 Steamworks 開發者帳號（$100 上架費），Steam depot 設定阻塞在帳號申請完成 | 帳號還沒申請，§2.6 列為待規劃、不開對應 issue |
| B8 | 本輪**要做** CI 自動化（GitHub Actions 自動出三平台 build） | 跟 §2.1 export_presets 骨架同時到位最省事——骨架剛做完、規則還新鮮，此時接上 CI 比之後回頭補的成本低；後續每次改動都能自動驗證三平台匯出沒壞掉，及早抓到匯出設定跟新功能衝突的問題 |
| B9 | Web／原生行動裝置（iOS／Android，若日後 POC 要做）一律強制走 `RemoteLLM`（雲端模型），不支援本機 Sidecar | 瀏覽器沙盒沒有能力像桌面版那樣 `OS.create_process()` 拉起獨立的 `llama-server` 背景進程，這是平台安全模型的硬限制，不是打包策略能繞過的；iOS／Android 同理受限於 `llama-server` 執行檔的 ARM 平台編譯與行動裝置的儲存/算力限制。**Steam Deck／SteamOS 不適用本條**——它是 x86-64 的 Linux 桌面系統，已被 B1「Linux」涵蓋，架構上能跑本機 Sidecar，差別只在效能是否夠用，那是效能驗證問題，不是平台相容性問題，不歸這條管。架構已具備支撐 B9 的抽象——`DecisionProvider` 本來就是 per-character 指派（見《12》§3），不需要新增介面，只需要在對應平台強制指派 `RemoteLLM`、UI 上隱藏本機模型選項，詳見 §3 |
| B10 | 開發期專用介面（debug 主控台、debug 疊圖、AI provider 就緒狀態列）一律用 `OS.is_debug_build()` 判斷，正式建置完全不啟用，不留特殊手勢/參數叫回來 | Godot 內建、不用額外的自訂旗標；`export_presets.cfg` 匯出 release preset 時 `is_debug_build()` 自動回傳 false，不需要在打包步驟另外處理。「完全不啟用」而非「保留但需要手勢」：主控台能存讀檔、開關角色 LLM 決策、直接送 LLM 探針請求（會消耗雲端額度），誤觸都是實際後果，不是單純介面問題，不值得為了方便回報問題而留一道攻擊面 |

## 2. 範圍拆分與驗收標準

依決策 B6～B8，本輪推進 §2.1～§2.4；§2.5～§2.6 待對應前置條件（憑證／Steamworks 帳號）到位後才展開，屆時各自對應一則 GitHub issue。

### 2.1 Godot export_presets 骨架

- 三個 export preset：Windows Desktop／macOS／Linux
- icon、版本號、resource include/exclude 基本規則
- exclude 開發用檔案：`note/`、`.claude/`、`.git/`
- **本機測試用的敏感連線設定不得進安裝包**：`data/` 目錄下不得出現真實的 `ai_config.json`（含 Tailscale IP 等連線資訊），這是比照 `note/本機/`（gitignored、不可進公開 repo）的同一條紅線延伸到 export 這步——resource include 規則只能收 `data/ai_config.example.json` 這個範本，不能無腦整包收 `data/`；`.gitignore` 已擋住它進版本控制，但 export 是從工作目錄的檔案系統直接打包，不是從 git 讀，兩者要分開擋，`.gitignore` 擋不住已經在磁碟上但未被 git 追蹤的檔案被 export_presets 收進去
- **不含** `SqliteSaveService` 用到的 GDExtension 原生函式庫（`.dll`/`.so`）匯出——MVP 只走 `JsonSaveService`（見《14》§4），SQLite 平行開發、非阻塞，等它真的要上線時才需要處理三平台原生函式庫匯出的坑（見《14》§3「匯出風險」對照表）

**驗收**：`godot --headless --export-release <preset>` 三平台都能成功匯出；匯出後的獨立執行檔（不透過編輯器）能開機到主選單。

**相關檔案**：`project.godot`、新增 `export_presets.cfg`

### 2.2 Sidecar（llama-server + 模型檔）打包整合

- 各平台預編譯的 `llama-server` 執行檔放哪、怎麼被 export_presets 收進去
- 遊戲執行期用 `OS.create_process()`（或等效 API）拉起子進程的跨平台路徑差異
- 模型檔案結構先弄乾淨、可分割——真正切 Steam depot（B4）是 §2.6 上架那步才動手，這步只確保檔案不會跟遊戲本體混在一起，之後好分割
- 確切模型量化等級（如 Q4_K_M）待效能實測後補（見《10》§6.1）
- **第三方開源授權合規**：Qwen2.5-7B-Instruct（Apache-2.0）與 `llama.cpp`／`llama-server`（MIT）都要求散布時附上對應的 LICENSE／NOTICE 檔案，安裝包裡要包含這兩份授權文字（例如放進一個 `THIRD_PARTY_LICENSES/` 目錄，隨遊戲本體一起匯出）。遊戲本身的授權已拍板為 Apache License 2.0（見 `README.md`、`LICENSE`），跟這兩個第三方元件相容，不再是待決項

**驗收**：匯出後的獨立執行檔能自動拉起 `llama-server` 並連線成功（複用既有連線教學〔`note/本機/地端模型測試教學.md`〕的驗證方式：`ai`／`ai dialogue` 指令觀察真實模型回應）；安裝包內含 Qwen2.5 與 llama.cpp 的授權檔案。此外要涵蓋基本失敗情境（執行檔或模型檔遺失、連接埠被佔用、啟動逾時），至少不能讓主執行緒卡死或無提示閃退——具體的玩家可見錯誤訊息與重試/正常關閉流程屬於實作細節，留給實際動工那則 issue 設計，這裡先定下「失敗要有動靜、不能悄悄卡住」這個底線。

**相關檔案**：`scripts/ai/ai_service.gd`、`scripts/ai/decision_provider*.gd`、
`scripts/ai/llama_sidecar.gd`（issue #772 實作，見《技術/LLM Sidecar 啟動》——
目錄慣例、啟動流程、失敗處理細節都在那份筆記，這裡只留架構決策）

### 2.3 `ai_config.json` 首次啟動自動產生

- 偵測 `user://` 沒有設定檔時，用內建 sidecar 的預設值（`127.0.0.1` 本機連線）自動寫一份，不需要玩家手動抄教學文件裡的 JSON
- 雲端模型（OpenRouter token）設定仍需玩家自己填，不在自動產生範圍內

**驗收**：全新安裝、乾淨的 `user://` 目錄下啟動遊戲，不用手動編輯任何檔案就能對話。

**相關檔案**：`scripts/ai/ai_config.gd`（或新建對應腳本）、`data/ai_config.example.json`

### 2.4 CI 自動化

- GitHub Actions 上跑 headless export（依賴 §2.1 的 `export_presets.cfg` 先落地）
- 觸發時機：PR merge 到 `main` 後自動跑三平台 export，產出 artifact 供內部測試下載；也保留手動觸發（`workflow_dispatch`），不用等 merge 才能拿一份 build
- 這階段先不含 §2.2 的 sidecar／模型檔打包（模型檔幾 GB，塞進 CI artifact 不現實）——CI 出的是「不含 sidecar 的裸遊戲執行檔」，用來驗證 export_presets 設定本身沒壞，跟本機手動打包測 sidecar 整合是兩件事，不衝突

**驗收**：PR merge 到 `main` 後，GitHub Actions 自動產出三平台 build artifact，下載後執行檔能開機到主選單。

**相關檔案**：新增 `.github/workflows/export.yml`

### 2.5 簽章與 Gatekeeper／SmartScreen〔待規劃，阻塞於 B6〕

Windows code signing、macOS notarization 串進打包流程。macOS 要用 Developer ID 憑證簽章並完成公證，才符合預設 Gatekeeper 設定——沒公證 Gatekeeper 直接擋掉，玩家開不了，不像 Windows 未簽章版本至少還能讓玩家手動點過 SmartScreen 警告執行。B6 決定本輪內部測試先用未簽章／未公證版本，這代表現階段的 build 只能團隊內部互傳，不能公開發，等真的要對外發布再回來做這節。

### 2.6 Steam depot 設定與上架〔待規劃，阻塞於 B7〕

依賴 Steamworks 帳號／App ID 建立（需組織/個人申請，非工程項目）。depot 拆分：遊戲本體 depot（含 export 出來的執行檔／pck）＋ 模型檔獨立 depot（B4）。

## 3. Web／行動裝置支援（B9 展開）

本節只到「原則層級」——B1（目標平台）目前只拍板 Windows／macOS／Linux 三個桌面平台，Web／行動裝置還不在本輪執行範圍內，這裡先記下已知的限制與需要驗證的風險，等真的有 POC 要做才展開成 §2 那種可驗收的任務拆分，避免現在就做超出實際需求的細部規劃。

### 3.1 已確認的限制

- **Godot 官方預設的 Web export template 不含 GDExtension 支援**（自訂 template 搭配對應的 WebAssembly 版擴充理論上可行，但需要額外編譯與維護，不是開箱可用）：`SqliteSaveService` 在標準 Web 匯出下無法使用，只能走 `JsonSaveService`。MVP 本來就只做 JSON（見《14》§4），不受影響，但這代表在沒有額外投入自訂 template 的前提下，Web 版的 `SaveService` 後端沒有選擇餘地，不是「先用 JSON、以後可以換 SQLite」
- **目前 renderer 設定（`gl_compatibility`，見專案 `project.godot`）恰好是 Godot Web 匯出唯一支援的 renderer**——不需要為了做 Web 版額外改 renderer，這是既有設定帶來的巧合，值得記下來避免以後有人誤以為要另外處理

### 3.2 需要實測才能確認〔待驗證，未實測前不可視為結論〕

- `user://` 在 Web 匯出對應瀏覽器 IndexedDB 虛擬檔案系統，寫入是否可靠、重新整理頁面後資料是否還在，需要實測，不能沿用桌面版 `FileAccess` 的行為假設
- `HTTPRequest` 呼叫 OpenRouter 在 Web 匯出走的是瀏覽器 `fetch`，受該端點的 CORS 政策約束。**若 OpenRouter API 對瀏覽器來源不開放 CORS，會需要一個轉發用的最小後端**——這會直接牴觸《LLM 串接與 AI 服務層》裡「出貨不走 Python 後端」的既有架構決定（見該文件開頭的 `[!success]` callout），屬於高風險項目，一旦成立就不是「Web 版怎麼做」的技術問題，而是要回頭重新拍板架構決定的層級
- 若 Web 版用到需要多執行緒的引擎功能，瀏覽器端需要 `SharedArrayBuffer` 支援，這要求托管網頁伺服器送出 `COOP`/`COEP` 標頭——目前不確定專案有沒有依賴這類功能，需要實際匯出後才能確認

### 3.3 發布通路是獨立於 B2 的新決定

Steam depot 機制是給原生執行檔設計的，Web 匯出（HTML5/WASM）是完全不同的發布形態——通常是靜態網頁檔案，host 在 itch.io、自架網站，或 Steam 本身另有「Direct to Web」這類機制，但那是額外的通路設定，不是 B2（Steam 原生發布）自動涵蓋的範圍。真的要做 Web 版時，通路要另外拍板，不能預設沿用 §1 的 B2。

## 5. 上架前端到端 QA checklist（issue #324，2026-08-31 拍板，《99》P-43）

§2.1～§2.4 各節都有自己的「驗收」標準，但那些各自只驗證單一環節。這裡是「準備要對外
發布前」的總檢查清單，把散在各節的驗收項目收攏成一份跑一遍的表，並明確分三層——
**Tier A：CI 出的裸執行檔**（§2.4，只驗證 export_presets 沒壞）、**Tier B：本機手動打包
含 sidecar 的完整安裝包**（§2.2，玩家實際會拿到的東西）、**Tier C：簽章與上架**（§5-3，
待前置條件到位才適用）；A／B 兩層不可互換，只測前者不能當作後者也過。

### 5-1 Tier A：CI 出的裸執行檔（對應 §2.1／§2.4）

目的：確認 export_presets 設定本身沒壞，不含 sidecar／模型檔。

- [ ] GitHub Actions 在 PR merge 到 `main` 後自動產出三平台（Windows／macOS／Linux）build artifact
- [ ] 三個 artifact 各自下載後，不透過編輯器直接執行，都能開機到主選單
- [ ] 開機過程沒有 script error／crash

> [!warning] 待確認（本節適用前提）
> Tier A 依賴的三平台匯出 CI 目前沒有對應 workflow（`.github/workflows/` 只有 PR 審查指
> 派）；而《17》「非玩法產品完整度」把三平台匯出 CI workflow 歸在「發布完整版」，跟本
> 文件 B8（本輪要做三平台 CI 自動化）矛盾——三平台 CI 屬本輪 MVP 還是完整版，待拍板。

### 5-2 Tier B：本機手動打包含 sidecar 的完整安裝包（對應 §2.2／§2.3）

目的：驗證玩家實際會拿到的東西——含模型與 sidecar 的完整版能不能真的玩。**Tier A 過
不代表 Tier B 過**，兩層要分開各自跑一次。

- [ ] 全新安裝、乾淨的 `user://` 目錄下啟動，不用手動編輯任何檔案就能對話（§2.3 驗收）
- [ ] 獨立執行檔能自動拉起 `llama-server` 並連線成功，用 `ai`／`ai dialogue` 指令觀察真實模型回應（§2.2 驗收，Local AI 路徑）
- [ ] Cloud AI（`RemoteLLM`）路徑同樣連線成功
- [ ] 至少驗證一種基本失敗情境（例如故意搬走／改名模型檔、佔用連接埠）——失敗要有動靜（錯誤訊息／重試／正常關閉），不能悄悄卡死或無提示閃退（§2.2 驗收底線）
- [ ] 安裝包內含 Qwen2.5、`llama.cpp` 的第三方授權檔案（`THIRD_PARTY_LICENSES/` 或等效位置）
- [ ] 存讀檔：新建角色 → 存檔 → 關閉遊戲 → 重開 → 讀檔，資料正確還原
- [ ] 三平台（Windows／macOS／Linux）**各自**手動跑過一輪以上項目——不能只測開發機所在的那個平台

### 5-3 Tier C：簽章與上架〔待 §2.5／§2.6 前置條件到位後才適用〕

B6／B7 決定本輪不投資簽章憑證、不申請 Steamworks 帳號，這層 checklist 先訂項目，實際
執行待前置條件到位、§2.5／§2.6 真的展開時才適用：

- [ ] Windows 版經過 code signing，執行時不觸發 SmartScreen 警告（或至少能正常點過）
- [ ] macOS 版經過 Developer ID 簽章＋公證，Gatekeeper 預設設定下可直接開啟
- [ ] Steam depot（遊戲本體＋模型檔獨立 depot，B4）設定正確，測試帳號能下載安裝

### 5-4 簽核方式

跟《規格書/99》其餘表格同一個原則，不在這裡手填人名——「誰簽核、什麼時候簽」屬於排程，
真正要發布時開對應 issue 指派，這裡只定規則本身：

- Tier A／B：由執行打包這一步的工程師本人先自檢跑過一輪全部項目。內部測試／demo 用途
  （目前 MVP 階段多數情況屬於這類）打包者自檢即可，不強制找第二人複核，避免拖慢日常的
  內部測試循環
- **真的要對外發布**（牽動 Tier C 的那次）：額外找一位不是打包者本人的人複核 Tier A／B
  的結果，確認清單每一項都有人實際驗證過——比照 `.claude/CLAUDE.md` 的 PR 審查規則
  （作者不得 self-approve；代修者代為 Approve 時也必須聲明「本人代修、審查由獨立
  agent session 執行」）的同一個精神：驗收結果不能只由執行者自己認定，複核只在對外
  發布這個更高風險的時間點才要求

### 5-5 跟《技術/測試計畫》（P-61）的分工

兩份 checklist 都在「發布前跑一次」，但驗證的層次不同，不重疊：本節（QA checklist）
假設遊戲邏輯本身沒問題，只驗證**打包這層**（安裝包能不能正常裝、跑起來、連線）；
