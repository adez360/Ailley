# 12｜決策來源抽象與執行架構規格書

本文件展開《10 模式、連線與世界設定規格書》§12，定義決策契約、決策來源介面、驗證機制，以及後端與 Godot 之間的職責邊界。取代《00 設計原則與架構》§7 原本以 tick 為觸發點的批次決策循環；事件驅動的觸發方式定義於《10》§5.1。

**適用對象**：AI 組、後端組、遊戲邏輯組、前端（Godot）組。

**本期是否實作**：其中「單一契約來源」與「DecisionProvider 介面」建議本期完成（純重構、不改變現有行為）；其餘為未來擴充的設計依據。

## 1. 問題陳述

現況：引擎的決策程式碼直接呼叫本機 llama-server，並手動組出 GBNF 字串。

依《10》已定案的規格，未來會有四種決策來源同時存在：

| 來源 | 依據 | 傳輸方式 |
|---|---|---|
| 本機內建模型 | 《10》§6.1 Sidecar | HTTP → localhost |
| 玩家自備雲端模型 | 《10》§6.3 OpenRouter | HTTP → 外部，需 token |
| 真人接管決策位 | 《10》§2.3 | 無網路，等待 UI 輸入 |
| 連線玩家的模型 | 《10》§6.6 | 反向連線，玩家連進房主 |

若不抽象，這四種會在引擎裡長成連續的 `if` 判斷，且逾時、重試、失效處理會被複製四份。

**關鍵差異不在傳輸層，而在傳輸層之上：**

| 面向 | llama-server | OpenRouter | 真人 |
|---|---|---|---|
| 請求格式 | `{prompt, grammar}` | `{model, messages}` | UI 表單 |
| 輸出約束 | GBNF（文法層強制） | JSON Schema（盡力而為） | 表單欄位限制 |
| 回應解析 | `content` | `choices[0].message.content` | 表單值 |
| 認證 | 無 | Bearer token | 無 |
| 錯誤語意 | 連線失敗、逾時 | 429 限流／402 額度／404 模型不存在 | 不回應 |

**GBNF 為 llama.cpp 專屬，雲端模型無法使用。** 這是四種來源必須各自實作的根本原因。

## 2. 單一契約來源：JSON Schema

### 2.1 原則

決策契約以 **JSON Schema 為唯一真相來源**，GBNF 由它產生，不再手寫。取代《04 Godot與AI資料介接規格》§8 原本描述的手寫 GBNF 約束範圍。

```
決策契約（JSON Schema）
        ├─→ json_schema_to_grammar → GBNF → llama-server
        ├─→ 直接置入 request        → OpenRouter
        ├─→ 自動生成表單欄位        → 真人 UI
        └─→ 收到回覆後驗證          → 四種來源共用
```

**效益**：契約只有一份。改欄位只需改 schema，四條路徑自動同步。若維持手寫 GBNF，改欄位需同時維護 GBNF 與雲端 schema 兩份，兩邊必然逐漸不一致。

**轉換器不需自行開發**：llama.cpp 專案已提供 `json_schema_to_grammar`，llama-server 內部即以此方式將 schema 轉為 GBNF。

### 2.2 契約範例

```python
def build_schema_for_call(char, world) -> dict:
    return {
        "type": "object",
        "properties": {
            "inner_monologue": {"type": "string"},          # 必填
            "action":          {"enum": world.available_actions(char)},
            "target":          {"enum": world.visible_actors(char) + [None]},
            "location":        {"enum": world.reachable_locations(char)},
            "emotion":         {"enum": EMOTIONS},           # 靜態 8 項
            "speech":          {"type": "string"},           # 可為空字串
            "speech_volume":   {"enum": ["whisper", "normal", "shout"]},
        },
        "required": ["inner_monologue", "action", "emotion"],
        "additionalProperties": False,
    }
```

### 2.3 動態欄位

原 `build_grammar_for_call()` 動態產生的 `target-value` 與 `location-value` 兩條規則，在 JSON Schema 中以 `enum` 表達，轉為 GBNF 後效果等同手寫版本。

**表達力不會損失**：靜態 enum（action／emotion／speech_volume）與動態 enum（target／location）皆可完整表達。

### 2.4 條件式欄位

依《10》§5.4、§5.5，下列欄位僅在特定條件下加入 schema，其餘時候 schema 中不存在該欄位，模型即無法輸出。

| 欄位 | 加入條件 |
|---|---|
| `update_plan` | 睡覺反思／意圖全數完成／意圖被事實推翻／AI 主動申請 |
| `appointment` | 對話情境中且在場有其他角色——**現況（2026-08-23）**：`plan_response_schema()` 還沒有這個欄位，尚未實作，見《10》§5.5 現況警告、issue #479 |

**這是條件式 schema 的主要價值**：不需要靠 prompt 叮嚀「這次不要填這個欄位」，直接從文法層移除。

## 3. DecisionProvider 介面

### 3.1 介面定義

```python
class DecisionProvider:
    """決策來源。引擎不需知道背後是模型、真人、還是遠端玩家。"""

    def decide(self, prompt: str, schema: dict, timeout: float) -> Decision:
        """
        回傳一份決策，或拋出 DecisionError。
        實作者負責：格式轉換、送出、解析、逾時。
        實作者不負責：語意驗證、成功失敗判定、狀態更新。
        """
        raise NotImplementedError


class Decision(NamedTuple):
    data: dict          # 決策內容
    source_model: str   # 實際使用的模型名稱，供《10》B33 結算揭露
    latency_ms: int     # 供效能監控與流速上限實測


class DecisionError(Exception):
    reason: str         # timeout / invalid_format / model_missing /
                        # quota_exceeded / rate_limited / no_response
```

### 3.2 引擎端呼叫

```python
# 佇列彈出「角色 C 該決策了」
schema = build_schema_for_call(char, world)
prompt = build_prompt(char, world)

try:
    decision = char.provider.decide(prompt, schema, timeout=TICK_BUDGET)
except DecisionError as e:
    handle_decision_failure(char, e)   # 見 §6
```

**引擎不知道也不在乎背後是誰在想。** 每個角色物件持有一個 `provider` 欄位。

### 3.3 四種實作

| 實作 | 對應規格 | 輸出約束 | 主要錯誤 |
|---|---|---|---|
| `LocalLLM` | 《10》§6.1 | schema → GBNF | timeout、連線失敗 |
| `RemoteLLM` | 《10》§6.3 | schema 置入 `response_format` | 429／402／404、格式不合 |
| `HumanInput` | 《10》§2.3 | schema → 表單欄位 | no_response |
| `RemotePlayer` | 《10》§6.6 | 由玩家端執行，房主僅驗證 | timeout、連線中斷 |

### 3.4 各實作要點

**LocalLLM**
- 呼叫本機 Sidecar 的 llama-server
- schema 經 `json_schema_to_grammar` 轉為 GBNF 後置入 `grammar` 參數
- `source_model` 填入內建模型型號

**RemoteLLM**
- 呼叫 OpenRouter，需 Bearer token
- schema 置入 `response_format`
- **必須實作驗證失敗重試**：schema 對雲端模型是請求而非保證，部分模型不支援結構化輸出
- 建議重試上限 2 次，仍失敗則拋出 `invalid_format`
- `source_model` 填入玩家選擇的模型名稱

**HumanInput**
- 不發送網路請求，跳出決策面板等待輸入
- **表單欄位由 schema 自動生成**：下拉選單只列出當前合法的 action／target／location，真人在物理上無法填出非法值
- 逾時語意與模型不同，見 §6.2

**RemotePlayer**
- **連線方向為反向**：玩家客戶端位於 NAT 後方，房主無法主動連入。實務上由玩家連進房主（WebSocket 或長輪詢），房主將工作放入佇列等待對方領取
- **安全要求（《10》§6.6）**：送給玩家客戶端的 prompt 只能包含該角色感知範圍內的資訊，否則玩家可直接讀取 prompt 看到其他角色的內心獨白

## 4. 三層防護

| 層 | LLM | 真人 |
|---|---|---|
| **L1 生成約束** | GBNF 文法層強制（本地）／schema 盡力而為（雲端） | UI 表單欄位限制 |
| **L2 收到後驗證** | schema 驗證 + 三條硬規定 | 完全相同 |
| **L3 失敗處理** | 逾時、格式錯誤、模型失效 | 不回應（發呆、離席） |

### 4.1 L2 不可省略

即使 L1 已在文法層保證格式，L2 仍為必要，理由有三：

1. **語意層規則 GBNF 管不到**。三條硬規定（不能宣告沒有的東西、不能宣告自己的傷好了、宣告不代表做得到）屬語意層，文法無法約束。
2. **雲端模型的 L1 不是保證**。schema 對部分模型僅為建議。
3. **多人架構下客戶端不可信**（《10》§6.6）。`HumanInput` 與 `RemotePlayer` 的輸出皆來自客戶端，可能被竄改。

**一份驗證程式碼同時服務三個用途**：格式檢查、硬規定檢查、防作弊。

### 4.2 驗證內容

```python
def validate_decision(decision: dict, schema: dict, char, world) -> None:
    # 1. 結構驗證
    jsonschema.validate(decision, schema)

    # 2. 三條硬規定
    assert_target_exists(decision, world)        # 不能宣告沒有的東西
    assert_no_self_healing(decision, char)       # 不能宣告自己的傷好了
    # 「宣告不代表做得到」由成功失敗判定處理，見 §5
```

## 5. 兩個接縫與職責邊界

系統中有兩個抽象接縫，方向相反：

| 接縫 | 位置 | 隱藏了什麼 |
|---|---|---|
| DecisionProvider | 後端 | **誰在想** |
| 操控層 | Godot | **怎麼執行** |

兩者之間傳遞的即為決策 JSON，符合專案的 Contract-First 方針。

### 5.1 資料流

```
玩家客戶端              房主機（權威）                Godot 操控層
──────────             ──────────────               ─────────────
LocalLLM               1. 組 prompt / schema
RemoteLLM        →     2. schema 驗證
HumanInput             3. 三條硬規定檢查
RemotePlayer           4. 成功／失敗判定        →    5. 尋路、播動畫
                       6. 世界狀態更新          ←    7. 回報執行結果
```

### 5.2 職責表

| 職責 | 歸屬 | 理由 |
|---|---|---|
| 組 prompt 與 schema | 房主機 | 需要世界權威狀態 |
| 產生決策 | Provider（可能在玩家端） | 見 §3 |
| schema 驗證 | **房主機** | 客戶端不可信 |
| 三條硬規定檢查 | **房主機** | 同上 |
| 成功／失敗判定 | **房主機** | 需要世界權威狀態，例如「藥草叢是否已被採空」 |
| 世界狀態更新 | 房主機 | 唯一正本 |
| 尋路、動畫、表現 | Godot 操控層 | 純呈現 |

### 5.3 邊界規則

**驗證不得寫在 Godot 操控層。**

操控層只接收**已驗證的**決策，專心執行。在多人架構下 Godot 端為 client，若把驗證寫在操控層，等同把守門員放在門外。

**成功失敗判定亦不在操控層。**

「採集失敗，因為藥草叢已被採空」這類判定需要世界權威狀態。操控層取得的是判定結果，只負責播放對應表現。

此劃分與既有原則一致：**LLM 只決定想做什麼，做不做得到由引擎判定。** 本文件將「引擎」明確指定為房主機，而非 Godot 客戶端。單機模式下房主機與 Godot 為同一台機器，此邊界仍成立，只是物理上不分離。

**操控層應維持為純播放器，不做任何決定。**

## 6. 逾時與失敗處理

### 6.1 LLM 逾時

| 情境 | 處理 |
|---|---|
| 未在 `TICK_BUDGET` 內回應 | 角色繼續執行當前動作，不排新事件 |
| 格式驗證失敗 | 重試（雲端上限 2 次） |
| 重試仍失敗／模型失效 | 依《10》§6.4，該角色視同離線，走入眠流程；玩家端顯示明確錯誤原因 |

因採事件驅動架構（《10》§5.1），角色在等待回覆期間仍在執行上一個動作，短暫延遲不影響畫面連續性。

### 6.2 真人逾時（待決策，見 P-22）

| 逾時長度 | 建議行為 |
|---|---|
| 短（動作已完成但未填表） | 維持待機或繼續當前動作，不推進 |
| 中（數分鐘） | 視同離線，入眠「被天神召喚中」 |
| 長（現實 72 小時） | 踢出世界（《10》B11） |

**與流速的關係**：依《10》§4.1，流速固定 1:60，一個 30 遊戲分鐘的動作只等於 30 現實秒。這跟本節原本「慢時鐘讓真人有充裕時間填表」的假設不再成立——真人接管決策位是《10》§11.3 排在 v1.2 的未來功能，本期不實作，這裡先誠實記下這個落差，短／中逾時的具體秒數（P-22）等真的要做真人參與時，須連同流速一起重新評估，不能沿用本節舊例子的數字。

### 6.3 錯誤原因對照

`DecisionError.reason` 需可映射為玩家可讀訊息：

| reason | 玩家端訊息 |
|---|---|
| `timeout` | 模型回應逾時 |
| `invalid_format` | 模型輸出格式不符 |
| `model_missing` | 找不到指定的模型 |
| `quota_exceeded` | 模型額度不足 |
| `rate_limited` | 模型呼叫過於頻繁 |
| `no_response` | 未在時限內做出決定 |

### 7.2 驗收標準

- 重構前後，同一組固定 seed 的模擬跑出**完全相同**的決策序列
- `build_schema_for_call()` 產出的 schema 可通過 `jsonschema` 自身的 meta-schema 驗證
- 動態 enum（target／location）內容與重構前的 GBNF 規則一致
- 條件式欄位（`update_plan`／`appointment`）在不符合觸發條件時，不出現在 schema 中

### 7.3 實測結果（issue #245，2026-08-17；補測 2026-08-18）

**§7.1 任務 1-3（`schema_to_gbnf()`＋自建 `/completion` GBNF 呼叫）從未被實作**，程式碼直接採用 §8 簡化路線（`response_format` + `AIConfig.Provider.supports_json_schema`）。原本設計的「手寫 GBNF vs schema 轉換 GBNF」比較做不了，沒有手寫版本可比。

改測**現行唯一路徑本身的可靠度**，以及「地端 GBNF 文法層強制」vs「純 prompt 約束（`supports_json_schema=false`，不送 `response_format`）」的差異：對同一個地端 provider、同一組 plan prompt，兩種設定各跑滿 50 次，跑了兩輪（`game_eval` 有 8 秒逾時限制，單次只能分批跑 2-3 次，分批累計到 50）。

**可重現性資訊**（兩輪共用，2026-08-18 從同一台機器反查得到，逐筆原始結果見 [[schema-gbnf-vs-prompt-reliability-log]]）：model `Qwen2.5-7B-Instruct-Q4_K_M.gguf`、llama.cpp build `b1-aff6eb6`、sampling 用 server 預設值（`temperature=0.8`／`top_p=0.95`／`top_k=40`／`min_p=0.05`）、**沒有固定 seed**（`AIService` 不送 `seed` 欄位，每次請求隨機）。

| 組別 | 樣本數（兩輪合計） | 通過 | 失敗原因 |
| --- | --- | --- | --- |
| GBNF 強制（`supports_json_schema=true`） | 100 | 100 | — |
| 純 prompt 約束（`supports_json_schema=false`） | 100 | 97 | 3 次 `action_not_allowed`（第一輪，模型自己生成 `"work"`，不在白名單內）；第二輪 50 次全過，沒有重現 |

**測出真的差異，但原本「6%」只是小樣本下的粗估**：GBNF 強制模式兩輪合計 100/100 零失敗；純 prompt 約束模式合計 97/100，失敗率落在 3% 附近——第二輪 50 次沒有重現第一輪的 `action_not_allowed`，這在真實失敗率為個位數百分比時，連續 50 次全過本來就有不低的機率發生，不代表問題消失，只代表第一輪的「6%」不是精確值。方向沒變：GBNF 強制模式下模型自己生成白名單外 action 在文法層物理上不可能發生（enum 是文法規則的一部分）；純 prompt 模式下模型可以自由生成任何字串，全靠 layer 3（`AISchema.validate_tasks()`）事後擋下——兩輪擋下的失敗全部正確攔住，代表三層保證的最後一道防線確實有效，但也代表**拿掉文法層強制，錯誤率不是 0，是靠 layer 3 補救出來的 0**，兩者背後的可靠度不一樣。

兩輪都**沒有出現社群回報過的「json_schema 與 grammar 不可同時指定」錯誤**（團隊目前使用的 llama.cpp 版本）。兩輪都各觀察到一次 `"Exponent too high"` 警告（`ai_schema.gd:102` JSON 數字解析層級，疑似又是 priority 欄位飆出離譜大的指數值，跟 #224 修的 `1e15` 問題同類），發生在這個分支（此分支未併入 #224 的 `is_finite()` 防護）——這個異常值當下沒有被擋下，兩輪都重現，直接印證了 #224 那道防線的必要性。

另外用合成的壞資料測過 `AISchema.validate_tasks()` 的 fallback（缺 `action`、`action` 不在白名單、型別錯、缺 `tasks` 欄位、`tasks` 不是陣列）全部正確擋下；`agent.gd::_decide_with_retry()` 的重試路徑也實測過（強制第一次驗證失敗、第二次放行），確認重試機制真的會觸發，不是只在理論上存在。

> [!note] 這次沒測的部分
> 「同一個 action 配上不合理的 duration/priority」（例如 `talk` 配 100 分鐘）這種語意層面的合理性，這次抽測的分支還沒併入 #224 對 `priority`／`duration` 的 prompt 量級指引與範圍驗證，測了也只是重現已知、已修好的舊問題，沒有新資訊，這輪略過。#224 併入 main 後可以另外花幾分鐘快速驗一次。

## 8. 簡化路線　☑ 已採用

實作採用 llama-server 的 OpenAI 相容端點：`/v1/chat/completions` + `response_format`（`AIConfig.Provider.supports_json_schema` 開關），內部仍轉 GBNF 但由 llama-server 自己處理，不是引擎自建轉換器。`LocalLLM`／`RemoteLLM` 共用同一套呼叫邏輯（`DecisionProvider` 基底類別），只用 `base_url`／`api_key` 區分，不需要 §7.1 原本規劃的 `build_schema_for_call()`／`schema_to_gbnf()`／自建 `/completion` 呼叫這三項。

§7.3 實測（50 次×2 組）確認：production 預設（`supports_json_schema=true`，GBNF 文法層強制）50/50 全過、零失敗，也沒有出現社群回報過的 schema/grammar 衝突錯誤，維持現狀，不改走 §7.1 原本規劃的自建 GBNF 轉換路線。對照組（純 prompt 約束）有 6% 驗證失敗率（見 §7.3），反過來印證 `supports_json_schema=true` 這個預設值該維持——這不是「兩條路都一樣好、隨便選」，是「文法層強制路徑實測比較可靠，剛好是現在的預設值」。
