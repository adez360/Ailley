## P-03　是否縮減傳送項目讓 AI 判斷更聚焦　☑ 已定案（MVP 範圍）

| **類型** | 已定案（MVP 走方案 A，B/C 留待之後） |
| --- | --- |
| **現況** | 每 tick 全量注入約 1,100~1,300 token |
| **對應章節** | 《01-3》§4、《04》§4-2 |
| **影響文件** | 01-3 / 04 |

**核心問題**：塞越多資料進去，AI 每項都只輕微參考一點，行為會趨向平均值。縮減注入項目能讓決策更聚焦，但要先決定「誰來決定給什麼」。

### 三個方案

|  | A：固定全量 | B：情境預測式 | C：兩段式按需 |
| --- | --- | --- | --- |
| 誰決定給什麼 | 全給 | 引擎 | AI |
| 呼叫次數 | 1 | 1 | 1~2 |
| token 降幅 | — | 40~60% | 50~70% |
| tick 延遲 | 基準 | 不變 | 最壞翻倍 |
| 需改 GBNF | 否 | 否 | 是 |
| 需改 DES 時序 | 否 | 否 | 是 |
| 實作成本 | 無 | 中 | 高 |
| 風險 | AI 注意力分散 | 引擎誤判導致缺資料 | 小模型濫用或不會用 |

**建議**：B 為主線，C 列入迭代二。

## P-32　飢餓數值三套不一致（spec／stats.gd／SQLite 原型）　☑ 已拍板

| **類型** | 已決策（2026-08-16） |
| --- | --- |
| **對應文件** | 01 角色數值規格書 §4-1、02 狀態情緒與流程、06 資料欄位對應表 |
| **現況（拍板前）** | `hunger` 的 range 與方向在三個地方各自不同 |

拍板前的落差：

| 位置 | range | 方向 |
| --- | --- | --- |
| 規格書《01》§4-1／《06》（拍板前） | float 0–100 | 越高越餓，預設 20，每 tick +1.5 |
| 實際引擎 `Ailley/scripts/character/stats.gd:27` | float 0–100 | 起始 100，每秒 -3.0 朝 0，越低越餓 |
| SQLite 驗證原型 `Ailley/database/schemas/NPCStateSchema.gd:16-17`（見 P-26） | float 0.0–1.0 | 註解「0.0=0%、1.0=100%」 |

### 需要決定的事

| # | 問題 | 決定 |
| --- | --- | --- |
| 1 | 最終 range 定為 0–100 還是 0.0–1.0？ | ☑ **0–100**：`stats.gd` 跟規格書都已經是這個 range，改這個等於零成本；只有 SQLite 原型要跟著改 |
| 2 | 方向定為「越高越餓」還是「越高越飽」？ | ☑ **越高越飽**：跟真的在跑的 `stats.gd` 對齊（100=飽、0=餓）；規格書《01》§4-1、《02》starving 條件（`hunger < 10`）、死亡規則（`hunger` 維持 0 達 7 日）已同步改 |
| 3 | 決定後，`stats.gd` 與（若保留）`NPCStateSchema.gd` 要不要同步改，還是允許引擎內部單位跟規格書不同、只在邊界轉換？ | ☑ **全部同步改**：`stats.gd` 本來就已經符合（免動），`NPCStateSchema.gd` 的 `hunger` 欄位已改成 0–100、預設 100、CHECK 範圍同步更新 |

**連帶決定（給模型的注入格式，另見 P-07）**：`hunger` 內部儲存維持「越高越飽」，但注入給 LLM 前換算成「飢餓度」百分比（＝`100 − hunger`）＋中文形容詞兩者並存，模型看到的仍是「越高越餓」的直覺數字，不用自己反著判斷。

> [!warning] `thirst` 目前沒有同步檢查
> 這次只處理 `hunger`。`NPCStateSchema.gd` 的 `thirst` 欄位還是 0.0–1.0，
> 跟規格書《01》§4-1 的 `thirst`（0–100，越高越渴）方向剛好相反，是同一類問題，
> 只是還沒發現有沒有其他程式碼在用它。之後真的要導入 SQLite（P-26）時要一併核對，
> 不要假設只有 hunger 有這個問題。
