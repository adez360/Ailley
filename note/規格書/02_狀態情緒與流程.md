## 1. 情緒系統 `emotion`

情緒是 AI **唯一可以自行宣告的內在狀態**，也是角色所有主觀感受的統一出口。引擎不計算情緒，只負責倒數。

### 1-1 八種情緒

`emotion.type` 會寫進 GBNF 靜態 enum，數量與代號必須先定案，否則 AI 會被 grammar 擋住輸出不了。

| # | 英文 enum | 中文 | 典型觸發 | 正／負 |
| --- | --- | --- | --- | --- |
| 1 | `joy` | 喜悅 | 願望達成、收到禮物、被讚美 | 正 |
| 2 | `anger` | 憤怒 | 被偷、被攻擊、被背叛 | 負 |
| 3 | `sadness` | 悲傷 | 失去、被拒絕、他人死亡 | 負 |
| 4 | `fear` | 恐懼 | 遭遇危險、瀕死、被威脅 | 負 |
| 5 | `surprise` | 驚訝 | 意外事件、天神之石 | 中性 |
| 6 | `disgust` | 厭惡 | 目擊不義、環境骯髒 | 負 |
| 7 | `anticipation` | 期待 | 計畫即將實現、約定 | 正 |
| 8 | `neutral` | 平靜 | 無特殊事件 | 中性 |

> [!note] 定案 8 種，早期 12 種草案作廢（2026-08-16）
> `neutral` 不是湊數用的——依《1-3》規則 AI 每次決策都必須宣告情緒，沒有特別感受就填 `neutral`，
> 它是「沒有強烈感受」的必要預設值，不是第 8 種真正的情緒，所以清單本質是 7 種情緒 ＋ 1 個預設狀態。
> 跟心理學上常見的 Plutchik 八情緒模型相比，本表少了「信任」；不補上是因為開一個 `trust` 情緒
> 沒有獨立的引擎消費者，違反《00》「沒有引擎消費者的欄位不留」的原則（同一條原則也是《99》P-06
> 在判斷三項人格參數要不要留的依據，2026-08-16 靠這條原則拿掉了 `affinity`／`familiarity`／`debt`，
> 見《01》§3-1；`relations.trust` 本身後來也因同一條原則整個拿掉，見 issue #601）。「信任」現在
> 交給《03》記憶系統自己記、自己判斷、自己演，不用另一組數值或情緒重複做同一件事；
> 公共名聲另有 `reputation` 承擔，不受這條影響。

### 1-2 欄位結構

| 欄位 | 型別 | 誰寫 | 說明 |
| --- | --- | --- | --- |
| `type` | enum | **LLM** | 上表 8 值之一 |
| `intensity` | int | **LLM** | 0–100 |
| `cause_event_id` | string | 引擎 | 起因事件，供回放與圖書館使用 |
| `duration_left` | int | 引擎 | 剩餘 tick，每 tick 減 1 |

### 1-3 宣告規則

| # | 規則 |
| --- | --- |
| 1 | AI 每次決策都必須回傳 `emotion`。沒有特別感受就填 `neutral` |
| 2 | AI **不能**直接指定 `duration_left`——那由引擎依人格算 |
| 3 | 新情緒宣告會**覆蓋**舊情緒，不疊加。同時只有一種情緒 |
| 4 | `duration_left` 歸零時，引擎自動轉為 `neutral`，`intensity` 設為 0 |

### 1-4 持續時間計算

```
duration_left = 基礎時長 × (intensity / 50) × 人格係數

基礎時長 = 12 tick（2 遊戲小時）

人格係數：
  正面／中性情緒 = 1 + (50 − stability) / 100
  負面情緒       = 1 + (50 − stability) / 100 + (grudge − 50) / 100

最終夾制 1 ~ 144 tick（上限一遊戲日）
```

**範例**：`stability = 90`、`grudge = 75` 的角色

| 情緒 | intensity | 計算 | 結果 |
| --- | --- | --- | --- |
| `joy` | 60 | 12 × 1.2 × 0.6 | 9 tick（約 1.5 小時） |
| `anger` | 60 | 12 × 1.2 × 0.85 | 12 tick（約 2 小時） |

情緒穩定的人退得快，但記仇的人負面情緒明顯撐得比較久——這正是《01》想要的角色差異。

## 2. 特殊狀態 `conditions`

### 2-1 結構

```json
"conditions": [
  { "type": "injured", "turns_left": 8 },
  { "type": "drunk",   "turns_left": 12 }
]
```

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `type` | enum | 見 §2-2 |
| `turns_left` | int | 剩餘 tick。`-1` 表示持續到條件解除為止 |
- 陣列可同時存在多筆
- **全部由引擎寫入**，LLM 不可宣告
- 注入 prompt 時屬於「不定筆數」資料，需過濾（見《01-3》§2）

### 2-2 狀態清單

**每個狀態屬於下面 3 種套路之一**（2026-08-16 定案，見《99》P-28）——加新狀態時先選套路、填參數，不用另外設計一套機制：

| 套路 | 意思 | 怎麼結束 |
| --- | --- | --- |
| **門檻自動** | 盯著某個生理／社會數值，跨過門檻就出現 | 數值退回門檻內，下次 tick 重新檢查時自動移除（§2-3 規則 4） |
| **倒數計時** | 事件觸發，帶一個固定或計算出來的持續時間 | `turns_left` 倒數到 0 自動移除 |
| **事件手動** | 特定事件觸發，設計上就是要玩家／NPC 主動介入才會消失 | 只能靠特定行動解除，不會自己好、也不是倒數計時 |

#### 生理衍生（由 `state.physical` 自動觸發，皆為「門檻自動」）

| `type` | 中文 | 觸發條件 | 效果 |
| --- | --- | --- | --- |
| `injured` | 受傷 | `injury > 0` | 所有行為成功率 −`injury × 0.4%` |
| `drunk` | 酒醉 | `alcohol > 30` | 成功率懲罰；提高說真心話機率 |
| `starving` | 極度飢餓 | `satiety < 10` | `health` 每 tick −0.5 |
| `dehydrated` | 脫水 | `hydration < 10` | `health` 每 tick −1.0 |
| `exhausted` | 力竭 | `stamina = 0` | 強制昏睡 |
| `filthy` | 骯髒 | `hygiene < 20` | 【待定】原效果「他人 `affinity` 增幅減半」綁在已移除的 `affinity` 欄位上，且原設計是別人在不知情下被引擎默默調整關係，本身也有問題；需要重新設計，見《99》P-35 |
| `sleepy` | 極度睏倦 | `wakefulness < 15` | 行動效率下降 |
| `bleeding` | 流血 | `injury ≥ 20` | `health` 每 tick −1.5，不設下限保護；放著不管扣到 0 觸發昏迷是預期行為 |

> [!note] `injured`（受傷）與 `bleeding`（流血）都是同一個 `injury` 數值的門檻，不是兩套機制（2026-08-16 整合，見《99》P-28）
> 舊設計是 `attack` 命中時**額外**觸發一個獨立的 `bleeding` 旗標，跟其他「門檻自動」狀態不同套路（不會因為數值退回去就自動解除，只能靠治療手動清）。現在統一成單純的「門檻自動」：
> - `attack` 命中只做一件事：`injury +20`（見《99》P-28）
> - `injury > 0` 就有 `injured`（成功率打折，隨傷勢輕重連續縮放）；`injury ≥ 20`（相當於中一下攻擊）額外疊加 `bleeding`（持續扣血），跟其餘 6 個生理衍生狀態同一套「每 tick 重新檢查、條件不成立自動移除」規則（§2-3 規則 4）
> - **唯一的例外規則**：`injury ≥ 20` 期間，`injury` 原本每 tick −0.5 的自然衰減**暫停**（見《01》§4-1）——這是刻意保留「流血不會自己好、需要主動治療」的緊張感，用「凍結自癒」取代「另外開一個不會自動解除的旗標」
> - 治療只需要做一件事：把 `injury` 降下去。`medicine` 使 `injury` −30（下限夾制 0）；藥草鋪治療（見《[[藥草鋪]]》）直接把 `injury` 歸零。`injury` 一旦低於 20，`bleeding` 跟 `injured` 都在下個 tick 自動消失，不用額外程式碼「順便清掉流血旗標」
> - `injury ≥ 20` 這個流血門檻是暫定值，跟其餘 MVP 新機制數值一樣，實測後可調（見《99》P-28）

#### 社會狀態

| `type` | 中文 | 套路 | 觸發條件 | 效果 |
| --- | --- | --- | --- | --- |
| `detained` | 拘留中 | 事件手動 | 被舉報累積 3 次，由 NPC 抓捕 | 強制移動至洗心革面所，期間不可自由行動；只能靠洗心革面所流程解除 |
| `outcast` | 被排擠 | 門檻自動 | `reputation < -50` | 商店拒絕交易、社交申請被拒率提高 |

#### 行動佔用（表示角色正在做某件事，皆為「倒數計時」）

| `type` | 中文 | 說明 |
| --- | --- | --- |
| `sleeping` | 睡眠中 | 自己家回復量較大 |
| `napping` | 打盹中 | 與睡眠同模組，僅體力回復值不同 |
| `working` | 工作中 | 行為進行中，佔用該行為的時間 |
| `talking` | 對話中 | 目前僅處理 2 人對話 |

#### 終局狀態

| `type` | 中文 | 套路 | 說明 |
| --- | --- | --- | --- |
| `petrified` | 石化 | 事件手動 | 死亡後本體停留原地變灰，只能靠復活流程解除，詳見《09》 |

### 2-3 疊加規則

| # | 規則 |
| --- | --- |
| 1 | 同一 `type` 不重複加入，只更新 `turns_left`（取較大值） |
| 2 | 行動佔用類同時只能有一個 |
| 3 | `petrified` 出現時清空所有其他 `conditions` |
| 4 | 生理衍生類每 tick 重新檢查，條件不成立即自動移除 |

## 3. 角色狀態機

```
                    ┌──────────────┐
         ┌─────────►│    閒置       │◄─────────┐
         │          │   (idle)      │          │
         │          └──────┬───────┘          │
         │                 │ AI 決定行動       │
         │                 ▼                   │
         │          ┌──────────────┐          │
         │          │   移動中      │          │
         │          │   (moving)    │──────────┤
         │          └──────┬───────┘          │
         │                 │ 抵達               │
         │                 ▼                   │
         │          ┌──────────────┐          │
         ├──────────│   行動中      │──────────┤
         │          │  (working /   │  完成／  │
         │          │   talking)    │  中斷    │
         │          └──────┬───────┘          │
         │                 │                   │
         │                 │ stamina = 0       │
         │                 ▼                   │
         │          ┌──────────────┐          │
         └──────────│   睡眠中      │──────────┘
                    │  (sleeping)   │  睡醒＋反思
                    └──────┬───────┘
                           │ health = 0
                           ▼
                    ┌──────────────┐
                    │   死亡        │  → 《09》
                    │  (petrified)  │
                    └──────────────┘
```

> 上圖的「死亡」是完整版終局狀態。**MVP 這條路徑改走「昏迷」**，不是終局、可被治療恢復，見 §5 MVP 說明。

### 中斷規則

| 事件 | 是否中斷當前行動 |
| --- | --- |
| 被攻擊 | ✔ 立即中斷（含 `work` 中——不可被搭話打斷是另一條規則，見下方，不擋這條） |
| 天神之石事件 | ✔ 中斷，處理完回原行動 |
| 他人發起對話 | ✘ 不中斷，對方收到「他正在忙」 |
| `stamina` 歸零 | ✔ 立即中斷，轉入強制昏睡 |
| 目睹他人死亡 | ✔ 立即中斷 |
| AI 自主決定中止（僅限長動作，見下方） | ✔ 可中止，中止有代價 |

**`work` 的「不可被搭話打斷」是獨立規則，不是本表的一部分**：`work` 期間「他人發起對話」一律不中斷（同上表），但本表其餘五個強制中斷事件（尤其被攻擊）優先於這條，一樣會中斷 `work`。

**AI 自主中止長動作**：長動作（見《01-2》§3 進行時間 > 一次 tick 週期的動作，如 `hunt_large`、`work`）**每隔 10 遊戲分鐘**（固定間隔檢查，2026-08-22 定案，見《99》P-14），引擎額外發起一次決策請求，讓 AI 選擇「繼續」或「放棄、改做別的事」——不是被引擎強制打斷，是它自己想清楚了。10 分鐘跟引擎對「一次動作」的最小時間顆粒（`MIN_ACTION_DURATION`）取同一個值：短於這個下限的動作在完成時的那次決策就順便收尾，不會落在任何一個中途檢查點上，不需要另外校準一個新量級。這是首次落地的建議值，等 `hunt_large`／`work` 真的有實跑數據再回頭調。

中止代價逐動作定。`work`（工作站）：**中止不撥款，已花的時間與精力不退還**（2026-08-16）。
`hunt_large` 2026-08-24 隨打獵拉進 MVP（見《17》「正式工作與經濟系統」），套用同一套邏輯：
**中止不掉落獵物**，已花的時間與精力不退還。`hunt_large` 進行時間已在《01-2》§3 定案為
40 分鐘；`work`（工作站）進行時間目前仍未定案，待補。

**檢查點不限於動作發起者。** `haul`（搬運）是長動作，套用同一套固定間隔檢查點；但檢查點觸發時，引擎會**同時**對搬運者與被搬運者各自發起一次決策請求——搬運者選「繼續搬」或「放棄，原地放下」，被搬運者選 `struggle`／`shout`／`idle`（見《07》§2-4）。這是本機制第一次用在「被動承受長動作的另一方」身上，不只是動作發起者自己想不想繼續；後續若有類似「一方長時間限制另一方行動」的機制（如 `detained`），比照這套模式，不要各自另兜一套。

## 4. 每 tick 處理順序

事件驅動，非輪巡：tick 只驅動生理數值與情緒這類**時間本身**的變化，
不是決策觸發器（見《00》§7、《10》§5.1）。決策請求以**單一角色**為單位、
在該角色完成當前動作時才發起，不是全體角色被同一個 tick 訊號同步喚醒送批次。

```
每 tick（全體角色）：
① 時間推進（tick += 1）
        ▼
② 生理數值更新（satiety −3.0、hydration −2.0、stamina −1.0…）
        ▼
③ conditions 重新檢查（新增／移除生理衍生狀態）
        ▼
④ 死亡判定（health ≤ 0 → 轉入死亡流程，本 tick 不再決策）
        ▼
⑤ emotion.duration_left −1（歸零則轉 neutral）

角色完成當前動作時（單一角色，事件驅動，見《00》§7 完整流程圖）：
⑥ 產生事實句（《01-3》§3）
        ▼
⑦ 截取快照 → 送 POST /decide 給 AI 後端（《04》§4-2）
        ▼
⑧ 收到決策 → 計算成功率 → 擲骰（《01-2》）
        ▼
⑨ 套用結果（房主機序列處理，避免 race condition）
        ▼
⑩ 寫回 last_action_result
```

> ⚠️ ⑦ 送出的快照必須是發起請求當下**同一時間點**截取的；角色等待回覆期間仍執行上一個動作。⑨ 才序列處理。

## 5. 死亡與昏迷判定

> [!note] MVP：本節「死亡」改成「昏迷」（2026-08-16，見《99》P-27）
> MVP 沒有真正的死亡，`health ≤ 0` 一律觸發**昏迷**（見《[[藥草鋪]]》治療流程），不是下表的
> 「死亡」。「維持極值達 N 日」這條額外的直接死亡規則 **MVP 不做**——`satiety` 觸底、`hydration` 觸底本來就會
> 透過 `starving`／`dehydrated` 兩個 condition 持續扣 `health`，最終一樣會走到 `health ≤ 0` →昏迷這條路徑，
> 不需要疊加一條獨立的天數判定。下表是**完整版**（有真正死亡）的規則，MVP 只取 `stamina = 0` 那一列。

| 條件 | 結果 |
| --- | --- |
| `health ≤ 0` | 死亡 |
| `satiety` 維持 0 達 7 遊戲日 | 死亡（餓死） |
| `hydration` 維持 0 達 3 遊戲日 | 死亡（渴死） |
| `stamina = 0` | 昏迷，強制轉入睡眠，非死亡 |

日常觀察模式下死亡觸發為**溫和／低頻**（意外、老化為主），避免博弈感過重影響調性。

死亡後流程詳見《09》（完整版）；MVP 昏迷流程見《99》P-27、《[[藥草鋪]]》。
