## 1-2 外觀 `appearance`　【待規劃】

**設計要求**：可儲存多個項目；前端用來渲染立繪，同時轉成自然語言供 LLM 閱讀。

```json
"appearance": [
  { "slot": "hair",      "item_id": "hair_short_grey",   "label": "剪得很短的灰髮" },
  { "slot": "face",      "item_id": "face_scar_left",    "label": "左眼下方有一道舊疤" },
  { "slot": "body",      "item_id": "body_lean",         "label": "身形精瘦" },
  { "slot": "top",       "item_id": "top_worn_jacket",   "label": "一件磨損的皮外套" },
  { "slot": "bottom",    "item_id": "bottom_work_pants", "label": "深色工作褲" },
  { "slot": "accessory", "item_id": "acc_glove_left",    "label": "左手戴著皮手套" }
]
```

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `slot` | enum | 部位代號。**清單【待規劃】**，由視覺組與前端共同定義 |
| `item_id` | string | 素材編號，對應美術資源 |
| `label` | string | 中文短句，上限 20 字。**組 Prompt 時使用的就是這個** |

### 規則

- 陣列可存多筆，順序即組句順序
- 同一 `slot` 原則上僅一筆；`accessory` 可多筆，上限【待規劃】
- 存檔時執行 `build_appearance_text()` 產生一次快取字串，外觀變更時重算
- 產生的文字寫入 `system_prompt`，**不逐 tick 注入**（外觀不會變，放常駐段可命中 KV 快取）

### 組句範例

```
輸入：上列 appearance[]
輸出：他剪得很短的灰髮，左眼下方有一道舊疤，身形精瘦，
      穿著一件磨損的皮外套與深色工作褲，左手戴著皮手套。
```

未定項目追蹤於《99》P-01。

## 1-3 角色特色 `character`

**這是「角色在意什麼」的唯一入口。** 沒有數值化的價值觀欄位——本地模型讀「他最在乎自己的東西不被碰」遠比讀 `property: 55` 準確。

| 欄位 | 型別 | 必填 | 限制 |
| --- | --- | --- | --- |
| `character` | string | ✗ | 上限 250 字 |

面板文案：

```
標題：這個角色是什麼樣的人？（選填）

placeholder：
崩塌前是機房維修員，獨自活過三次斷電。
說話很短，不耐煩時會發出鼻音。
最在乎自己的東西不被別人碰。
```

- 下方小字：「寫外表、口癖、過去經歷、他最在乎什麼都可以。不要寫能力或數值。」
- 附「隨機範例」按鈕，從 50 個 NPC 模板庫抽一段填入

## 1-4 對造物主的話 `words_to_creator`

**設計核心**：角色看著自己被賦予的性格，想對「把它設定成這樣的人」說的一句話。

這是角色唯一一次的**元層次自覺**——它知道自己的個性不是自己選的。內容可以是吐槽、質問、抱怨、認命、甚至道謝。

這句話**不是遊戲中發生的事**。生成時世界尚未開始運轉，角色沒有任何經歷可講，它唯一擁有的就是自己的性格設定。

### 結構

```json
"words_to_creator": {
  "content": "你把我設計成連話都懶得講，那你現在是想聽什麼？",
  "generated_at": "2026-08-08T10:00:00Z",
  "is_spoken": false,
  "spoken_at": null,
  "trigger": null
}
```

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `content` | string | 一句話，上限 60 字。LLM 自由填寫 |
| `generated_at` | timestamp | 生成時間，唯讀 |
| `is_spoken` | bool | 是否已在遊戲中說出口，預設 `false` |
| `spoken_at` | timestamp | null | 說出的時間 |
| `trigger` | string | null | 觸發原因代號，**【待定】** 見下方 |

### 生成時機

**建角存檔時**，在 `system_prompt` 組裝完成後立即發出一次「生成呼叫」。此後 `content` 永不重新生成。

```
system_prompt 組裝完成
        │
        ▼
┌──────────────────────────────┐
│  生成呼叫（僅此一次）          │
│  輸入：system_prompt          │
│         （行為準則＋character）│
│  輸出：一句話（≤60 字）        │
└──────────────┬───────────────┘
               ▼
     words_to_creator.content
```

### 生成規則（寫入呼叫的指示中）

| # | 規則 |
| --- | --- |
| 1 | 只能寫**一句話**，上限 60 字 |
| 2 | 主題是「**你被設定成這種性格，你想說什麼**」 |
| 3 | **不得提及任何遊戲中的事件、物品、地點或其他角色**——此時世界尚未開始 |
| 4 | 不得提及數值、參數名、系統機制（不可出現「勤勉 70」這種寫法） |
| 5 | 語氣須符合 `system_prompt` 的行為準則與 `character` |

### 範例

| 角色傾向 | 產出範例 |
| --- | --- |
| 冷漠孤僻 | 「你把我設計成連話都懶得講，那你現在是想聽什麼？」 |
| 討好順從 | 「我不會拒絕任何人——這是你要的吧？那我照做。」 |
| 敵意攻擊 | 「你憑什麼決定我一睜眼就想罵人。」 |
| 自私狡猾 | 「把我做成這樣，出了事你也有一半責任。」 |
| 完美主義 | 「你連我會為了小事失眠都設計好了，真周到。」 |
| 病態好奇 | 「你給了我這麼多好奇心，卻沒說能不能問你問題。」 |

### 說出時機

**觸發條件：玩家用天神之石對這個角色說話時。**

角色一生只觸發一次。觸發後 `is_spoken = true`，之後天神之石再對它說話都不會重複。

```
玩家在天神之石輸入一段話
        │
        ▼
Event Parser 轉為結構化事件
        │
        ▼
範圍內角色接收
        │
        ├─► 一般反應（相信與否、情緒、回話）
        │
        └─► words_to_creator 觸發判定
                │
                ├─ is_spoken = true ──► 不觸發
                │
                └─ 擲骰【機率待填】
                        │
                        ├─ 成功 ──► 注入該次 prompt
                        │           由 AI 決定說不說
                        │
                        └─ 失敗 ──► 只做一般反應
```

**為什麼是天神之石**：這是玩家唯一能對村民說話的手段。玩家在那個當下，字面上就是造物主——對話的對象與時機都正確。

觸發機率【待填】，追蹤於《99》P-10。

### 說出方式

觸發時，引擎在該次事件的 prompt 中額外注入一行：

```
你突然很想說出這句話：「<content>」
```

**由 AI 自己決定要不要真的說出口。**

| AI 的處理 | 結果 |
| --- | --- |
| 把這句話放進 `speech` | `is_spoken = true`、`spoken_at = now`、`trigger = "divine_stone"` |
| 沒有放進 `speech` | 不算觸發，`is_spoken` 維持 `false`，下次還有機會 |

### 誰聽得到

**只有玩家看得到。** 以浮動文字或內心狀態視窗呈現。

其他 NPC **不接收**這句話為對話事件，也不寫入任何人的記憶。

這是為了避免「我們是被創造的」擴散進其他 AI 的長期記憶——那會讓全村的世界觀在一次觸發後永久改變，且不可逆。

> 未來若要開放其他村民聽得到，應做成可開關的實驗選項，不作為預設。

### 用途

| 場合 | 行為 |
| --- | --- |
| 平時 | 不注入 Prompt，角色本人不會反覆想起 |
| 天神之石觸發時 | 注入該次 prompt，由 AI 決定說不說 |
| 角色死亡並安葬後 | 刻上墓碑公開（無論生前是否說過），詳見《09》 |
| 圖書館 | 列入成就紀錄，跨局永久保存 |

> 💡 玩家可能整局都沒聽到這句話，也可能在對某個角色說話時突然被回一句吐槽。這種不確定性正是本設計的觀察價值所在。

# 2. L1 人格層 `personality`

**0–100 整數，共 10 項。由《01-1》的 6→10 轉換函式產生，玩家不直接編輯。**

| # | 中文 | 英文欄位 | 引擎用途 |
| --- | --- | --- | --- |
| 1 | 勤勉 | `diligence` | 採集／捕魚成功率 |
| 2 | 膽識 | `courage` | 打獵／偷竊／攻擊成功率 |
| 3 | 社交 | `sociability` | 說服成功率；作為偷竊目標時的警覺度 |
| 4 | 道德 | `morality` | 傾向文案進 `system_prompt`（《01-1》§4）；`report` 隨《洗心革面所》延後，屆時接舉報意願判定（見《99》P-06） |
| 5 | 情緒穩定 | `stability` | 情緒 `duration_left` 衰減倍率 |
| 6 | 浪漫藝術 | `romanticism` | 演奏成功率 |
| 7 | 好奇心 | `curiosity` | 探索新地點權重 |
| 8 | 記仇度 | `grudge` | 負面記憶衰減率（見《03》） |
| 9 | 貪婪 | `greed` | 傾向文案進 `system_prompt`（《01-1》§4），不做正式議價公式（見《99》P-06） |
| 10 | 誠實度 | `honesty` | 傾向文案進 `system_prompt`（《01-1》§4），不做正式說謊判定公式（見《99》P-06） |

## 2-1 這 10 項不注入 Prompt

| 誰 | 讀什麼 | 為什麼 |
| --- | --- | --- |
| **引擎** | `personality` 10 項數字 | 算成功率、算記憶衰減 |
| **LLM** | `system_prompt` 的行為準則文字 | 本地模型看到 `curiosity: 60` 沒有基準，不知 60 是高是低，也分不出 60 與 55 |

兩者由同一份 HEXACO 輸入在建角時同步產出，不會互相矛盾。

## 2-2 變動規則

- 僅睡覺反思時變動，單項最多 ±3，夾制 0–100
- 反思**不回推** HEXACO 滑桿，`hexaco_input` 恆為建角紀錄、唯讀

## 2-3 附屬欄位

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `hexaco_input` | object | 6 項建角紀錄，唯讀。詳見《01-1》 |
| `system_prompt` | string | 建角時組裝，之後固定。每次呼叫 LLM 直接注入 |

# 3. L2 社會層

## 3-1 關係 `relations`

**對每個認識的人只留一項引擎欄位：`trust`（信任）。**

原本還有 `affinity`（好感）／`familiarity`（熟悉）／`debt`（虧欠）三項，2026-08-16 全庫查過一輪引擎消費者後拿掉（見《99》決策紀錄）：套用《00》原則三「除了餵給 LLM 讀，引擎自己有沒有拿它算東西」，這三項從沒被任何公式讀取過，只被寫入、餵給 AI 看——不符合留下來當引擎數值的理由。AI 對一個人有沒有好感、熟不熟、欠不欠人情，改交給《03》的記憶系統自己記、自己判斷、自己演（`related_npcs` 已經能把事件連結到特定角色），不用另一組引擎數值重複做同一件事。

| 中文 | 英文欄位 | 範圍 | 預設 | 怎麼變 |
| --- | --- | --- | --- | --- |
| 信任 | `trust` | 0 ~ 100 | 20 | 承諾兌現 ↑ / 被騙被偷 ↓↓ |

### 變動幅度【建議值，可調】

| 事件 | trust | 判定依據 |
| --- | --- | --- |
| 深度對話 | +2 | 5 句以上 |
| 一起用餐喝酒 | +1 | — |
| 兌現承諾 | +3 | — |
| 被說謊（發現） | -25 | — |
| 被偷竊（目擊） | -35 | — |
| 被攻擊 | -50 | — |
| 被救助 | +15 | — |
| 舉報他 | -10 | `report` 尚未實作，見《99》待規劃 |

> ⚠️ **`trust` 的降幅必須遠大於升幅**（+3 對 -25）。信任建立慢、崩壞快，這符合直覺，也讓村莊不會變成烏托邦。
> 

> 💡 普通聊天、被拒絕互動、`give`（送禮）不列在表裡——這些互動不自動改變任何引擎數值，同一動作在不同情境下對雙方的真實意義可能天差地遠（見《00》原則二），交給 AI 自己透過《03》記憶系統記錄、判斷、演出，不寫死公式。

## 3-2 名聲 `reputation`

| 欄位 | 型別 | 範圍 | 預設 | 說明 |
| --- | --- | --- | --- | --- |
| `reputation` | int | -100 ~ 100 | 0 | **公共數值**，整村對他的共同看法 |
- 名聲 < -50 → 商店拒絕交易、社交申請被拒率提高
- **變動來源【待填】**：被目擊偷竊 -15、被舉報 -10、公開表演 +8、救人 +20
- 新認識的人，`reputation` 附中文形容詞注入給 AI（見《00》三條硬規定第 3 條），初始觀感由 AI 自己判斷，引擎不預設一個好感度數字

## 3-3 經濟 `economy`

| 中文 | 英文欄位 | 型別 | 預設 |
| --- | --- | --- | --- |
| 金錢 | `money` | int | 300 |
| 隨身庫存 | `inventory` | array | `[]`，上限 36 格（快捷欄 9 ＋主背包 27），見《08》§4 |
| 家中儲存 | `home_storage` | array | `[]`，上限 50 格，見《08》§4 |

物品結構：

```json
{ "item_id": "herb", "count": 4, "decay": 22, "durability": 100 }
```

`decay` 腐壞值 0–100（100 = 完全腐壞），`durability` 耐久值 0–100（0 = 損毀）。詳見《08》。

# 4. L3 狀態層 `state`

## 4-1 生理 `state.physical`（0–100）

> `satiety`／`hydration` 表格內的「即死亡」是完整版方向的敘述。MVP 沒有真正的死亡，`satiety`／`hydration`
> 觸底一樣是透過拖垮 `health` 走到 `health ≤ 0`（見《02》§2-2 `starving`／`dehydrated`），跟其他任何造成
> `health ≤ 0` 的路徑共用同一套「觸發昏迷」的 MVP 覆蓋規則（見《02》§5），不是獨立的餓死／渴死天數判定。

| 中文 | 英文欄位 | 方向 | 預設 | 每 tick | 玩家可見 | 說明 |
| --- | --- | --- | --- | --- | --- | --- |
| 飽足感 | `satiety` | 越高越飽 | 100 | -3.0 | ✔ | 7 天觸底缺食物即死亡（2026-08-16 定案，見《99》P-32：跟實際引擎 `stats.gd` 對齊，觸底＝最餓；原欄位名 `hunger` 已改名，理由見下方） |
| 水分 | `hydration` | 越高越有水分 | 80 | -2.0 |  | 3 天觸底未飲水即死亡（原欄位名 `thirst`，2026-08-16 改名＋翻正方向，跟 `satiety` 統一） |
| 體力 | `stamina` | 越高越有精神 | 80 | -1.0（行動另計） | ✔ | 見底則暈倒；靠睡眠、飲食、休息回復 |
| 清醒度 | `wakefulness` | 越高越清醒 | 90 | -1.2 |  | 影響睡覺意願與行動效率（原欄位名 `sleepiness`，2026-08-16 改名＋翻正方向） |
| 清潔 | `hygiene` | 越高越乾淨 | 70 | -0.5 |  | 影響他人觀感 |
| 酒精濃度 | `alcohol` | 越高越醉 | 0 | -3（代謝） |  | 提高隨機講出真心話的機率；事件累積型，故意不跟其他 7 項同方向，理由見下方 |
| 生命值 | `health` | 越高越健康 | 100 | 0 | ✔ | 見底則死亡 |
| 傷勢 | `injury` | 越高傷越重 | 0 | -0.5（`injury ≥ 20` 時暫停，見《02》§2-2 `bleeding`） | ✔ | 影響所有行為成功率；事件累積型，故意不跟其他 7 項同方向，理由見下方 |

> ⚠️ 這 8 項 **LLM 完全不可宣告**。AI 說「我的傷好了」一律忽略。

> [!note] 方向與命名統一（2026-08-16 定案，見《99》P-32）
> `satiety`／`hydration`／`stamina`／`wakefulness`／`hygiene`／`health` 這 6 項是**需求型**欄位——
> 會隨時間自然消耗、需要玩家主動維護，統一成「越高越好」，理由是引擎的 `Stats.get_lowest_need()`／
> `needs_attention()`（見 `Ailley/scripts/character/stats.gd`）直接拿數值做 `< CRITICAL` 比較，找出「最該優先
> 處理的需求」；只要有一項方向不同，這個共用機制就會比錯方向。欄位名稱也一併對齊方向直覺——
> `satiety`（飽足感）、`hydration`（水分）、`wakefulness`（清醒度）都是新名字，取代原本「名字唸起來是負面詞、
> 數值卻越高越好」的 `hunger`／`thirst`／`sleepiness`（那正是 P-32 一開始會搞混方向的原因）。
> `stamina`／`hygiene`／`health` 名字本來就跟方向一致，不用改名。
>
> `alcohol`／`injury` 是**事件累積型**——不是自然消耗、而是特定事件才升高（喝酒、受傷），事後才慢慢代謝／
> 癒合，預設值（0）本身就是好狀態。這兩項**不參與** `get_lowest_need()` 掃描，故意維持「越高越差」，
> 不跟需求型 6 項統一方向。

> ⚠️ 注入時**每項換算成百分比＋中文形容詞**（2026-08-16 拍板，見《99》P-07）：`satiety` 是內部儲存直接就是
> 「越高越飽」，但注入給模型前要換算成「飢餓度」＝ `100 − satiety`，例如內部值 18 要寫成「飢餓度 82%
> （極度飢餓）」，讓模型看到的字面方向維持直覺的「越高越餓」；`hydration` 同理換算成「口渴度」＝
> `100 − hydration`，`wakefulness` 換算成「睡意」＝ `100 − wakefulness`。其餘欄位（`stamina`／`hygiene`／
> `alcohol`／`health`／`injury`）注入方向跟形容詞本來就同向，不用做這層轉換。8 項的 5 級距形容詞對照表
> 已定案，見《99》P-07。

## 4-2 情緒 `state.emotion`

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `type` | enum | 8 種情緒，**由 LLM 自行宣告**，定義見《02》 |
| `intensity` | int | 0–100，LLM 宣告 |
| `cause_event_id` | string | 引擎回填 |
| `duration_left` | int | 剩餘 tick，引擎倒數；衰減速率受 `stability` 與 `grudge` 影響 |

**情緒是 AI 唯一可以自行宣告的內在狀態，也是角色所有主觀感受的統一出口。**

沒有 `stress` / `loneliness` / `satisfaction` 這類欄位——那些是感受，由 AI 依處境自行產生，不由引擎計算。
